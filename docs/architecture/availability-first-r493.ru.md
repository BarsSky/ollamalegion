# Приоритет доступности: почему запрос уходит в очередь при свободных бэкендах (R493, разбор)

**Дата:** 2026-11-11 · **Основание:** два архива второго стенда
(`2026-11-11 09:05` и `10:23`) + код и документация репозитория.

Это разбор, а не список заплаток: сначала — что документация обещает, затем —
где реализация расходится с обещанием, затем — что должно измениться, чтобы
расхождение исчезло по существу.

---

## 1. Что обещает документация

`docs/architecture/balancing-guide.ru.md` §2.1 («Алгоритм выбора бэкенда v2»)
описывает четыре приоритета и четыре этапа:

| Приоритет | Условие |
|---|---|
| **P1 LOADED** | модель в памяти, `loadRatio < triggerLoadThreshold` |
| **P2 WARMING** | модель загружается |
| **P3 FREE** | свободные слоты, модель не загружена — **здесь запускается загрузка** (этап 3, `SyncModelLoad.Enabled`) |
| **P4 FALLBACK** | любой healthy по скорингу |

Плюс отдельный механизм §2.1.2 `dispatchWithModelLoad()`: «инициирует загрузку
модели на free-бэкенд с наибольшим свободным VRAM» — то есть **по замыслу**
балансер сам поднимает модель на свободной машине, а не ставит клиента в очередь.

`docs/architecture/request-lifecycle.ru.md` §2 закрепляет порядок шагов:
`choice backend + admission` → `preflight` → `если модель не загружена → load`.
Ключевая мысль: **admission (очередь) — это «нет capacity», а не «нет решения»**.
Если capacity есть на другой машине (свободный слот + модель влезает + файл есть),
заявка обязана уехать туда и загрузиться, а очередь — только последний вариант.

- У **всех** бэкендов `maxConcurrentRequests = 1` (кластер в архиве), то есть

- В логах `ASTRA-I9` / `WIN-I9` / `A10-126` — **ноль** упоминаний модели и
  **ноль** попыток загрузки: балансер туда даже не пытался её поднять.

Итог, который видел оператор: второй запрос встал в очередь к **занятому**
мастеру на 300 с, хотя рядом стоял `A10-126` с 20 ГБ свободной VRAM (единственная
машина, куда 27B физически влезает: 8-гигабайтные `ASTRA-I9`/`WIN-I9` — нет).

## 3. Где реализация расходится с замыслом

Три места, и они складываются в наблюдаемое поведение.

### 3.1 Привязка сессии к бэкенду действует как замок, а не как предпочтение

`internal/balancer/proxy.go:1614-1623`:

```go
sessionFromBackend := ""
if sessionKey != "" && p.config.Balancing.SessionStickiness && p.sessionMgr != nil {
    if s, ok := p.sessionMgr.GetSnapshot(sessionKey); ok {
        sessionFromBackend = s.BackendID        // ← бэкенд сессии
    }
}
unifiedBackend, ... := p.waitForInferenceBackendWithMoveR480(ctxWithRID, model, bt, sessionKey, sessionFromBackend)
```

`waitForInferenceBackendWithMoveR480` — это правило R480/P1-7: очередь **не
выдаёт** заявке слот на «чужом» бэкенде, если сессия привязана к прогретой копии
(«правило R139»: переезд на узкую копию сломал бы окно контекста). Смысл правила
правильный, но применён он **без проверки доступности**: у занятого мастера
свободного слота нет, и вместо решения «поднять модель на свободной машине»
заявка ждёт именно мастера. Это ровно то, что оператор описал как «маркер к
бэкенду ставится сразу на сессию, доступность не проверяется, и сессия уходит в
очередь при остальных свободных бэкендах».

### 3.2 Загрузка на свободный бэкенд (P3) не участвует в решении очереди

P3 живёт только внутри `selectBackend` (`internal/balancer/backend_selector.go:321-355`)
и срабатывает **до** admission-ожидания и **независимо** от него. Если выбор уже
вернул бэкенд (или сессия к нему привязана), путь «жду слот → вижу, что рядом
есть свободная машина → поднимаю там» в коде отсутствует. То есть обещанный
`dispatchWithModelLoad()` (§2.1.2) не подключён к очереди: он может случиться на
этапе выбора, но никогда — как реакция на «я стою в очереди, а рядом простаивает
подходящая машина».

### 3.3 «Подходящая машина» нигде не проверяется по существу

Для решения нужны три факта: (а) свободный слот, (б) файл модели есть на узле,
(в) модель влезает в свободную VRAM с резервом. Сейчас:

- (а) проверяется как `loadRatio < 0.8` по **заявленной** `MaxConcurrentReqs`, а не
  как «слот свободен сейчас»;
- (б) файл проверяется каталогом моделей (`model_catalog_r91`), и при отсутствии
  записи узел молча выпадает из P3 — без причины в очереди;
- (в) VRAM учитывается только внутри P3 (`orderCandidatesByVramFit`, R248), но не
  в решении о переезде.

Отдельно: **загрузка на 8-гигабайтную карту 27B-модели бессмысленна**, а в
решении о переезде класса карты нет — только «свободно/занято».

## 4. Как должно быть (по существу, а не заплатками)

Правило одного предложения: **очередь допустима только тогда, когда ни один узел
не может обслужить заявку сейчас и не может начать обслуживать её через
загрузку.** Реализация этого правила — четыре связанные части.

1. **Доступность — предикат, а не коэффициент.** Кандидат «доступен сейчас», если
   `tryAcquireSlot` удался (реальный слот), а не если `ActiveReqs/MaxConcurrent`.
   `MaxConcurrentReqs` — это заявка узла о параллельности; при `=1` коэффициент
   всегда 1.0 и перестаёт что-либо различать (в архиве именно так).
2. **Привязка сессии — предпочтение.** Сначала пробуем бэкенд сессии; если он не
   может принять сейчас — пере-выбор по полному правилу, включая загрузку на
   свободном узле. Прогретая копия остаётся **первым** кандидатом и побеждает,
   когда слот свободен; она не блокирует переезд, когда его нет.
3. **Загрузка вместо очереди.** Если ни один loaded-узел не принимает сейчас, а
   есть узел с (файл есть) И (VRAM с резервом ≥ потребность) — инициировать
   загрузку там (P3/`dispatchWithModelLoad`), и только затем проксировать. Выбор
   узла — по VRAM-fit с приоритетом класса карты (A10 24 ГБ раньше RTX4000 8 ГБ),
   а не «первый свободный».
4. **Причина очереди — по каждому кандидату.** Если заявка всё-таки встала, в
   `why_queued` должны быть причины отказа **всех** кандидатов:
   `no_slot: <узел>`, `vram_insufficient: need 21 GiB, free 5 GiB`, `file_absent:
   <узел>`, `window_smaller: 32768 < 131072`. Без этого «почему в очереди» снова
   придётся выяснять по логам воркера.

## 5. Что НЕ надо делать (и что я уже сделал зря)

- **Сессии по разным портам не надо сливать в одну.** R490 (`05bb89af`) убирал
  `endpointType` из ключа сессии, исходя из того, что «один разговор идёт через
  два API». Разговор физически один и тот же быть не может, а слияние ключа
  делает хуже: два независимых разговора одного клиента начинают считаться одной
  сессией, и привязка к бэкенду усиливается. Правка откачена (`R490 revert`), в
  документации остаётся прежняя семантика: сессия = разговор.
- **Счётчик «сессий=1» — не причина.** Оба порта обслуживает ОДИН `Proxy`
  (`cmd/balancer/main.go:240,515`), поэтому слоты и очередь общие; причина не в
  разделённом состоянии, а в решении 3.1.

## 6. Что нужно подтвердить на стенде (два факта)

1. `balancing.syncModelLoad.enabled` в `config/config.json` стенда (в
   `config/config.example.json:162-165` — `true`). Если у них `false`, P3 не
   работает вообще, и это первое, что надо включить.
2. `/api/tags` каждого узла — есть ли `Qwen3.8-27B-UD-Q4_K_M` в каталоге узла.
   Оператор говорит, что файл лежит всегда; если каталог узла его не показывает,
   балансер считает узел неподходящим молча — это отдельный дефект (3.3-б).

## 7. Порядок реализации (R493)

| Шаг | Что | Проверка |
|---|---|---|
| 1 | Доступность слотом: кандидат проходит, только если `tryAcquireSlot` удался (или `canAcceptNow`), `loadRatio` остаётся для прогрева/скоринга | тест: у loaded-узла `MaxConcurrent=1`, `Active=1` → он НЕ кандидат P1 |
| 2 | Привязка сессии как предпочтение: sticky-узел пробуется первым, при занятости — обычный выбор | тест: sticky-узел занят, свободный есть → запрос уходит на свободный |
| 3 | «Загрузка вместо очереди»: если loaded-узлы заняты, а свободный узел подходит (файл+VRAM+класс), инициировать загрузку и обслужить | тест: 1 занятой A10 + 1 свободная A10 → load на свободной, очередь не создаётся |
| 4 | Причины отказа по каждому кандидату в `why_queued` | тест: очередь из-за VRAM/файла/окна — причина названа |
| 5 | Не грузить модель, которая не влезает (8 ГБ и 27B) — отказ с числами, а не «первый свободный» | тест: RTX4000 8 ГБ не выбирается под 27B |

Пункты 1–3 — это и есть «не ставить в очередь, если есть свободные машины»; пункты
4–5 — чтобы следующий разбор не начинался с чтения логов воркера.

## 8. Что реализовано (и чем это доказано)

Пункты 1–3 и 5 закрыты кодом; пункт 4 (причины по каждому кандидату в
`why_queued`) остаётся открытым — он про диагностику, а не про само решение.

| Что | Где | Доказательство |
|---|---|---|
| Счёт занятости в P1 идёт от **эффективной** вместимости (`EffectiveMaxConcurrentRequests`, R71), а не от статического лимита конфига | `backend_selector.go`, этап 1 | `TestR493_P1UsesEffectiveCapacity`: статический лимит 4, заявка узла 1, `Active=1` → узел не выбран. Мутация «вернуть `MaxConcurrentReqs`» → тест падает |
| Привязка сессии — предпочтение: sticky-узел передаётся в очередь, только если у него есть свободный слот | `proxy.go` + `stickyBackendIfAvailableR493` | `TestR493_StickyBackendNotPinnedWhenSaturated`, `TestR493_StickyReleaseWiredInProxy` (по AST `proxy.go`: ровно один вызов хелпера, нет прямого `GetSnapshot`). Мутация «вернуть `GetSnapshot`» → тест падает |
| Загрузка вместо очереди: если ни один loaded-узел не принимает, выбирается свободный узел и модель поднимается там | `backend_selector.go`, этап 3b + `pickLoadableFreeBackendR493` | `TestR493_SelectorSkipsSaturatedLoadedBackend` (занятый мастер ВЫГОДНЕЕ по score, но заявка уходит на свободный) — без этапа 3b тест падает |
| Этап 3b не обходит выключатель автозагрузки | тот же этап, гейт `lbAutoLoadAsync \|\| SyncModelLoad.Enabled` | `TestR493_NoAutoloadNoFreeNodeLoad`. Мутация «снять гейт» → тест падает |
| Модель не грузится туда, где не влезает | `pickLoadableFreeBackendR493` (VRAM-fit) | `TestR493_LoadableFreeBackendRespectsVram`: 12 ГиБ → узел с 20 ГБ, не с 6 ГБ; 40 ГиБ → «некого выбирать». Мутация «снять фильтр» → тест падает |
| Узел под загрузку не берётся, если на хосте идёт image-генерация (Phase 6) | `pickLoadableFreeBackendR493` | существующий `TestImageLockWaitCap_SoleBlockerCapsWait`. Мутация «снять image-гейт» → тест падает |

Отдельно, чего в реализации **сознательно нет**:

- **P4 (`selectByResources`) не менялся.** Первая попытка «сначала среди свободных»
  ломала resource-aware выбор: при двух узлах со свободными слотами произвольный
  (map-порядок) побеждал более подходящий, и `TestBalancerResourceAware` падал
  («выбран ollama-1 вместо ollama-2»). Правильное место для «свободный вместо
  очереди» — этап 3b, где узел всё равно выбирается под загрузку; там порядок
  задаёт VRAM-fit, а выбор — обычный score.
- **`hasFreeSlotNowR493` в P1 не нужен.** Порог `loadRatio < 0.8` от эффективной
  вместимости строго сильнее предиката «есть слот» (при `threshold ≤ 1`), поэтому
  дублирующая проверка была бы заклёпкой без собственного наблюдаемого эффекта.
  Предикат остался там, где он решает: привязка сессии и выбор узла под загрузку.

### Открытые пункты

1. **Причины отказа по каждому кандидату** (`no_slot`, `vram_insufficient: need 21
   GiB, free 5 GiB`, `file_absent`, `window_smaller`) — `backendRejectionsR460`
   уже собирает часть причин, но VRAM-причины в нём нет.
2. **Каталог моделей узла.** Пункт 3.3-б: если каталог узла не показывает файл,
   узел молча выпадает из P3. Требуется проверка на стенде (`/api/tags` каждого
   узла) и, при подтверждении, отдельная правка — сейчас `pickLoadableFreeBackendR493`
   честно деградирует только для узлов БЕЗ метрик, а «каталог есть, файла в нём
   нет» выглядит как «модель не загружена» и лечится загрузкой.
3. **Живая проверка на стенде** не выполнена: нужен прогон «мастер занят, рядом
   свободный A10» с новым образом и подтверждение в логах выбора
   (`R493: свободный узел выбран под загрузку модели` / `R493: привязка сессии не
   действует`).
