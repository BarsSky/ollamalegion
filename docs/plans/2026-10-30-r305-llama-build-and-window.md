# R305: сборка llama.cpp и окно клиента — что проверено на стенде

Дата: 2026-10-30. Ветка: `centurion`. Предыдущий разбор: `2026-10-30-r303-1-d3-load-wait.md`.

Разбирались два пункта из отчёта по двухузловому стенду: **D6** (`llama_build=unknown`,
`llama_build_mismatch=true`, `relation=unknown` при одинаковом коммите) и **D5**
(«`profile_context_length=32768` и `ignoreDefaults` применяются к каждому запросу,
`num_ctx` из тела игнорируется»).

## D6: сборка не знала, из чего она собрана

**Причина оказалась двойной.**

1. `docker/cppworker/Dockerfile.gpu` печёт `CPPWORKER_LLAMA_BUILD` из build-arg, а
   build-arg никто не передавал → в образ уходило `unknown`. Compose при этом
   задавал env `CPPWORKER_LLAMA_BUILD=0eadefebd`, поэтому воркер честно сообщал
   «факт: unknown, намерение: 0eadefebd, расхождение: да». Само расхождение было
   правдой о сборке, но читалось как «узлы собраны по-разному».
2. Сравнение шло по строкам: `CompareLlamaBuilds` считал коммиты равными только
   при полном совпадении, а узел пишет короткий хеш (`0eadefebd`), GitHub —
   полный (`8642541b255bfb5d…`). И у сборки не было ДАТЫ, поэтому шаг «сравнить по
   дате» не достигался никогда.

**Что сделано.** Compose передаёт коммит и дату коммита
(`CPPWORKER_LLAMA_BUILD_DATE`, `git -C c/llama.cpp log -1 --format=%cs`), дата
печётся отдельной переменной и отдаётся в `/api/info` как `llama_build_date`;
агент отправляет `buildInfo` строкой `<коммит> <дата>`; балансер сравнивает
коммиты по 7-символьному префиксу и добавляет к строке релиза дату публикации
(поле `publishedAt` было объявлено с R269 и всегда пустое — теперь заполняется).

**Побочно закрыто.** Проверка совместимости узлов раскладки сравнивала строку
версии целиком и имела уровень ERROR: узел со старым образом (без даты) рядом с
новым получил бы «узлы собраны из разных коммитов» и раскладку не собрал бы.
Теперь узлы группируются по коммиту, а в отчёт идут полные строки.

**Проверка живьём.** До: `/api/info` → `llama_build=unknown, env=0eadefebd,
mismatch=true`; `llamaBuild.relation=unknown, reason="different commits, no
comparable version"`. После (образ `cppworker:gpu-5bb1a774`, балансер `5bb1a774`):

```
/api/info:            llama_build=0eadefebd  env=0eadefebd  date=2026-09-01  mismatch=false
/api/v1/backends:     buildInfo="0eadefebd 2026-09-01"
                      llamaBuild.relation=behind
                      llamaBuild.reason="build date earlier than release"
                      llamaBuild.publishedAt="2026-10-28T12:47:51Z"
```

То есть «устарело» теперь говорится с основанием: сборка от 2026-09-01 старше
стабильного v0.8.0 от 2026-10-28.

Замечание по порядку событий: запись бэкенда хранила старое `buildInfo` до
следующей регистрации агента (регистрация — один раз на старт контейнера), поэтому
после обновления образа значение обновилось только после перезапуска воркера. Это
поведение регистрации, а не ошибка сравнения; в отчёте фиксирую как факт.

## D5: окно из тела запроса НЕ игнорируется

Описание в отчёте («профиль форсит 32768 для каждого запроса») на текущем коде
**не воспроизводится**. Замеры на стенде (модель gemma-4-E4B, `gguf_max_context=131072`,
операторский потолок `LB_NCTX_RELOAD_MAX_N_CTX=32768` в `deployments/.env`):

| Запрос | Результат |
| --- | --- |
| `options.num_ctx=65536` | `413` + `requested num_ctx=65536 exceeds operator limit auto_reload_max_n_ctx=32768` + совет, что делать |
| `options.num_ctx=16384` | `200` за 1 c |
| `options.num_ctx=32768` | `200` за 3 c |
| без `num_ctx` | `200` за 2 c (берётся загруженное окно) |

То есть тело запроса читается, а 32768 — это **потолок оператора**, названный в
отказе; молчаливого урезания окна больше нет.

### Что осталось от D5 (перенесено в следующий блок)

`max_vram_n_ctx=0` при `vram_known=true` и работающей модели с `ctx=32768` и
`gguf_max_context=131072`. По документации поля `0 + vram_known=true` значит
«веса не помещаются ни при каком gpu_layers» — а модель работает. Это и есть
пункт «числа в 413 не сходятся»: в отказе по окну ветка «связывает физический
предел» не может быть ни посчитана, ни проверена оператором. Считать нужно
потолок ДЛЯ модели (веса + KV при данном окне), а не «сколько ещё влезает поверх
уже загруженной». Не полуфиксил: правка в memfit-расчёте, нужен отдельный разбор
и живые числа.

Отдельное наблюдение: запрос клиента может попасть в момент AutoTune-перезагрузки
(`kv_cache q8_0 → f16`) и получить `503` (reload pending) на здоровом стенде —
это R283-поведение (отказ дедупликации), но выглядит как «кнопка думает».
