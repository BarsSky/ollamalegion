# Раскладка исчезает при «Применить профиль»: доказательства и следующий шаг (R174, 2026-10-18)

## Что чинилось и что проверялось

Дефект: после применения профиля модели из WebUI («Применить и перезагрузить») модель
перезагружается **без удалённого узла** — все слои уходят на локальную карту, скорость
падает, а UI об этом молчит.

Проверено живьём на стенде: донор `192.0.2.10` включён, узел раскладки поднят
(`listening`, `reachable=true`), мастер — образ `cppworker:gpu-r174b-layout-keep`,
балансер — `r174b-merge-window`.

## Сценарий и результат

| Шаг | Действие | Факт |
|---|---|---|
| 1 | `load-with-params` (ctx=8192, parallel=1, gpuLayers=42) | `CPU:5 CUDA0:21 RPC0:17` — раскладка работает |
| 2 | профиль `{contextLength:16384, parallel:2}` + `POST /apply` (путь кнопки WebUI) | параметры применились верно: `ctx=16384, perSeq=8192, slots=2` |
| 3 | слои после того же reload | `CPU:1 CUDA0:42` — **RPC0 нет** |
| 4 | повторный reload | то же (`CPU:1 CUDA0:42`) |
| 5 | свежая загрузка (для восстановления стенда) | снова `CPU:5 CUDA0:21 RPC0:17` |

Дефект воспроизводится **только на пути reload**: обычная загрузка раскладывает слои на узел.

## Три факта, которые требовались

### 1. Бюджет: пересчитывается, и узлы в нём ЕСТЬ

Бюджет не переиспользуется из прошлой загрузки — он считается заново и в него попадает
ёмкость узла (лог воркера, непосредственно перед обоими reload):

```
MemfitBudget: ёмкость RPC-узлов добавлена в бюджет
  rpc_devices=1 remote_free_mb=7033 remote_total_mb=8123 vram_free_mb=14130
```

Планировщик **видел** 7 ГБ на доноре и запросил 42 слоя на GPU, что подтверждает
`load_tensors: offloaded 42/43 layers to GPU`.

### 2. Какие серверы допущены: узел допущен

Отказов версии нет (сообщения `узел раскладки исключён: версия llama.cpp не совпала` в логе
нет), и адрес дошёл до моста:

```
RPC-раскладка передана в мост  model=gemma-4-E4B-it-Q4_K_M servers=[192.0.2.10:50052]
```

### 3. Почему снимок без RPC: снимок был С RPC, а ЗАГРУЗКА — без

Здесь и находится настоящая причина. Две соседние операции видят разные наборы устройств.

**Снимок (проба) — узел виден**, поэтому бюджет и получил 7033 МБ.

**Загрузка модели при reload — узел не зарегистрировался** (лог llama.cpp):

```
llama_prepare_model_devices: using device CUDA0 (RTX 3070) - 7097 MiB free
load_tensors: offloaded 42/43 layers to GPU
load_tensors:        CUDA0 model buffer size = 2428.59 MiB
```

Строки `using device RPC0` в этой загрузке **нет вообще**. А на следующей (свежей) загрузке
она появляется, и раскладка снова работает:

```
llama_prepare_model_devices: using device RPC0 (192.0.2.10:50052) (unknown id) - 7033 MiB free
load_tensors: offloaded 38/43 layers to GPU
load_tensors: RPC0[192.0.2.10:50052] model buffer size = 1153.94 MiB
```

То есть между решением о раскладке и `llama_prepare_model_devices` RPC-сервер **тихо
выпадает**: `ggml_backend_rpc_add_server` не дал устройства, llama.cpp просто пропустил узел.
Наш загрузчик этого не замечает — он не сверяет «сколько серверов передали» с «сколько
RPC-устройств реально зарегистрировалось».

Побочно видна вторая проблема того же пути: при reload сплит берётся из ПРОШЛОГО инстанса
(`manual tensor split applied tensorSplit=[0.538, 0.462]`), а не пересчитывается по
фактическому набору устройств. Если устройств стало меньше, лишние пропорции молча
игнорируются.

## Наиболее вероятный механизм (что проверять дальше)

Узел обслуживает ОДНО соединение за раз. При reload старая сессия закрывается поздно, и
рукопожатие новой на этапе загрузки либо ставится в очередь `accept`, либо не успевает —
llama.cpp считает сервер непригодным и молча его выбрасывает. Проба (снимок) при этом
успевает, потому что идёт отдельным подключением на 0.6-1.5 с раньше.

Косвенное подтверждение со стороны донора: в окне reload видны только короткие
`Accepted client connection` без единой операции (`[alloc_buffer]`/`[init_tensor]`), то есть
загрузочная сессия до узла не дошла.

## Следующий шаг (конкретно)

1. **Сверка «передали / зарегистрировалось».** В пути загрузки после сборки `cfg` с
   `RPCServers` спросить у моста фактический список устройств и сравнить с числом
   переданных серверов. Если RPC-устройства нет — это факт, а не тишина.
2. **Ожидание освобождения слота узла.** При расхождении — повтор регистрации с backoff
   (3 попытки, 200-400 мс): узел освобождает слот после закрытия прошлой сессии. Только
   после исчерпания попыток — отказ.
3. **Честный отказ вместо тихой деградации.** Если узел так и не зарегистрировался: либо не
   начинать загрузку (ответ «раскладка не применена: узел занят прежней сессией»), либо
   загрузить локально и пометить модель `layout_degraded=true`, чтобы это видели балансер и
   карточка WebUI.
4. **Пересчёт сплита при reload.** Не копировать `current.TensorSplit` вслепую: пересчитать
   по фактическому списку устройств (или проверить, что длина сплита равна числу устройств).
5. **Тесты:** (а) «серверов 1, RPC-устройств 0 → загрузка помечается degraded и пишет
   причину»; (б) «сплит длины 2 при 1 устройстве → пересчитывается, а не игнорируется»;
   (в) живая проверка на доноре: apply профиля → в логе есть `using device RPC0`.

## Что уже сделано и чем это НЕ является

- Исправлено и подтверждено живьём: **применение параметров** (устаревший `contextPerSeq`
  больше не перекрывает явные значения: `8192/1` → `8192, perSeq 8192, parallel 1`).
- Исправлено и подтверждено живьём: **auto-continue** больше не удлиняет ответ против
  лимита клиента (матрица клиентов 39/39).
- Добавлена защита «занятость не стирает раскладку» (последний успешный снимок) — она
  закрывает ветку `layoutBusy`, но, как показал этот прогон, **не эту причину**: бюджет
  вообще не терял узел, терялась регистрация при загрузке.
- Сохранность раскладки при reload **исправлена в R179**: reload не передавал
  SplitMode, мост получал 0 = LLAMA_SPLIT_MODE_NONE и llama.cpp отбрасывал RPC-узел.
  Проверено живьём: см. раздел «РЕШЕНО (R179)» в конце документа.

## Состояние стенда на момент отчёта

Раскладка восстановлена: `CPU:5 CUDA0:21 RPC0:17`, `ctx=8192`, 1 слот. Образы: cppworker
`gpu-r174b-layout-keep`, balancer `r174b-merge-window`, webui `r175c-merge-styles`.

## РЕШЕНО (R179, 2026-10-19): причина — SplitMode=0 на пути reload

Дальнейшие прогоны (R176-R179) довели разбор до одной строки: `handleReloadModel` не
передавал `SplitMode`, поэтому мост получал `0 = LLAMA_SPLIT_MODE_NONE`, а при NONE
llama.cpp оставляет из списка устройств только `main_gpu` и **RPC-узел отбрасывает**.
Свежая загрузка (`/api/models/load-with-params`) режим передавала всегда — поэтому
раскладка работала там и пропадала на reload.

Что проверено живьём после исправления (`reloadSplitMode`: явный запрос > env >
конфиг > -1):

```
manual tensor split applied [0.538, 0.462]
llama_prepare_model_devices: using device CUDA0 (RTX 3070) - 7097 MiB free
llama_prepare_model_devices: using device RPC0 (192.0.2.10:50052) - 7033 MiB free
load_tensors: offloaded 42/43 layers to GPU
```

Факт после «Применить профиль»: `CPU:1 CUDA0:23 RPC0:19`, `layout_degraded=false`,
окно 12288, окно на слот 12288, слоты 1. Приёмка
`scripts/webui-e2e/verify-layout-reload-r176.js` — 20/20 (проверяется СОСТАВ:
раскладка по устройствам, окно, слоты, флаг деградации, токен-метрики чата).

Остальные найденные по пути дефекты тоже закрыты: сверка «передали/загрузилось»
(`layout_degraded` + причина), сплит только под фактическое число устройств, гейт
готовности узла, счётчики токенов в не-стрим `/api/chat`.
