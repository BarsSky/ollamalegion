# Замер выигрыша RPC-раскладки на qwen3.8 (R231, 2026-10-24)

Вопрос, на который отвечает этот документ: **даёт ли раскладка слоёв на второй узел
(RPC, порт 50052) реальный выигрыш на большой модели — или это только «больше
влезает», а по скорости выходит хуже?**

Замер — живой, на стенде: одинаковый промпт, одинаковая модель, одинаковые
параметры загрузки; различается только режим раскладки (`off` / `on`).

## Стенд и запрос

| Параметр | Значение |
|---|---|
| Мастер | 8 ГБ VRAM (локальная карта), cppworker + балансер |
| Донор | второй узел, 8 ГБ VRAM, `rpc-server` на `:50052` |
| Канал мастер → донор | измерен `scripts/verify-...` / `POST /api/v1/backends/{id}/measure-link` — **≈8.9 Гбит/с** |
| Модель | `Qwen3.8-27B-UD-Q4_K_M` (15.33 GiB) |
| Загрузка | `contextSize=16384`, `kvCacheType=q8_0`, слои — auto |
| Запрос | `/api/chat`, `num_predict=96`, `temperature=0`, промпт 58 токенов |
| Сборка | llama.cpp `0eadefebd` на мастере и доноре (правило «один коммит») |

Переключение режима — тумблер оператора:
`PUT /api/v1/backends/{backendID}/rpc-layout` с `{"mode":"off"|"on"|"auto"}`.
`auto` — поведение по умолчанию: раскладка включается, если донор доступен и
совпадают коммит/архитектура; при потере узла мастер сам уходит в локальную загрузку.

## Результаты

| Метрика | RPC `off` | RPC `on` | Разница |
|---|---|---|---|
| Раскладка | CUDA0 **20/66**, CPU 46 | CUDA0 **26** + RPC0 **22** = **48/66**, CPU 18 | +28 слоёв на GPU |
| Загрузка модели | 278.5 с | 285.4 с | +2.5 % |
| 96 токенов (3 прогона) | 146.7 / 125.5 с | 49.2 / 44.7 / 45.0 с | — |
| Скорость генерации | 0.65–0.77 tok/s (ср. 0.71) | 1.95–2.15 tok/s (ср. 2.08) | **≈ ×2.9 (+193 %)** |
| Средняя задержка ответа | 136.1 с | **46.3 с** | **−66 %** |
| Свободно VRAM мастера после загрузки | 623 МБ | 774 МБ (донор занял ~5.6 ГБ весов + ~0.6 ГБ буферов) | — |

**Вывод:** на этой конфигурации RPC-раскладка даёт **≈2.9× по скорости генерации**
практически без удорожания загрузки. Причина видна в раскладке: без донора 46 из
66 слоёв считались на CPU, с донором — только 18; 22 слоя уехали на RPC0 донора,
и ещё 6 дополнительных слоёв поместились на локальную карту (26 против 20).

Почему выигрыш именно такой:

- RPC-слой считает **GPU донора**, а не CPU мастера; обмен активациями идёт по
  быстрому каналу (~8.9 Гбит/с), поэтому накладные расходы сети не съедают выигрыш;
- веса на донора передаются один раз при загрузке (≈5.6 ГБ), поэтому время
  загрузки почти не изменилось (+7 с);
- при **медленном** канале (сотни Мбит/с) картина может быть обратной: перенос
  весов и активаций станет узким местом. Замеряйте канал
  (`POST .../measure-link`) и сравнивайте на своей модели/контексте.

## Как воспроизвести

```powershell
# 1) донор должен быть онлайн; проверьте канал
curl -X POST http://<balancer>:18081/api/v1/backends/<backend>/measure-link

# 2) оба режима, по 3 замера на режим
pwsh -File scripts/bench-rpc-qwen38.ps1 -Mode both -Runs 3 -NumPredict 96 -LoadTimeoutSec 1300
```

Скрипт сам: ставит режим `off`, грузит модель, делает прогрев и замеры; затем
ставит `on`, повторяет; в конце возвращает `auto` и выгружает модель. Артефакт
прогона — JSON в `_diag/` (вне git). Переменные админ-доступа — `LB_ADMIN_USER` /
`LB_ADMIN_PASSWORD` в окружении.

**Обязательно для больших моделей:** `CPPWORKER_LOAD_STALL_SEC=1200` в
`deployments/.env`. При дефолтных 300 с загрузка 15-ГБ модели с медленного диска
обрывается watchdog'ом (`model load cancelled`), и замер «не стартует».

## Ограничения и что проверять дальше

- Цифры получены для `ctx=16384`. На большем контексте (например, 32768 из
  профиля) выигрыш RPC обычно **больше**: без донора KV и слои уезжают в RAM,
  с донором помещаются на GPU. Это отдельный замер.
- Донор — обязательное условие: при его выключении гард возвращает локальную
  загрузку (см. `docs/architecture/rpc-layout-rules.ru.md`), а не ошибку.
- Разница в скорости зависит от канала и от того, сколько слоёв реально удаётся
  перенести (VRAM донора, `n_ctx`, KV-тип). Скрипт печатает раскладку и tok/s,
  поэтому на другом железе сравнение остаётся таким же воспроизводимым.
