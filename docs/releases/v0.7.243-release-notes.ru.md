## 1. Зачем

Пока идёт тест 27B-стенда, нужен ответ на вопрос «кто держал ответ»: воркер (не
отдавал токены), балансер (буферизовал) или клиент/сеть. Раньше по `duration_ms`
это было неразличимо: и потоковый ход, и «всё в конце» дают одну длительность.

## 2. Что добавлено

### 2.1. `first_byte_ms` в строке `request trace`

Момент, когда клиенту ушёл ПЕРВЫЙ байт:

| Наблюдение | Вывод |
|---|---|
| `first_byte_ms` близко к `duration_ms` | ответ пришёл одним куском — держал **воркер** (удержание R471/R482) или балансер не флашил |
| `first_byte_ms` мал, `duration_ms` велик | отдавали сразу — вопрос к клиенту/сети |
| `first_byte_ms = -1` | клиенту не ушло ни байта (отказ до записи) |

Живой пример на стенде: холодная загрузка модели — `duration_ms=83178,
first_byte_ms=82100`; тёплый потоковый ход — `duration_ms=674, first_byte_ms=8`.
Раньше оба выглядели одинаково.

### 2.2. Кольцо сбоев воркера учитывает не только 5xx

`workerFailureR477` получил `kind` и `detail`; туда попадают события хода,
которые раньше жили только в тексте лога:

| `kind` | Когда | `detail` |
|---|---|---|
| `hold_released` | R482 снял удержание вывода | `hold_timeout`/`hold_bytes`, `held_ms`, `held_bytes` |
| `client_gone` | запись клиенту сорвалась | — |
| `client_cancelled` | клиент отменил запрос | — |
| `unparsed_tool_markup` | модель выдала разметку вызова, но вызов не распознан | `raw_len`, `clean_len`, `emitted` |
| `turn_retry` | повтор хода из-за пустого/нераспознанного вывода | причина |

Всё попадает в `failures.json` архива (`/api/v1/cppworker/debug/bundle`).

## 3. Как читать вместе

Для хода из жалобы:

1. Балансер: `request trace` по `request_id` → `first_byte_ms`, `duration_ms`,
   `stage`, `stage_final`.
2. Воркер: `/api/chat stream response summary` → `hold_released*`,
   `first_content_ms`, `tool_calls_from_reasoning`, `reasoning_chars_raw`.
3. Архив воркера: `failures.json` → записи с этим `request_id` и их `kind`.
