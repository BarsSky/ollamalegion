# OllamaLegion v1.0 — source release

**Date:** 2026-09-27 · **Type:** source-only (no binaries or Docker images)
**What this is:** the source code of the whole project + a brief description of what actually
works, what works partially, and what stands as a stub.

---

## 1. What this project is

A load balancer and orchestrator for inference on **llama.cpp** (plus
Ollama-compatible backends) with adaptive model loading: the system decides by itself
how many model layers will move to the GPU, which `n_ctx` will fit, and what to do if
nothing fits.

Clients (OpenWebUI, Cline, anything-llm, curl) talk to **one** address —
the balancer — and do not know on which machine and with which parameters the model
will actually be loaded.

```
client ──► balancer :18080 (OpenAI + Ollama API)   :18081 (admin API)
              │
              ├── agent :18032 ── node metrics (GPU/RAM/CPU) into the balancer
              └── cppworker :18092 ── llama.cpp (CGo), GGUF loading, streaming
                    └── webui :8080 ── operator dashboard (ours, not OpenWebUI)
```

## 2. What actually works (verified on a live stand)

| Area | What is done |
|---|---|
| **llama.cpp inference** | `/api/chat`, `/api/generate`, `/v1/chat/completions`, `/v1/completions`, `/api/embeddings`; NDJSON and SSE streaming; tool calls (native + 7 text formats); reasoning/thinking |
| **Ollama compatibility** | `/api/tags`, `/api/show`, `/api/copy`, `/api/create`, `/api/pull` (`hf:` sources), `/api/ps`, `/api/delete`; `keep_alive` |
| **Memory and layout** | A single solver `internal/memfit` (one KV-cache formula, typed bytes, an honest "unknown"); n_ctx ceilings, a 422 refusal instead of an attempt to load the impossible; honest mode fields (`n_ctx_degraded`, `max_exact_fit_n_ctx`) |
| **Model loading** | Asynchronous (202 + `progressUrl`), deduplication by path, single-flight, protection against double loading; reload with rollback on failure; auto-unload of idle models |
| **Queue and fairness** | A single admission queue of slots, `X-Queue-Position`/`X-Queue-Wait-Ms`, keepalive for waiting streaming clients, per-session fairness, distinguishing OpenWebUI users |
| **Placement (multi-backend)** | Policy by model/class: `single`, `pool`, `replicated`, `auto` (selection by VRAM fit); "never switch to another strategy silently" (503 or `X-LB-Placement-Fallback`); replication groups, adoption of already-loaded copies, request failover to a live copy |
| **Observability** | `/api/v1/metrics`, `/api/v1/health`, `/api/v1/health/detailed` (recentErrors from the SSE buffer), `/api/v1/queue/stats`, `/api/v1/placement`, dashboard `/monitor`, notifications about loading failures and about degradation |
| **Operations** | Release scripts with a tag manifest, checking that compose ↔ `.env` agree, hardware presets for RTX 30xx/40xx/50xx and A10, live invariant verifiers |

**Volume:** 457 test files in 27 packages; the key suites are `balancer` (172),
`cppworker` (88), `api` (42), `cppbackend` (33).

## 3. What works partially

| Feature | State | What it looks like to the client |
|---|---|---|
| `sharded` (tensor parallelism) | **stage P2, not executed** — awaiting the choice of transport (llama.cpp RPC vs B8.7) | 503 with the reason and a `placement` block, or `single` + `X-LB-Placement-Fallback` at `fallback=single`. In `/api/v1/placement` they are **not** in the `executable` list — visible machine-readably |
| `rpc` (distributed inference) | **stage P2, not executed** — the same choice of transport | the same |
| RPC coordinator | works, but **tokens in metrics = 0** (`TODO (Phase 9)`) | token statistics for the rpc mode are incomplete |
| Batched scheduler | works, but **cannot cancel** generation (`TODO R63.x`) | abort does not interrupt the batch instantly |
| Ollama registry (`/api/pull` by name without `/`, `/api/push`) | **a deliberate stub** | an honest 501 with a hint: use `hf:<repo>/<file.gguf>` or `/api/hf/download` |
| Security (mTLS, thin rate limiting, audit) | basic (tokens, CORS, limits) | in the post-1.0 backlog |
| `stub` build (`-tags llama_stub`) | **the stub is intentional** — for CI without a GPU | there is no inference, everything else (API, loading, metrics) works |

## 4. What stands as a stub (deliberately, post-1.0)

- **Pipeline parallelism** — not implemented.
- **Expert parallelism for MoE** — not implemented.
- **Continuous batching** — not implemented (there is dynamic selection of `n_parallel`).
- **Real ggml/NCCL tensor parallelism** — research-grade (`docs/archive/rounds/phase-8-p3-tensor-parallel-research.md`).

All four **do not promise to work**: they are either absent from the API, or (for
placement) honestly marked as non-executable in `/api/v1/placement`.

## 5. What is needed for the final v1.0 tag

One step remains that requires hardware (A10 24 GB or an equivalent) and cannot be
done in CI:

- **a manual smoke run** through `docs/releases/v1.0-smoke-checklist.ru.md` — 12 scenarios
  (loading, streaming, tools, context, queue, replication, failover,
  notifications);
- after it — the `v1.0` tag (right now the source release is marked `v1.0-rc2-src`).

## 6. Where to start

### 6.1. What you need before the first build

- **Go 1.21+** — for the balancer, cppworker (the Go part), the agent, the WebUI server.
- **The `llama.cpp` submodule.** In the source archive the `c/llama.cpp` directory is **empty**:
  it is a git submodule (`https://github.com/ggml-org/llama.cpp.git`, branch `master`),
  and `git archive` does not carry the contents of submodules. Initialize it:

  ```bash
  git clone https://github.com/BarsSky/ollamalegion.git && cd ollamalegion
  git submodule update --init --recursive c/llama.cpp
  ```

  If you unpacked the archive — put the llama.cpp checkout into `c/llama.cpp` by hand.
  Without it **only `-tags llama_stub`** builds (a stub without inference): that is
  enough to run all the tests and check the code.
- **A C toolchain** (MSVC or GCC/CMake) — needed only for a real build of
  cppworker with CPU/CUDA inference.
- **`.env`.** There are no working environment files in the archive — and that is deliberate (they
  contain tokens). Take the templates: `config/cppworker.example.env`,
  `config/agent.example.env`, `deployments/.env.bundled-with-agent`.

### 6.2. Order of actions

```bash
# 1. Read: docs/getting-started/installation.ru.md, docs/getting-started/configuration.ru.md, docs/api/env-vars.ru.md
# 2. Choose a preset for the hardware:
python scripts/apply-hardware-preset.py <preset>   # see docs/getting-started/hardware-presets.ru.md
# 3. Check the code and tests without CGo:
go build -tags llama_stub ./...
go test  -tags llama_stub ./...
# 4. Production stack: deployments/docker-compose.cppworker-bundled-with-agent.yml
```
