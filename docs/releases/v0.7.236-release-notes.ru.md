# v0.7.236 — R476: диагностика стенда одним архивом

**Дата:** 2026-11-09 · **Тип:** исходники + образы стенда
**Образы:** balancer `r261109-1410` (`4c7578a9`), cppworker `gpu-261109-1404`
(`b176967d`), webui `r261109-1410` (`4c7578a9`). Манифест:
`deployments/release-manifest.json`.

---

## 1. Зачем

Разбор живого дефекта упирался не в код, а в доступ к данным. Версии — на одной
странице, окно и профили — в админке, флаги — в `.env` на другом хосте, логи
бэкендов — только через `docker logs` на стенде, сводка хода — в stdout воркера.
Каждый разбор превращался в переписку «пришлите ещё вот это», и выводы делались
по догадке — отсюда и серия правок «под конкретную модель».

## 2. Что появилось

| Что | Где | Зачем |
|---|---|---|
| `request trace` — строка на каждый запрос: `request_id`, метод, путь, статус, `duration_ms`, объём, `backend` | лог балансера, `LB_REQUEST_TRACE=off\|summary\|full` | по `request_id` ход находится в сводке воркера — раньше логи двух сторон жили отдельно |
| `request_id` в сводке `/api/chat stream response summary` | лог воркера | одна строка на ход: что реально отдано (`streamed_content_bytes`, `final_content_len`), `tool_calls`, `done_reason`, `dumped_args_instead_of_call` |
| `GET /api/v1/diag/summary` | балансер (admin API) | версии, флаги `set`/`unset`, `nctx_reload`, `nctx_ceiling` (с причиной ограничения), профили моделей с действующим окном, кластер, очередь |
| `GET /api/v1/diag/bundle` | балансер (admin API) | zip: сводка + логи балансера + архивы воркеров + `/api/info` каждого бэкенда + README |
| `GET /api/v1/cppworker/debug/bundle` | воркер | zip: `info.json`, `logs.txt` (кольцевой буфер, `CPPWORKER_LOG_BUFFER_ENTRIES`), `last-prompt.json`, `last-stream.json`, `prompt-last.txt`, `request-last.json`, `unparsed-tool-calls.jsonl`, `unparsed-ring.json`, `env.json` (белый список), README |
| Страница **«Диагностика»** | WebUI (`#diagnostics`) | блоки «Версии», «Окно и профили», «Флаги», «Бэкенды»; копирование блока кнопкой, значение — кликом; кнопка «Скачать архив диагностики» |
| `CPPWORKER_LOG_LEVEL` | воркер | уровень логирования без правки `command` (раньше только флаг `-verbose`, недоступный в compose) |
| `CPPWORKER_LOG_BUFFER_ENTRIES` | воркер | кольцевой буфер логов: до R476 его не было, логи жили только в stdout |
| `LB_DIAG_RING` / `CPPWORKER_DIAG_RING` | оба | псевдонимы размеров буферов (основные имена главнее) |
| `CPPWORKER_STREAM_TRACE=1` | воркер | `stream_chunks`, `stream_bytes`, `stream_sha256` в сводке хода — побайтовое доказательство «отдано всё» |
| `CPPWORKER_DIAG_KEEP_FILES=N` | воркер | прошлые версии `prompt-last.txt`/`request-last.json` (`path.1` … `path.N`) — разбор «дефект был ход назад» |
| `?since=30m` у `/api/v1/diag/bundle` | балансер | архив только по нужному окну времени (свой буфер режется на месте, параметр уходит воркерам) |

`request_id` теперь есть и в логах РЕШЕНИЙ: «preflight: DecidePreflight inputs»,
«R466 окно урезано до потолка», «context growth decision (R301)», «prompt tokens:
точный подсчёт токенизатором». Раньше по логу нельзя было понять, ПОЧЕМУ ход
перезагрузил модель, — только сопоставить по времени.

Секретов в выгрузке нет: флаги идут по белому списку, это закреплено тестами.

## 3. Живая проверка (числа, не пересказ)

- `GET :18081/api/v1/diag/summary` → ключи `cluster, flags, generated_at,
  model_profiles, nctx_ceiling, nctx_reload, operating_mode, queue_stats,
  version, version_text`; в flags 24 заданных значения и 9 незаданных;
  `nctx_ceiling = {envCeiling: 65536, limitedBy: "env"}`; профилей 21.
- `GET :18081/api/v1/diag/bundle` → zip 22 КБ: `summary.json` 22050 B,
  `flags.txt` 1098 B, `balancer-logs.txt`, `backends/cppworker-gpu-bundled-agent.info.json`
  1155 B, `backends/cppworker-gpu-bundled-agent.bundle.zip` 6961 B, `README.txt`.
- Внутри архива воркера: `logs.txt` 17168 B — реальные записи кольцевого буфера
  (включая строки `applied … from env`), `env.json` 319 B, отсутствующие дампы
  честно помечены `*.missing.txt` с подсказкой про `CPPWORKER_DEBUG_*`.
- Строка трассировки в логе балансера:
  `{"msg":"request trace","request_id":"req55e2ed4a","method":"GET","path":"/api/version","status":200,"duration_ms":0,"bytes":207}`.
- WebUI `:18083` отдаёт страницу (`#diagnostics-page`, пункт меню, скрипт),
  модуль 18965 B с `window.Diagnostics`, стили `.diag-table` в `pages.css`.

**Найдено и исправлено живой проверкой:** первый архив собрался вообще без части
воркера — балансер ходил на `OllamaPort` (11434) вместо `CppWorkerPort` (18092) и
получал `connection refused`. Теперь адрес берётся тем же методом, что и для
инференса, а причина неудачи пишется в архив файлом. Тест этого поймать не мог: он
поднимал `httptest`-сервер, где порт был правильный по построению.

## 4. Обновление стенда

```bash
cd deployments
# .env: BALANCER_TAG=r261109-1410, CPPWORKER_GPU_TAG=261109-1404, WEBUI_TAG=r261109-1410
docker compose -f docker-compose.stack.yml up -d --no-deps loadbalancer cppworker-gpu webui
curl -s http://127.0.0.1:18080/api/version            # build_commit=4c7578a9
curl -s -H "X-API-Token: $CPPWORKER_API_TOKEN" \
     http://127.0.0.1:18081/api/v1/diag/summary | head -c 400
```

Дальше — WebUI → «Диагностика» → «Скачать архив диагностики».
