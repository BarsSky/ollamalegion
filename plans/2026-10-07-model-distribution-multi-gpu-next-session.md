**Чего эта приёмка НЕ покрывает (честно):**

1. **Раскладка слоями между ДВУМЯ машинами** — не проверена и не может быть проверена на

2. **Реальная передача тензоров по RPC** — не начата (S1): нужен `rpc-server` в образе

3. **Версии сторон RPC** — проверка есть (`version_unknown` честно предупреждает), но живого

**Находка 7 (репозиторий, sm_120): базовый образ cppworker не умеет Blackwell, хотя комментарий обещает.**
В `docker/cppworker/Dockerfile.gpu` версия CUDA была **литералом `12.2.0` в пяти строках FROM**,
при этом комментарий к `CUDA_ARCH` перечисляет в списке «all» архитектуру `120` (sm_120, RTX 50xx).
CUDA 12.2 архитектуру sm_120 не знает — сборка с `CUDA_ARCH=120` падает на
`Unsupported gpu architecture 'compute_120'`. То есть собрать узел под 5060 (машина 2) на этом
Dockerfile было нельзя, и выяснилось это только при попытке (драйверы на обеих машинах — 617.42,
12.8 они поддерживают).
Правка: версия вынесена в `ARG CUDA_VERSION=12.2.0` (дефолт не меняется — прежние сборки под
sm_86 остаются как были), а `scripts/build-containers.ps1` получил `-CudaVersion` и `-CudaBase`
(реестр: умолчание Dockerfile — timeweb, который отдаёт devel-слой ~110 КБ/с; `mirror.gcr.io/nvidia/cuda`
тянет его за секунды). Сборка узла на машине 2 идёт с
`-CudaArch 120 -CudaVersion 12.8.0 -CudaBase mirror.gcr.io/nvidia/cuda`.
Побочный вопрос на будущее: compose (`docker-compose.stack.yml`) пробрасывает в build только
`CUDA_ARCH`, поэтому для `docker compose up --build` под Blackwell туда нужен ещё `CUDA_VERSION`.

**Находка 6 (приёмка, R101): доставка версии llama.cpp в бандл-стенде не задействована.**
`GET /api/v1/backends` отдаёт пустой `buildInfo` **и на новом cppworker** (`version=r107`,
`bridgeVersion=0.2.0` в логе), то есть дело не в старой сборке образа. Причина по проводке:
`buildInfo` кладёт в тело регистрации только Go-сторона cppworker
(`cmd/cppworker/balancer_register.go:249`, источник — env `CPPWORKER_LLAMA_BUILD`), а
бандл-стенд регистрацию Go-стороной ВЫКЛЮЧАЕТ (`CPPWORKER_REGISTER_DISABLE=true` в
`docker-compose.stack.yml`) — бэкенд регистрирует встроенный агент (`internal/agent`), и в
его регистрации/ heartbeat поля `buildInfo` нет вовсе. Плюс сам env `CPPWORKER_LLAMA_BUILD`
в compose не передаётся.
Следствие: валидатор §7 честно пишет `version_unknown` («совместимость протокола RPC не
подтверждена») — то есть проверка версий есть, но подтвердить её на этом стенде нечем.
Правка (отдельный раунд): встроенный агент должен нести `buildInfo` в своей регистрации
(он живёт в том же контейнере и может взять значение из конфига cppbackend), а compose —
пробрасывать `CPPWORKER_LLAMA_BUILD` (сейчас сабмодуль llama.cpp = `1d2869c6e`, tag `b10415`).

**Находка 5 (проводка, живьём не воспроизводилась намеренно).** `MigrateOperatingModeToPlacement`
вызывается РОВНО из одного места — `internal/config/config.go:52` (загрузка конфига). Значит
живой `PUT /api/v1/cluster/config {"operatingMode":"replication"}` (`handlers_cluster.go:418–452`)
переключает режим и включает `modelReplication.Enabled`, но политику размещения и заметки
миграции НЕ пересчитывает: `GET /api/v1/placement` продолжит объяснять оператору конвертацию
прежнего режима (`operatingMode=standard → …`), хотя режим уже другой. Живьём это не
воспроизводилось сознательно: переключение режима на рабочем стенде — не безобидная операция,
оно включает репликацию/координатор как побочный эффект.
Минимальная правка (отдельный раунд): при применении `operatingMode` из PUT гасить
`s.config.ModeMigrationNotes` — заметка описывает конвертацию при загрузке, и после явного
выбора режима оператором она неверна. Альтернатива (пересчитывать конвертацию) хуже: она бы
переписывала политику, которую оператор только что задал руками.

### 0.5.1 Машина 2: почему не отвечает (диагностика)

Не «стек не запущен» и не «машина выключена». Факты:

* ARP-запись `192.0.2.10 → fc-9d-05-48-34-07` живёт, а `192.0.2.0/24` — свой
  маршрут через Ethernet → машина включена и в одной подсети с нами;
* **порт 5040 отвечает** (встроенное правило Windows «Connected Devices Platform»);
* а 135, 139, 445, 3389, 5201, 11434, 18092, 18093, 18033, 50052 — **timeout, а не
  refused** (`scripts/stand-ports.ps1 -Action Probe -Target 192.0.2.10`).

Разница между `refused` и `timeout` здесь решающая: `refused` означал бы «хост ответил,
просто слушать некому», а `timeout` — «пакет дропнут». Значит причина — **входящие правила
фаервола**, а не отсутствие сервисов. Windows по умолчанию рубит входящие и пускает
исходящие; отсюда неочевидное следствие, о которое легко споткнуться:

| Направление | Нужно правило? |
|---|---|
| агент машины 2 → балансер (регистрация, метрики) | **нет** — это исходящее с машины 2 |
| балансер → cppworker машины 2 (`:18092`) | **да** — входящее на машину 2 |
| мастер раскладки → `rpc-server` машины 2 (`:50052`) | **да** |
| Вы (WebUI/API) → машина 2 (`:18083`, `:18081`) | **да** |
| `iperf3 -s` на машине 2 (`:5201`) | **да**, и правило Docker'ом не создаётся (это не контейнер) |

Поэтому «агент же сам отдаёт данные, значит порты открыты» верно только для одного
направления из четырёх.

Чинится скриптом **`scripts/stand-ports.ps1`** (проверен: `-Action Probe` прогнан на живую,
`-Action Open` — через `-WhatIf`): создаёт группу правил `OllamaLegion` по одному на порт,
идемпотентно, с `-Action Remove` для отката, `-RemoteAddress LocalSubnet` по умолчанию.
Запускать **на той машине, чьи порты открываются** (для машины 2 — в консоли администратора
там же). Уже существующий `scripts/deploy-llama-remote.ps1` разворачивает узел по WinRM/SSH,
но ему нужен ровно тот канал, который и закрыт: сначала правила, потом развёртывание.

Docker Desktop для публикуемых портов обычно создаёт правило сам — но полагаться на это
нельзя (автоправил на стенде не появилось, а у iperf3 их не будет вовсе).

Здесь был указан `192.0.2.11` — это адрес из документационного диапазона RFC 5737, то есть заглушка:
настоящий адрес выяснился только при подключении машины. Сеть — MikroTik hAP ac³, 5×1 Гбит/с, MTU 1500, jumbo frames нет.

**Шаг 0 (до любого кода) — измерить сеть и понять, что вообще доступно:**

```powershell

iperf3 -s
# с машины 1 на машину 2, 30 секунд, 4 потока
iperf3 -c 192.0.2.10 -t 30 -P 4
```

Ожидаемый ориентир: **110–118 МБ/с** (≈900–940 Мбит/с полезной нагрузки). Если получится заметно меньше —
сначала чинится сеть/драйверы, потому что всё дальнейшее считается от этой цифры (см. §3).

**Результат шага 0 (2026-10-11): измерено, но не `iperf3` — он на этой машине не работает.**
Сборка iperf3 под Windows — Cygwin; на машине 2 (`Windows 26300`) сервер принимает управляющее
и потоковое соединения, а затем падает с `iperf3: error - unable to send control message … Bad
file descriptor`. Проверено в трёх вариантах запуска: через WMI, в живой SSH-сессии (с нормальной
консолью) и с временным правилом фаервола «разрешить всё из подсети» — последнее заодно доказало,
что фаервол тут ни при чём (в журнале сервера видно и `Accepted connection`, и установленный
поток `[5] local 192.0.2.10 port 5201 connected to …`).
Поэтому канал измерен сокетами .NET: **`scripts/measure-network.ps1`** (режимы `Server`/`Client`,
оба направления, 300 МБ на направление, буфер 256 КБ, случайные данные — чтобы исключить сжатие).

| Направление | Клиент (честный конец-в-конец) | Сервер (независимая сторона) |
|---|---|---|
| машина 2 → машина 1 (**download**) | **92.2 МБ/с** (738 Мбит/с), 3.252 с | 104.4 МБ/с (835 Мбит/с), 2.873 с |
| машина 1 → машина 2 (**upload**) | 110.2 МБ/с (882 Мбит/с), 2.722 с | **109.9 МБ/с** (880 Мбит/с), 2.729 с |

Расхождение внутри пары «download» ожидаемо: отправитель останавливает секундомер, когда данные
уже в буфере ядра, а получатель — когда они реально дошли, поэтому честная цифра — клиентская (92.2 МБ/с).
На «upload» стороны совпали (110.2 против 109.9), и это лучшая проверка метода: две независимые
реализации дали одну цифру.

**Что это значит для §3:** посылка «112 МБ/с в обе стороны» верна только для направления
машина 1 → машина 2 (110 ≈ 112). Обратное направление на **~18 % медленнее**: при 92 МБ/с
слой 8 КБ/токен стоит уже **0.089 мс** вместо 0.073, а префилл 512 токенов — **45.6 мс** вместо 37.4.
Для раскладки это не приговор (слоями трафик мизерный), но для row split разница существенна, и
считать надо от 92, а не от 112. Причину асимметрии (настройки NIC/энергосбережение ноутбука или
порт MikroTik) стоит посмотреть отдельно.

### 0.5.2 Двухузловой стенд: что проверено живьём (2026-10-11)

Машина 2 подключена как **второй бэкенд**, и это разблокировало ровно те проверки, которые
на одноузловом стенде были недостижимы. Приёмка (`scripts/placement-live-acceptance.ps1
-Node2Id CPPWORKER-34`) — **15 PASS / 0 FAIL / 2 INFO**.

| # | Было (один узел) | Стало (два узла) |
|---|---|---|
| A4 | `single`, degraded — «не влезает никуда» | **`sharded`**: «ни один узел не вмещает (10.5 ГБ при 7.6 ГБ), а сумма по 2 узлам (14.0 ГБ) — вмещает: раскладка слоями» |
| A4t | INFO — трафика нет | **PASS**: `layer=0.091 мс/токен`, `row=3.657 мс/токен`, `prefill512=46.8 мс` |
| A4c | `single` | **`replicated`**: «влезает в 2 узла по отдельности — копии дают кратную пропускную способность» |
| A3 | узел не зарегистрирован | узел найден; живая проба дала `rpc_unreachable` на `192.0.2.10:50052` и `version_unknown` по ОБОИМ узлам |
| A7 | `vramKnown=1`, `degraded=true` | `vramKnown=2`, `degraded=false` |

**Числа §3 сошлись с измеренной сетью.** Трафик слоя, посчитанный планировщиком по формулам §3,
дал **0.091 мс/токен** — это ровно 8 КБ ÷ 92 МБ/с (измерено в §0: 92.2 МБ/с). То есть полоса,
замеренная своими сокетами, и математика плана — про одно и то же, независимо друг от друга.
Это лучшая проверка обеих: если бы замер или формула врали, они бы разошлись.

**Узел на машине 2 (сборка под sm_120) проверен живьём:**
* образ `cppworker:gpu-r107-120` (CUDA 12.8, `-CudaArch 120`) собран на машине 2 из её же репозитория
  (тот же коммит `fa7f71d`, тот же сабмодуль llama.cpp `1d2869c6e`);
* `/api/gpu` отдаёт `vramFreeSource: "cudaMemGetInfo"` — **CUDA на Blackwell инициализируется**;
* запрос чата прямо на узел: HTTP 200 за 134 с (первая загрузка модели), VRAM 1090 → 2938 МБ;
* **запрос через балансер**: `X-Backend-Id: CPPWORKER-34`, 3.4 с — инференс реально ушёл на вторую машину.

**Находка 8 (конфиг узла): GPU используется наполовину.** В логе загрузки:
`load_tensors: offloaded 19/43 layers to GPU`, `CPU_Mapped model buffer size = 3114 MiB`,
`CUDA0 model buffer size = 1251 MiB`, `effective n_ctx=32768` (хотя env просил 65536).
То есть на 5060 с 8 ГБ gemma-4 села частично: 3.1 ГБ весов остались в оперативной памяти.
Причина — логика подбора (auto-offload/ram-fallback), а не сломанная сборка; но именно поэтому
«медленно» на этой машине может быть не про сеть и не про архитектуру, а про то, что половина
модели считается на CPU. Это ровно тот вопрос, который §0.5 ставит для imageworker, — и он
подтвердился на текстовом узле.

**Машина 2 как узел: как поднята (для повторения).**
Переменные сняты снимком с работающего местного контейнера (`docker exec … printenv`, белый список
`CPPWORKER_*`/`AGENT_*`/`BALANCER_*`), чтобы узел не отличался поведением; переопределены только
машинно-зависимые: `AGENT_ID=cppworker-cyborg-bundled-agent` (иначе столкновение с местным
бэкендом — балансер привязывает агента по ID), `CPPWORKER_ADVERTISE_HOST`/`AGENT_PUBLIC_HOST=192.0.2.10`
(иначе балансер получает hex-хостнейм контейнера), `BALANCER_URL=http://192.0.2.20:18081`
(18081 — ADMIN API, куда идёт регистрация), `MODELS_DIR=C:/ollama/ollamalegion/models`.
Публикуются 18092 (инференс) и 18034 (встроенный агент: на отдельной машине балансеру больше
нечем до него дотянуться). Оба порта добавлены в `scripts/stand-ports.ps1` — в список по умолчанию
их класть нельзя, они нужны только на отдельной машине.

### 0.5.3 Репликация на двух машинах — проверена работой (2026-10-11)

Первая доступная без S1 проверка, которая показывает распределение реально, а не в предложении.

Что сделано: модель `gemma-4-E4B-it-Q4_K_M` загружена на **оба** узла (местный 3070 — 2962 МБ VRAM,
машина 2 — 2948 МБ), применена политика `models[{strategy: replicated}]`, резолвер вернул
`strategy=replicated source=model`, затем 8 запросов через балансер с разным `User-Agent`
(иначе session-stickiness прибила бы все запросы к одному бэкенду).

Результат: **`CPPWORKER-34` (машина 2) — 7 запросов, `cppworker-gpu-bundled-agent` (машина 1) — 1**.
То есть распределение по двум машинам работает: балансер отправил инференс на вторую машину,
и это не «повезло один раз» — семь из восьми. Политика возвращена в исходное состояние.

**Находка 9 (операционная): репликация живёт, пока модель тёплая на ВСЕХ узлах.**
Первый заход теста оказался недействительным, и это поучительно: между загрузкой модели на
машину 2 и запросами прошло больше десяти минут, сработал `CPPWORKER_IDLE_UNLOAD_MINUTES=10`
(переменная приехала из снимка местного окружения), машина 2 выгрузила модель — и все шесть
запросов ушли на единственный узел, где модель осталась. Снаружи это выглядит как «replicated
не распределяет», хотя планировщик был прав: реплик с моделью не осталось.
Практический вывод: на репликах `CPPWORKER_IDLE_UNLOAD_MINUTES` должен быть `0` (или заметно
больше окна теста), иначе `replicated` молча деградирует до `single` через десять минут простоя.
Это же объясняет, почему «вторая карта простаивает» может быть не про планировщик.

**Находка 10 (открытый вопрос): распределение неравномерное — 7:1, а не 50:50.**
Оба узла имели модель и почти одинаковую свободную VRAM (5229 и 5175 МБ), так что по памяти
перевеса нет; похоже на оценку загрузки/латентности в селекторе (`resource-aware`,
`ModelLatencyTracker`), но снаружи это не докажешь. Это не отказ (запросы идут на оба узла),
но и не то, что обещает слово «репликация»; разбирать — в селекторе, отдельным шагом.

**Побочное наблюдение про передачу файлов.** Копирование модели (3.93 ГБ) с машины 2 на машину 1
через `scp` дало **23.4 МБ/с** (171.5 с) — вчетверо меньше, чем 92 МБ/с, измеренные чистыми
сокетами. Узкое место, судя по всему, приёмный диск (`D:` с 20 ГБ свободных) или шифр SSH, а не
сеть. Для плана это важно в другом смысле: «перекинуть веса на второй узел» — это минуты, а не
секунды, и в раскладке слоями такие пересылки надо считать отдельно от per-token трафика.

**Шаг 0.5 — проверить, на чём реально считает imageworker на машине 2.** Открытый вопрос из прошлой сессии:
генерация 512×512 / 8 шагов занимает ~287 с. Это на 1–2 порядка медленнее ожидаемого для RTX 5060
и похоже на **CPU-исполнение** (не подобран `--backend cuda` / sd.cpp собран без CUDA).
Если это так — половина «медленности» imageworker решается конфигом, а не распределением.

**Шаг 0.6 — зафиксировать версии:** обе стороны RPC обязаны быть собраны **из одного коммита llama.cpp**
(протокол RPC версионно-чувствителен). Разные `CMAKE_CUDA_ARCHITECTURES` — нормально
(sm_86 у 3070, sm_120 у 5060), но исходник один.

## 1. Что просил пользователь (дословный смысл запроса)

1. Распределение одной модели между несколькими видеокартами **на разных бэкендах**, в т.ч. llama.cpp и imageworker.
2. Полностью понимать разграничения («что где живёт»), чтобы **постепенно уйти от режимов работы**:
   два бэкенда с одной моделью, стандартный одиночный вариант, или поднятый бэкенд Ollama — всё это
   должно выражаться одной конфигурацией, а не взаимоисключающими режимами.
3. **Полностью переделать логику первоначальной настройки** (setup wizard) с проверкой, что в ней указано верно.
4. Отдельное **окно объединения бэкендов** между собой, чтобы поднимать более тяжёлые модели.
5. Приоритет — чтобы распределение **работало даже на 1 Гбит/с**, с прицелом на перенос на более быструю сеть
   (то есть архитектура не должна требовать 10 Гбит/с, а лишь выигрывать от них).

## 3. Сетевой бюджет 1 Гбит/с — почему это вообще возможно

Формулы (для llama.cpp-подобной раскладки; `H` — hidden size, `L` — число слоёв, `B` — размер префилла):

| Схема | Трафик на токен | Трафик на префилл `B` | Комментарий |
|-------|-----------------|------------------------|-------------|
| **Layer split (pipeline)** | `H × bytes` на пересечение границы | `B × H × bytes` | Границу батч пересекает один раз за проход |
| **Row/tensor split** | `H × bytes × L` | `B × H × bytes × L` | Каждый слой обменивается партиалами |

Числа при `H = 4096`, `L = 32`, канал **112 МБ/с** (1 Гбит/с, TCP):

| Схема | F16 | F32 | Доля от 33 мс/ток (30 tok/s) |
|-------|-----|-----|------------------------------|
| Layer split, токен | 8 КБ → **0.07 мс** | 16 КБ → **0.14 мс** | < 0.5 % — **незаметно** |
| Layer split, префилл 512 | 4.2 МБ → **37 мс** | 8.4 МБ → **75 мс** | разовая плата за TTFT |
| Row split, токен | 256 КБ → 2.3 мс | 512 КБ → **4.6 мс** | +7…14 % к времени токена |
| Row split, префилл 512 | 134 МБ → 1.2 с | 268 МБ → **2.4 с** | заметно на длинных промптах |

**Вывод для проектирования:**
- **Layer split по 1 Гбит/с — рабочий вариант** (декод почти не страдает). Это основной путь для «поднять модель тяжелее 8 ГБ».
- **Row split** терпим на decode, дорог на prefill → включать осознанно, с предупреждением в UI (оценка по формуле выше, а не «на глаз»).
- **MoE-модели** (активны не все эксперты) переносят по сети кратно меньше → на нашей сети это самый выгодный класс.
- Порог, за которым 10 Гбит/с становится обязательным: row split при `H ≥ 8192` **и** длинных префиллах (>4k) —
  вот эту оценку и должен показывать wizard, вместо молчаливого «будет медленно».

**Альтернатива, которую надо измерить прежде, чем строить распределение:** CPU+GPU hybrid на **одной** машине
(24.5 GiB RAM + 8 ГБ VRAM). Часто для dense-модели это быстрее сетевого сплита. Acceptance-критерий §6
требует сравнения трёх чисел: `single`, `hybrid CPU+GPU`, `network layer split` на одной и той же модели.

## 5. Разграничения: что где живёт (чтобы «уйти от режимов»)

```
Клиент (Cline / OpenWebUI / curl)
        │  OpenAI / Ollama API
        ▼
[Балансер]  ← ЕДИНСТВЕННОЕ место, где принимается решение о размещении
  ├─ placement resolver: запрос → модель → класс → глобальный дефолт
  ├─ исполнители: single | pool | replicated | sharded(RPC) | rpc
  ├─ admission-очередь: слоты считаются у ЛОГИЧЕСКОГО бэкенда (группа = 1 слот)
  └─ наблюдаемость: /api/v1/placement, /api/v1/metrics, /monitor
        │
        ├─► [cppworker A]  llama.cpp, GPU 0 (мастер группы)
        │        └── RPC-канал (50052) ──► [cppworker B] llama.cpp, GPU 1 (слои N/2..N)
        ├─► [ollama]       отдельный тип бэкенда, в той же политике
        └─► [imageworker]  image_cpp-тип, batch-split
```

Правила разграничения (зафиксировать в `docs/backend-type-isolation.md` и `docs/rpc-coordinator.md`):

1. **Режим больше не влияет на маршрутизацию.** `operatingMode` — только совместимость/миграция (см. §9).
2. **Логический бэкенд** — новый первоклассный объект: `id`, `members[]`, `role` (master/worker), `strategy`, `vramBudget`.
   Все существующие счётчики (слоты, active, X-Backend-ID) работают с логическим id.
3. **Одна модель = один логический бэкенд** при `sharded`; реплики остаются группой из нескольких независимых.
4. **Agent** (на каждой машине) остаётся владельцем железа: NVML/VRAM/heartbeat. Через него же — список RPC-узлов.
5. **cppworker** знает только про свой GPU и про список RPC-серверов; он не знает, «какой режим» в балансере.
6. **WebUI** — только читает состояние и пишет **политику** (`balancing.placement`), никогда не переключает «режим».

## 7. Первоначальная настройка: что именно проверять

Валидатор (S4) обязан отклонять/предупреждать **до** сохранения:

| Проверка | Уровень | Сообщение |
|----------|---------|-----------|
| Узел недоступен / порт RPC закрыт | ошибка | «узел X не отвечает на 50052» |
| Разные коммиты llama.cpp / разные бэкенды ggml | ошибка | «версии не совпадают: A=…, B=…» |
| Сумма VRAM < веса × 1.25 | ошибка | «нужно 9.4 ГБ, доступно 7.8 ГБ по узлам» |
| RAM под KV-кэш при заданном n_ctx | ошибка | «KV при ctx=65536 требует 3.1 ГБ, свободно 1.2 ГБ» |
| Оценка трафика row split > 10 % времени токена | предупреждение | «row split: ≈+12 % к токену, ≈2.4 с на префилл 512» |
| Модель влезает в один узел | подсказка | «достаточно `single`; `replicated` даст ×2 пропускной способности» |
| Тип бэкенда несовместим с моделью | ошибка | «image_cpp не обслуживает текстовые модели» |
| Неоднородные GPU при `auto.requireHomogeneous` | предупреждение | «3070 (sm_86) + 5060 (sm_120): группа неоднородна» |

## 9. Миграция режимов → политика

| Было (`operatingMode`) | Стало (`balancing.placement`) |
|------------------------|-------------------------------|
| `standard` | дефолт: `auto` (single → replicated по fit) |

| `rpc_coordinator` | `sharded` (транспорт RPC) |
| группы репликации | `replicated` |

Автоконверт при загрузке конфига + запись в лог «mode X → placement Y». Обратная совместимость чтения — да,
записи — нет (через один релиз `operatingMode` убрать из примеров, затем из кода).

## 10. imageworker: честные границы

- sd.cpp **не поддерживает** распределение одной генерации по нескольким GPU → V6 (stage-split) — форк/ресёрч.
- Что реально: **V5 batch-split** (несколько изображений параллельно по разным бэкендам) и **разные модели на разных бэкендах** (роутинг).
- Побочные задачи: видимость image-запросов в статистике, профиль CUDA на машине 2, VRAM image-бэкенда в placement-fit.
