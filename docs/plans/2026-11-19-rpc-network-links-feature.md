# RPC-раскладка по выбранной сети: интерфейсы, связи, роли (фича на будущее)

**Дата:** 2026-11-19. **Статус:** 🔵 **ПРЕДЛОЖЕНИЕ (не начато)** — заложено на будущее.
**Номер раунда:** не закреплён.
**Связанные документы:** `docs/architecture/rpc-link-bandwidth.ru.md` (замер канала),
`docs/architecture/layer-sharding.ru.md`, `docs/plans/2026-10-07-model-distribution-multi-gpu-next-session.md` (S1–S8),
`docs/plans/2026-11-19-webui-and-balancer-fixes.md` (§7 состояние, §8 критичная ошибка декода).

**Задача.** Дать оператору **осознанно** отдавать бэкенду сетевой интерфейс (например, 10Gb), видеть список
доступных интерфейсов, устанавливать и **проверять** связь с конкретным бэкендом на другом конце, определять, кто
ведомый, а кто ведущий, и раскладывать слои **по этой линии** — чтобы складывать память узлов и получать скорость
обмена, а не «какой-нибудь» маршрут, выбранный ОС.

## 2. Модель данных (новые типы)

```go
// NetIface — интерфейс, ВИДИМЫЙ процессу, который будет слушать rpc-server (cppworker, не агент!).
type NetIface struct {
    Name    string `json:"name"`            // eth0, eth1, macvtap0
    Addrs   []string `json:"addrs"`         // IPv4/IPv6, CIDR
    MAC     string `json:"mac,omitempty"`
    MTU     int    `json:"mtu"`
    SpeedMbps int  `json:"speedMbps,omitempty"` // 0 = неизвестно (в контейнере часто так)
    Driver  string `json:"driver,omitempty"`
    Default bool   `json:"default"`         // маршрут по умолчанию
    Source  string `json:"source"`          // net.Interface | ethtool | declared
}

// NetBinding — ЯВНЫЙ выбор оператора: какую линию отдать раскладке.
type NetBinding struct {
    BackendID string `json:"backendId"`
    Iface     string `json:"iface"`      // имя, не IP: IP в контейнере меняется
    BindAddr  string `json:"bindAddr"`   // адрес на этом интерфейсе (проверяется при применении)
    Port      int    `json:"port"`       // по умолчанию 50052
    AllowCIDR []string `json:"allowCidr,omitempty"` // кому разрешено подключаться
    Applied   bool   `json:"applied"`    // rpc-server уже перезапущен на этой привязке
}

// NetPeer — кто на другом конце (ответ на hello).
type NetPeer struct {
    BackendID string `json:"backendId"`
    Role      string `json:"role"`       // master|donor|standalone
    LlamaCommit string `json:"llamaCommit"`
    RPCProto  string `json:"rpcProto"`
    Iface     string `json:"iface"`
    VRAMFreeMB uint64 `json:"vramFreeMb"`
}

// NetLink — измеренная линия между двумя бэкендами (неориентированная).
type NetLink struct {
    A, B NetEndpoint `json:"a"`; // BackendID + Iface + Addr
    MeasuredAt time.Time `json:"measuredAt"`
    RTTms   float64 `json:"rttMs"`
    Mbps    float64 `json:"mbps"`        // измерено продуктом, не из .env
    Bytes   int64   `json:"bytes"`
    MTU     int     `json:"mtu"`
    Ok      bool    `json:"ok"`
    Note    string  `json:"note,omitempty"` // «подсеть не совпадает», «MTU 1500», «peer другой сборки»
}
```

Хранение: `NetLink` и `NetBinding` — в `state.json` рядом с бэкендами (переживают рестарт балансера),
`NetIface` — только как снимок от воркера (не персистится).

## 3. Новое API

| Метод | Путь | Исполняет | Зачем |
|---|---|---|---|
| `GET` | `/api/v1/backends/{id}/net/interfaces` | балансер → воркер (`GET /api/net/interfaces`) | инвентарь интерфейсов **того контейнера**, который будет слушать rpc-server |
| `PUT` | `/api/v1/backends/{id}/net/binding` | балансер → воркер | явная привязка: `iface`/`bindAddr`/`port`/`allowCidr`; **применяется** перезапуском rpc-server (только если он не участвует в активной раскладке — иначе 409) |
| `DELETE` | `/api/v1/backends/{id}/net/binding` | балансер → воркер | вернуть `0.0.0.0:50052` |
| `POST` | `/api/v1/backends/{id}/net/hello` | воркер | «кто на другом конце»: `{addr}` → `NetPeer` (роль, сборка, proto, свободная VRAM) |
| `POST` | `/api/v1/backends/{id}/net/probe` | воркер | замер **с этого интерфейса** до `addr`: RTT (TCP) + скорость (`/api/rpc-link-probe` с `LocalAddr`-биндом) → `NetProbeResult` |
| `GET/PUT` | `/api/v1/net/links` | балансер | реестр измеренных линий (матрица); `PUT` — ручная правка/инвалидация |
| `POST` | `/api/v1/net/links/measure` | балансер | прогнать замер по списку пар (асинхронно, 202 + SSE как у reload) |
| `GET` | `/api/v1/backends/{id}/net/rpc-server` | балансер → воркер | статус: bind, порт, слушается, последние 10 строк лога (`rpcServerLog`) |

Правила контракта:
- **источник истины об интерфейсах — воркер**, а не агент: агент может жить в другом контейнере/сети и видеть другое;
- любое применение привязки **перезапускает** rpc-server → активная раскладка рвётся, поэтому `409` при живой
  раскладке и явное подтверждение в UI («перезапустит узел раскладки»);
- `probe` **никогда не пишет** в конфиг: только измеряет; запись измерения — отдельный `PUT /net/links` (или авто-
  запись после `measure`, с полем `source: product`).

## 4. Docker: как «осознанно отдать интерфейс» (варианты и что выбрать)

Контейнер видит **только** то, что дал Docker. Отсюда три способа дать бэкенду 10Gb:

| Способ | Как выглядит в compose | Плюсы | Минусы / что решить |
|---|---|---|---|
| **host network** | `network_mode: host` | виден физический интерфейс, скорость `ethtool` доступна, MTU настоящий | нет изоляции, порты занимаются на хосте; на одной машине два бэкенда не поднять |
| **macvlan** (рекомендую для 10Gb) | `networks: net10g: {ipv4_address: 10.20.0.11}` + внешняя сеть `macvlan` на `eth1` | реальный L2, полная скорость vNIC, отдельная подсеть от служебной; `rpc-server` биндится на `10.20.0.11` | L2-изоляция: хост не видит контейнер (нужен `macvlan` shim или статический маршрут); **решение**: разрешаем ли bрidж-сеть для управления + macvlan для раскладки одновременно (да, это две сети) |
| **ipvlan L2** | то же, `driver: ipvlan` | не ломает связь с хостом | нет broadcast (mDNS-автообнаружение не сработает) — влияет на выбор auto-discovery |
| **вторая bridge-сеть** | `networks: [default, net10g]` | просто | скорость = скорость хоста (нет гарантии 10Gb), часто делит один физический NIC |

Обязательное следствие для кода: **две сети у воркера** — «управляющая» (балансер ↔ /api/*) и «линия
раскладки» (rpc-server ↔ rpc-server). Балансер должен знать **оба** адреса и никогда не путать их.

**Явное решение №1.** Как оператор объявляет интерфейс: (а) только в compose, а бэкенд **только читает** что видит;
(б) в compose **и** явный allow-list в конфиге бэкенда (`net.exposedInterfaces: [eth1]`), и воркер отказывается
биндиться на интерфейс, которого нет в списке. Рекомендую (б): «осознанность» = декларация, а не «что попалось».

## 5. Роли без «формирования групп»: явная привязка донора к мастеру

### 5.1 Что уже есть (важно: API давно готов, не хватает UI там, где оператор ищет)

| Есть | Где |
|---|---|
| Роли `standalone` / `main` / `donor` в модели бэкенда | `pkg/types/backend.go:38-44,185-188` |
| `PUT /api/v1/backends/{id}/role` (`{role}`), ошибки 400 на неизвестную роль | `internal/api/handlers_backends.go:239-362` |
| **Персист роли** в `runtime-overrides/backend-roles.json` — переживает рестарт балансера и перерегистрацию агента | `handlers_backends.go:93-232` (`LoadBackendRoles`/`SaveBackendRoles`, `roleForBackend`), `state_host_persist_r351_test.go` |
| Балансер применяет роль: главному уходят `rpcEnabled` + список `rpcServers`, донору — приказ поднять rpc-server | `handlers_backends.go:446-461`, `rpc_layout_node_r133.go:304,408` |
| Донор не держит своих копий; «донор занят чужим мастером» | `donor_exclusive_r304.go:133`, `cannotHostModelR304` |
| Гейт «можно ли поднимать раскладку при такой роли» | `rpc_layout_role_r148_test.go`, `rpc_layout_guard.go:122,338` |
| Роль в WebUI — **только** на «Мониторе» и в окне «Объединение бэкендов» | `webui/js/monitor/layout-panel.js:78`, `monitor/monitor-backends.js:160`, `webui/js/modules/backend-merge.js:999-1074` |

**Чего нет (и что просит оператор).**
1. На странице **«Бэкенды»** (`#backends-page`, где настраивают бэкенд) контрола роли **нет** — оператор ищет её там
   и не находит; единственный путь — Монитор или «Объединение бэкендов» (а это ровно та групповая политика, которой
   доверия нет).
2. **Нет связи «этот донор принадлежит этому мастеру».** Сейчас главному отдаются **все** узлы с ролью `donor`
   (`backend_role_r118_test.go:8`: «адреса доноров собираются из бэкендов с ролью донор»), а исключительность донора
   обеспечивается косвенно (`donor_exclusive`). Оператор не может сказать «донор D — только для мастера M».

### 5.2 Предложение: роль + явный `DonorOf`

```go
// Backend (новое поле рядом с Role)
DonorOf string `json:"donorOf,omitempty"` // backendID мастера, которому отдан донор; только для Role=donor

// API
PUT /api/v1/backends/{id}/role   // существующий; расширяется телом
//   {"role":"donor","masterId":"cppworker-gpu"}   — донор закреплён за мастером
//   {"role":"donor"}                              — донор «свободный» (закрепление снимается)
//   {"role":"main","donorIds":["a10-126"]}        — мастер и его доноры (атомарно, одним запросом)
//   {"role":"standalone"}                         — снять роль
```

Семантика (всё проверяет **балансер**, а не UI):

- донор принадлежит **ровно одному** мастеру: `DonorOf` заполняется при закреплении; пока донор закреплён, он
  **не выбирается** ни другим мастером, ни как самостоятельный бэкенд с полной моделью;
- мастер ведёт **своих** доноров (`DonorOf == master.ID`): ему уходит `rpcServers` только из них, а не из «всех доноров»;
- донор с загруженной моделью (полной копией) **не может** быть донором — 409 с причиной (уже есть `cannotHostModelR304`,
  нужно явное сообщение и отказ в UI до запроса);
- `main` без доноров = обычный бэкенд с полной моделью (поведение не меняется);
- снятие роли/удаление мастера: донорам снимается `DonorOf` (они становятся «свободными донорами») — **явно**
  логируется, а не наследуется молча;
- смена роли при **активной** раскладке — 409 «сначала освободите узел» (иначе повторяется история R172/R173, где
  роли перезапускали rpc-server под живой передачей слоёв).

### 5.3 Вместо формирования групп

- **RPC-раскладка** перестаёт зависеть от `backendGroups`/`placement.groups`: единственный вход — роли
  (`main` + закреплённые `DonorOf`). Группы остаются **производными** («мастер M + его доноры» — представление, а не
  источник), генерируются для отображения и для `/api/v1/placement`.
- **Репликация текстовых моделей** (`replicated`) групповой политикой пока **пользуется** — её трогать в этой задаче
  не нужно; в документе фиксируем границу: роль управляет **раскладкой слоёв**, группы — **копиями**.
  Это место требует решения владельца отдельно (§8, п. 3a).
- Миграция: при загрузке конфига существующие группы раскладки → `DonorOf`-связи (по `rpcEndpoint`/host),
  с отчётом «перенесено N связей, M не удалось — вот почему» (как `mode_migration.go` для режимов).

### 5.4 Переговоры перед раскладкой (кто мастер, кто ведомый)

1. Балансер берёт пару «мастер → закреплённый донор» из ролей (оператор уже решил, кто главный — п. 2 решений);
2. мастер отправляет `POST /api/v1/backends/{donor}/net/hello` на адрес **по выбранному интерфейсу**;
3. донор отвечает `NetPeer` (backendID, роль, сборка, proto, свободная VRAM, интерфейс);
4. балансер проверяет: proto/сборка совпадают (`R486`), `AllowCIDR` допускает источник, линия есть (измерена или
   «не измерена» — по решению №4 разрешаем с пометкой), `Mbps ≥ minMbps` если измерена;
5. только затем — приказ «подними rpc-server на этом интерфейсе» и раскладка по этой линии.

**UI-состояния роли (то, что просил оператор):** в списке бэкендов и на вкладке «Сеть» —
`донор мастера M` · `свободный донор` · `мастер (доноров: N)` · `самостоятельный` ·
**`доступен, но не донор`** — в этом случае связь для раскладки **не применяется** (кнопки проб/закрепления сети
видны, но помечены «только для доноров»), и это объясняется подсказкой на месте.

### 5.5 Защита

`AllowCIDR` (только из подсети линии), отказ биндиться на `0.0.0.0` в не-default сеть без подтверждения, запрет
двух мастеров на одном доноре, «одна активная раскладка на узел», отказ менять роль при живой раскладке, отказ
делать донором узел с полной моделью.

### 5.6 Источник раскладки: оператор или балансер (и почему балансер её не трогает)

Роли отвечают на вопрос «кто кому отдаёт память», но не на «какие именно слои где лежат». Это второй слой решения,
и у него ровно два источника:

```go
// Модель (или её инстанс) получает:
LayoutSource string `json:"layoutSource"` // "operator" | "balancer"
LayoutPinned bool   `json:"layoutPinned"` // true = оператор применил и запретил авто-изменения
LayoutRev    int    `json:"layoutRev"`    // растёт при каждом изменении (для diff и аудита)
```

**Контракт (то, что просил оператор):**

| Ситуация | Поведение балансера |
|---|---|
| Оператор задал раскладку, `POST /api/v1/placement/validate` вернул **без errors** → он нажал «Применить» | `layoutSource=operator`, `layoutPinned=true`. Балансер **никогда** не меняет эту раскладку сам, только показывает предложения (`POST /api/v1/placement/suggest`) |
| Оператор задал раскладку, validate вернул errors | «Применить» заблокировано, показываются числа и причина; ничего не сохраняется |
| Раскладку сделал балансер (`layoutSource=balancer`) | Балансер владеет ею и **не пересчитывает «просто так»**: только по триггерам ниже, каждый — с событием, причиной и diff |
| Оператор снял закрепление / нажал «Спросить балансер» | `layoutSource=balancer`, `LayoutPinned=false` |

**Единственный штатный триггер пересчёта — выросшее контекстное окно** (нужно больше GPU-слоёв). Остальные —
аварийные, и каждый обязан попадать в журнал с причиной:

1. **рост окна** (клиент просит больше, чем покрывает текущая раскладка слоёв) — главный триггер;
2. узел-донор ушёл (unhealthy/выключен/роль снята);
3. изменилась свободная VRAM (другая модель заняла карту) — только если текущая раскладка физически перестала
   помещаться, а не «стало неоптимально»;
4. сменилась модель/файл;
5. явная команда оператора.

Что **не** является триггером: «балансеру кажется, что можно быстрее», изменение нагрузки, перезапуск балансера
(раскладка читается из состояния), heartbeat. При `layoutPinned=true` даже аварийные триггеры дают **предложение**
и требуют подтверждения оператора — кроме одного случая: узел физически недоступен, и модель перестала
обслуживаться (тогда — отказ с числами, а не тихая переукладка).

## 6. Раскладка по линии: как учитывать скорость

- В `placement`/`rpc_layout` добавляется `linkPolicy`: `{ minMbps: 5000, prefer: "measured", requireMeasured: true }`.
- Раскладка берёт **измеренную** скорость линии из `NetLink` (а не `LB_RPC_LINK_MBPS`), считает бюджет трафика
  layer-режима по существующей формуле (`docs/architecture/rpc-link-bandwidth.ru.md`) и **отказывается**, если
  линия ниже порога — с числами в причине.
- В `/api/v1/placement` и в журнал пишется, **по какой линии** разложено: `a.iface → b.iface, Mbps, RTT, MTU`.
- `MTU` учитывается: если на одной стороне 1500, а на другой 9000 — предупреждение (в архиве 2026-11-18 уже
  зафиксировано «MTU 1500: jumbo не включён — возможна фрагментация», `info.json` воркера).

**Явное решение №4.** Что делать, если линия не измерена: (а) запрещать раскладку (`requireMeasured: true`);
(б) разрешать с pessimism-коэффициентом и пометкой «не измерено». Рекомендую (а) для новых раскладок,
(б) — только для уже работающих (не рвать живую).

### 7.5 Пока бэкенд в роли донора — WebUI не даёт ни грузить, ни менять настройки

Решение владельца: не помечать в карточке модели «модель разложена». Вместо этого — **замок по флагу донора**:

| Где | Пока у узла стоит роль `donor` (или заполнен `DonorOf`) |
|---|---|
| «Модели» → загрузка модели | кнопка **«Загрузить/Перезагрузить»** недоступна, подсказка: «узел отдан донором; снимите флаг донора в „Бэкендах“, чтобы он снова мог держать модель» |
| Карточка модели → «Настройки» (GGUF) | поля параметров загрузки **read-only**, «Применить» скрыта; та же подсказка со ссылкой на «Бэкенды» |
| Карточка модели → витрина | **никакой пометки «разложена»** (как и просил оператор) |
| Вкладка **«Загружено»** | только **отображение**: состояние (`loaded`/`loading`/`partial_offload`), **сколько слоёв принимает каждый узел** (`device_layers`/`device_layers_exact`), окно на слот, kv-тип, суммарно слоёв/узлов. Никаких кнопок изменения |
| «Бэкенды» | снятие роли `donor` — **единственный** способ разблокировать: балансер останавливает rpc-server, разбирает раскладку, узел освобождается; после этого загрузка/настройки снова доступны |

**Сервер обязан отказывать сам** (UI — только удобство): `POST /api/models/load`, `/api/models/reload`,
`/config/update` на узле с ролью `donor` → **409** с `roleRefused: true` и текстом причины. Этот контракт уже
существует для «донор не держит своих копий» (`internal/api/model_op_status_r371.go:19`,
`cannotHostModelR304`) — нужно распространить его на все перечисленные ручки и вернуть `roleRefused` в ответе,
чтобы WebUI мог показать тот же текст, а не общий 500.

Порядок разблокировки (важно, иначе получается тупик «нельзя снять роль, потому что идёт раскладка»):
1. в «Бэкендах» у донора выбирается роль `standalone` → балансер проверяет, что раскладка не передаёт данные
   прямо сейчас (живой rpc-server с активной сессией даёт 409 с текстом «дождитесь/освободите»);
2. балансер останавливает дочерний rpc-server и снимает `DonorOf` у этого узла;
3. только после этого WebUI разблокирует загрузку и настройки на этом узле.

### 8.1 Что значит «линия не измерена» (к п. 4)

«Не измерена» = **нет актуального результата `NetLink`** для пары бэкендов. Причины ровно четыре, и все они должны
быть видны оператору:

1. **Никогда не запускали** пробу (`NetLink` отсутствует) — норма на свежем стенде;
2. **Проба не удалась**: TCP не открылся (rpc-server не слушает / порт закрыт / нет маршрута), таймаут, RST —
   полный текст ошибки хранится в `NetLink.Note`;
3. **Результат устарел** (старше TTL, например 24 ч или после смены IP/MTU);
4. **Измерение было, но числа подозрительные** (0 Мбит/с, отрицательный RTT, объём передан не полностью).

Поведение: раскладка **разрешается**, но в UI и в отчёте раскладки стоит пометка `link: unknown` + причина, а бюджет
трафика считается по пессимистичной оценке (минимальная известная скорость линии или «не менее 1 Гбит/с»).
На вкладке «Сеть» рядом с парой — кнопка «Измерить» и раскрывающийся текст причины. Это и есть «разрешать, но с
пометкой и возможностью разобраться».

### 8.2 MTU и jumbo-кадры — что это и зачем (к п. 8)

**MTU** — максимальный размер полезной части Ethernet-кадра. Обычный MTU = **1500 байт**, «jumbo» = **9000**.
Зачем это раскладке: при раскладке слоёв между узлами идут **мегабайты** активаций на каждый слой (`ggml-rpc`
передаёт тензоры), то есть **много пакетов**; чем больше полезная часть кадра, тем меньше накладных расходов на
заголовки и прерывания.

Арифметика на пальцах: 10 МБ данных — это ≈ 6 700 пакетов по 1500 или ≈ 1 100 по 9000. Меньше пакетов → меньше CPU на
обработку, меньше потерь на пересылку. На 10Gb выигрыш от jumbo обычно **5–15 %** пропускной способности и заметно
ниже нагрузка на CPU при межсетевой передаче; на 1Gb выигрыш мизерный, и всё упирается в гигабит.

Где ломается: если на одном конце 1500, а на другом 9000, крупные кадры будут отбрасываться/фрагментироваться,
а при некоторых схемах (VPN/overlay) — молча теряться (PMTUD blackhole): получается «сеть вроде есть, а скорость
падает и время от времени обрывается». Поэтому:
- MTU должен совпадать **на всём пути** (оба конца, MACVLAN-интерфейс на хосте, физический порт, свитч);
- в macvlan Docker наследует MTU физического интерфейса; в bridge-сети — 1500; overlay/VPN обычно ≤1500;
- продукт **читает MTU** каждого интерфейса, показывает его в таблице и предупреждает при расхождении на линии.

Вывод для стенда: либо выставить 9000 везде (порт + свитч + macvlan), либо оставить 1500 и не ждать jumbo-выигрыша.
Продукт ничего не «включает» сам — только измеряет и предупреждает.

### 8.3 Откуда берётся «скорость интерфейса» (к п. 10)

Три источника, и путать их нельзя:

1. **Объявленная оператором** (`net.declaredSpeedMbps` в конфиге бэкенда или `LB_RPC_LINK_MBPS`-аналог) — удобно
   для документации стенда, но **может врать** (ровно этот дефект и лечили в R118.15: цифра из `.env` устаревала
   молча).
2. **Из ОС**: `/sys/class/net/<if>/speed` или `ethtool`. Даёт скорость «линка», но: в контейнере `ethtool` часто
   недоступен (нет `CAP_NET_ADMIN`), у `veth`/`macvtap` скорость часто `unknown` (или 10000, унаследованная), а для
   bridge-сети это вообще не скорость канала раскладки.
3. **Измеренная продуктом** — `/api/rpc-link-probe` (передаём известный объём «несжимаемого» потока по той же сети до
   того же хоста, где живёт rpc-server). **Это единственная цифра, которой можно верить** для бюджета раскладки.

Правило отображения: в таблице три поля с явными пометками — `скорость линка (ОС)` / `объявлено` / **`измерено`**.
Если ОС не даёт скорость — честное «неизвестно» (не подставлять 10G по имени интерфейса). Бюджет трафика раскладки
считается по **измеренной**, а при её отсутствии — по объявленной, иначе по пессимистичному минимуму (§8.1).

## 10. Чего не делать

- **Не менять сетевые настройки контейнеров из WebUI** (docker socket, `--network`, macvlan) — это вне продукта:
  WebUI только читает, что видит контейнер, и явно выбирает из этого.
- **Не изобретать свой протокол поверх ggml-rpc** — переговоры (`hello`) идут по HTTP воркера, раскладка — по
  `host:port` rpc-server, как сейчас.
- **Не хранить «скорость линии» как настройку `.env`** — только измеренная величина + пометка «не измерено».
- **Не разрешать mesh** на этом шаге (см. решение №3).
- **Не путать управляющую сеть и линию раскладки**: адрес для балансера и адрес для rpc-server — два разных поля.
- **Не оставлять в WebUI вторую таблицу раскладки** (группы) рядом с ролями: два источника одной истины — это ровно
  тот дефект, который проект уже проходил (R493 `algorithm`, R112 «залипший backendEngine»).
- **Не давать балансеру переписывать закреплённую раскладку «ради оптимизации»**: только предложение с числами.
  Тихий пересчёт = потеря доверия оператора и лишние перезагрузки модели.
- **Не делать ручную раскладку «формой без проверки»**: без ответа `/placement/validate` до применения оператор
  узнает о несовместимости только по падению загрузки.
- **Не помечать карточку модели «разложена»** и не рисовать в ней состояние раскладки: единственное место для этого —
  вкладка «Загружено» (read-only, слои по узлам) и вкладка «Раскладка».
- **Не блокировать донора только в UI**: серверный 409 `roleRefused` обязателен, иначе прямой вызов API обойдёт замок.

## 11. Инструкция оператора: как этим пользоваться (к решению №1)

### Шаг 1. Дать бэкенду второй интерфейс (Docker, один раз)

```yaml
# deployments/docker-compose.stack.yml — только для воркеров, которым нужна линия раскладки
networks:
  default: {}
  net10g:
    external: true            # создаётся один раз: docker network create -d macvlan \
                              #   --subnet=10.20.0.0/24 --gateway=10.20.0.1 \
                              #   -o parent=eth1 net10g
services:
  cppworker-gpu:
    networks:
      default: {}
      net10g:
        ipv4_address: 10.20.0.11
    environment:
      CPPWORKER_NET_EXPOSED_INTERFACES: "eth0,eth1"   # allow-list: что разрешено биндить
      CPPWORKER_NET_DECLARED_SPEED_MBPS: "eth1=10000" # необязательная подсказка, не для бюджета
```

Проверка, что контейнер действительно видит интерфейс:

```bash
docker exec cppworker-gpu ip -br addr     # ожидаем eth0 (управление) и eth1 (10.20.0.11/24)
docker exec cppworker-gpu cat /sys/class/net/eth1/mtu
```

### Шаг 2. Назначить роли в WebUI («Бэкенды»)

1. Открыть страницу **«Бэкенды»** (`?page=backends`).
2. В строке узла, у которого будет **полная модель**, выбрать роль **«Мастер»**.
3. В строках узлов, которые будут отдавать память, выбрать **«Донор»** и в соседнем поле указать **мастера**
   (по умолчанию — того, кого выбрали в п. 2). Балансер запомнит связь (`DonorOf`) в `backend-roles.json`.
4. Убедиться, что появились бейджи: `мастер (доноров: N)` у мастера и `донор мастера M` у доноров.
   Узел **не** отмеченный донором показывается как `доступен, но не донор` — для раскладки он не используется.
5. **Сразу после назначения донора WebUI запирает узел**: на «Моделях» кнопка загрузки для него недоступна, параметры
   загрузки на вкладке «Настройки» — только чтение (сервер тоже ответит 409 `roleRefused`). Это нормально: память
   узла отдана мастеру. Карточка модели при этом **не** помечается «разложена» — состояние и число слоёв смотрите на
   вкладке **«Загружено»**.

### Шаг 3. Привязать линию (вкладка «Сеть» на странице GGUF)

1. На странице **GGUF** открыть карточку мастера → вкладка **«Сеть»** (седьмая, после «Настройки»).
2. В таблице интерфейсов выбрать **`eth1` (10.20.0.11)** — это и есть 10Gb-линия; MTU и скорость показаны рядом
   с пометкой источника (§8.3).
3. Нажать **«Привязать»** → подтвердить: rpc-server будет перезапущен на этом адресе (при активной раскладке — 409).
4. То же для донора (его вкладка «Сеть»), чтобы оба конца слушали линию.

### Шаг 4. Проверить связь и линию

1. В «Проверке связи» ввести адрес донора по линии: `10.20.0.22:50052` → **«Проверить»**.
2. Ожидаемый ответ: `RTT 0.2 мс`, `Mbps ≈ 9400`, `peer: cppworker-a10 (donor), llama b1b770d9, proto 10.0.0`.
3. Если `link: unknown` — раскрыть причину: «проба не запускалась» / «TCP недоступен» / «результат устарел» /
   «подозрительные числа» (§8.1). Раскладка при этом разрешена с пометкой.
4. Предупреждение `MTU 1500 ≠ 9000` означает, что jumbo не настроен на всём пути (§8.2) — на 10Gb это минус 5–15 %
   и больше нагрузки на CPU; правится на свитче/хосте, не в продукте.

### Шаг 5. Разложить модель

1. Загрузить модель на мастере (карточка GGUF → «Настройки» → загрузка) с окном, которое влезает в **его** VRAM.
2. Выбрать способ раскладки:
   - **отдать балансеру** — ничего не делать: раскладку он спроектирует сам по ролям, линиям и предпочтениям;
     в отчёте будет `master cppworker-gpu → donor cppworker-a10 по eth1, измерено 9.4 Гбит/с, слоёв N,
     бюджет трафика X МБ/токен`. Если линия ниже `minMbps` — отказ с числами;
   - **сделать вручную** — вкладка **«Раскладка»**: задать слои по узлам, дождаться вердикта балансера
     (`errors`/`warnings`/`hints` + числа), нажать «Применить». После этого раскладка помечена
     `раскладка: ручная (закреплена)`, и балансер её **не меняет** — только предлагает (`«Спросить балансер»`).
3. Проверить в `/api/v1/placement` и на «Мониторе»: донор занят этим мастером, полной копии модели у него нет.

### Шаг 6. Что будет при выросшем контексте

Если клиент попросит окно больше, чем покрывает текущая раскладка (нужно больше GPU-слоёв), то:
- при **закреплённой** ручной раскладке — появится **предложение** с числами («нужно N слоёв вместо M, ожидаемый
  прирост окна до K»), и только оператор решает, применять ли;
- при раскладке **балансера** — он пересчитает её сам, запишет в журнал причину и diff (слои было/стало),
  и покажет это в «Мониторе». Никакие другие события (нагрузка, перезапуск, heartbeat) раскладку не трогают.

### Если что-то не так — где смотреть

| Симптом | Куда смотреть |
|---|---|
| Интерфейса нет в таблице | `docker exec … ip -br addr`; не добавлен в `networks:` или не попал в allow-list |
| «Доступен, но не донор» | роль не выставлена (§Шаг 2); балансер намеренно не использует узел для раскладки |
| Привязка отклонена (409) | у узла активная раскладка — сначала освободить (снять роль/выгрузить) |
| `link: unknown` | нажать «Измерить»; при провале — `docker logs cppworker | grep rpc-server`, проверить порт и подсеть |
| Проба даёт 1 Гбит/с вместо 10 | интерфейс в bridge-сети (скорость хоста/общий NIC), либо MTU/фрагментация (§8.2) |
| Кнопка «Загрузить» недоступна / 409 `roleRefused` | у узла стоит флаг донора (§7.5): снять роль в «Бэкендах» — это единственный способ разблокировать |
| В карточке модели не видно «разложена» | так и задумано: состояние и число слоёв — на вкладке **«Загружено»**, слои по узлам из `device_layers` |
