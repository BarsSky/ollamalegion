# Loop-экспорт Inkling-2: загрузка файла без апгрейда upstream (R709, 2026-11-25; проверено на стенде)

Вопрос, на который отвечает документ: **файл `Inkling-2-Mini-UD-Q4_K_M.gguf` —
loop-развёрнутый экспорт; можно ли загрузить его текущей сборкой, не дожидаясь
нового llama.cpp?**

Короткий ответ: да, но не одними метаданными. Файл — экспорт той же модели: он
объявляет визиты вместо физических слоёв и держит межпроходные запросы двумя
глобальными матрицами. Наша сборка (`cppworker` `gpu-r261120-r710`, llama.cpp
`5bacb7c868`) знает loop-схему как отдельную архитектуру `inkling2_loop` и ждёт
другую раскладку тензоров. `scripts/gguf_loop_meta_patch.py` переписывает
метаданные и складывает две матрицы запросов в тензоры по блокам, которые нужны
загрузчику; пропатченный файл загружается и осмысленно генерирует.

## Что объявляет файл

| Факт | Значение |
|---|---|
| `general.architecture` | `inkling2` |
| `inkling2.block_count` | 48 |
| Физических блоков в тензорах | 24 (`blk.0`..`blk.23`) |
| `inkling2.num_loops` | 3 |
| `inkling2.loop.core_start` / `core_end` | 6 / 18 |
| `inkling2.loop.gate_rank` | 64 |
| `inkling2.attention.head_count` | массив из 48, каждое значение 24 |
| `inkling2.attention.head_count_kv` | массив из 48, каждое значение 8 |
| `inkling2.attention.sliding_window_pattern` | массив из 48, паттерн 5 true + 1 false, повторён 8 раз |
| Тензоров | 734 |
| Контроллеры ядра `blk.{6..17}.loop_{attn,k,v,mlp}_{down,gain,forget}` | все на месте (144 тензора) |
| `loop_res_query.weight` / `loop_kv_res_query.weight` | обе на месте, `[2304, 24]` F32 |
| `blk.{6..17}.loop_msg_query.weight` | **нет** |
| `inkling2.loop.start` / `loop.end` / `loop.count` | **нет** |

То есть метаданные — это 48 визитов (6 прелюдии + 12 ядра x 3 прохода + 6
постудии), тензоры — 24 физических слоя, а loop-ключи записаны в старом
написании. Загрузчик читает `block_count` как число физических слоёв, идёт по
блокам `0..47` и падает на первом несуществующем тензоре:

```text
[llama.cpp] llama_model_load: error loading model: check_tensor_dims:
            tensor 'blk.24.attn_q.weight' not found
```

## Что меняет патч

| Что | До | После |
|---|---|---|
| `general.architecture` | `inkling2` | `inkling2_loop` |
| Префикс ключей | `inkling2.*` | `inkling2_loop.*` |
| `block_count` | 48 (визиты) | 24 (физические слои) |
| Три массива по визитам | длина 48 | длина 24 (первые 24 визита — это физические слои 0..23) |
| Имена контроллеров | `loop_attn_*`, `loop_mlp_*` | `loop_q_ctrl_*`, `loop_ffn_ctrl_*` |
| Loop-ключи | `num_loops`, `loop.core_start`, `loop.core_end` | плюс канонические `loop.start`, `loop.end`, `loop.count`, `loop.varying` |
| Матрицы запросов | 2 тензора по 221184 байта | 12 тензоров `blk.{6..17}.loop_msg_query.weight` по 36864 байта, в тех же байтах |

Массивы усекаются только после того, как скрипт докажет, что они по визитам:
визит `j` обязан повторять значение того физического слоя, в который он ведёт.
Для этого файла порядок визитов — прелюдия, ядро, ядро, ядро, постудия, поэтому
слоты 0..23 и есть физические слои 0..23.

Две матрицы запросов заменяются на месте, а не дописываются в конец: читатель
GGUF требует, чтобы смещения тензоров шли подряд от нуля в порядке описаний, а
обе матрицы — первые два описания в этом файле. Их суммарный размер ровно равен
12 тензорам по 36864 байта, поэтому данные никуда не сдвигаются.

## Чего патч не делает

- Не пересчитывает, не переупорядочивает и не копирует веса: каждый исходный байт
  данных остаётся на своём смещении. Переписываются только две области запросов.
- 12 тензоров `loop_msg_query` — это выборка строк из двух матриц, которые уже
  лежат в файле, ровно как это делает конвертер
  (`c/llama.cpp/conversion/inkling2.py`):

```text
msg_query[i] = stack([q[2i], kv[2i], kv[2i+1], q[2i+1]])   # q = loop_res_query, kv = loop_kv_res_query
```

- Не выдумывает значения: если двух матриц нет, скрипт отказывается, а не
  синтезирует их.

## Как запускать

```bash
# что в файле и что изменится
python scripts/gguf_loop_meta_patch.py --src <in.gguf> --dry-run --fuse-loop-queries

# записать пропатченную копию (источник не меняется)
python scripts/gguf_loop_meta_patch.py --src <in.gguf> --dst <out.gguf> --fuse-loop-queries

# только факты и побайтовая сверка данных
python scripts/gguf_loop_meta_patch.py --check <file.gguf>
python scripts/gguf_loop_meta_patch.py --verify-data <in.gguf> <out.gguf>
```

Dry-run стоит одного чтения заголовка: 4.4 с в контейнере на этом стенде. Полный
проход читает 16610543328 байт и пишет 16610544736 байт, поэтому на приёмнике
нужно 15.46 ГиБ свободного места; скрипт измеряет его до старта и отказывается с
точными числами «нужно / свободно», а не забивает диск на середине.

Медленная сторона — источник, а не приёмник. Чтение файла через Windows
bind-mount дало 19 МБ/с, поэтому проход занял 883 с (14 мин 43 с); docker-том
пишет на 342 МБ/с и читает тот же файл обратно на 414 МБ/с. Пиши выход сразу в
том и грузи модель из тома: тот же файл через bind-mount читается примерно на
30 МБ/с, а на такой скорости загрузка не дошла до `loaded` до срабатывания
сторожа 300 с (R227).

```bash
docker volume create inkling-test
docker run --rm \
  -v "$PWD/scripts:/scripts:ro" \
  -v "/d/ollama-legion-models:/in:ro" \
  -v inkling-test:/out \
  python:3.12-slim python /scripts/gguf_loop_meta_patch.py \
    --src /in/Inkling-2-Mini-UD-Q4_K_M.gguf \
    --dst /out/inkling2-loop.gguf --fuse-loop-queries
```

Прогон заканчивается проверенными фактами заголовка, и больше ничего не нужно
сверять руками:

```text
готово: {"arch": "inkling2_loop", "block_count": 24, "tensors": 744,
         "data_start": 11979872, "visits": 48, "loop": [6, 18, 3], "msg_query": 12}
```

Без `--fuse-loop-queries` скрипт пишет только метаданные. Такой файл проходит
архитектуру и массивы по визитам, но останавливается на пропавшем тензоре
контроллера:

```text
[llama.cpp] llama_model_load: error loading model: check_tensor_dims:
            tensor 'blk.6.loop_msg_query.weight' not found
```

Это и есть граница исправления одними метаданными: веса запросов сообщений
обязаны прийти из файла, а взять их можно только из матриц запросов.

## Как проверять

```bash
python scripts/test_gguf_loop_meta_patch.py
```

Тест собирает синтетический мини-GGUF с 3 физическими слоями и 5 визитами и
проверяет четыре вещи: у пропатченного заголовка верные ключи и длины массивов;
у файла с фьюзом есть 12 тензоров запросов с точным фолдом; у файла только с
метаданными тензоров запросов нет; массив не по визитам отклоняется.

с 24 ГиБ RAM):

```bash

  -v inkling-test:/app/models \
  -e CPPWORKER_MODELS_DIR=/app/models -e API_TOKEN=<token> \
  -e CPPWORKER_REGISTER_DISABLE=true \
  -e CPPWORKER_LOAD_STALL_SEC=3600 -e CPPWORKER_LOAD_WAIT_MAX_SEC=3600 \
  -e CPPWORKER_LOAD_STALE_SEC=7200 \
```

R709; все остальные строки измерены в этом прогоне.

## Память: что влезает на RTX 3070

Веса — 15.46 ГиБ, поэтому полный выгруз на GPU в 7 ГБ невозможен; воркер может
только делить слои между VRAM и RAM.

| Что | Значение |
|---|---|
| Размер файла | 16610544736 байт, 15.46 ГиБ |
| Веса в RAM (доля CPU, 43 из 49 слоёв) | 15359.88 МиБ |
| Веса на карте (6-7 слоёв) | 469.33 МиБ |
| Вердикт memfit при ctx 32768 | 7 слоёв, нужно 4803 МБ, доступно 5007 МБ, RAM нужно 11666 МБ против 2050 МБ свободных |
| KV всего кэша, ctx 8192, q8_0 | 680 МиБ |
| KV всего кэша, ctx 32768, q8_0 | 2720 МиБ |
| Печатаемый compute-буфер GPU при ctx 8192 / 32768 | 8034.12 МиБ / 10536.76 МиБ |
| Измеренная прибавка VRAM на 6-7 слоёв | около 6.6 ГиБ |

KV растёт с контекстом, а не с числом слоёв на GPU: с ctx 8192 до ctx 32768 он
идёт 680 МиБ -> 2720 МиБ, тогда как выгруженная доля остаётся 6-7 из 49 слоёв.
Печатаемый compute-буфер (8034.12 МиБ при ctx 8192) — это резерв худшего случая
на весь граф, и он больше карты; фактически процесс держит измеренные 6.6 ГиБ, и
при уже занятых рабочим столом 1238 МиБ карта заполняется на 6 слоях.

Настоящий потолок — RAM: 15359.88 МиБ отображённых весов плюс 680-2720 МиБ KV
дают около 16.5 ГиБ при ctx 8192 и около 18.6 ГиБ при ctx 32768. Воркер жил под
cgroup в 20 ГиБ и упирался в 16.02 ГБ и 19.66 ГБ соответственно, то есть у ctx
8192 запас есть, а ctx 32768 — на границе этого лимита.

## Что осталось

- Подсказка R704 для этого случая неверна: для файла, который уже объявляет
  `inkling2_loop` и не имеет контроллера ядра, ответ говорит
  `physical_blocks: 6` и предлагает ре-экспорт как `inkling2_loop_loop` с
  `block_count=6`. Нужна ветка «архитектура уже loop-схема».
- Вариант только с метаданными не может работать by construction; на этой сборке
  единственный путь — файл с фьюзом.
- Фолд повторяет конвертер, и короткая генерация связна, но полное сравнение
  перплексии с эталонной реализацией не делалось.
- Скорость для интерактива на этом стенде непригодна: 0.2 ток/с при обоих
  значениях ctx, потому что 43 из 49 слоёв модели на 26.07 B остаются на 6 vCPU.
  Доля на GPU (6-7 слоёв) измеренную скорость не меняет. Путь к рабочей скорости —
  карта на 24 ГБ под полный выгруз или меньшая квантизация.
- Пропатченный файл лежит в docker-томе `inkling-test` (внутри — `/out/inkling2-loop.gguf`).
  Сценарий D11 в UI можно прогнать по нему, не повторяя 15-минутный патч;
  `docker volume rm inkling-test` удаляет том.
