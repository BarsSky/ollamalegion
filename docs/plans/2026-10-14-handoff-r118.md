# Передача R118: что закрыто по жалобе на OpenWebUI/параллельность, что открыто (2026-10-14)

Дополнение к `docs/plans/2026-10-14-handoff-r117.md`. Жалоба была на три вещи; ниже —
что с каждой, с живыми доказательствами. Всё закоммичено и раскатано.

## Коммиты и образы

| Коммит | Что |
|---|---|
| `ef3f738` | R118: read-only пути Ollama API больше не грузят модель и не отдают 503 |
| `79046fd` | R118: занятый бэкенд больше не исключается из кандидатов (сторож = soft) |

Раскатано: `balancer:r118-softlimits` (в нём оба фикса), `webui:r117-gguf1`.
Стенд: cppworker healthy, **модель выгружена** (`count=0`), балансер здоров.

## 1. «OpenWebUI 503 / Server Connection Error, а до правок работало» — ЗАКРЫТО

Это была настоящая регрессия контракта Ollama API, и виноват был не клиент.

`POST /api/show` (OpenWebUI делает его при открытии чата) уходил в
**inference-транспорт**, где живёт preflight n_ctx:

```
proxyRequest: checking backend type for llamacpp routing   path=/api/show
preflightNCtxReload: detected n_ctx mismatch, loaded_n_ctx=0 requested=32768
preflightNCtxReload(async): starting reload ... target_n_ctx=32768
cppworker: loading model ctxSize=32768 gpuLayers=-2 (partial_offload/cpu_only)
proxyRequestLlamaCppNonStream: preflight n_ctx reload, returning 503
```

Чтение метаданных грузило модель (на стенде — почти целиком на CPU), CPU уходил в
96%, сторож ресурсов начинал блокировать бэкенд, а клиент не получал ответа:
`curl -X POST /api/show` → `http=000` после 10, 60 и 120 с.

**Фикс:** read-only/mgmt пути (`/api/show`, `/api/tags`, `/api/ps`, `/api/version`,
`/v1/models`, `/api/models[/files]`, `/api/pull`, `/api/copy`, `/api/delete`,
`/api/create`, `/api/blobs/*`) проксируются напрямую — без preflight, слота и
авто-загрузки. Inference-пути не тронуты.

**Живая проверка:** `POST /api/show` → **200 за 0.055 с** с реальными метаданными
(`architecture qwen35`, `parameter_size 20.1B`), загрузка не запускается;
`GET /api/tags|ps|version` → 200 (~0.01 с).

**Тесты:** `internal/balancer/readonly_no_inference_r118_test.go` — список путей
закреплён (и граница с обратной стороны: `/api/chat`, `/api/generate`,
`/v1/chat/completions`, `/api/embed` read-only НЕ считаются), `/api/show` не
обращается к `/api/models/load`, каждый read-only путь доходит одним прямым
запросом. Проверено мутацией: при отключённой ветке тест падает.

## 2. «Второй Cline / параллельная работа → 503» — ЗАКРЫТО ЧАСТИЧНО

Причина 503 найдена и убрана: `checkResourceLimits` (13 точек выбора бэкенда)
жёстко блокировал по мгновенной утилизации (`CPU > 95%`, `GPU > 90%`, VRAM-процент
выше резерва). На стенде с частичным offload это блокировало ВСЕ запросы во время
любой генерации — лог плотным циклом `backend CPU usage critical, blocking,
cpu_usage=96.35`. Теперь утилизация только логируется, лишний запрос ждёт в
очереди; жёсткими остались RAM > 98% и диск; прежнее поведение возвращается
флагом `LB_RESOURCE_LIMITS_HARD_BLOCK=true`.

Тесты: `resource_limits_soft_r118_test.go` (занятый — кандидат; RAM/диск —
жёстко; флаг возвращает старое) + обновлён устаревший
`TestCheckResourceLimitsExceeded`.

**Честно:** живое подтверждение «два параллельных запроса» снять не удалось — в
окно проверки стенд перезагружал модель и она исчезла (см. п. 4). Правка
подтверждена тестами, но живой прогон под нагрузкой остаётся за новой сессией.

## 3. «Два экземпляра Cline с одной машины не разделяются» — НЕ НАЧАТО

Координаты: ключ сессии очереди приходит из `getSessionIDWithModel`
(`internal/balancer/client.go:299`) → `proxy.go:1154` (`sessionKey = sessionID`) →
`waitForInferenceBackend` → `aq.enqueue`. При наличии `X-Client-ID` ключ =
`clientID + IP + модель + endpoint` (+`::req:<X-Request-ID>`, +`::tab:<X-Tab-ID>`
если клиент их шлёт); без явных заголовков — отпечаток IP+User-Agent, который у
двух экземпляров одной машины совпадает. Живые наблюдения одного места: с
`X-Session-Id: sess-B` очередь показывает `sess-B::<модель>::gen`; без заголовков
— `fp:d1c51dcaef1cbdbe::curl/8.21.0::<модель>::gen`.

Решение (нужно принять осознанно): добавить различитель экземпляра, но тот же
ключ — ключ липкости (`sessionMgr`), поэтому у клиентов с пофреймовым
`X-Request-Id` привязка к бэкенду перестанет работать. Вариант без потери
липкости: различитель только в метке очереди (`waiting_detail`), а не в ключе
сессии.

## 4. НАЙДЕНО ЖИВЬЁМ, НЕ ИСПРАВЛЕНО: пустой кэш n_ctx после рестарта → лишний reload

Каждый рестарт балансера: `loaded_n_ctx = 0` у УЖЕ загруженной модели, и первый
inference-запрос трактует это как «несовпадение» и запускает ПОЛНУЮ перезагрузку:

```
preflightNCtxReload: num_ctx decision  body_num_ctx=8192 chosen_source=request
preflightNCtxReload: detected n_ctx mismatch, scheduling async reload
  loaded_n_ctx: 0, requested_n_ctx: 8192
preflightNCtxReload(async): starting reload ... target_n_ctx: 8192
cppworker: runAsyncLoad: background load failed ... memory breakdown → модель выгружена
```

Последствия на живом: запросы висят до бюджета ожидания (900 с), модель может не
загрузиться вовсе, стенд выглядит «сломанным» сразу после перезапуска балансера
(в моём прогоне: два запроса не завершились за 13 минут, `count=0` в конце).

Лечение: `loaded_n_ctx == 0` — это «неизвестно», а не «не совпало»; обновлять
значение из живого бэкенда (`GET /api/models` → `context_size` /
`context_per_seq`) и НЕ перезагружать, если загруженная модель уже удовлетворяет
запрос. Это, по-видимому, и есть главная причина «стало медленно и сломалось»
после рестартов — приоритет №1 на следующую сессию.

## 5. Прочее, что остаётся открытым (из R117-передачи)

* устойчивость набора `internal/balancer`: в этот раз набор упал по таймауту на
  `TestCPPWorker_Failure_NetworkDrop` (в изоляции — PASS за 1.57 с) — известная
  нестабильность, не связана с правками; после правки устаревшего теста набор
  снова прошёл (`ok`), но чередование сохраняется;
* перезапуск cppworker с `ExitCode=0` после `force=true`-выгрузки брошенного
  запроса (п. 1c предыдущей передачи) — причина не установлена;
* прогон Cline в двух режимах `LB_AUTO_CONTINUE_ON_TRUNCATION`;
* хвосты по памяти/профилям.

## 6. «Поднять другую модель на другом бэкенде параллельно»

На стенде физически **один** llama.cpp-бэкенд (`cppworker-gpu-bundled-agent`,
`maxModels=1`); донор `192.0.2.10` недоступен (Docker не запущен, RDP закрыт),
а `imageworker` — только картинки. То есть «другой бэкенд» сейчас некуда
поставить: нужен либо второй llama.cpp-бэкенд (поднять донора), либо `maxModels>1`
на существующем (тогда две модели делят одну GPU — на этом стенде они не влезут
одновременно: 27B уже уходит в partial_offload).
