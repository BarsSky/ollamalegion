# Приоритет доступности: почему запрос уходит в очередь при свободных бэкендах (R493, разбор)

**Дата:** 2026-11-11 · **Основание:** два архива второго стенда
(`2026-11-11 09:05` и `10:23`) + код и документация репозитория.

Это разбор, а не список заплаток: сначала — что документация обещает, затем —
где реализация расходится с обещанием, затем — что должно измениться, чтобы
расхождение исчезло по существу.

---

## 1. Что обещает документация

`docs/architecture/balancing-guide.ru.md` §2.1 («Алгоритм выбора бэкенда v2»)
описывает четыре приоритета и четыре этапа:

| Приоритет | Условие |
|---|---|
| **P1 LOADED** | модель в памяти, `loadRatio < triggerLoadThreshold` |
| **P2 WARMING** | модель загружается |
| **P3 FREE** | свободные слоты, модель не загружена — **здесь запускается загрузка** (этап 3, `SyncModelLoad.Enabled`) |
| **P4 FALLBACK** | любой healthy по скорингу |

Плюс отдельный механизм §2.1.2 `dispatchWithModelLoad()`: «инициирует загрузку
модели на free-бэкенд с наибольшим свободным VRAM» — то есть **по замыслу**
балансер сам поднимает модель на свободной машине, а не ставит клиента в очередь.

`docs/architecture/request-lifecycle.ru.md` §2 закрепляет порядок шагов:
`choice backend + admission` → `preflight` → `если модель не загружена → load`.
Ключевая мысль: **admission (очередь) — это «нет capacity», а не «нет решения»**.
Если capacity есть на другой машине (свободный слот + модель влезает + файл есть),
заявка обязана уехать туда и загрузиться, а очередь — только последний вариант.

## 3. Где реализация расходится с замыслом

Три места, и они складываются в наблюдаемое поведение.

### 3.1 Привязка сессии к бэкенду действует как замок, а не как предпочтение

`internal/balancer/proxy.go:1614-1623`:

```go
sessionFromBackend := ""
if sessionKey != "" && p.config.Balancing.SessionStickiness && p.sessionMgr != nil {
    if s, ok := p.sessionMgr.GetSnapshot(sessionKey); ok {
        sessionFromBackend = s.BackendID        // ← бэкенд сессии
    }
}
unifiedBackend, ... := p.waitForInferenceBackendWithMoveR480(ctxWithRID, model, bt, sessionKey, sessionFromBackend)
```

`waitForInferenceBackendWithMoveR480` — это правило R480/P1-7: очередь **не
выдаёт** заявке слот на «чужом» бэкенде, если сессия привязана к прогретой копии
(«правило R139»: переезд на узкую копию сломал бы окно контекста). Смысл правила
правильный, но применён он **без проверки доступности**: у занятого мастера
свободного слота нет, и вместо решения «поднять модель на свободной машине»
заявка ждёт именно мастера. Это ровно то, что оператор описал как «маркер к
бэкенду ставится сразу на сессию, доступность не проверяется, и сессия уходит в
очередь при остальных свободных бэкендах».

### 3.2 Загрузка на свободный бэкенд (P3) не участвует в решении очереди

P3 живёт только внутри `selectBackend` (`internal/balancer/backend_selector.go:321-355`)
и срабатывает **до** admission-ожидания и **независимо** от него. Если выбор уже
вернул бэкенд (или сессия к нему привязана), путь «жду слот → вижу, что рядом
есть свободная машина → поднимаю там» в коде отсутствует. То есть обещанный
`dispatchWithModelLoad()` (§2.1.2) не подключён к очереди: он может случиться на
этапе выбора, но никогда — как реакция на «я стою в очереди, а рядом простаивает
подходящая машина».

### 3.3 «Подходящая машина» нигде не проверяется по существу

Для решения нужны три факта: (а) свободный слот, (б) файл модели есть на узле,
(в) модель влезает в свободную VRAM с резервом. Сейчас:

- (а) проверяется как `loadRatio < 0.8` по **заявленной** `MaxConcurrentReqs`, а не
  как «слот свободен сейчас»;
- (б) файл проверяется каталогом моделей (`model_catalog_r91`), и при отсутствии
  записи узел молча выпадает из P3 — без причины в очереди;
- (в) VRAM учитывается только внутри P3 (`orderCandidatesByVramFit`, R248), но не
  в решении о переезде.

Отдельно: **загрузка на 8-гигабайтную карту 27B-модели бессмысленна**, а в
решении о переезде класса карты нет — только «свободно/занято».

## 4. Как должно быть (по существу, а не заплатками)

Правило одного предложения: **очередь допустима только тогда, когда ни один узел
не может обслужить заявку сейчас и не может начать обслуживать её через
загрузку.** Реализация этого правила — четыре связанные части.

1. **Доступность — предикат, а не коэффициент.** Кандидат «доступен сейчас», если
   `tryAcquireSlot` удался (реальный слот), а не если `ActiveReqs/MaxConcurrent`.
   `MaxConcurrentReqs` — это заявка узла о параллельности; при `=1` коэффициент
   всегда 1.0 и перестаёт что-либо различать (в архиве именно так).
2. **Привязка сессии — предпочтение.** Сначала пробуем бэкенд сессии; если он не
   может принять сейчас — пере-выбор по полному правилу, включая загрузку на
   свободном узле. Прогретая копия остаётся **первым** кандидатом и побеждает,
   когда слот свободен; она не блокирует переезд, когда его нет.
3. **Загрузка вместо очереди.** Если ни один loaded-узел не принимает сейчас, а
   есть узел с (файл есть) И (VRAM с резервом ≥ потребность) — инициировать
   загрузку там (P3/`dispatchWithModelLoad`), и только затем проксировать. Выбор
   узла — по VRAM-fit с приоритетом класса карты (A10 24 ГБ раньше RTX4000 8 ГБ),
   а не «первый свободный».
4. **Причина очереди — по каждому кандидату.** Если заявка всё-таки встала, в
   `why_queued` должны быть причины отказа **всех** кандидатов. Формат в теле и в
   логе — `backend=<код>(<числа>)`, коды стабильные:
   `all_slots_busy(заняты все слоты (1/1))`, `over_load_threshold`,
   `vram_insufficient(модель не влезает: need 21.0 GiB, free 5.9 GiB)`,
   `file_absent(файла модели нет на диске узла (в каталоге N файлов, снимок M с
   назад))`, `catalog_unavailable(каталог моделей узла недоступен…)`,
   `window_too_small(<числа и источник окна>)`, `model_not_loaded`,
   `disabled_by_operator`, `donor_or_group_worker`, `not_healthy`,
   `type_not_allowed`, `no_metrics`, `resource_limit`, `no_slots_configured`.
   Различие `file_absent` / `catalog_unavailable` / `model_not_loaded` — не
   косметика: первое означает «здесь грузить нечего, копируйте файл», второе —
   «каталог узла отвалился, проверять нечего», третье — «файл, возможно, есть, но
   загрузка стоит минуты». Без этого «почему в очереди» снова придётся выяснять
   по логам воркера.

## 5. Что НЕ надо делать (и что я уже сделал зря)

- **Сессии по разным портам не надо сливать в одну.** R490 (`05bb89af`) убирал
  `endpointType` из ключа сессии, исходя из того, что «один разговор идёт через
  два API». Разговор физически один и тот же быть не может, а слияние ключа
  делает хуже: два независимых разговора одного клиента начинают считаться одной
  сессией, и привязка к бэкенду усиливается. Правка откачена (`R490 revert`), в
  документации остаётся прежняя семантика: сессия = разговор.
- **Счётчик «сессий=1» — не причина.** Оба порта обслуживает ОДИН `Proxy`
  (`cmd/balancer/main.go:240,515`), поэтому слоты и очередь общие; причина не в
  разделённом состоянии, а в решении 3.1.

## 6. Что нужно подтвердить на стенде (два факта)

1. `balancing.syncModelLoad.enabled` в `config/config.json` стенда (в
   `config/config.example.json:162-165` — `true`). Если у них `false`, P3 не
   работает вообще, и это первое, что надо включить.
2. `/api/tags` каждого узла — есть ли `Qwen3.8-27B-UD-Q4_K_M` в каталоге узла.
   Оператор говорит, что файл лежит всегда; если каталог узла его не показывает,
   балансер считает узел неподходящим молча — это отдельный дефект (3.3-б).

## 7. Порядок реализации (R493)

| Шаг | Что | Проверка |
|---|---|---|
| 1 | Доступность слотом: кандидат проходит, только если `tryAcquireSlot` удался (или `canAcceptNow`), `loadRatio` остаётся для прогрева/скоринга | тест: у loaded-узла `MaxConcurrent=1`, `Active=1` → он НЕ кандидат P1 |
| 2 | Привязка сессии как предпочтение: sticky-узел пробуется первым, при занятости — обычный выбор | тест: sticky-узел занят, свободный есть → запрос уходит на свободный |
| 3 | «Загрузка вместо очереди»: если loaded-узлы заняты, а свободный узел подходит (файл+VRAM+класс), инициировать загрузку и обслужить | тест: 1 занятой A10 + 1 свободная A10 → load на свободной, очередь не создаётся |
| 4 | Причины отказа по каждому кандидату в `why_queued` | тест: очередь из-за VRAM/файла/окна — причина названа |
| 5 | Не грузить модель, которая не влезает (8 ГБ и 27B) — отказ с числами, а не «первый свободный» | тест: RTX4000 8 ГБ не выбирается под 27B |

Пункты 1–3 — это и есть «не ставить в очередь, если есть свободные машины»; пункты
4–5 — чтобы следующий разбор не начинался с чтения логов воркера.

## 8. Что реализовано (и чем это доказано)

Пункты 1–3 и 5 закрыты кодом; пункт 4 (причины по каждому кандидату в
`why_queued`) остаётся открытым — он про диагностику, а не про само решение.

| Что | Где | Доказательство |
|---|---|---|
| Счёт занятости в P1 идёт от **эффективной** вместимости (`EffectiveMaxConcurrentRequests`, R71), а не от статического лимита конфига | `backend_selector.go`, этап 1 | `TestR493_P1UsesEffectiveCapacity`: статический лимит 4, заявка узла 1, `Active=1` → узел не выбран. Мутация «вернуть `MaxConcurrentReqs`» → тест падает |
| Привязка сессии — предпочтение: sticky-узел передаётся в очередь, только если у него есть свободный слот | `proxy.go` + `stickyBackendIfAvailableR493` | `TestR493_StickyBackendNotPinnedWhenSaturated`, `TestR493_StickyReleaseWiredInProxy` (по AST `proxy.go`: ровно один вызов хелпера, нет прямого `GetSnapshot`). Мутация «вернуть `GetSnapshot`» → тест падает |
| Загрузка вместо очереди: если ни один loaded-узел не принимает, выбирается свободный узел и модель поднимается там | `backend_selector.go`, этап 3b + `pickLoadableFreeBackendR493` | `TestR493_SelectorSkipsSaturatedLoadedBackend` (занятый мастер ВЫГОДНЕЕ по score, но заявка уходит на свободный) — без этапа 3b тест падает |
| Этап 3b не обходит выключатель автозагрузки | тот же этап, гейт `lbAutoLoadAsync \|\| SyncModelLoad.Enabled` | `TestR493_NoAutoloadNoFreeNodeLoad`. Мутация «снять гейт» → тест падает |
| Этап 3b работает ТОЛЬКО если прогретая копия где-то есть и занята | `modelLoadedSomewhereR493` | `TestR493_NoLoadedCopyNoFreeBackendHijack` + CI-регресс `TestReplication_Scenario_LiveRequestReplicated` |
| Модель не грузится туда, где не влезает | `pickLoadableFreeBackendR493` (VRAM-fit) | `TestR493_LoadableFreeBackendRespectsVram`: 12 ГиБ → узел с 20 ГБ, не с 6 ГБ; 40 ГиБ → «некого выбирать». Мутация «снять фильтр» → тест падает |
| Узел под загрузку не берётся, если на хосте идёт image-генерация (Phase 6) | `pickLoadableFreeBackendR493` | существующий `TestImageLockWaitCap_SoleBlockerCapsWait`. Мутация «снять image-гейт» → тест падает |

**Найденный по ходу регресс (и почему правило выше появилось).** Первая версия этапа
3b срабатывала на любом свободном узле и выбирала его по score. В CI упал
`TestReplication_Scenario_LiveRequestReplicated`: два узла БЕЗ метрик, 10 запросов
round-robin — при равных score (у обоих `computeNoMetricsScore` = 1) всегда
выигрывал первый из map-порядка, и один узел получал все 10 запросов, второй 0, то
есть балансер снова «не распределял нагрузку». Проверено сравнением: на коммите до
R493 тест проходил 10/10, с первой версией 3b падал. Поэтому теперь этап 3b
включается только при наличии прогретой копии (`modelLoadedSomewhereR493`): если
модель не загружена нигде, решает обычный алгоритм, а не «загрузка вместо очереди».

Отдельно, чего в реализации **сознательно нет**:

- **P4 (`selectByResources`) не менялся.** Первая попытка «сначала среди свободных»
  ломала resource-aware выбор: при двух узлах со свободными слотами произвольный
  (map-порядок) побеждал более подходящий, и `TestBalancerResourceAware` падал
  («выбран ollama-1 вместо ollama-2»). Правильное место для «свободный вместо
  очереди» — этап 3b, где узел всё равно выбирается под загрузку; там порядок
  задаёт VRAM-fit, а выбор — обычный score.
- **`hasFreeSlotNowR493` в P1 не нужен.** Порог `loadRatio < 0.8` от эффективной
  вместимости строго сильнее предиката «есть слот» (при `threshold ≤ 1`), поэтому
  дублирующая проверка была бы заклёпкой без собственного наблюдаемого эффекта.
  Предикат остался там, где он решает: привязка сессии и выбор узла под загрузку.

### Открытые пункты

1. **Причины отказа по каждому кандидату** (`no_slot`, `vram_insufficient: need 21
   GiB, free 5 GiB`, `file_absent`, `window_smaller`) — `backendRejectionsR460`
   уже собирает часть причин, но VRAM-причины в нём нет.
2. **Каталог моделей узла.** Пункт 3.3-б: если каталог узла не показывает файл,
   узел молча выпадает из P3. Требуется проверка на стенде (`/api/tags` каждого
   узла) и, при подтверждении, отдельная правка — сейчас `pickLoadableFreeBackendR493`
   честно деградирует только для узлов БЕЗ метрик, а «каталог есть, файла в нём
   нет» выглядит как «модель не загружена» и лечится загрузкой.
3. **Живая проверка на стенде** не выполнена: нужен прогон «мастер занят, рядом
   свободный A10» с новым образом и подтверждение в логах выбора
   (`R493: свободный узел выбран под загрузку модели` / `R493: привязка сессии не
   действует`).

## 9. R659 (2026-11-20): почему «загрузка вместо очереди» не работала на живом стенде

Раздел §3.2 был прав, и это подтвердилось новым архивом: путь «стою в очереди →
вижу свободную машину → поднимаю там модель» в коде отсутствовал. Этап 3b выбирал
узел, но работал **только на этапе выбора бэкенда**, то есть до очереди; а заявка,
привязанная к занятой копии, попадала в очередь другим путём (`proxy.go` →
`waitForInferenceBackendWithMoveR480`), где гейт R459 отклоняет холодного
кандидата. Итог на стенде: **304 выбора свободного A10-126 за прогон** (каждые
250 мс, по одному на шаг ожидания), **ноль** `POST /api/models/load` на этом узле,
заявка отменена клиентом через 300 с.

Что изменилось (R659, `cold_load_placement_r659.go`):

| Что | Где | Чем доказано |
|---|---|---|
| Заявка, у которой слот не взят ни на одной прогретой копии, **запускает загрузку** на свободном узле | `proxy.go` (ServeHTTP, после R301 и до очереди) + `unified_queue_gate.go` (до постановки в очередь и в цикле ожидания) | `TestR659_QueueAttemptsLoadWhileWaiting`, `TestR659_ServeHTTPStartsColdLoadBeforeQueue` (AST: вызов стоит ДО очереди) |
| Заявка **не переезжает**: ждёт в очереди и обслуживается тем, что станет готово раньше (своя копия или новая) | там же | `TestR659_RequestServedFromNewCopyAfterLoad`: после загрузки очередь отдаёт заявку НОВОМУ узлу, а не держит её до таймаута |
| Узел выбирается по «влезает ли **нужное окно**»: веса + KV(окно, тип KV) + резерв против свободной VRAM (та же арифметика R230/R498; KV — формула memfit) | `coldLoadWindowFitR659` | `TestR659_PlanChoosesFreeNodeByWindowFit` (KV 512 МБ на окно 131072), `TestR659_WindowDoesNotFitNoLoad` (окно 1048576 не влезает → загрузку не начинаем) |
| Модель не грузится на карту, где не помещается: 27B не уходит на 8-гигабайтный узел | `canLoadModelNowR493` (общий предикат с этапом 3b) | `TestR659_NarrowCardRejectedForBigModel` |
| Окно уезжает как `contextPerSeq` (окно НА КЛИЕНТА, R83), а не только как `contextSize` (суммарное) | `warmupOptions.ContextPerSeq` → `warmupLlamaCppModel` | `TestR659_StartLoadSendsPerSeqWindow`, `TestR659_ColdLoadKeepsWindowRule` |
| Одна загрузка на узел, а не по одной на каждую ждущую заявку | `coldLoadStateR659` (TTL 120 с) | `TestR659_DedupSingleLoadPerNode` |
| Выключатель автозагрузки не обходится | `coldLoadAutoLoadAllowedR659` | `TestR659_AutoloadDisabledNoLoad` |
| В `why_queued` — настоящая причина: `model_loading` (загрузка идёт), `window_does_not_fit` (с числами), `window_fit_unknown` | `backend_rejections.go` | `TestR659_WhyQueuedNamesLoadStarted`, `TestR659_WhyQueuedNamesWindowDoesNotFit` |

**Границы правила (сознательно).**

- **Живая сессия не переезжает.** Загрузка инициируется, но бэкенд заявки не
  меняется: R139 в силе (уход на холодный узел посреди сессии стоил живого
  агентского хода — pi-ai idle timeout 300 с). Заявка обслужится новой копией
  только когда та реально готова и проходит гейт окна.
- **Сжатия окна нет.** Окно новой копии — `max(окно текущей копии сессии,
  потребность запроса, названное клиентом окно)`; меньше любого из них загрузка не
  начинается (R294/R459).
- **Не «холодный старт».** Если прогретой копии в кластере нет вообще, решает
  обычный выбор (этап 3b/3c): иначе повторился бы регресс R493, где «выбери
  свободный узел» забрал заявки у нормального распределения.
- **Неизвестное не выдумывается.** Нет геометрии модели или метрик VRAM — решение
  принимается с `verified=false` (как этап 3b с «VRAM неизвестна»), и это видно в
  логе. Узел, у которого метрика окна устарела, кандидатом **не** считается:
  перезагрузка узла, где модель уже поднята с широким окном, была бы тем самым
  сжатием под живым клиентом.

### 9.1. R660: почему проверка окна сначала была «неверифицированной»

Живая проверка R659 (локальный стенд: балансер из R659 + настоящий воркер r658 +
свободный узел-заглушка) показала: у загруженной модели в `/api/models` были
`n_layers` и `n_embd`, но **не было** `n_kv_heads`/`head_dim_k`/`head_dim_v` — при
том что `max_vram_n_ctx` воркер считает именно по ним. Балансер получал пустую
геометрию и уходил в `verified=false`, то есть грузил на свободный узел БЕЗ
проверки «влезет ли окно».

R660 закрывает это публикацией трёх полей (`cmd/cppworker/handlers_model_list.go`):
имена — ровно те, что разбирает балансерный поллер
(`llamacpp_metrics_poller.go`), поэтому геометрия доезжает до `coldLoadGeometryR659`
без нового контракта. Проверено `TestR660_ListModelsExposesKVGeometry` (значения, а
не только ключи). Практическое следствие: **ближайший выпуск должен включать
cppworker**, иначе проверка окна на стенде останется неверифицированной.

### 9.2. R664 (2026-11-20): рост окна — после хода клиента, отказ без заявки — с числами

Обе половины правки — про одно: рост окна запускался не по заявке клиента, а по
НАШЕЙ оценке промпта, и запускался в неподходящий момент. Шаг A меняет момент,
шаг B — основание.

**Что было (шаг A).** Запрос: 15 токенов промпта, `options.num_ctx=16384` при
загруженных 8192 на слот, `stream=true`. Ответ 200, но первый байт — через
**46.9 с** (`load_duration=46.925 s`): модель выгрузилась и загрузилась ПОД ЭТИМ
ЖЕ запросом, клиент платил за перезагрузку своим первым байтом. Лог при этом
утверждал обратное: «проактивная заявка клиента — поднимаем окно в фоне, запрос
обслуживается сейчас».

**Почему так выходило.** Решение «расти в фоне» принимал preflight
(`growth_stream_guard.go` → `triggerBackgroundGrowthR664`) и проверял только
`active_streams`/`reload_pending`. Текущий ход стримом ещё не учтён:
`beginClientStreamR271` стоит в транспорте, после admission и после ответа
апстрима. Счётчик был 0, блокировок не виделось — unload+load шёл немедленно.

**Шаг A — что стало.** Preflight заявку только ставит в очередь
(`deferGrowthAfterTurnR664`); ход клиента учитывается ДО preflight
(`beginClientTurnR664`), а очередь разбирается на ЗАВЕРШЕНИИ хода
(`drainDeferredGrowthR664`) — когда на бэкенде не идёт ни одного хода:

| Где | Что делает |
|---|---|
| `growth_deferral.go:101` | `deferGrowthAfterTurnR664` — заявка в очередь; ничего не перезагружает и не ждёт. Цель — РОВНО заявленное клиентом окно, не оценка промпта |
| `growth_deferral.go:143` | `beginClientTurnR664` — учёт хода начинается ДО preflight (покрывает промежуток, в котором стрим ещё не зарегистрирован); возвращает функцию завершения, идемпотентна |
| `growth_deferral.go:240` | `drainDeferredGrowthR664` — разбор очереди в фоне на завершении хода: ходов нет, активных стримов и перезагрузок нет (R271/R288), цель всё ещё больше загруженного окна; одна заявка за разбор |

Почему без таймера и фонового цикла: рост нужен МЕЖДУ ходами (следующий ход уже
должен получить новое окно), а «когда-нибудь по таймеру» — то же обещание без
срока. Точка «ход закончился» — единственный момент, про который известно, что
модель свободна.

**Шаг B — что стало.** Основание роста одно — заявка клиента
(`options.num_ctx` в теле, R83/R68). Данные не влезают, а заявки нет — ответ
окончательный и с числами: HTTP 413, `error=context_window_exhausted_no_growth_request`.
Модель при этом НЕ перезагружается. Тело (`preflight_nctx_reject.go:267`):
`prompt_tokens`, `loaded_window_tokens`, `required_window_tokens`
(промпт + нижняя граница ответа + slack, выровнено по 256), `requested_n_ctx`
(0 — не заявил), `available_context_tokens` (потолок на клиента),
`physical_ceiling_tokens`, `gguf_max_context`, `auto_reload_max_n_ctx`, `slots`,
`context_per_seq`, `what_to_do`. `Retry-After` не ставится: окно само не вырастет,
и «повторите позже» клиент прочитал бы как «завтра получится».

Пример из тестов (числа — как в живом случае): промпт 13023 при загруженных
8192 → 413; та же 13023 с заявкой 16384 → рост до 16384 и обслуживание; заявка
400000 при потолке 262144 → прежний отказ по потолку (`makeWindowTooBigReject`),
а не код шага B. Код отказа один на оба пути — preflight-движок (`:155`, `:306`)
и стриминговый вердикт R301 (`window_decision.go:248`); паритет тел проверяется
`context_window_reject_parity_test.go`.

**Какие правила соблюдены.**

| Правило | Как соблюдено здесь |
|---|---|
| **R294** — окно не уменьшаем, чужой ход не рвём | цель отложенной заявки не понижается более поздней (`growth_deferral.go:116`, `:307`); при 413 модель не перезагружается |
| **R447** — «нужен рост» ≠ «можно отказать» | отказ только если загруженное окно реально не обслуживает запрос (`windowServeAsIsR447`); числа отказа — из того же снимка решения |
| **R448/R330** — одна формула чисел на все пути | `neededWindowTokensR330` = оценка промпта + бюджет вывода, но не меньше заявленного клиентом; `required_window_tokens` считается ею же |
| **R301** — вердикт «расти/обслужить/отказать» до сети, один на стриминг и нестриминг | отложенная заявка ставится из того же вердикта (`growth_stream_guard.go:191`, `:380`), отказ 413 — из него же; второго «мозга» не заведено |
| **R385** — выключатель роста на стриме | `LB_NCTX_GROW_FOR_STREAM` действует и на отложенное исполнение: `streaming` едет в заявке, проверка — `background_growth.go:51` |

**Границы (сознательно).** Немедленный рост остаётся немедленным там, где данные
не влезают И клиент заявил покрывающее окно (`growthRequiredR664`): запрос всё
равно не обслуживается, ждать ему нечего. Заявка, которую нельзя исполнить
(чужой ход, перезагрузка), не теряется — остаётся в очереди и повторяется на
следующем завершении хода. Очередь живёт в памяти процесса: перезапуск
балансера её теряет, но к этому моменту ход клиента уже завершён.

**Чем доказано.** `window_growth_policy_r664_test.go` (шаг A: заявка не
исполняется под ходом и исполняется после), `window_refuse_no_growth_request_r664_test.go`
(шаг B: 413 с числами и без перезагрузки; заявка растёт и обслуживается; заявка
выше потолка — прежний отказ), `growth_deferral_test.go`,
`growth_deferral_queue_test.go` (заявка не теряется и не уменьшается),
`context_window_reject_parity_test.go` (тела отказа двух путей совпадают).
