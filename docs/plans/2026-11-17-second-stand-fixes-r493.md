# Второй стенд: четыре исправления по числам и занятости (R493, 2026-11-17)

Продолжение разбора архива второго стенда (`2026-11-16T14:53:34Z`). Правило
отказа по окну было закрыто отдельно (`2026-11-17-window-growth-unification.md`).
Здесь — четыре оставшихся пункта: два про «числа врут» и два про «перезагрузка
поверх живого хода» и «молчаливое противоречие профиля».

Каждый пункт: что было → почему это неверно → что сделано → чем проверено →
чем доказана правка (мутация).

## 1. Точный подсчёт токенов не зависел от калибровки — а фактически зависел

**Что было.** В `applyPromptCalibration` (`internal/balancer/prompt_calibration_r302.go`)
стоял ранний выход:

```go
if raw <= 0 || p == nil || p.promptCalib == nil {
    return
}
```

а вызов `p.applyExactPromptTokensR473(meta)` жил ПОСЛЕ него.

**Почему неверно.** Калибровка (коэффициент на эвристике) и точный подсчёт
(вопрос к токенизатору модели) — разные вещи, и вторая от первой не зависит.
При отсутствии хранилища калибровки — юнит-тесты, лёгкая сборка, прокси без
state-файла — ни один запрос не получал точное число, и решения об окне
считались по оценке, которая на живых замерах завышает в **1.92–2.01** раза.
Это ровно та причина, из-за которой в архиве клиент получил 503 с
`needed=184296` при фактических **93962** токенах.

**Сделано.** Калибровка применяется, только если хранилище есть; точный подсчёт
вызывается всегда. Плюс в `RequestMeta.PromptTokensSource` уже виден источник
(`estimate` / `tokenizer`), так что решение можно проверить по логу.

**Проверено.** `internal/balancer/exact_tokens_without_calibration_r493_test.go`:
два теста — прокси БЕЗ `promptCalib` (живой дефект) и с ним (прежнее поведение).
Оба против httptest-воркера, который реально отвечает на `/api/tokenize`.

**Мутация.** Возврат раннего выхода по `p.promptCalib == nil` → первый тест
красный (`источник токенов = "estimate", ожидался tokenizer`). Откат — зелёный.

## 2. `bridge_info` отдавал нули как факт

**Что было.** `writeCppWorkerErrorWithBridgeInfo` (`cmd/cppworker/utils.go`)
берёт числа у ПОСЛЕДНЕЙ ошибки C-моста:

```json
"bridge_info": {"current_n_ctx": 0, "required_n_ctx": 0, "max_vram_n_ctx": 443530}
```

**Почему неверно.** Функция вызывается и для ошибок, родившихся ВНЕ моста
(`llama_decode` вернул ненулевой код, таймаут, проверка на стороне Go). Тогда
числа — нули и остатки прошлой ошибки, но в JSON они лежат рядом с настоящим
`code` и читаются как измерение: «окно 0», «нужно 0». В том же архиве узел
показывал `maxVramNCtx=156444` (bundled) и `41472` (A10) — то есть в ответе
клиенту было число, не имеющее отношения к делу.

**Сделано.** У блока появились `known` (false = числа не измерены) и `note` с
объяснением, откуда взялась ошибка и куда смотреть. Числовые ключи оставлены —
их читает разбор на стороне балансера (`internal/balancer/llamacpp_error.go`),
ломать контракт незачем. При `known=false` в лог идёт Warn.

**Проверено.** `cmd/cppworker/error_bridge_info_r493_test.go`: `known=false`,
`note` не пуст, `current_n_ctx`/`required_n_ctx`/`max_vram_n_ctx` на месте,
`code` и `error` на месте.

**Мутация.** Переименование поля `known` → тест красный. Откат — зелёный.

## 3. Перезагрузка могла начаться поверх живого хода

**Что было.** Проверки занятости есть в решателях — `growthDeferR299`,
`contextGrowthBlocker`, `decideWindowR493` — и они стоят ДО решения. Между
решением и фактическим `unload+load` проходит время.

**Почему неверно.** Живой факт архива: reload в **06:24:53** (`n_ctx=194296`) и
**06:25:43** (следующий), а в **06:25:02** узел уже грузился с
`partial offload 62/64`; ходы Cline при этом шли. Перезагрузка выгружает модель,
то есть рвёт чужой ответ — ровно то, от чего защищают проверки в решателях, но
они успевают «состариться» за время решения.

**Сделано.** У координатора появился хук `SetBeforeReloadGuard`
(`internal/balancer/nctx_reload.go`); Proxy ставит его в конструкторе и
запрещает старт, если `ActiveStreamsOnBackend(backendID) > 0`. Проверка
вызывается в `RunPreflight` ПОСЛЕ гейтов «рост бесполезен» (`growthWorthReload`)
и «окно не уменьшаем» (R294) — чтобы не откладывать то, что всё равно не стало
бы делать. Отказ — это `PreflightNoOp` с Warn-строкой: клиент получает отказ
«занято, повторите», а не оборванный чужой ответ.

**Проверено.** `internal/balancer/reload_busy_guard_r493_test.go`:
(1) отказ хука → `PreflightNoOp` и **ноль** reload-запросов к мок-воркеру;
(2) разрешение → `PreflightAsyncReload` и запрос приходит (положительный
контроль — без него тест доказывал бы только «мы что-то запретили»).
Отдельно поймана ловушка теста: с `nil`-loader отрицательный тест проходил по
неверной причине (перезагрузке просто нечем было случиться), поэтому оба теста
идут с настоящим `DefaultNCtxReloadHTTPClient`.

**Мутация.** Отключение условия (`!allow && false`) → отрицательный тест
красный (`решение = async_reload, ожидался NoOp`). Откат — зелёный.

## 4. Противоречие профиля сохранялось молча

**Что было.** Профиль с `contextLength=194296` при `contextLengthMax=131072`
(архив 2026-11-16) сохранялся без единого слова. R400 в балансере осознанно
отдаёт приоритет заявленному окну и пишет WARN — но только в лог ЗАГРУЗКИ.

**Почему неверно.** Оператор видит «сохранено, ок 194296», а узлы поднимаются с
РАЗНЫМИ окнами для одной модели (**194304** и **131072**): запрос, помещавшийся
на одном, на другом получает отказ или перезагрузку. Это не ошибка R400 — это
невысказанное противоречие в данных.

**Сделано.** `PUT /api/v1/cppworker/model-profiles/{name}` теперь отвечает
`warnings[].code = context_length_exceeds_max` с обоими числами и советом
выровнять; в лог — Warn с impact. Сам профиль сохраняется: право оператора не
отменяется, меняется только молчание. Правило вынесено в
`contextWindowConflictMessage(contextLength, contextLengthMax)` — одна функция,
ноль в любом поле означает «не задан».

**Проверено.** `internal/api/profile_window_conflict_r493_test.go`: таблица
случаев (равные — тишина, меньше — тишина, живой 194296/131072 — предупреждение,
нули — тишина) + страж «ветка рабочая».

**Мутация.** Условие «сделать мёртвым» (`false && conflict != ""`) → страж
красный. Первая версия стража искала просто имя функции и мутацию НЕ ловила —
исправлено на проверку рабочей формы вызова (`if conflict := ...; conflict != ""`).

**Остаток.** Расхождение окон между узлами с разными потолками GGUF — физическое
следствие их конфигурации. Закрывается выравниванием значений в профиле (о нём
теперь сказано в ответе API), а не кодом балансера.

## 6. Что НЕ проверено

- Живой стенд для этих четырёх правок: поведение с активным стримом проверено
  юнит-тестом с хуком, а не живым Cline-ходом (нужен второй стенд с моделью).
- Реальный `llama_decode` с ошибкой вне моста: `known=false` проверен на
  stub-мосте (он всегда «OK»), то есть проверена ветка «мост чисел не дал».
- Расхождение окон между узлами после предупреждения: правка меняет сообщение
  API, а не физику загрузки.
- Остаток 12r(а)/12s: решение о РОСТЕ по-прежнему по оценке, когда токенизатор
  недоступен после повтора; закрывается продукт-вопросом «укороченный ответ или
  ожидание роста».
