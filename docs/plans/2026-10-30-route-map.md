# Карта маршрутов сообщений: вход → преобразование → воркер → обратно → клиент

**Дата:** 2026-10-30
**Тип документа:** аудит только по чтению кода (ничего не менялось)
**Предмет:** балансировщик `ollama-loadbalancer` (процесс `dsh`/`balancer`), воркер `cppworker`, Ollama-бэкенды.
**Правило документа:** каждое утверждение сопровождается ссылкой `файл:строка`. Где вывод сделан по чтению кода, но не проверен живым прогоном — так и написано. Где код не найден — «не найдено».

## 3. Админский API (18081) и WebUI (18083)

### 3.1 Что такое WebUI 18083

WebUI — **не Go-сервер**: это nginx-контейнер со статикой `webui/` и обратным прокси.
Слушает внутренний 80 (`webui/nginx.conf:2` — `listen ${NGINX_PORT};`), публикуется как 18083 (`deployments/docker-compose.bundled-full.yml:285`).
Upstream'ы берутся из окружения: `LB_API_URL=http://loadbalancer:18081` (`deployments/docker-compose.bundled-full.yml:287`).
Разделение проксирования в `webui/nginx.conf`:

| location | Куда | Строка |
|---|---|---|
| `/api/` (catch-all) | **18081** (админ-API) | `webui/nginx.conf:187-189` |
| `/api/v1/events` | 18081, SSE без буферизации | `webui/nginx.conf:69-74` |
| `/api/v1/image/` | 18081 | `webui/nginx.conf:112-114` |
| `/api/v1/gguf/` | 18081 (прогресс загрузки) | `webui/nginx.conf:135-137` |
| `/api/image/`, `/api/chat`-подобные | **18080** (клиентская поверхность) | `webui/nginx.conf:151-153`, `webui/nginx.conf:166-167` |
| `/api/worker/` | напрямую в cppworker, минуя балансер | `webui/nginx.conf:41-44` |

**Вывод:** у WebUI нет собственных инференс-ручек. Все его действия — это запросы в 18081 (управление) или в 18080 (как у обычного клиента).

### 8.2 Где терминальный кадр может **не дойти**

1. Клиент ушёл: ветка `client_cancel` пишет кадр в мёртвое соединение и возвращает `nil` — `llamacpp_transport.go:934-944` (кадр нужен логу/тесту, комментарий `:2300-2302`).
2. `isHeadersSent` (`llamacpp_handlers_inference.go:1164-1169`) определяет «заголовки уже ушли» по `Content-Type` — если транспорт не выставил `Content-Type`, ветка `writeStreamErrorChunk` не выполнится, и клиент получит обрыв без терминатора (`:991-997`, `:1153-1159`).
3. Ошибка записи в `emitDeferredDone` логируется, но клиенту уже ничего не отправить — `llamacpp_transport.go:1912-1919`.
4. `writeStreamingSSEDone` при `usageChunkSeen` **не пишет** терминатор (`llamacpp_transport_helpers.go:185-188`), полагаясь на то, что `translateUsageChunkToOllama` уже его отдал. Если usage-чанк был подавлен по `priorStatsEmitted` (`llamacpp_translate_resp.go:653-655`) — терминатора не будет вовсе. Не проверено живым прогоном, следует из чтения двух условий.
5. `EmitContinuationNDJSON` возвращает ошибку при `apiPath` не `/api/chat` и не `/api/generate` (`auto_continue.go:1134-1136`) — на других путях терминатор оттуда не придёт.

### 8.3 Где терминальный кадр **дублируется**

1. Историческая защита встроена в `translateOpenAISSEDataToOllamaWithFlags`: `priorDoneEmitted` и `priorStatsEmitted` — `llamacpp_translate_resp.go:597-660`.
2. `writeStreamingSSEDone` / `emitDeferredDone` / `emitTerminalDoneOnly` — все три идемпотентны по `doneEmitted`/`usageChunkSeen` (`llamacpp_transport.go:1904-1941`).
3. **Потенциальный дубль (не проверено на стенде):** на нативном пути при обрыве до первой строки срабатывают и `abortFramesR296` (`llamacpp_transport.go:2246` → терминатор `done:true done_reason:"error"`), и `buildDoneResponse` (`:2263` → `done:true done_reason:"stop"`), потому что `lastData` заполняется только на строках (`:1226`, `:1249`) и остаётся пустым. Клиент на NDJSON-пути получит два `done:true` с разными причинами.

## 10. Места, где решение принимается дважды или противоречиво

### 1. Две разные формулы ёмкости слотов, и разная семантика нуля

* `backendHasFreeSlot` — `backend_selector.go:186-187`: `EffectiveMaxConcurrentRequests()`, `0` = «слот есть всегда».
* `tryAcquireSlot` — `slot_manager.go:35`: `EffectiveMaxConcurrentRequests()`, `maxReqs > 0 && active >= maxReqs` — `0` = без ограничения.
* `selectBackend` P1 — `backend_selector.go:246` и `selectByResourcesExcluding` — `backend_selector.go:516`: **`state.Backend.MaxConcurrentReqs`** (статическое поле!), причём на `:516` без проверки `> 0` → `0` трактуется как «всегда занято».
* `selectFreeBackendAny` — `backend_selector.go:983`: `maxReqs >= 0 && active >= maxReqs` — `0` = занято.

Итог: четыре места, три формулы, два противоположных смысла нуля.

### 2. Один и тот же preflight вызывается дважды в одном запросе

`llamacpp_handlers_inference.go:155-164` и повторно `:235-244` — те же аргументы (`body`, `model`, `backendID`, `backendURL`). Комментарий на `:228-234` объясняет, зачем второй раз, но первый при этом не убран.

### 3. `n_ctx` резолвится дважды и независимо

`handleOpenAIChatCompletions`: `ResolveNumCtx` (`:169`) → загрузка модели → **ещё раз** `ApplyCppCtxHeader` (`:246`), который резолвит то же значение заново. То же в `handleChat`: `:898` и `:933`; в `handleGenerate`: `:1083` и `:1114`.

### 4. Потенциально два терминальных кадра на одном обрыве

`abortFramesR296` (`llamacpp_transport.go:2246`) + `buildDoneResponse` (`:2263`) при `lastData == ""` — см. §8.3 п. 3.

### 5. Трансляция Ollama→OpenAI формально есть, но по умолчанию недостижима

`translatePathForLlamaCpp` (`llamacpp_translate_req.go:13-18`) и `translateOllamaBodyToOpenAI` (`:26-40`) вызываются только при `!nativePath` (`llamacpp_transport.go:79-89`), а `shouldRouteOllamaNative` по умолчанию `true` для ровно этих путей (`llamacpp_native_path.go:76-89`). Два mutually exclusive решения об одном и том же, при этом «мёртвая» ветка продолжает поддерживаться и тестироваться (`llamacpp_translate_req_test.go`).

### 6. Четыре разных имени поля для размышлений на одном и том же ответе

| Путь | Поле | Строка |
|---|---|---|
| воркер, `/api/chat` (оба имени одновременно) | `message.thinking` + `message.reasoning` | `cmd/cppworker/handlers_chat.go:1261-1262` |
| воркер, `/v1` | `delta.reasoning_content` / `message.reasoning_content` | `cmd/cppworker/handlers_openai.go:949, 826` |
| балансер, SSE→NDJSON `/api/chat` | `message.thinking` | `llamacpp_translate_resp.go:1049` |
| балансер, SSE→NDJSON `/api/generate` | `thinking` (верхний уровень) | `llamacpp_translate_resp.go:1293` |
| балансер, не-стрим `/api/chat` | `message.reasoning` | `llamacpp_transport_nonstream.go:813` |
| балансер, не-стрим `/api/generate` | `thinking` (верхний уровень) | `llamacpp_transport_nonstream.go:803` |
| балансер, `/v1`-выход | `delta.reasoning_content` | `reasoning_egress_r256.go:414-417` |

Один и тот же текст в зависимости от пути приходит клиенту под тремя разными именами; клиент, читающий `thinking`, не увидит не-стрим `/api/chat`.

### 7. `done_reason` «stop» по умолчанию против «length» по факту

* `writeStreamingSSEDone` умеет только `stop` и `tool_calls` — `llamacpp_transport_helpers.go:251-255`, `:282-287`. Если usage-чанк не пришёл и апстрим сказал `finish_reason:"length"`, клиент получит `done_reason:"stop"`.
* При этом R321 (`native_done_hygiene_r321.go:119`) и воркер R320 (`handlers_chat.go:1487-1491`) специально ставят `length`. То есть в одном потоке два слоя придерживаются противоположных правил: один — «причина от воркера факт», другой — «всегда stop».

### 8. Статистика может потеряться на стыке двух флагов

`writeStreamingSSEDone` не пишет статистику вообще (комментарий `llamacpp_transport.go:1712-1715`), а usage-чанк подавляется при `priorStatsEmitted` (`llamacpp_translate_resp.go:653-655`). Если stats-строка была отдана как `done:false`, а затем `writeStreamingSSEDone` пишет `done:true` без статов — клиент видит `done` без `eval_count`. Это же поведение зафиксировано как «сознательное» в комментарии `:1712`, но живой Ollama в `done`-чанке статистику всегда даёт.

### 9. Два места, где ставится `finish_reason:"error"` — и это не значение по спецификации OpenAI

`llamacpp_handlers_inference.go:1200` и `stream_abort_frames_r296.go:49`. Спецификация OpenAI допускает `stop|length|tool_calls|content_filter`; клиент, валидирующий enum, на `error` может упасть. Альтернативная ветка того же обрыва ставит `truncated` (`llamacpp_transport.go:2338`), третья — `length` (`stream_abort_frames_r296.go:50-52`).

### 10. Дублирование логики stickiness/ребаланса

`session_handler.go:12-98` (`resolveSessionBackend`/`rebalanceIfNeeded`) и `proxy.go:1162-1272` — две реализации одной логики; в проде работает inline-код в `proxy.go`, вторая живёт только в тестах.

### 11. Два ответа на «все слоты заняты»

`writeAdmissionUnavailable` — JSON (`admission_queue.go:834-843`) для llama.cpp-хендлеров; основной flow отвечает plain-text `http.Error` (`proxy.go:1446, 1486, 1492, 1549, 1654`). Один и тот же отказ клиент видит в двух форматах в зависимости от того, какой путь его обслуживал.

### 12. `modelAnswerable` есть на `/v1/chat/completions` и `/api/generate`, но нет на `/api/chat`

`modelAnswerable` вызывается в обработчиках `/v1/chat/completions` (`llamacpp_handlers_inference.go:122`), `/v1/completions` (`:465`), `/v1/embeddings` (`:701`) и `/api/generate` (`:1041`) — и возвращает терминальный 404 на неизвестную модель (`model_known_r193.go:143`). В `handleChat` (`:792-999`) такой проверки нет: неизвестное имя уходит в `selectLlamaCppBackendForModelWithNCtx` (`:862`), и защита остаётся только в preflight-ветке транспорта (`llamacpp_transport.go:156-163`). Это расхождение контракта между двумя Ollama-путями.

### 13. Предел тела запроса применяется не везде

`readRequestBodyLimited` (64 MB, `llamacpp_native_path.go:162-206`) — только в handler-путях (`llamacpp_handlers_inference.go:32, 801, 1011`). Основной flow читает без лимита — `proxy_request.go:194`. То есть `/api/embeddings`, `/api/embed`, management-пути и всё, что перехватил основной flow, не ограничены.

### 14. `isHeadersSent` — не про заголовки

`llamacpp_handlers_inference.go:1164-1169` считает «заголовки отправлены», если у `ResponseWriter` выставлен `Content-Type`. Ветка выбора «терминатор в стрим vs 503» (`:317-323`, `:991-997`, `:1153-1159`) зависит от этого признака, а не от фактического факта отправки статуса.

### 15. Два разных `retry_after` на один класс отказа

Преflight-отложение отдаёт `Retry-After: 30` (`llamacpp_transport.go:189`), admission — `admissionRetryAfterSec = 15` (`admission_queue.go:67, 828`), автозагрузка — `writeAutoLoadRetryAfter` (`llamacpp_handlers_inference.go:211`). Три числа для «подожди и повтори».

### 16. «Модель загружена» определяется четырьмя разными способами

| Определение | Семантика | Строка |
|---|---|---|
| `backendHasModel` | подстрочное `strings.Contains(m.Name, modelName)` | `backend_selector.go:753-767` |
| `backendHasModelStrict` | точное равенство | `backend_selector.go:770-782` |
| `backendHasModelByID` | три источника (`Contains` + `metrics.Models` + `llamaMetrics`) | `replication_reality_r80.go:62-84` |
| `ModelStateUsable` | только состояние `loaded` | `cluster_state.go:210-235` |
| «файл на диске» | каталог моделей, не память | `model_catalog.go:576-579` |

Следствие: один и тот же узел одновременно считается «держащим модель» для P1-приоритета и «не держащим» для prewarm/репликации, если имя пришло с суффиксом или в другой форме.

### 17. `n_ctx` живёт в двух измерениях, и в тексте отказа они смешиваются

* Суммарное окно: `loadedWindowFromCache` берёт максимум `ContextLength` — `num_ctx_resolver.go:574-577`; значение `loadedNCtx` — `nctx_reload_handlers.go:1055`.
* Окно на слот: `loadedPerSeqNCtx` = `ContextPerSeq`, иначе `ContextLength/MaxSlots` — `num_ctx_resolver.go:394-430`; дубль формулы — `preflight_nctx.go:511-519`.
* Сравнение с клиентским `num_ctx` идёт **по слоту** — `nctx_reload_handlers.go:1101-1119`.
* Цель reload пересчитывается обратно в **суммарное**: `reloadTarget = PadContext(perSeqTarget) * slots` — `preflight_nctx.go:495-507`.
* **В отказе суммарное печатается как «per slot»**: `"(loaded=%d per slot)"` с подстановкой `loadedNCtx` — `nctx_reload_handlers.go:1454, 1462`.
* Кэш после reload получает суммарное значение — `nctx_reload_handlers.go:1396, 1484`.

### 18. `loadRatio` считается по локальному счётчику, а `score` — по числам агента

Порог попадания в P1/P3: `ActiveReqs / Backend.MaxConcurrentReqs` (`candidate.go:102-105`, `backend_selector.go:249-252`).
Штраф в `score`, которым выбирается «лучший» узел: `Ollama.ActiveRequests / Ollama.MaxConcurrentRequests * 15` (`scoring.go:32-33`).
То есть отбор кандидатов и ранжирование внутри отобранных используют **разные источники данных о нагрузке**.

### 19. Предел ожидания слота сообщается клиенту задним числом

`writeAdmissionUnavailable` при `waited < maxWait` подменяет `maxWait = waited` (`admission_queue.go:822-827`), то есть «лимит» в ответе становится фактическим временем ожидания. При этом `GetQueueStats` всегда отдаёт **бюджет** как `wait_max_sec` (`cluster_state.go:412`). Оператор и клиент видят разные пределы для одного и того же механизма.

### 20. Порт воркера по умолчанию — два разных числа

* Конфиг выставляет `CppWorkerPort = 18091`, если он не задан — `internal/config/config.go:546`.
* `handlers_cluster_model_info.go:276` тоже возвращает **18091**.
* А рантайм-хелперы, которые строят URL к воркеру, по умолчанию берут **18092**: `backend_state.go:65` (с комментарием «18091 is legacy»), `health.go:247`, `backend_registry.go:81`, `model_management.go:244`, `gguf_backend_proxy.go:103`, `handlers_cppworker_profiles.go:775`, `handlers_backends.go:1386`.

Следствие: при бэкенде, зарегистрированном без явного `CppWorkerPort`, разные подсистемы балансера пойдут на разные порты одного и того же узла. В compose-раскладке это маскируется тем, что порт приходит от агента, но инвариант «один дефолт» кодом не держится.

1. **`Proxy.ServeHTTP` (`proxy.go:896-1657`) прочитан фрагментарно** — только точки вызова (`:1158`, `:1462`, `:1505`). Внутренние ретраи, auto-pull, обработка `ModelNotFoundError`/`BackendBusyError` (`proxy_request.go:985-998`) не разобраны.

4. **Оценка токенов** (`calibratedEstimateOnly`, `extractRequestMeta`, `contextGrowthBlocker`, R288/R299) — упомянуты, но не разобраны: это отдельный пласт (предсказание prompt-tokens).
