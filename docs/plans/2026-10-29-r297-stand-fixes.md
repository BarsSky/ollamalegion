# R297 (2026-10-29): четыре живых дефекта стенда — что изменено и как проверять

Основание: живой прогон на `940d8b0a` (R296). Оператор подтвердил четыре дефекта;
ниже — что именно изменено, чем это доказано СЕЙЧАС и что ещё нужно проверить на
стенде (п. «Живая проверка»). Ни один пункт не объявлен исправленным «по коду».

## 1. Неудачный reload с невозможным окном выгружал модель

**Живой факт.** reload с `contextSize=200000` → модель выгружена, затем 500;
стенд остался без модели (`loaded_models:0`), восстановление заняло 72 с.

**Причина.** Проверок две, и обе стояли ПОСЛЕ разрушительного шага: сначала
`unload`, потом попытка загрузки. Отказ в перезагрузке необратимо снимал сервис.

**Что сделано.**
- `internal/balancer/window_feasible_r297.go` — `WindowFeasibility(backend, model,
  requested)`: потолок = минимум из ИЗВЕСТНЫХ `GGUF max`, заявленного оператором
  окна (`declaredWindowTotal`) и `ContextLengthMax` профиля. «Неизвестно» не
  запрещает: отказ по догадке дороже. Env-потолок авто-роста
  (`LB_NCTX_RELOAD_MAX_N_CTX`) СОЗНАТЕЛЬНО не участвует — по контракту R267 он
  защищает от авто-роста, а не ограничивает явное действие оператора.
- `internal/balancer/nctx_declared_r255.go` — `declaredWindowTotal` вынесен из
  `effectiveAutoReloadCeiling`: одно мнение о «заявленном окне» на два
  потребителя (иначе — класс дефекта R267).
- `internal/api/handlers_cluster_models.go` — проверка выполнимости ПЕРЕД
  `unload` (400 с числом потолка и явным «the model was left loaded»); снятие
  параметров текущей загрузки до `unload`; при провале новой конфигурации —
  восстановление прежней (`restorePreviousModelOnBackend`) и честный текст в
  ответе.

**Тесты.** `TestR297_WindowFeasibility` (отказ с числом; env-потолок не
запрещает ручную загрузку; неизвестный бэкенд — не отказ).

## 2. Guard `context_growth_pending` не срабатывал

**Живой факт.** Запрос с `num_ctx` больше окна уходил в очередь допуска и висел
60 с; на `/v1` ответ 200 пришёл через 90 с; в теле — `required=4098`,
`active streams=0`, поля в snake_case.

**Причина.** «Нет активных стримов» считалось равным «рост возможен», хотя
перезагрузка уже шла (счётчик стримов обнулился раньше, чем окно выросло).
Число «нужно» считалось только по оценке промпта и игнорировало явно
запрошенное клиентом окно.

**Что сделано.**
- `internal/balancer/context_growth_r288.go` — блокировка также при
  `nctxReload.IsReloadPending(backend, model)`; в лог добавлено
  `reload_pending`.
- `internal/balancer/deferred_ops_r291.go` — `contextGrowthNumbers`:
  `needed = max(оценка промпта + бюджет вывода, requested num_ctx)`; при
  неизвестном загруженном окне числа не выдумываются (нули, прежний контракт).

**Тесты.** `TestR297_ContextGrowthNumbersRequestedFloor`,
`TestR297_BlockerWhenReloadPending`.

## 3. Стрим завис без терминатора

**Живой факт.** последний кадр 15:01:20, соединение открыто, `done:true`/`[DONE]`
не пришёл — клиент ждал бесконечно.

**Причина.** `LB_STREAMING_NEVER_TIMEOUT=1` на стенде гасит ВСЕ idle/first-byte
таймауты стрима; вместе с ними исчез единственный сторож тишины. Мёртвый-но-не-
закрытый воркер ждался вечно.

**Что сделано.**
- `internal/balancer/proxy_request_hijack.go` — сторож зависания на тике
  heartbeat: тишина `LB_STREAM_STALL_ABORT_SEC` (по умолчанию 300 с) посреди
  УЖЕ начатого стрима → кадр-причина + ровно один терминатор + `[DONE]`.
  До первого кадра сторож не работает (молчание в начале — префилл, его
  обрывать нельзя: именно поэтому оператор и выключил общие таймауты).
- `internal/balancer/stream_stall_r297.go` + `internal/settings/builtin_r278.go`
  — порог живёт в реестре настроек (горячий, `0` выключает), не константой.
- `deployments/docker-compose.stack.yml`, `.env.example`, `docs/api/env-vars.*`
  — переменная доведена до контейнера (иначе «настройка не работает»).
- **Побочно найденный дефект того же класса.** Все РАННИЕ выходы hijack-пути
  (сторож, кадр-ошибка воркера R294, ошибка чтения) закрывали соединение БЕЗ
  chunked-терминатора `0\r\n\r\n`: strict-клиенты получали `unexpected EOF`.
  Это нашёл поведенческий тест, а не глаза. Теперь терминатор пишется через
  `defer` один раз на любой исход.

**Тесты.** `TestR297_StallTimeoutSetting` (дефолт/env/override/`0`),
`TestR297_StallWatchdogEmitsTerminator` (живой путь: воркер отдал кадр и
замолчал, не закрывая сокет → клиент получает причину, один терминатор и
`[DONE]` за ~2 с при пороге 2 с), `TestR297_StallWatchdogWaitsForFirstFrame`
(до первого кадра не срабатывает).

## 4. `done_reason="truncated"` при `docker kill` воркера

**Живой факт.** при убийстве воркера клиент получал `done_reason="truncated"` —
«ответ закончился естественно», хотя соединение умерло.

**Что сделано.** `internal/balancer/stream_abort_frames_r296.go` — терминатор
реального обрыва (`upstream_eof`/`upstream_error`/…): `finish_reason=error` для
SSE и `done_reason=error` для NDJSON; `length` остаётся только за нашим лимитом
строки (`our_limit`). Кадр-причина по-прежнему `done:false` и несёт
`error_type`.

Граница проведена явно (`llamacpp_transport.go`): `truncated` остаётся ТОЛЬКО в
`emitTruncatedChunk` — это наш собственный таймаут стрима и уход клиента, а не
обрыв воркера. Поэтому же обновлены ожидания в
`llamacpp_transport_truncated_test.go` (там проверялся старый контракт).

**Тест.** `TestR297_AbortDoneReasonMapping`.

## Инструментальная правка (не дефект продукта)

`llamacpp_handlers_inference_long_gen_test.go`: мок принимал соединения и терял
ссылки (`_ = conn`), Go-финализатор закрывал сокет при сборке мусора, и под
нагрузкой полного прогона тест получал `wsarecv: forcibly closed` вместо
таймаута заголовков. Ссылки теперь удерживаются и закрываются централизованно.

## Живая проверка на стенде (ещё НЕ выполнена)

1. **Невозможное окно.** `POST /api/v1/cluster/models/{model}/reload` с
   `contextSize` больше заявленного/GGUF → ожидается **400** с числом потолка,
   `loaded_models` НЕ падает до 0.
2. **Восстановление.** Тот же reload с физически возможным, но ломающим загрузку
   окном (например, больше VRAM) → модель возвращается в прежней конфигурации,
   в ответе `previous configuration restored`.
3. **Сторож зависания.** `LB_STREAM_STALL_ABORT_SEC=10`, затем `docker pause`
   cppworker посреди потока (сокет остаётся открытым): клиент обязан получить
   кадр `reason=upstream_error`, `finish_reason=error` и `[DONE]` через ~10–20 с,
   в логе — `hijack streaming: upstream stalled`. `docker unpause` после.
4. **Причина обрыва.** `docker kill` cppworker посреди потока → в теле
   `finish_reason=error` / `done_reason=error` (НЕ `truncated`), ровно один
   терминатор.
5. **Рост окна под идущей перезагрузкой.** Запрос с `num_ctx` больше загруженного
   окна при активной перезагрузке → 503 «отложено» сразу, в теле
   `requiredTokens >= requested`, `activeStreams`/`reloadPending` в camelCase.

## Откат

`LB_STREAM_STALL_ABORT_SEC=0` выключает сторожа без пересборки. Полный откат —
вернуть теги балансера и webUI на `940d8b0a` и `docker compose up -d
loadbalancer webui`.
