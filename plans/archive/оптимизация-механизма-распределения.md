# Оптимизация механизма распределения запросов в OllamaLegion

**Дата:** 2026-05-02
**Статус:** План реализации (v1.0)

---

## 1. Проблема

При полной загрузке кластера не происходит перераспределения запросов на свободный бэкенд, на котором модель присутствует в конфигурации, но **не загружена в VRAM**. Балансер продолжает направлять запросы только на уже загруженные бэкенды (Model Affinity), игнорируя свободные ресурсы.

**Симптомы:**
- Один бэкенд перегружен (active = maxConcurrent), запросы попадают в очередь
- Другие бэкенды простаивают, хотя имеют достаточно VRAM для загрузки модели
- Модель присутствует в конфигурации простаивающего бэкенда (`models: [...]`), но не загружена (`loaded_models: []`)

---

## 2. Корневые причины

### 2.1 Уровень кода (proxy.go: selectBackend)

**Баг 1: Некорректный расчёт `maxConcurrent` для GPU-бэкендов**

```go
// proxy.go ~line 630
activeSlots := int(math.Min(1, float64(max(1, backend.MaxConcurrent-active)))) 
```

Фактически `activeSlots` всегда равен **1** (кроме случая 0/0). Это делает `maxConcurrent` неэффективным — балансер считает бэкенд "занятым" уже при 1 активном запросе.

**Баг 2: Model Affinity без проверки загрузки бэкенда**

```go
// proxy.go ~line 600
if cfg.ModelAffinity {
    if be := findBackendWithModel(...); be != nil {
        return be // НЕМЕДЛЕННЫЙ возврат без проверки capacity
    }
}
```

При включённом ModelAffinity балансер немедленно возвращает бэкенд с уже загруженной моделью, не проверяя:
- Загрузку бэкенда (CPU/GPU/VRAM)
- `maxConcurrent`
- Доступность альтернативных бэкендов

**Баг 3: Отсутствие логики "подгрузки модели" на свободный бэкенд**

После того как ModelAffinity находит перегруженный бэкенд, код переходит к Resource-Aware Fallback. Но fallback **не учитывает**, что на свободном бэкенде модель есть в конфигурации, но не загружена — он просто считает score на основе свободных ресурсов.

### 2.2 Уровень архитектуры

| Проблема | Описание |
|----------|----------|
| **Отсутствие "Threshold Load"** | Нет порога, при котором балансер начинает искать альтернативный бэкенд вместо sticky |
| **Отсутствие proactive loading** | Балансер не может инициировать предзагрузку модели на свободный бэкенд |
| **Статический Model Affinity** | Affinity всегда имеет приоритет, без учёта общей загрузки кластера |
| **Отсутствие LRU eviction** | Нет механизма выгрузки неиспользуемых моделей для освобождения VRAM |

## 3. Текущий алгоритм (как есть)

```
1. Session Cache → если есть привязка, проверить healthy → вернуть
2. Model Affinity → найти бэкенд с загруженной моделью → вернуть (без проверок)
3. Resource-Aware Fallback → calculateScore по всем healthy → вернуть лучший
4. Capacity Check → если нет места → очередь
```

**Формула calculateScore (текущая):**
```
Score = (
    gpuFreePercent   * 0.35 +
    vramFreePercent  * 0.25 +
    cpuFreePercent   * 0.20 +
    modelCapacity    * 0.15 +
    predictionBonus  * 0.05
) * weight - requestPenalty
```

---

## 4. Предлагаемый улучшенный алгоритм

```
1. Session Cache → если есть привязка:
   a. Проверить healthy
   b. Проверить loadRatio <= thresholdLoad (новый параметр, default 0.7)
   c. Если оба условия — вернуть cached backend
   d. Иначе — сбросить sticky и перейти к шагу 2

2. Model Affinity → найти бэкенды с загруженной моделью:
   a. Отфильтровать healthy
   b. Отсортировать по loadRatio
   c. Если есть бэкенды с loadRatio < thresholdLoad → вернуть лучший
   d. Если все найденные перегружены → НЕ возвращать, перейти к шагу 3

3. Candidate Expansion (НОВЫЙ ЭТАП):
   a. Найти ВСЕ healthy бэкенды, где модель есть в конфигурации (models: [...])
   b. Разделить на две группы:
      - Group A: модель уже загружена (loaded_models содержит модель)
      - Group B: модель в конфигурации, но НЕ загружена (доступна для подгрузки)
   c. Рассчитать enhanced score для каждой группы

4. Enhanced Scoring (новая формула):
   Score = (
       gpuFreePercent       * 0.25 +  // было 0.35
       vramFreePercent      * 0.25 +  // было 0.25
       cpuFreePercent       * 0.15 +  // было 0.20
       modelAlreadyLoaded   * 0.15 +  // НОВЫЙ: бонус за предзагрузку (было modelCapacity 0.15)
       modelLoadFeasibility * 0.10 +  // НОВЫЙ: возможность подгрузки
       loadBalanceFactor    * 0.10    // НОВЫЙ: фактор балансировки кластера
   ) * weight - requestPenalty

   Где:
   - modelAlreadyLoaded = 1.0 если модель в loaded_models, иначе 0
   - modelLoadFeasibility = 1.0 если (vramFree >= modelSize), иначе 0
   - loadBalanceFactor = 1.0 - (clusterLoadRatio), поощряет менее загруженные бэкенды

5. Capacity Check → если выбранный бэкенд проходит → вернуть
   Если нет → очередь (с новым механизмом dispatch)
```

**Новый механизм dispatch очереди:**
```
При освобождении бэкенда:
1. Проверить pending-запросы, для которых модель УЖЕ загружена → приоритет
2. Проверить pending-запросы, для которых модель доступна в конфигурации → отправить с подгрузкой
3. Если ничего не подходит → ждать следующего освобождения
```

## 6. Новые конфигурационные параметры

| Параметр | Тип | Default | Описание |
|----------|-----|---------|----------|
| `thresholdLoad` | float | 0.7 | Порог загрузки бэкенда (loadRatio), после которого начинается поиск альтернатив |
| `useEnhancedScoring` | bool | true | Использовать улучшенную формулу score |
| `modelLoadTimeout` | int | 120 | Таймаут ожидания загрузки модели (сек) |
| `stickySessionMigration` | bool | true | Разрешить миграцию sticky-сессий при превышении thresholdLoad |
| `weightModelAlreadyLoaded` | float | 0.15 | Вес компонента «модель уже загружена» в score |
| `weightModelLoadFeasibility` | float | 0.10 | Вес компонента «возможность подгрузки» в score |
| `weightLoadBalanceFactor` | float | 0.10 | Вес фактора балансировки кластера в score |

## 7. Сценарии валидации

### Сценарий A: Два бэкенда, одна модель, load > threshold

```
Дано: ollama-1 (llama3.1 загружена, active 6/8), ollama-2 (пустой, llama3.1 в конфиге)
Запрос: llama3.1
Ожидание: запрос уходит на ollama-2 с подгрузкой llama3.1
```

### Сценарий B: Два бэкенда, одна модель, load < threshold

```
Дано: ollama-1 (llama3.1 загружена, active 2/8), ollama-2 (пустой)
Запрос: llama3.1
Ожидание: запрос уходит на ollama-1 (affinity, load < threshold)
```

### Сценарий C: Полная загрузка + очередь

```
Дано: ollama-1 (active 8/8), ollama-2 (active 8/8)
Запрос: llama3.1 → очередь
Освобождение ollama-1 (active 7/8) → запрос из очереди на ollama-1
```

### Сценарий D: Конкуренция за VRAM

```
Дано: ollama-1 (VRAM 20/24), ollama-2 (VRAM 6/24)
Запрос: модель 7 GB
Ожидание: ollama-2 (modelLoadFeasibility = 1, vramFree 18 >= 7)
```

## 8. Оценка рисков

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Подгрузка модели на неподходящий бэкенд | Средняя | Высокое | Валидация modelSize vs vramFree перед dispatch |
| Увеличение latency из-за загрузки модели | Высокая | Среднее | modelLoadTimeout, индикация в мониторе |
| Регресс существующей логики | Низкая | Высокое | Сохранить старый код за флагом `useEnhancedScoring` |
| Несовместимость с агентами без modelSize | Средняя | Среднее | Fallback к старому поведению при отсутствии modelSize |
