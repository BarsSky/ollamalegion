# R459: семантика окна при переезде сессии — варианты решения

**Дата:** 2026-11-09. **Статус:** варианты, код не менялся.
**Повод:** P1-4…P1-7 из `docs/architecture/debts.ru.md`. Это единственный блок
долгов, который нельзя закрыть «правильным кодом»: у него несколько разумных
политик, и выбор меняет поведение балансера (риск 503, риск лишних загрузок
модели, риск «сессия застряла на занятой копии»).

---

## 0. Что такое R459 по факту

`session_move_window_r459.go` не даёт сессии переехать на копию модели, у
которой окно меньше, чем «нужно». Цель — не сломать живой запрос переездом на
урезанное окно.

Сегодня «нужно» = `need` = окно ЖИВОЙ СЕССИИ (`sessionMoveNeed`), а не
потребность КОНКРЕТНОГО запроса. Это осознанная осторожность R459: сессия с
коротким запросом остаётся на «широкой» копии, даже если рядом есть свободная
«узкая».

Дополнительно:
- `loadedPerSeqNCtx = 0` означает и «модели нет», и «поллер ещё не обновился»
  (~30 с), и «идёт reload» — три разных состояния склеены в одно;
- обходные пути переезда (выбор «исключая бэкенд» в `backend_selector.go`)
  гейт R459 не применяют;
- единая очередь выдаёт слот на любом свободном бэкенде, не зная про veto R459.

## 1. Вариант A — «need = потребность запроса» (простая, самая полезная)

`need = max(промпт + резерв, минимально допустимое окно)`. Сессия может уехать
на копию, если её окно покрывает ИМЕННО этот запрос.

**Что даёт:** короткий запрос уезжает с занятой широкой копии на свободную
узкую — минус ожидание в очереди, ровно та балансировка, по которой была
жалоба.

**Чем платим:** следующий запрос ТОЙ ЖЕ сессии окажется в сессии, окно которой
больше, чем у текущей копии → повторный переезд (пинг-понг) или отказ 413 по
окну клиента. Нужен счётчик «сколько раз эта сессия уже переезжала» или
запрет второго переезда в течение TTL.

**Как проверить:** тест «длинная сессия, короткий запрос → переезд на узкую
копию разрешён»; тест «следующий длинный запрос той же сессии не отказывает
413», т.е. переезд назад разрешён.

## 2. Вариант B — «TTL на окно сессии» (осторожная)

Оставляем `need` = окно сессии, но с TTL: если сессия не присылала запросов
N минут, её окно перестаёт быть «требованием», и сессия может уехать.

**Что даёт:** ничего не ломает для живых сессий; мёртвые сессии перестают
держать «широкую» копию.

**Чем платим:** проблему «короткий запрос стоит в очереди» не решает вовсе —
это лечение подвисших сессий, а не балансировка.

**Как проверить:** тест «сессия без запросов дольше TTL → переезд разрешён»,
«сессия активна → запрещён».

## 3. Вариант C — «A + B вместе» (рекомендация)

`need = max(потребность запроса, окно сессии в пределах TTL)`. Живая сессия
держит широкую копию (нет пинг-понга), а мёртвая — не держит.

**Что даёт:** балансировка для коротких запросов + защита от застрявших
сессий.

**Чем платим:** две новые ручки (TTL и «резерв»), больше ветвлений, сложнее
объяснить в логе; нужна строчка причины вида
`move_rejected window: need=32768 (request=4096, session=32768, ttl_left=42s)`.

## 4. Отдельно: TTL «холодного кандидата» (P1-5)

Не путать с B. Здесь TTL — про метрику, а не про сессию: `loadedPerSeqNCtx=0`
означает «неизвестно», а не «точно нет». Предлагается хранить время последнего
успешного опроса слотов и считать `0` достоверным только если опрос моложе TTL
(например, 2× интервала поллера). Это чистый код, продуктового выбора не
требует — но без него вариант A/B/C будет чаще отказывать «неизвестно».

## 5. Отдельно: гейт на обходных путях (P1-6) и очередь (P1-7)

Это дефекты, а не политика: обходные пути (`selectBackendExcluding`) и единая
очередь обходят R459. Их надо закрыть НЕЗАВИСИМО от выбора A/B/C — иначе
выбранная политика действует только на одном из путей, и поведение снова
расходится по маршрутам (ровно то, на что была жалоба «потеряно распределение»).

## 6. Что нужно решить

1. Какую политику брать: A, B или C (по умолчанию рекомендуется C).
2. Резерв к промпту (для A/C): фиксированный (например, 4096 токенов) или
   процент от промпта.
3. TTL сессии (для B/C): минуты.
4. Разрешать ли второй переезд сессии туда-обратно в пределах TTL (если нет —
   сессия после одного переезда закрепляется).
