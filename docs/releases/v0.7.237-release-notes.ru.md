# v0.7.237 — R477/R478: стадия сбоя в логе, OpenWebUI снова получает ответ

**Дата:** 2026-11-09 · **Тип:** исходники + образы стенда
**Повод:** живые жалобы «с OpenWebUI балансер перестал корректно работать — модель
генерирует токены, а ответ не доходит», «потеряно распределение нагрузки»,
«потеряна работа с разными типами моделей». Плюс требование: расширить

## 1. Что было сломано на самом деле

Четыре независимых аудита (стриминг, распределение, типы бэкендов, архитектура)
дали один и тот же вывод: **«после последних правок» — верно только для одного
дефекта**, остальное — старые расхождения путей.

| Симптом | Причина | Статус |
|---|---|---|
| OpenWebUI: токены идут, ответа нет | гейт R470 стоял в ОБЩЕЙ функции `writeChatStreamResponse`; у reasoning-моделей парсер стартует внутри размышлений и весь видимый текст до закрывающего маркера выбрасывался | **исправлено** (гейт только на tools-пути) |
| «размышления не доходят / теряются» | то же + обёртка ответа R476 объявляла `Hijack` всегда → на HTTP/2 диалог ожидания перезагрузки шёл в hijack и падал | **исправлено** (тип обёртки по возможностям writer'а) |
| «в логе не видно, кто сломался» | строка `request trace` не печатала стадию; 5xx не попадали в диагностику; паника в обработчике обрывала запрос молча | **исправлено** (R477: стадии + кольцо сбоев) |
| «потеряно распределение» | R459 отклонял Ollama-кандидата ВСЕГДА (окна слота у Ollama в наших метриках нет) → сессия никогда не переезжала на живую Ollama-копию; отказы были только в Debug | **исправлено** (Ollama-кандидат допускается, отказ виден на INFO) |
| «ответ не дошёл» на админских ручках | `proxyRequest` в `ollama_router_admin.go` игнорировал ошибку → пустой `200` | **исправлено** (502 JSON с бэкендом и request_id) |
| `/api/show|copy|delete` по модели на cppworker | модель искалась в поле, которое в проде не заполняется | **исправлено** (источник `metricsMgr.llamaMetrics`) |
| разные типы моделей на `/v1/*`, `/ollama/*` | `/v1/*` жёстко привязан к `llama_cpp`; префикс `/ollama` нормализует только `LlamaCppRouter` | **не исправлено разом** — это часть плана рефакторинга (см. §4), нужен паритет путей, а не заплатка |

## 2. Диагностика (R477)

- Стадии хода: `select_backend`, `admission`, `preflight`, `upstream`, `stream`,
  `client_write`, `done`. Строка `request trace` печатает `stage` и `stage_ms`.
- Ответ 5xx и паника попадают в кольцо последних сбоев: `recent_failures` в
  `GET /api/v1/diag/summary`, `failures.json` в `/api/v1/diag/bundle`.
- Паника в обработчике больше не убивает запрос молча: клиент получает 500 с
  `request_id`, в логе — `request failed at stage`.
- Воркер: свои 5xx пишет в кольцо (`failures.json` в его архиве), строка
  `HTTP request` несёт `request_id`, сводка хода — `stage`-независимые поля
  (stream_chunks/bytes/sha256 при `CPPWORKER_STREAM_TRACE=1`).
- WebUI → «Диагностика» → блок **«Последние сбои»**: время, стадия, статус,
  `request_id`, бэкенд, причина; копирование блока и отдельных значений.

## 4. Аудит и план рефакторинга

Подтверждено кодом: на один и тот же JSON приходят **две разные машины**
(`/api/chat` — generic-путь; `/v1/chat/completions` и `/ollama/api/chat` —
handler-путь), с разной очередью, разными правилами окна и разными фичами.
Плюс 39 функций выбора бэкенда, 4 «очереди», 8 циклов стрима в балансере и 11
писателей стрима в воркере.

План (этапы, флаги, тесты-предохранители, критерии отката) вынесен в
`docs/architecture/refactoring-plan.ru.md`. Порядок: сначала T1–T5
(характеризационные тесты: матрица маршрутов, golden-байты, таблица окна,
одинаковые `X-Queue-*`, стюард стадий), затем этапы 1–8 за флагами
(`LB_WINDOW_UNIFIED`, `LB_UNIFIED_ADMISSION`, `LB_ONE_INFERENCE`,
`LB_STREAM_PIPE`, `CPPWORKER_STREAM_SAFE`).
