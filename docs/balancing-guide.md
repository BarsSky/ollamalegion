### 1.1 Компоненты системы

```
┌─────────────────┐     ┌─────────────────────┐     ┌─────────────────┐
│    Клиенты      │────▶│   Балансировщик     │────▶│   Бэкенды     │

                               │                            ▲
                               │                            │
                               │                    ┌───────┴───────┐
                               │                    │    Агенты     │
                               │                    │(GPU metrics)  │
                               │                    │ Heartbeat 3с  │
                               │                    └───────────────┘
                               │                            │
                               └────────────────────────────┘
                                    Push metrics каждые 5с
```

**Компоненты:**

| Компонент | Ответственность |
|-----------|----------------|
| **Балансировщик** | HTTP-прокси, выбор бэкенда, управление очередью, сессиями, сбор метрик |
| **Бэкенд** | Инстанс Ollama, обслуживает запросы к `/api/generate`, `/api/chat` |
| **Агент** | Собирает GPU/VRAM/CPU/RAM метрики, список загруженных моделей, передаёт балансеру |
| **WebUI** | Визуальное управление, мониторинг состояния кластера |

## 2. Алгоритм выбора бэкенда (v2)

### 2.1 Многоэтапный выбор (5 этапов)

Метод `selectBackend()` в `internal/balancer/proxy.go` реализует 5-этапную логику поверх `expandCandidates()`.  
Этапы 2–4 опциональны и зависят от конфигурации (`SyncModelLoad.Enabled`, `Prewarm`, etc.).

#### 2.1.1 `expandCandidates(modelName)` — группировка бэкендов по приоритетам

Функция `expandCandidates()` анализирует все healthy бэкенды и группирует их по 4 приоритетам:

| Приоритет | Название | Условие |
|-----------|----------|---------|
| **P1** | **LOADED** | Модель в памяти, `loadRatio < triggerLoadThreshold` |
| **P2** | **WARMING** | Модель в `WarmingUpModels` (загружается) |
| **P3** | **FREE** | Свободные слоты, модель не загружена |
| **P4** | **FALLBACK** | Все healthy бэкенды с метриками |

```text
          Request arrives
                    │
                    ▼
    ┌───────────────────────────────────────┐
    │      expandCandidates(modelName)       │
    │  ┌─────────────────────────────────┐   │
    │  │ P1: LOADED (model in memory)  │   │
    │  │ P2: WARMING (model loading)   │   │
    │  │ P3: FREE (slots available)    │   │
    │  │ P4: FALLBACK (any healthy)    │   │
    │  └─────────────────────────────────┘   │
    └──────────────────┬────────────────────┘
                       ▼
    ┌───────────────────────────────────────┐
    │           selectBackend(model)         │
    │                                        │
     │  Этап 1: Session Stickiness             │
     │    ├─ Есть сессия с backend affinity?  │
     │    ├─ Бэкенд healthy и loadRatio < 80%? │
     │    └─ Да → вернуть тот же бэкенд       │
     │                                        │
     │  Этап 2: Model Affinity (P1 — LOADED) │
     │    ├─ Первый бэкенд из P1             │
     │    ├─ Проверить loadRatio < threshold │  (default 80%)
     │    └─ Если ок → вернуть бэкенд        │
     │                                        │
     │  Этап 3: Model Warming (P2)           │
     │    ├─ Найти бэкенд в процессе загрузки │
     │    ├─ Проверить ETA < syncTimeout     │  (default 30s)
     │    └─ Ожидать готовности (polling)    │
     │                                        │
     │  Этап 4: Sync Model Load (P3 — FREE)  │
     │    ├─ Если SyncModelLoad.Enabled       │
     │    ├─ Запустить загрузку на free      │
     │    └─ Ожидать готовности (с таймаутом) │
     │                                        │
     │  Этап 5: Resource-Aware Scoring (P4)  │
     │    └─ selectByResources() →             │
     │       calculateScore() /              │
     │       calculateScoreSimple()           │
    └──────────────────┬────────────────────┘
                       ▼
    ┌───────────────────────────────────────┐
    │           Decision Router             │
    │  ┌── Backend Ready → Проксировать     │
    │  ├── Model Loading → Wait/Poll        │
    │  ├── Нет Capacity → В очередь         │
    │  └── Queue > 90% → 503 (Backpressure) │
    └───────────────────────────────────────┘
```

#### 2.1.2 `dispatchWithModelLoad()` — асинхронная загрузка модели

Отдельный механизм, инициирующий загрузку модели на free-бэкенд с наибольшим свободным VRAM:

1. Вызывает `expandCandidates()` для получения P3 (FREE)
2. Выбирает бэкенд с максимальным `GPU.MemoryFree`
3. Запускает `warmupModel()` через POST `/api/pull`
4. Добавляет модель в `WarmingUpModels` с дедлайном `ModelLoadTimeout` (default 120s)
5. Возвращает `backendID` и `deadline` для ожидания

Этот механизм используется для ребалансировки и предварительной загрузки.

### 2.2 Расширенная формула скоринга (calculateScore v2)

Поведение скоринга контролируется флагом **`useEnhancedScoring`** в `balancing`:

- **`useEnhancedScoring: true`** — полная формула v2 с учётом модели, очереди и ошибок
- **`useEnhancedScoring: false`** (default) — упрощённая формула (обратная совместимость)

#### Упрощённая формула (`calculateScoreSimple`, default)

```
Score = (
    gpuFreePercent        * 0.30  +    // 30% — GPU загрузка
    vramFreePercent       * 0.20  +    // 20% — свободная VRAM
    cpuFreePercent        * 0.15  +    // 15% — свободный CPU
    − requestPenalty                     // штраф за активные запросы
) * weight                             // Мультипликатор веса бэкенда
```

#### Полная формула v2 (`calculateScore`, useEnhancedScoring=true)

```
Score = (
    gpuFreePercent        * 0.30  +    // 30% — GPU загрузка
    vramFreePercent       * 0.20  +    // 20% — свободная VRAM
    cpuFreePercent        * 0.15  +    // 15% — свободный CPU
    modelLoadedBonus      * wLoaded +  // вес из конфига (default 0.15)
    predictionBonus       * wPred   +  // вес из конфига (default 0.10)
    modelCapacityScore               +   // ёмкость под модели
    − requestPenalty                     // штраф за активные запросы
    − queueDepthPenalty    * wQueue −  // вес из конфига (default 0.05)
    − errorRatePenalty     * wError    // вес из конфига (default 0.05)
) * weight                             // Мультипликатор веса бэкенда
```

**Дополнительные компоненты v2 (только при useEnhancedScoring=true):**
- **modelLoadedBonus** — бонус за количество загруженных моделей (`ModelAlreadyLoaded * 10.0 * count`)
- **queueDepthPenalty** — штраф за глубину глобальной очереди (`QueueDepthPenalty * len(queue)`)
- **errorRatePenalty** — штраф за высокую частоту ошибок (`ErrorRatePenalty * errorRate * 100`, при `TotalAttempts > 10`)
- **predictionBonus** — бонус/штраф на основе прогноза критического состояния

**Конфигурация весов (`balancing.scoring`):**
```json
{
  "scoring": {
    "modelAlreadyLoaded": 0.15,
    "modelLoadingCost": 0.10,
    "queueDepthPenalty": 0.05,
    "errorRatePenalty": 0.05,
    "predictionBonus": 0.10
  }
}
```

### 2.3 Headroom Reservation (Ресурсный резерв)

На каждом бэкенде резервируется процент GPU памяти как горячий резерв.
Бэкенд блокируется для новых запросов если VRAM usage > (100 − headroom_percent)%.

Конфигурация: `balancing.resource_reservation.gpu_headroom_percent: 15`.

### 2.4 Feature Flag: useEnhancedScoring

Параметр `balancing.useEnhancedScoring` включает расширенную формулу скоринга:

| Значение | Поведение |
|----------|-----------|
| `false` (default) | Упрощённый скоринг: только GPU/VRAM/CPU + weight |
| `true` | Полная формула v2: + model affinity, queue depth, error rate, prediction |

Рекомендуется включать в продакшене после калибровки весов (`balancing.scoring`).

### 2.4 Фильтры здоровья (дополненные)

Бэкенд считается healthy, если:
- Последний heartbeat не старше таймаута
- GPU usage < `gpuMaxUsage` (default 90%)
- VRAM usage < `vramMaxUsage` (default 85%)
- CPU usage < `cpuMaxUsage` (default 80%)
- RAM usage < `ramMaxUsage` (default 85%)
- Диск free > `minFreeDisk` (default 10240 MB)
- **VRAM usage не превышает headroom-резерв (default 85%)**


## 3. Пошаговые сценарии балансировки

### 3.1 Сценарий 1: Один пользователь — одна модель

```
Время: t0

┌─────────────────────┐
│ Backend: ollama-1   │
│ VRAM: 0 / 24 GB     │
│ Active: 0 / 8       │
│ Models: []          │
└─────────────────────┘
┌─────────────────────┐
│ Backend: ollama-2   │
│ VRAM: 0 / 24 GB     │
│ Active: 0 / 8       │
│ Models: []          │
└─────────────────────┘

Действие: Пользователь A → запрос модели llama3.1 (8 GB)

Результат:
1. Нет сессии → создаётся новая
2. Model affinity: модель не загружена нигде → skip
3. Resource-aware fallback:
   - ollama-1: score 1.0 (всё свободно, lastUsed далёкий)
   - ollama-2: score 1.0 (всё свободно, lastUsed недавний)
   - Tie-breaking: ollama-1 (более давний lastUsed)
4. Capacity check: 0/8 < 1, maxModels не превышен
5. Запрос уходит на ollama-1

После:
┌─────────────────────┐
│ Backend: ollama-1   │
│ VRAM: 8 / 24 GB     │
│ Active: 1 / 8       │
│ Models: [llama3.1] │
│ Sessions: [sess-A]  │
└─────────────────────┘
```

### 3.2 Сценарий 2: Два пользователя — одна модель

```
Время: t1 (после сценария 1)

┌─────────────────────┐
│ Backend: ollama-1   │
│ VRAM: 8 / 24 GB     │
│ Active: 1 / 8       │
│ Models: [llama3.1] │
│ Sessions: [sess-A]  │
└─────────────────────┘
┌─────────────────────┐
│ Backend: ollama-2   │
│ VRAM: 0 / 24 GB     │
│ Active: 0 / 8       │
│ Models: []          │
└─────────────────────┘

Действие: Пользователь B → запрос модели llama3.1 (8 GB)

Результат (ТЕКУЩАЯ ЛОГИКА):
1. Нет сессии → создаётся новая
2. Model affinity: модель загружена на ollama-1
3. Проверить ollama-1: healthy? Да. active < max? 1/8 → Да
4. ВЕРНУТЬ ollama-1 (sticky к тому же бэкенду)

После:
┌─────────────────────┐
│ Backend: ollama-1   │
│ VRAM: 8 / 24 GB     │ ← модель уже загружена, не занимает
│ Active: 2 / 8       │   дополнительную VRAM
│ Models: [llama3.1] │
│ Sessions: [sess-A,  │
│            sess-B]  │
└─────────────────────┘

⚠️ ОГРАНИЧЕНИЕ: ollama-2 остаётся простаивающим, хотя мог бы
   параллельно обслуживать. Это связано с Model Affinity:
   балансер предпочитает использовать уже загруженную модель,
   чтобы избежать дополнительной загрузки на ollama-2.
```

**Идеальный сценарий (для доработки):**

```
Если на первом бэкенде загрузка > threshold (например, 50% от maxConcurrent):
  → искать второй бэкенд, где можно загрузить модель
  → подгрузить модель на ollama-2
  → создать sess-B на ollama-2
```

### 3.3 Сценарий 3: Три пользователя — одна модель (очередь)

```
Время: t2

┌─────────────────────┐
│ Backend: ollama-1   │
│ Active: 8 / 8       │ ← полностью загружен
│ Models: [llama3.1] │
└─────────────────────┘
┌─────────────────────┐
│ Backend: ollama-2   │
│ Active: 2 / 8       │

└─────────────────────┘

Действие: Пользователь C → запрос модели llama3.1 (8 GB)

Результат:

3. Проверить ollama-1: active 8/8 → НЕТ места
4. Resource-aware: ollama-2 healthy, но модель НЕ загружена
```

```
Время: t3

┌─────────────────────┐
│ Backend: ollama-1   │
│ Active: 8 / 8       │
│ Models: [llama3.1] │
└─────────────────────┘
┌─────────────────────┐
│ Backend: ollama-2   │
│ Active: 8 / 8       │

1. Нет сессии → создаётся новая

3. Resource-aware: оба полностью заняты
4. Проверить capacity: ни один не проходит
5. → ПОСТАВИТЬ В ОЧЕРЕДЬ

Очередь:
```

**Освобождение очереди:**

```

```

## 4. Управление сессиями

### 4.1 Структура сессии

```go
type Session struct {
    ID            string      // UUID сессии
    BackendID     string      // Привязка к бэкенду (sticky)
    Model         string      // Модель, запрошенная клиентом
    ClientIP      string      // IP-адрес клиента
    RequestCount  int         // Количество запросов в сессии
    LastActivity  time.Time   // Время последнего запроса
    CreatedAt     time.Time   // Время создания
}
```

### 4.2 Жизненный цикл сессии

```text
Создание
   │
   ▼
┌───────────────────────────────────────────┐
│ 1. При первом запросе клиента           │
│    (IP + модель → SessionManager)       │
│    Создаётся новая запись в map         │
└───────────────┬───────────────────────────┘
                │
                ▼
┌───────────────────────────────────────────┐
│ 2. При последующих запросах               │
│    Если сессия существует → возвращает   │
│    тот же backendID (sticky)            │
└───────────────┬───────────────────────────┘
                │
                ▼
┌───────────────────────────────────────────┐
│ 3. Обновление метаданных                  │
│    RequestCount++, LastActivity = now     │
└───────────────┬───────────────────────────┘
                │
                ▼
┌───────────────────────────────────────────┐
│ 4. Таймаут/Очистка                        │
│    Если LastActivity > idleTimeout        │
│    → сессия удаляется                     │
└───────────────┬───────────────────────────┘
                │
                ▼
            Уничтожение
```

### 4.3 Session Stickiness

Параметр `session_stickiness` (включён по умолчанию):

- **Когда работает:** при повторных запросах того же клиента к той же модели — направляет на тот же бэкенд
- **Когда НЕ работает:** если бэкенд стал unhealthy или `maxConcurrent` превышен — балансер выбирает новый
- **Trade-off:**
  - ✅ Плюс: модель уже в VRAM, быстрый отклик
  - ❌ Минус: перегрузка одного бэкенда, пока другие простаивают

## 5. Жизненный цикл модели на бэкенде

### 5.1 Состояния модели

```text
┌─────────────┐     ┌──────────────┐     ┌──────────────┐
│ Not Loaded  │────▶│ Loading      │────▶│ In Memory    │
│             │     │ (progress %) │     │ (available)  │
└─────────────┘     └──────────────┘     └──────┬───────┘
                                                  │
                                           ┌──────┴──────┐
                                           │ Active Use  │
                                           │ (inferring) │
                                           └──────┬──────┘
                                                  │
                                           ┌──────┴──────┐
                                           │ Idle        │
                                           │ (no reqs)   │
                                           └──────┬──────┘
                                                  │
                                           ┌──────┴──────┐
                                           │ Unload      │
                                           │ (optional)  │
                                           └──────┬──────┘
                                                  ▼
                                           ┌─────────────┐
                                           │ Not Loaded  │
                                           └─────────────┘
```

### 5.2 Как балансер отслеживает модели

1. Агент отправляет heartbeat каждые 3 секунды
2. Heartbeat содержит поле `models: [...]` — список загруженных моделей
3. Балансер обновляет `Backend.Models` в своём состоянии
4. При выборе бэкенда `findBackendWithModel()` ищет совпадение

### 5.3 Выгрузка моделей

Параметр `unload_idle_models` (опционально):

- Если включён: модель выгружается из VRAM после `idle_timeout` без запросов
- Если выключен: модель остаётся в VRAM до перезагрузки Ollama

⚠️ **Текущее ограничение:** нет активной выгрузки модели для освобождения места под другую. Выгрузка — только по таймауту неактивности.

## 6. Управление очередью

### 6.1 Структура очереди

```go
type QueueManager struct {
    items          []QueueItem     // Все элементы
    pending        []QueueItem     // Ожидающие
    processing     []QueueItem     // Выполняющиеся
    maxSize        int             // Максимальный размер (default 100)
    workers        int             // Количество воркеров
    processedTotal int64           // Всего обработано
}
```

### 6.2 Состояния элемента очереди

| Статус | Описание |
|--------|----------|
| `pending` | Ждёт свободного бэкенда, не назначен target |
| `processing` | Назначен бэкенд, запрос в процессе |
| `completed` | Завершён успешно |
| `failed` | Завершён с ошибкой (retry count exceeded) |
| `cancelled` | Отменён клиентом |

### 6.3 Механизм dispatch

```text
Запрос поступает ──▶ Проверка capacity бэкенда
                          │
              ┌───────────┴───────────┐
              │ Место есть              │ Места нет
              ▼                         ▼
        ┌──────────┐            ┌──────────────┐
        │ Направить│            │ Добавить в   │
        │ на       │            │ очередь      │
        │ бэкенд   │            │ status:      │
        │          │            │ pending      │
        └──────────┘            └──────────────┘
                                          │
                              ◀──────────┘
                              Завершение запроса
                              на бэкенде
                              │
                              ▼
                        ┌──────────────┐
                        │ Проверить    │
                        │ очередь      │
                        │ на предмет   │
                        │ подходящего  │
                        │ элемента     │
                        └──────┬───────┘
                               │
                    ┌──────────┴──────────┐
                    │ Найден               │ Не найден
                    ▼                      ▼
              ┌──────────┐         ┌──────────┐
              │ Dispatch │         │ Ожидать  │
              │ следующий│         │ следующего│
              │ запрос   │         │ завершения│
              └──────────┘         └──────────┘
```

### 6.4 Fair Queuing (планируемая доработка)

Текущая реализация: **FIFO** (первый пришёл — первый обслужен).

Рекомендуемая доработка:

```
Priority = enqueueTime + (modelSize * weight) + (sessionAge * factor)

Где:
- modelSize: чем больше модель, тем дольше ожидание
- sessionAge: новые сессии могут получать бонус
- VIP-флаг: для критичных запросов
```

## 8. Текущие ограничения и рекомендации

### 8.1 Различия: текущая реализация vs идеальный сценарий

| Аспект | Текущая реализация | Идеальный сценарий |
|--------|-------------------|-------------------|
| **Model Affinity** | Всех направляет на один бэкенд | Подгружает дубликаты при загрузке > threshold |
| **Выгрузка моделей** | Только по idle timeout | Активная выгрузка при конкуренции |
| **Очередь** | FIFO | Fair queuing с приоритетами |
| **Session Migration** | Нет | Перебалансировка при перегрузке |
| **Мониторинг** | 3 endpoint'а polling | WebSocket real-time |

### 8.2 Рекомендации по доработке

**Приоритет: Высокий**
1. Добавить `threshold_load` — при превышении загрузки бэкенда искать альтернативу для новых сессий
2. Исправить монитор (API_BASE, секция моделей, CORS-диагностика)

**Приоритет: Средний**
3. Активная выгрузка моделей при нехватке VRAM (LRU eviction)
4. Fair queuing с приоритетами

**Приоритет: Низкий**
5. WebSocket для real-time обновлений
6. Session migration между бэкендами

### 8.3 Конфигурационные параметры

| Параметр | Описание | Default |
|----------|----------|---------|
| `balancingAlgorithm` | Алгоритм: resource-aware, least-connections, round-robin | resource-aware |
| `modelAffinity` | Предпочитать бэкенд с загруженной моделью | true |
| `sessionStickiness` | Привязывать сессию к бэкенду | true |
| `useEnhancedScoring` | Использовать расширенную формулу скоринга v2 | true |
| `predictionFiltering` | Использовать предиктор загрузки | true |
| `gpuMaxUsage` | Макс. GPU usage (%) | 90 |
| `vramMaxUsage` | Макс. VRAM usage (%) | 85 |
| `cpuMaxUsage` | Макс. CPU usage (%) | 80 |
| `ramMaxUsage` | Макс. RAM usage (%) | 85 |
| `minFreeDisk` | Мин. свободного диска (MB) | 10240 |
| `queueMaxSize` | Макс. размер очереди | 100 |
| `sessionIdleTimeout` | Таймаут неактивной сессии | 30 мин |

## 9. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Бэкенд** | Инстанс Ollama с GPU, обслуживающий запросы |
| **Балансер** | Компонент, распределяющий запросы по бэкендам |
| **Sticky Session** | Привязка клиента к конкретному бэкенду |
| **Model Affinity** | Предпочтение бэкенда, где модель уже в VRAM |
| **Capacity** | Максимальное количество одновременных запросов (maxConcurrent) |
| **Score** | Численная оценка пригодности бэкенда для запроса |
| **Queue** | FIFO-очередь запросов, ожидающих свободного бэкенда |
| **Dispatch** | Процесс отправки запроса из очереди на бэкенд |
| **Eviction** | Выгрузка модели из VRAM для освобождения места |
