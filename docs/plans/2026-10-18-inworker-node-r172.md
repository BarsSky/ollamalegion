# Встроенный узел раскладки: протокол разбора и гипотезы (R172, 2026-10-18)

## 1. Что уже установлено фактами

| Факт | Как проверено |
|---|---|
| встроенный узел (дочерний процесс `cppworker`) + клиент **на той же машине** — работает | мастер, gemma-4, локальная раскладка: чат 200 |
| встроенный узел + клиент **на другой машине** — падает | 3 прогона: `ggml-rpc.cpp:566 … malformed response` + `Aborted` на мастере |
| отдельный контейнер (`/app/rpc-server`, тот же образ) + клиент на другой машине — работает | 2 прогона: с чистым env и с env-файлом донора; чат 200 |
| llama.cpp и сеть «виноваты» — **опровергнуто** | тот же коммит llama.cpp, тот же порт, то же плечо сети |
| версия/сборка узлов совпадает | `llama_build=0eadefebd` у обоих, хеши `rpc-server` совпадают |
| внешний узел (compose-профиль `rpc-node`) — рабочий обход | R171: живая цепочка 200 за 5.83 с, `RestartCount=0` |

**Чего НЕ было:** серверной стороны аварии. `Remote RPC server crashed or returned malformed
response` — клиентское сообщение; `RPC_STATUS_ASSERT` (ggml-rpc.cpp:35) поднимает его на
любой ответ со статусом false, а сервер закрывает сессию на первой неудачной операции
(`if (!server.op(...)) return;`, ggml-rpc.cpp:1857+). Причину печатает только сервер —
`GGML_LOG_ERROR` в stderr, и этот вывод (а) шёл только в `docker logs` донора, (б) исчезал
при пересоздании контейнера, (в) нами ни разу не читался в момент аварии.

R172 закрывает именно это: exit-статус процесса + кольцевой буфер его вывода
(`GET /api/v1/cppworker/rpc-server/log`), плюс `GGML_RPC_DEBUG=1` при необходимости.

## 2. Гипотезы (все проверяемые одним прогоном)

| # | Гипотеза | Что увидим в R172-данных, если верна | Контрфакт, если неверна |
|---|---|---|---|
| H1 | Узел **падает** (segfault/abort/OOM-kill) | `lastExit = signal: …`, процесс исчез, `restarting`/`restarts` растут | `lastExit` пуст, PID/uptime не менялись |
| H2 | Узел жив, но **операция вернула false** (регион тензора вне буфера = рассинхрон протокола) | `lastExit` пуст, в строках `tensor region … out of bounds` / `error deserializing tensor` | строки есть, но про память |
| H3 | **Нехватка VRAM** у дочернего процесса (родитель держит контекст на 8-ГБ карте) | в строках `Failed to allocate …` / `ggml_backend_cuda_buffer_type_alloc_buffer: allocating … failed`; `lastExit = exit status …` (сервер выходит после false) | в строках нет аллокаций, VRAM в норме |
| H4 | **Одиночный клиент**: TCP-проба (статус узла/гейт) занимает единственный слот `accept`, пока мастер грузит модель | авария коррелирует с опросом статуса; в debug-логе видно `Accepted client connection` без последующих операций | в логе ровно один `Accepted client connection` на прогон |
| H5 | **Архитектура/драйвер** (sm_120, Blackwell): падение в ядре на конкретной операции | `signal: segmentation fault` при живом standalone-узле на той же карте | падение и у standalone |
| H6 | **stdio**: дочерний процесс блокируется на записи в stdout контейнера | в логе после `Accepted client connection` тишина, узел жив, клиент ждёт | в логе видны строки операции |

Порядок разбора: сначала H1/H2 (это R172 решает однозначно), затем H3 (по строкам), затем
H4/H6 (по debug-логу), H5 — если H1 даёт segfault.

## 3. Протокол прогона

Подготовка (один раз): образ с R172, донор пересоздан со **встроенным** узлом и отладкой.

```powershell
# 1. Образ (на мастере)
scripts/build-containers.ps1 -CppWorker -Tag r172-node-diag -CudaArch "86;120" `
  -CudaVersion "12.8.0" -CudaBase mirror.gcr.io/nvidia/cuda `
  -GoDownloadBase https://mirrors.aliyun.com/golang

# 2. Донор: встроенный узел + отладочный лог протокола, без внешнего адреса
scripts/upgrade-donor-node.ps1 -NewImage ollama-legion/cppworker:gpu-r172-node-diag `
  -TransferImage -Ports '18034:18034','18092:18092','50052:50052' `
  -ExtraEnv 'CPPWORKER_RPC_SERVER_ENABLED=true','CPPWORKER_RPC_SERVER_PORT=50052',`
            'CPPWORKER_RPC_EXTERNAL_ADDR=','CPPWORKER_RPC_SERVER_DEBUG=true',`
            'CPPWORKER_RPC_SERVER_RESTART=false'
```

`RESTART=false` на время разбора: повторный подъём стирает картину (PID/uptime/exit
перезаписываются новым циклом) и мешает связать аварию с конкретной операцией.

Сам прогон:

```powershell
# 3. Мастер принимает донора как узел раскладки
Invoke-RestMethod -Method Post -Uri 'http://127.0.0.1:18081/api/v1/backends/<id>/role' `
  -Headers @{'X-API-Token'='changeme-bundled-with-agent-token'} -Body '{"role":"donor"}'

# 4. Загрузка модели с раскладкой (мастер)
#    gpuLayers считается балансером по VRAM узла; на доноре ожидается 2-4 слоя.
curl.exe -s -X POST http://127.0.0.1:18092/api/models/load -H "Content-Type: application/json" `
  -d '{"name":"gemma-4-E4B-it-Q4_K_M","contextSize":8192,"gpuLayers":42}'

# 5. Чат (это и есть операция, на которой падает клиент)
curl.exe -s -X POST http://127.0.0.1:18080/api/chat -H "Content-Type: application/json" `
  -d '{"model":"gemma-4-E4B-it-Q4_K_M","messages":[{"role":"user","content":"2+2"}],"stream":false}'
```

Снятие доказательств (сразу после аварии, ДО пересоздания контейнера донора):

```powershell
curl.exe -s -H "X-API-Token: changeme-bundled-with-agent-token" `
  "http://192.0.2.10:18092/api/v1/cppworker/rpc-server/log?lines=200"
# что смотреть: lastExit, lastExitPid, restarts, lines[] (ищи allocate/bounds/deserialize)
```

## 4. Как читать результат (правило решения)

* `lastExit` = `signal: …` → H1. Дальше по сигналу: `segmentation fault` — падение в
  ядре/бэкенде (H5), `killed` — OOM-киллер (H3 на стороне хоста), `abort` — `GGML_ABORT`
  (в логе будет причина прямо перед ним).
* `lastExit` пуст, процесс жив → H2 (операция вернула false). Тогда `lines[]` содержит
  `GGML_LOG_ERROR` сервера: `tensor region … out of bounds` (рассинхрон протокола — сверять
  сборки), `invalid tensor type` (сборка/тип), `Failed to allocate` (H3).
* В `lines[]` ни одной строки операции при `Accepted client connection` → H4/H6 (сессия
  занята пробой либо процесс блокирован на записи).

## 5. Что будет считаться исправлением

Не «падает реже», а: встроенный узел переживает загрузку с раскладкой между машинами,
`RestartCount=0` у мастера, `lastExit` пуст, `restarts=0`, и отдельный контейнер
`rpc-node` для этого не нужен. Если причина — нехватка VRAM (H3), исправление обязано
либо уменьшить число слоёв на узел (планирование по реально свободной памяти ребёнка), либо
сделать узел чувствительным к отказу аллокации заранее (отказ ДО загрузки, а не abort
клиента).

## 7. Прогон без донора: топология сама по себе НЕ причина (2026-10-18)

Пока донор был выключен, авария проверялась на ОДНОЙ машине двумя одноразовыми
контейнерами того же образа (`scripts/repro-inworker-node-r172.ps1`, стенд `ol-stack-*` не
затрагивается):

* контейнер-СЕРВЕР: `CPPWORKER_RPC_SERVER_ENABLED=true`, `..._DEBUG=true`, `..._RESTART=false`;
* контейнер-КЛИЕНТ: `CPPWORKER_RPC_ENABLE=true`, `CPPWORKER_RPC_SERVERS=<сервер>:50052`,
  `CPPWORKER_SPLIT_MODE=1`; соединение идёт по пользовательской сети `ol-net`, то есть НЕ
  через loopback — как между машинами.

Результаты (все — с включённым `GGML_RPC_DEBUG`, то есть с серверной стороной в руках):

| Прогон | Топология | Результат | Серверная сторона |
|---|---|---|---|
| A | клиент без своей карты (`CUDA_VISIBLE_DEVICES=`), 20 слоёв на узел | чат **200 за 1.60 с** | `running=true`, `lastExit=''`, `restarts=0`, 1686 строк лога, `[graph_compute] device: 0, n_nodes: 1153` |
| B | клиент без своей карты, 42 слоя | загрузка прошла, но 43 слоя ушли на CPU (`gpu_count=0`), чат 6.5 с | узел жив, `lastExit=''`; `vram_remote_free=0` — узел в тот момент не отдал объём памяти |
| C | **клиент со своей картой + удалённый узел** (как у мастера в аварии), 30 слоёв | чат **200 за 2.42 с**, раскладка `CUDA0 + RPC0` | `running=true pid=15`, `lastExit=''`, `restarts=0`, 759 строк, `[graph_recompute] device: 0` |

**Что установлено.** Топология «клиент на другой машине + встроенный узел» САМА ПО СЕБЕ не
ломается: узел поднимается дочерним процессом, принимает загрузку модели, кладёт слои на
свою карту и исполняет графы; клиент не падает. Значит причина аварии на доноре —
**свойство той машины** (архитектура sm_120/драйвер, свободная VRAM или RAM, ограничение
контейнера), а не устройство встроенного узла. Это согласуется с единственным наблюдаемым
различием: на доноре в момент аварии было ~3 ГБ свободной VRAM и ~3 ГБ RAM.

**Что из этого следует для разбора.** Гипотезы H4 (одиночный слот `accept`), H6 (блокировка
на stdout) и «клиент на другой машине» — ослаблены: в прогонах A и C тот же механизм работал
при постоянных пробах порта (в логе десятки `Accepted client connection`) и при стенде,
который параллельно опрашивал статус. Приоритет переходит к H1/H3 на доноре, и R172 даёт
для них прямые данные (`lastExit`, строки `Failed to allocate …`).

**Побочное наблюдение (B).** `vram_remote_free=0` у клиента при живом узле — заявка на
отдельный разбор: если объём удалённой памяти читается как 0, планировщик кладёт слои на
CPU, и раскладка молча деградирует (в прогоне B это ровно и случилось: 43 слоя на CPU при
доступном узле). Не тот же дефект, что авария, но того же класса «UI/планировщик верят не
факту».

Скрипт воспроизведения оставлен в репозитории: `scripts/repro-inworker-node-r172.ps1`
(параметры: образ, сеть, каталог моделей, число слоёв; `-KeepContainers` не убирает
контейнеры для ручного разбора).

## 8. Живой прогон на доноре: ПРИЧИНА ДОКАЗАНА (2026-10-18, R173)

Донор включён, образ с R172 перевезён (`gpu-r172-node-diag`), контейнер пересоздан со
**встроенным** узлом и отладочным логом (`CPPWORKER_RPC_SERVER_ENABLED=true`,
`..._DEBUG=true`, `..._RESTART=false`), внешний адрес очищен. Роль `donor` выдана
балансером: `rpcNode.reachable=true addr=192.0.2.10:50052`.

Раскладка действительно состоялась (лог мастера):

```
load_tensors: offloaded 42/43 layers to GPU
load_tensors:   CPU_Mapped model buffer size =  1936.74 MiB
load_tensors:        CUDA0 model buffer size =  1177.51 MiB
load_tensors: RPC0[192.0.2.10:50052] model buffer size =  1251.07 MiB
```

Узел со своей стороны это подтвердил: `[alloc_buffer] device: 0, size: 1311845120 ->
remote_ptr …` (ровно 1251 МиБ) и сотни `[set_tensor]` при передаче весов. Ошибок у узла НЕТ.

Авария воспроизведена (мастер перезапущен: `RestartCount=1`, второй прогон — `ExitCode=141`):

| Время (UTC) | Мастер | Узел донора |
|---|---|---|
| 10:00:48 | буферы назначены: RPC0 1251 МиБ | — |
| 10:00:48–10:01:11 | передача весов в сокет RPC | 272 строки `[set_tensor]`, ошибок нет |
| 10:01:10.717 | «……» (трейс) и смерть, `ExitCode=141` = **SIGPIPE** | — |
| 10:01:11.305 | — | `config saved`, `rpc-server: узел раскладки остановлен pid=318` |
| 10:01:11.31 | — | `узел раскладки поднят внутри cppworker pid=…` (новый процесс) |

**Причина.** Балансер на каждом согласовании роли присылает
`PUT /api/v1/cppworker/config/update` с `rpcServerEnabled`/`rpcServerPort`. Обработчик
воркера реагировал на **факт поля в запросе**, а не на изменение значения: гасил дочерний
`rpc-server` и создавал новый супервизор. Если в этот момент мастер грузил модель через
этот узел, сессия рвалась на середине передачи весов, и мастер умирал по SIGPIPE
(в первом прогоне — с трейсом ggml и без сообщения: SIGPIPE в C++-слое llama.cpp не
перехватывался).

Почему отдельный контейнер «работал»: в режиме внешнего узла (R171) `SetEnabled` **не
порождает и не гасит процесс** — он только проверяет адрес. Приказ балансера физически не
мог убить чужой контейнер. То есть «встроенный узел падал» было не свойством узла, а
следствием того, что его убивали приказом.

**Исправления (R173).**

1. `cmd/cppworker/handlers_config.go`: приказ применяется **идемпотентно** — настройки не
   изменились → процесс не трогаем вообще; изменилась только «включённость» →
   `SetEnabled`; изменилась ИДЕНТИЧНОСТЬ (адрес/порт/бинарь/внешний адрес/отладка) →
   только тогда пересоздание, с предупреждением в лог.
2. `internal/cppbackend/rpc_server_child.go`: `RequiresRecreate(cfg)` — единственное место,
   где решается вопрос пересоздания.
3. `cmd/cppworker/main.go`: `signal.Ignore(syscall.SIGPIPE)` — смерть от закрытого сокета
   превращается в ошибку записи (EPIPE), которую llama.cpp сообщает как отказ операции;
   клиент выживает, причина видна. Раньше процесс умирал молча (код 141).
4. Тесты: `rpc_server_idempotent_r173_test.go` (матрица «что требует пересоздания» +
   живой helper-процесс не перезапускается повторным приказом),
   `rpc_server_idempotent_handler_r173_test.go` (два одинаковых приказа — один и тот же
   супервизор; смена порта — новый).

**Приёмка на стенде (тот же сценарий, что падал).**

| Что | Результат |
|---|---|
| раскладка | `CPU:1 CUDA0:23 RPC0:19` — 19 слоёв на донорской карте |
| чат через балансер | **200 за 4.69 с** |
| мастер | `RestartCount=0`, контейнер не перезапускался |
| узел донора | PID **34 → 34** (не пересоздан), `restarts=0`, `lastExit` пуст |
| приказ во время прогона | пришёл (`config saved`), строки `остановлен` НЕТ — 822 тензорные области пережили приказ |

**Остаётся известным артефактом (не дефект исправления).** Пока узел занят единственной
сессией раскладки, проба порта изнутри контейнера может не ответить, и статус показывает
`listening=false` при `running=true`: сервер ggml-rpc обслуживает ОДНО соединение, а пробы
складываются в очередь `accept`. Раньше это (вместе с приказом) и приводило к убийству
узла; теперь приказ безвреден. Если понадобится убрать и шум в журнале, решение — считать
«порт не подтверждён» отличимым от «порт не слушает» и не переспрашивать узел, пока он
отчитывается `running=true` с растущим uptime.

**Что нужно от оператора.** Ничего обязательного: узел работает без второго контейнера.
Контейнер `rpc-node` (профиль `rpc-node`, порт 50055) остаётся как резервный путь и может
быть остановлен: `docker compose --profile rpc-node stop rpc-node`.
