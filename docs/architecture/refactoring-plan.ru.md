# Рефакторинг: два мозга, четыре окна, четыре очереди (план)

**Дата:** 2026-11-09. **Статус:** план, код не менялся.
**Повод:** живые жалобы после серии правок R459–R476 — «перестал работать
OpenWebUI», «потеряно распределение нагрузки», «потеряна работа с разными типами
моделей». Аудит кода (четыре независимых прохода: стриминг, распределение, типы
бэкендов, архитектура) показал: это не «сломалось одно место», а **несколько
параллельных реализаций одного пути**, которые расходятся в поведении.

## 2. Почему это не «переписать всё»

Формулы окна уже сведены в одну точку и покрыты тестами; парсеры tool-call'ов —
это РАЗНЫЕ форматы моделей, а не дублирование; `pkg/types`, `internal/settings`,
`pkg/logger`, i18n — стабильны. Проблема в **маршрутизации и дублировании пути
запроса**, а не в математике.

## 3. Этапы (каждый — отдельный коммит с флагом и откатом)

Сначала тесты-предохранители (их сейчас нет):

- **T1 матрица маршрутов** — для (поверхность 18080/18079, путь из
  `/api/chat`, `/ollama/api/chat`, `/v1/chat/completions`, тело
  `stream:true|false|отсутствует`, `tools:да|нет`) утверждать, какие стадии
  вызвались и что формат ответа одинаков при отсутствии `stream`.
- **T2 golden-байты** NDJSON/SSE для шести комбинаций + «ровно один терминатор».
- **T3 окно**: таблица (needed, loaded, requested, активные стримы, reload) →
  вердикт, одинаковый на всех путях.
- **T4 очередь**: одинаковые `X-Queue-*` и `/queue` на обоих путях.
- **T5 стюард**: у каждой стадии R477 есть prod-вызов; `w.(http.Flusher)` только
  в `safe_stream_writer.go`.

| Этап | Что | Критерий готовности | Флаг |
|---|---|---|---|
| 1 | `request_plan.go`: одно решение о стриме/модели/лимитах в контексте | запрос без `stream` одинаков на всех путях | — |
| 2 | один буфер тела в контексте, один лимит | тело читается ≤1 раза; 413 одинаков | — |
| 3 | один `decideWindow()` (R288+R447+R466 внутри) | T3 на всех путях | `LB_WINDOW_UNIFIED` |
| 4 | один `Admitter` за интерфейсом | T4 | `LB_UNIFIED_ADMISSION` |
| 5 | один `runInference()` для chat/generate/OpenAI | паритет R86/R403 на трёх поверхностях | `LB_ONE_INFERENCE` |
| 6 | один стрим-пайплайн, hijack как inner-writer | T2 побайтово | `LB_STREAM_PIPE` |
| 7 | воркер: все писатели через `safeStreamWriter`, единый терминатор, сводка на всех поверхностях | T5 | `CPPWORKER_STREAM_SAFE` |
| 8 | удалить мёртвое (`executeWithFallback`, `acquireSlotWithRetry`, `bindSession`, `SetQueueManagerProxy`, дубль `/health`) | тесты зелёные | — |

Откат любого этапа — снять флаг или `git revert` одного коммита; данные не
мигрируют.

## 4. Проверка на двух стендах (один чек-лист на этап)

- **9B / частичный оффлоад:** длинный prefill (>60 c) + heartbeat; запрос без
  поля `stream`; tool-call на три хода; отмена в очереди; ответ дольше 120 c.
- **A10 / 27B:** две копии модели (выбор копии под окно, R118.5; переезд R459);
  reload под окно (R385); отказ по памяти с числами; четыре параллельных клиента.
- Артефакты на этап: `request trace` по `request_id` на трёх поверхностях,
  `recent_failures`, `X-Queue-*`/`X-Backend-ID`, байтовый diff ответа
  старый/новый.

## 5. Чего пока нет в коде

- ни одной метрики с меткой стадии (только лог-строки);
- теста, фиксирующего, какой внутренний путь обслуживает `/api/chat` против
  `/v1/chat/completions` (поэтому расхождение и живёт);
- общего интерфейса очереди/селектора/транспорта;
- лимита тела на generic-пути.
