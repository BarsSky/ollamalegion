## 4. Честно: что НЕ проверено на живом стенде

1. Ветка `202 StillLoading` (R262) — модель успевала загрузиться к концу окна
   ожидания, поэтому живьём прошёл путь «recovered from HTTP timeout»; сама
   ветка покрыта только юнит-тестами.
2. «Вытеснение» модели (R257) — на этой карте (8 ГБ) недостижимо: cppworker
   держит обе модели, Qwen уходит в CPU-offload (~0.65 ток/с). Проверен
   инвариант «API == фактическое `state` воркера», а не сам факт вытеснения.
3. Случай «один SSE-чанк > 1 МиБ» (R259) — на доступной модели невоспроизводим
   (чанки мелкие): фикс подтверждён сторожевой юнит-схемой (1.5 МиБ при старом
   лимите даёт `ErrTooLong`) и отсутствием ложных срабатываний на 431/304 КБ.
4. R255 (окно 256000 из профиля) — проверено юнит-тестами; живой стенд с
   достаточной VRAM и профилем 256000 нужен отдельно.
5. Полный агентский сценарий 150–250 строк на DSH — не прогнан: 27B на 8 ГБ даёт
   0.65 ток/с, слабая gemma не тянет цикл без явных подсказок.

## 5. Остаточный тех-долг (осознанно не трогали)

- **Fold-сопоставление профиля**: вынесено в явный параметр (`profileCapCtx(…, fold)`),
  но правило «терпимое совпадение имени» остаётся знанием, размазанным по двум
  потребителям (клиентские запросы vs preflight).
- **`resolveModelMaxContext`**: отвечает на другой вопрос (предел для решения о
  reload: в hard-режиме профиль может быть НИЖЕ физики), несёт диагностику
  оператору — сведение с физическим потолком изменило бы решения.
- **Устаревание `PhysicalMaxContext`**: геттер `physicalCeiling()` возвращает уже
  посчитанное значение; при смене профиля/VRAM без reload значение живёт до
  следующего пересчёта — это осознанно (повторный поход в конфиг/метрики посреди
  решения о reload менял бы картину).
- **Legacy-путь `proxy_request.go`** и **три места с собственными лимитами** уже
  сведены к `streamMaxLineBytes`, но сам legacy-цикл остаётся дублем hijack-пути
  (кандидат на удаление отдельной задачей).
