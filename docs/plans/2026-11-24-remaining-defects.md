## D1. P0. Профиль модели на стороне воркера берёт чужой ключ

**Симптом.** В логах воркера: `conservative profile detected … profile_n_ctx=32768`, тогда как на балансере для ключа `Qwen3.8-27B-UD-Q4_K_M` лежит профиль с `contextLength=131072`. Балансер растит окно по 131072, воркер «видит» 32768 → расходятся рекомендации и `feasible`.

**Причина (известна).** Резолвер профилей воркера (`internal/cppbackend`, магазин профилей) ищет по короткому имени и попадает в соседний профиль `Qwen3.8-27B` (32768). Класс тот же, что закрывал R692 для WebUI, но на серверной стороне.

**Что делать.** Ввести единый нормализатор ключа профиля на стороне Go (зеркало `GgufModelKey` из R692) с порядком: точное имя → точное + `.gguf` → канонический ключ (basename, без `.gguf`, регистр сохраняется) → без учёта регистра. **Без поиска по подстроке** (на стенде рядом живут профили-префиксы — подстрочный поиск подставит чужой). Источник истины — `balancer.NormalizeModelProfileKey` (`internal/balancer/num_ctx_resolver.go:148-161`): переиспользовать его, а не копировать.

**Проверка.** `logs` воркера не содержат `conservative profile … profile_n_ctx=32768` для этого ключа; `GET /api/models`/профиль показывает 131072; тест: «поиск по полному имени файла находит профиль без расширения», «модель без профиля не получает чужой», «ключ с `.gguf` тоже находится»; красный до правки.

**Риск.** Изменение резолва профилей влияет на `feasible`/`n_ctx` → прогон полного пакета `internal/cppbackend` + балансера, плюс живой замер на 27B (если файл доступен на узле).

## D2. P0. `/api/tokenize` воркера отвечает 46 секунд

**Симптом.** `06:24:24 POST /api/tokenize duration=46.155s` на локальном воркере, при том что на соседнем узле те же токенайзы — 45–47 **мс**. Следствие в балансере: `exact prompt tokens unavailable … timeout` (1500/6000 мс) и работа «по оценке», завышающей примерно в 2 раза (`estimated 48121 → actual 33839`, калибровка по 55 сэмплам).

**Причина.** Не локализована. Гипотезы: (а) токенайз идёт под занятым слотом/под мьютексом инференса — тогда это блокировка, а не медленный токенизатор; (б) воркер создаёт временный контекст/модель для токенизации; (в) проблема в самом вызове моста (аллокация словаря на каждый запрос).

**Что делать.** 1) Воспроизвести на изолированном контейнере: `POST /api/tokenize` при свободном и занятом слоте, замерить; 2) профилировать (pprof есть в Go-слое; если блокировка — видно сразу); 3) если токенизация под локом — вынести в отдельный лёгкий путь (токенайзер без захвата слота); 4) если мешает `n_ctx`/аллокации — переиспользовать словарь.

**Проверка.** `POST /api/tokenize` < 100 мс на 6–13k токенов и при свободном, и при занятом слоте; в логах балансера пропадает `exact prompt tokens unavailable`; точная оценка используется в решениях о росте; тест: «токенайз не блокируется инференсом» (на стабах/семафоре).

**Риск.** Трогает горячий путь воркера — отдельный прогон `-race` и замер скорости обслуживания до/после.

## D6. P1. `gemma-4-E4B` не грузится в CPU-образе

**Симптом.** В CPU-сборке: с `flash_attn=enabled` — `SIGSEGV` в `graph_reserve` (`signal arrived during cgo execution`), с `flashAttn=0` — «quantized V cache requires flash_attn to be enabled» (воркер просит kv q8_0). Воспроизводится на пинах b1b770d90d и b12642, GPU-путь не затронут.

**Что делать.** 1) Воспроизвести и снять стек с символами (сборка с `-g`, `ggml` без `NDEBUG`); 2) проверить, не наш ли это `backend_vram`/`n_ctx` (передаём несовместимые параметры CPU); 3) если это баг CPU-бэкенда llama.cpp — зафиксировать как known-issue, а для нас: не предлагать q8_0 KV на CPU (авто-выбор `f16`/`q4_0`), вывести понятную ошибку вместо SIGSEGV.

**Проверка.** CPU-образ загружает gemma-4 с рабочими параметрами (или честно отказывает с указанием «CPU: kv q8_0 не поддерживается без flash_attn»); нет SIGSEGV; тест на выбор kv-типа по бэкенду.
