# R306–R307: числа в 413 и закрытые административные ручки воркера

Дата: 2026-10-30. Ветка: `centurion`. Предыдущий разбор: `2026-10-30-r305-llama-build-and-window.md`.

## R306: `max_vram_n_ctx=0` при работающей модели

**Живой факт.** Стенд, gemma-4-E4B, `ctx=32768`, модель отвечает; `/api/models`
отдавал `max_vram_n_ctx=0` при `vram_known=true` и `gguf_max_context=131072`. По
контракту поля (R83) ноль при известной VRAM значит «веса не влезают ни при каком
gpu_layers» — ложь.

**Причина.** `memfit.Ceilings` считает потолок как
`(свободная VRAM − размер весов) / KV на токен`, то есть предполагает, что модель
ещё НЕ загружена. У загруженной модели веса уже вычтены из свободной VRAM, и
Ceilings вычитает их второй раз: на стенде свободных было ~2.5 GB при весах
4.2 GB — потолок 0 при любом окне.

**Следствие было не косметическим:** отказ по окну (413) не мог сослаться на
физический предел, и оператор не понимал, поможет ли поднять
`LB_NCTX_RELOAD_MAX_N_CTX`. Это и был пункт отчёта «числа в 413 не сходятся»
(`max_vram_n_ctx < current_n_ctx` при работающей модели).

**Что сделано.** Перед расчётом веса загруженной модели возвращаются в бюджет
(`restoredWeightsBytesR306`). Возвращаются ТОЛЬКО веса, а не весь `VRAMUsage`:
KV-кэш текущего окна при перезагрузке освободится, но в расчёте потолка он и не
вычитается (Ceilings считает окно с нуля); смешать эти вещи значило бы завысить
потолок на размер текущего KV. Доля — по числу слоёв на GPU: при частичной
выгрузке в RAM ушли не все веса. Ноль слоёв на GPU — возвращать нечего.

**Проверка живьём** (образ `cppworker:gpu-be9a1df1`):

| | до | после |
| --- | --- | --- |
| `/api/models` `max_vram_n_ctx` (модель загружена, ctx 32768) | `0` | `131072` |
| `/api/models` `vram_known` / `gguf_max_context` | `true` / `131072` | `true` / `131072` |
| отказ на `num_ctx=65536` | «operator limit 32768» (физический предел «0» проверить нельзя) | тот же текст, но теперь видно, что железо позволяет 131072 → совет «поднять env» выполним |

Тесты: `resource_limits_r306_test.go` — четыре случая (загружена/не загружена;
полный/половинный оффлоад/ноль слоёв/nil) и отдельная проверка механизма на
реальных параметрах KV (8 KV-слоёв, head_dim 128, как у gemma-3/4): с
возвращёнными весами окно 32768 помещается целиком — это окно модель уже держит.

## R307: административные ручки воркера были открыты

**Живая дыра, найденная при проверке R304.** В cppworker под `authMiddleware`
стояли `/api/models/reload` и `/api/models/import`, а `/api/models/load`,
`/api/models/load-with-params`, `/api/models/unload`, `/api/models/delete` и их
алиасы (`/load`, `/api/delete`) — нет. Достаточно было видеть порт 18092 в сети,
чтобы в обход балансера загрузить модель в память (заняв VRAM, которую балансер
планировал иначе), выгрузить чужую работающую модель или удалить файл с диска.
Все проверки балансера (роль донора R304, занятость R292, дедлайны R271) при этом
не участвовали вообще.

**Что сделано.**

- Воркер: шесть маршрутов обёрнуты `authMiddleware`. Legacy-режим сохранён: если
  токен не сконфигурирован, middleware пропускает — стенд без токена продолжает
  работать.
- Балансер: одно правило (`worker_admin_token_r307.go`) — путь из набора
  административных получает `X-API-Token` с токеном ЭТОГО бэкенда. Применяется в
  `ModelManager` (load / unload / delete — через новый
  `sendRawRequestWithTokenR307`), в прогреве через `/load` и в обоих транспортных
  путях прокси, включая ретраи. Клиентский токен (токен балансера) воркеру не
  годится, поэтому заголовок клиента ПЕРЕЗАПИСЫВАЕТСЯ токеном воркера.

**Проверка живьём** (образы `balancer:c4fd8628`, `cppworker:gpu-c4fd8628`):

| # | Проверка | Результат |
| --- | --- | --- |
| S1 | `POST :18092/api/models/load` без токена | **401** (было: загрузка принималась) — PASS |
| S2 | `POST :18092/api/models/unload?name=…` без токена | **401** — PASS |
| S3 | `POST :18092/api/models/load` с токеном | запрос дошёл до обработчика (400 на кривое тело) — PASS |
| S4 | загрузка через балансер (`POST /api/v1/backends/<id>/models`) | `success:true`, модель загружена за 71 c — PASS (балансер предъявляет токен) |
| S5 | клиентский unload через 18080 (`/api/models/unload`) | `200 {"status":"unloaded"}`, модель ушла с воркера — PASS (прокси перезаписал токен) |
| S6 | восстановление стенда загрузкой через балансер | модель `loaded ctx=32768`, чат `200` за 1 c — PASS |

**Не проверено живьём:** путь прогрева `/load` (репликация/префарм) — он
вызывается только при репликации/прогреве и покрыт юнит-тестами; и
`/api/models/refresh` оставлен открытым осознанно (это повторное сканирование
каталога, не изменение памяти/диска).

**Сторожа.** `worker_admin_routes_r307_test.go` парсит `router.go`: каждый
обработчик, меняющий память/диск, обязан быть под `authMiddleware`, и каждый
закрытый маршрут обязан быть в таблице — новая ручка без обёртки ломает тест, а
не открывает дыру молча. На стороне балансера — сторож согласованности двух
списков: если воркер закрыл маршрут, который балансер не считает
административным, тест падает (иначе загрузка модели сломалась бы на живом
стенде).
