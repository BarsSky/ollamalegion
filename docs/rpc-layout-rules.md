# Правила раскладки слоёв (RPC): один коммит, своя архитектура, явный флаг

Документ фиксирует правила, добытые живыми прогонами на двух машинах
(мастер `192.0.2.20`, узел `192.0.2.10`). Это не теория: каждое правило
стоило падения процесса с `SIGABRT`, и каждое имеет наблюдаемый признак.

## 1. Узел допускается, только если совпали коммит И архитектура

Раскладка работает поверх `ggml-rpc`: мастер и узел обмениваются структурами
`ggml_tensor` и командами бэкенда. Требуется одновременно:

* **один и тот же коммит llama.cpp** на обеих машинах;
* **ядра CUDA под видеокарту каждой машины** — в бинарнике узла должен быть его
  `sm_XX`, в бинарнике мастера — свой.

Проверка (обе команды обязаны быть > 0 и относиться к *своей* карте):

```bash
docker exec <контейнер> grep -a -c sm_86  /app/rpc-server   # мастер, RTX 3070
docker exec <контейнер> grep -a -c sm_120 /app/rpc-server   # узел,  RTX 5060
```

**Живые симптомы нарушения.**

| Что сделали | Что увидели |
|---|---|
| На узел поставили бинарник мастера (сборка только `sm_86`) | Загрузка заходит дальше (`offloaded 16/66`, буферы `CUDA0 2116 MiB`, `RPC0 2246 MiB`), затем `ggml-rpc.cpp:823: Remote RPC server crashed or returned malformed response` → `SIGABRT`. Узел при этом жив и молчит. |
| Узел со своей сборкой, но **другого коммита** (`gpu-rpc120` от 11 окт против `1d2869c6e`) | То же самое: буферы размещаются, первая же RPC-операция не разбирается, мастер падает, у узла `RestartCount=0`. |

`RPC_STATUS_ASSERT` (`ggml-rpc.cpp:30`) — это не «узел упал», а «ответ не
разобран»: llama.cpp на такое отвечает `abort()`, поэтому предсказуемого отказа
без вмешательства быть не может — узел надо отсекать ДО раскладки.

**Практика: один образ на все машины.** `CUDA_ARCH=86;120` и
`CUDA_VERSION=12.8.0` в `deployments/.env`, сборка одна, запускается и на
мастере, и на узле (`deployments/docker-compose.rpc-node.yml` берёт тот же
`CPPWORKER_GPU_TAG`). Тогда совпадают и коммит, и (при наличии обоих наборов
ядер) архитектура, а узел начинает нести `CPPWORKER_LLAMA_BUILD` — иначе он
отдаёт пустой `buildInfo`, и проверка версии слепа.

Две ловушки сборки, обе уже стоили времени:

* дефолт `CUDA_ARCH=all` в `docker/cppworker/Dockerfile.gpu` — это
  `50;61;70;75;80;86;89;90`, **без `120`**; «all» здесь не спасает;
* дефолт `CUDA_VERSION=12.2.0` не знает `sm_120` вовсе; нужен `12.8.0`
  (драйвер 617.42 на обеих машинах это умеет);
* дефолтное зеркало `dockerhub.timeweb.cloud` на образе `12.8-devel` (~6 ГБ)
  практически останавливает сборку (50+ минут, почти нулевой CPU).
  Обход: `CUDA_BASE=mirror.gcr.io/nvidia/cuda` (build-arg появился в R115).

## 2. Выключение раскладки — флагом, и флаг решающий

```bash
CPPWORKER_RPC_ENABLE=false      # раскладки нет: ни одного dial'а к узлам
CPPWORKER_RPC_SERVERS=          # список можно не стирать — он будет очищен
```

До R115 непустой `CPPWORKER_RPC_SERVERS` **силой включал** режим, поэтому
`RPC_ENABLE=false` не работал: мастер продолжал дозваниваться до узлов и
планировать по их памяти. Теперь явный `false` выигрывает и очищает список;
если флаг не задан, поведение прежнее (непустой список включает раскладку).

«Выключено» означает именно это: узлы не попадают ни в параметры моста, ни в
бюджет памяти, ни в сторожевые проверки; планирование идёт по локальной карте.
Единственный способ выключить режим — не «стереть список узлов», а поставить
флаг.

## 3. Ёмкость раскладки: итог и состав

`available_vram_mb` в `/api/models` — это **итог** (локальная карта + узлы), так
его считает `memfit`. По одному числу нельзя понять, откуда гигабайты, поэтому
R115 отдаёт состав отдельными полями:

```
rpc_enabled, rpc_servers_active, vram_remote_nodes,
vram_local_free_mb, vram_local_total_mb,
vram_remote_free_mb, vram_remote_total_mb,
vram_layout_free_mb, vram_layout_total_mb
```

Их читают балансер (в метрики бэкенда) и WebUI. Недоступный узел из бюджета
исключается автоматически: `available_vram_mb` падает до локальной карты, то
есть «номинальная ёмкость» не переживает падение узла.

Узел с **нулевой свободной памятью** в раскладку не берётся вовсе: раньше ему
принудительно давали минимум 5% («узел не должен выпасть»), и llama.cpp пытался
положить туда слои, которых карта не вмещает.

## 4. Более двух машин

Код не двухместный: список узлов — до 16 адресов (`CPPWORKER_RPC_SERVERS`,
`host:port` через запятую), планировщик читает до 32 устройств, пропорции
считаются по всем устройствам (мастер + N узлов) с суммой 1.0, `main_gpu`
остаётся локальным. Порядок устройств для llama.cpp: сначала локальные, затем
узлы — в том же порядке, в каком посчитан `tensor_split`.

## 5. Настройка из WebUI

Вкладка параметров бэкенда (GGUF) → блок «Раскладка слоёв между машинами»:
галочка режима и список узлов (по одному `host:port` в строке). Значения
уходят в `PUT /api/v1/cppworker/config/update` как `rpcEnabled` / `rpcServers`
и **применяются при следующей загрузке модели** — ответ несёт
`rpc_reload_required`, и WebUI говорит это оператору прямо. Смена раскладки не
перезагружает модель молча: это минуты простоя.

## 6. Кто назначает доноров и кто поднимает узел (R132/R133, 2026-10-16)

Раздел 5 описывал ручную настройку списка узлов. Начиная с R133 источник правды —
**роль бэкенда в панели**, а не `.env` и не список в форме:

| Что | Кто решает | Где видно |
|---|---|---|
| кто донор, кто главный, кто самодостаточен | оператор в панели (`PUT /api/v1/backends/{id}/role`) | селектор роли в строке бэкенда |
| состав списка узлов у главного | балансер (собирает из ролей, проверяет живость, выключает раскладку, если живых нет) | `rpcLayout` в `/api/v1/backends` |
| поднят ли `rpc-server` НА САМОМ доноре | балансер отправляет донору приказ (`rpcServerEnabled=true`) | `rpcNode` в `/api/v1/backends` |
| переживёт ли решение пересоздание контейнера | файл операторских переопределений воркера (приоритет над env) | `/api/v1/cppworker/config` |

Почему так. Роль `donor` до R133 работала в одну сторону: главному список узлов
отправлялся, а сам донор не получал ничего — его `rpc-server` поднимали руками
(`CPPWORKER_RPC_SERVER_ENABLED=true` на донорской машине или тумблером на месте).
Плюс `.env` со `CPPWORKER_RPC_ENABLE=true` и адресом донора при каждом
пересоздании контейнера возвращал мастера к СТАРОМУ узлу, включая выключенный.
Оператор видел «роль есть, узел не работает» и не понимал, какой параметр
обязателен.

Правила, которые из этого следуют:

* `CPPWORKER_RPC_ENABLE` / `CPPWORKER_RPC_SERVERS` в `.env` для обычной работы
  **не нужны**: они остались аварийным бутстрапом для стенда без ролей.
* Балансер управляет узлом **только** у бэкендов с ролью `donor` и гасит узел
  **только там, где поднимал его сам**: ручной тумблер оператора на остальных
  бэкендах не оттаптывается.
* «Поднят» и «доступен» — разные утверждения. Узел может слушать порт ВНУТРИ
  контейнера и быть недостижимым с балансера (порт не опубликован при запуске
  контейнера). Поэтому статус несёт три поля (`running`, `listening`,
  `reachable`) и причину словами; публикацию порта из панели изменить нельзя —
  это свойство запуска контейнера.
* Справочные пути (`GET /api/models`, `GET /api/models/effective`) **не
  дозваниваются** до узлов вообще (R132): вклад узлов берётся из последнего
  собранного снимка, а поле `vram_remote_source` различает `none` («на этом пути
  узлы не измерялись»), `cache` и `probed`. Дозвон остался только на пути
  решения — там ёмкость донора нужна как основание.

## 7. Живая причина падений — ВТОРОЕ соединение к узлу (не версии)

Раздел 1 утверждает требование «один коммит + своя архитектура», и оно остаётся
верным требованием к поставке. Но **наблюдавшееся падение объяснялось не им**, и
это проверено прямым экспериментом: мастер и узел были переведены на ОДИН образ
(коммит `1d2869c6e`, архитектуры `86;120`), и падение повторилось с тем же
стеком. Версию пришлось снять.

Что оказалось на самом деле. Строка, на которой падал процесс:

```c
static void get_device_memory(...) {
    bool status = send_rpc_cmd(sock, RPC_CMD_GET_DEVICE_MEMORY, ...);
    RPC_STATUS_ASSERT(status);        // ggml-rpc.cpp:823
```

Это **запрос памяти устройства**, то есть наша собственная фоновая проверка
бюджета, а не перенос весов:

```
load_tensors:   CPU_Mapped model buffer size = 10993.98 MiB
load_tensors:        CUDA0 model buffer size =  2116.47 MiB
load_tensors: RPC0[192.0.2.10:50052] model buffer size =  2246.03 MiB
ggml-rpc.cpp:823: Remote RPC server crashed or returned malformed response
```

Буферы размещены, а падает следующий же запрос — который сделал не загрузчик.
`rpc-server` обслуживает соединения по одному; пока мастер грузил модель (держа
своё соединение), фон открывал второе и получал неразобранный ответ. llama.cpp
на это отвечает `RPC_STATUS_ASSERT` -> `GGML_ABORT`, то есть падением процесса,
а узел при этом жив и молчит (`RestartCount=0`).

**Правило.** Пока идёт загрузка модели или инференс, до узлов раскладки
**дозваниваться нельзя** — ни за памятью, ни за чем-либо ещё. Реализовано в
`layoutBusy()` + `rpcDeviceSnapshot` (`internal/cppbackend/`): во время работы
берётся только уже собранный снимок, а если его нет — локальные устройства без
RPC (бюджет консервативнее, зато процесс жив). Проверяется тестом со
слушателем, считающим входящие соединения: при загрузке и при активном
инференсе их ноль.

**Практический вывод.** Плоский TCP-порт узла (проверка доступности) безвреден:
это `connect`, а не RPC-команда. Опасны именно вызовы, которые говорят с
`rpc-server` по протоколу — сбор памяти устройств и всё, что ходит через мост.

## 8. Эксплуатационная заметка: кэш сборки CUDA вытесняется

Пересборка образа после правки только в Go всё равно компилирует `ggml-cuda`
заново (наблюдалось: 29% и ~1.5 ч), потому что CUDA-слои весом в десятки
гигабайт вытесняются из кэша Docker. Если правка не касается C/CUDA, дешевле не
пересобирать весь образ; но `rpc-server` и `cppworker` линкуются из одного
дерева, поэтому отдельного «быстрого» пути для Go-правки в этом образе нет.

## 9. Допуск узла по версии (R115): несовпавший коммит - не «попробуем», а отказ

Правило из раздела 1 перестало быть советом и стало проверкой в коде
(`internal/cppbackend/rpc_version_gate_r115.go`).

**Откуда мастер узнаёт версию узла.** `rpc-server` не отдаёт HTTP, поэтому
спрашивается **cppworker-поверхность узла**: `GET /api/v1/cppworker/config` ->
`config.llamaBuild` (то же значение, что печётся в образ как
`CPPWORKER_LLAMA_BUILD`). Таймаут 1.5 с, кэш 120 с: версия меняется только при
обновлении образа узла, а снимок устройств берётся раз в 30 с.

**Что происходит:**

| Коммит узла | Решение |
|---|---|
| совпал с коммитом мастера | узел в раскладке (`version_match`) |
| не совпал | узел ИСКЛЮЧЁН, в логе `version_mismatch: <узел> != <мастер>` |
| неизвестен (узел недоступен или не отдал поле) | исключён; снимается явным `CPPWORKER_RPC_ALLOW_VERSION_UNKNOWN=true` |
| мастер сам не знает своей версии | не судим (иначе отказали бы всем узлам сразу) |

Важно: **несовпадающий коммит не допускается никогда**, даже при
`ALLOW_VERSION_UNKNOWN` - исключение сделано только для «неизвестно».

**Порт узла** задаётся `CPPWORKER_RPC_NODE_HTTP_PORT` (по умолчанию 18092), потому
что cppworker-поверхность узла может слушать не стандартный порт.

**Зачем это.** Раньше несовпадение коммитов приводило к `GGML_ABORT` - падению
мастера при живом и молчащем узле (раздел 1). Теперь такой узел просто не
участвует в раскладке, а причина видна в логе одной строкой. Порядок остальных
узлов сохраняется: он же порядок устройств для `tensor_split`.


## 10. Есть ли выигрыш от раскладки? Замер на qwen3.8 (R231, 2026-10-24)

Правила выше отвечают «можно ли раскладывать». Этот раздел — «стоит ли»: живой
замер на одной модели, одинаковом запросе и двух режимах (`rpc-layout=off`/`on`).

Стенд: мастер 8 ГБ VRAM + донор 8 ГБ VRAM, канал ≈8.9 Гбит/с, модель
`Qwen3.8-27B-UD-Q4_K_M` (15.33 GiB), `ctx=16384`, KV `q8_0`, запрос 96 токенов.

| Метрика | off | on | Δ |
|---|---|---|---|
| Раскладка | CUDA0 20/66, CPU 46 | CUDA0 26 + RPC0 22 = 48/66, CPU 18 | +28 слоёв на GPU |
| Загрузка | 278 с | 285 с | +2.5 % |
| 96 токенов | 126–147 с | 45–49 с | — |
| Скорость | 0.65–0.77 tok/s | 1.95–2.15 tok/s | **≈ ×2.9** |
| Задержка | 136 с | **46 с** | **−66 %** |

Вывод: на быстром канале раскладка даёт **≈2.9× по генерации** почти без
удорожания загрузки; на медленном канале (сотни Мбит/с) возможен регресс, поэтому
перед включением измеряйте канал (кнопка «Замерить» / `POST .../measure-link`).
При выключении/потере узла гард возвращает локальную загрузку (раздел 2).

Методика, воспроизведение и ограничения — [rpc-benchmark-qwen38.md](rpc-benchmark-qwen38.md);
скрипт — `scripts/bench-rpc-qwen38.ps1 -Mode both`.
