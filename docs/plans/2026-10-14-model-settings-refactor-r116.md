# R116 — Рефактор настроек моделей: профиль как источник истины, видимый приоритет и честная проверка памяти

Статус: спецификация принята (владелец проекта, 2026-10-14). Реализация — по шагам ниже.

## 1. Что не так сейчас

На странице «GGUF models» в одном списке лежат поля **четырёх разных слоёв**, и выглядят они одинаково:

| Слой | Поля | Когда действует |
|---|---|---|
| Дефолты для будущих загрузок | `defaultCtxSize`, `defaultGpuLayers`, `defaultKvCacheType`, `defaultEnableReasoning`, `defaultReasoningBudget` | только при **следующей** загрузке |
| Runtime бэкенда | `enableReasoning`, `reasoningBudget`, `idleUnloadMinutes`, `enableMetrics` | сразу, без перезагрузки |
| Load-affecting (запускают авто-reload) | те же `default*`, `autoGpuDistribution`, `tensorSplitStrategy` | по сохранению — авто-reload всех загруженных |
| Профиль модели (`profileSyncer`, `config/cppworker-*.json`) | ctx, слои, kv, split, reasoning | при загрузке; **перебивает** конфиг |

Наблюдаемые симптомы (жалоба владельца):

1. непонятно, где применится настройка: при сохранении, при перезагрузке или «когда-нибудь»;
2. нет понятного действия «применить к текущей загруженной модели»;
3. «явное переопределение настроек дефолтом для gemma4» — это невидимый в UI профиль модели, у которого приоритет выше конфига;
4. флаг размышлений где-то сработал, но непонятно где (два разных поля: runtime `enableReasoning` и `defaultEnableReasoning` для загрузки);
5. контекст не совпадает с явно указанным в настройках (у загруженной модели действует профиль/запрос, а не `defaultCtxSize`);
6. по кнопке «перезагрузить» не видно, чья модель и какие параметры будут применены;
7. загрузка из вкладки «Модели» идёт не по тем параметрам, что на странице настроек (вкладка шлёт UI-состояние `state.loadOptions`, страница пишет `default*` в конфиг бэкенда).

## 2. Целевая семантика (решение владельца)

**Приоритет ровно один и видимый:**

```
параметр запроса  >  профиль модели  >  дефолт бэкенда
```

* Профиль модели — **источник истины** для параметров загрузки конкретной модели.
* Дефолт бэкенда — только отправная точка, в том числе «маленький контекст по умолчанию для тяжёлых моделей».
* **Последнее слово за пользователем**: если он задал значение в профиле, оно применяется как задано; система не подменяет его молча.

## 3. Контракт проверки памяти (главное требование)

Проверка обязана оценивать **ту конфигурацию, которую задал пользователь** (профиль/запрос), и честно сказать, влезает ли она в суммарную память.

1. Вердикт считается тем же расчётом, что и загрузка: `memfit` (`internal/memfit` через `internal/cppbackend/memfit_adapter.go`) — единый источник, второй формулы быть не должно.
2. Если **не влезает совсем** → отказ до загрузки, HTTP 422 `n_ctx_infeasible`, с полем `memory_breakdown` (R115: VRAM локальная + узлы, RAM, лимит cgroup, веса, KV, потолки n_ctx) и подсказкой, какой рычаг помогает (уменьшить ctx / kv q4_0 / меньше слоёв).
3. Если влезает **с выгрузкой в RAM** (partial_offload/cpu_only) → загрузка **разрешается**, но предупреждение показывается явно: какая часть на CPU, сколько это RAM, что будет медленнее. Сейчас это уже сообщается (`n_ctx_degraded`, `max_exact_fit_n_ctx`), но не видно в UI.
4. **Автоуменьшение контекста не должно быть молчаливым.** `calculateLazyLoadOpts` умеет урезать n_ctx (`reducing n_ctx for cpu-only offload`); в UI это обязано быть видно как «запрошено 32768 → загружено 8192, причина: не хватает VRAM», иначе это ровно та «подмена настроек», на которую жалуется владелец.

## 4. Целевой UI вкладки «Настройки» (GGUF)

Три блока вместо одной простыни, у каждого — подпись «когда действует»:

1. **«Загруженная модель (сейчас)»** — что реально применено: ctx, слои, kv, раскладка, reasoning, и **источник каждого значения** (запрос / профиль / дефолт). Здесь же — предупреждение о памяти по разделу 3.
2. **«Профиль модели»** — редактирование профиля с явным выбором модели в заголовке («Профиль: gemma-4-E4B-it-Q4_K_M»). Кнопка **«Применить к загруженной модели»** — перезагрузка **именно этой** модели с показом целевых параметров до запуска.
3. **«Дефолты бэкенда (для моделей без профиля)»** — то, что сейчас на странице.

Дополнительно:

* кнопка перезагрузки подписана моделью и её контекстом: «Перезагрузить gemma-4 (ctx 8192)»;
* «Сохранить» отчитывается, что применено сейчас, а что — с следующей загрузки;
* вкладка «Модели» при загрузке отправляет **профиль** модели, а UI-состояние остаётся только черновиком формы (иначе расхождение воспроизводится снова).

## 5. API, которое для этого нужно

| Метод | Назначение |
|---|---|
| `GET /api/models/{name}/effective` | эффективные параметры + источник каждого + вердикт по памяти (из memfit) |
| `GET/PUT /api/models/{name}/profile` | чтение/запись профиля модели (источник истины) |
| `POST /api/models/{name}/reload` | перезагрузка конкретной модели с её профилем, с отчётом запрошено/применено |

Первым делом — `effective`: он даёт ответ на вопрос «почему контекст не тот» без перезагрузки и без гаданий.

## 6. Порядок работ

1. **Сервер:** `GET /api/models/{name}/effective` (профиль + вердикт memfit + источники). Тесты: профиль перебивает дефолт; запрос перебивает профиль; отказ 422 с `memory_breakdown`; видимое автоуменьшение ctx.
2. **Сервер:** `GET/PUT /api/models/{name}/profile`; при записи — та же проверка памяти, что и при загрузке.
3. **Сервер:** `POST /api/models/{name}/reload` с отчётом «запрошено → применено».
4. **WebUI:** три блока по разделу 4 на `effective`/`profile`; кнопка перезагрузки с именем модели; вкладка «Модели» шлёт профиль.
5. **Проверка живьём** на gemma4: (а) профиль перебивает дефолт и это видно; (б) пользователь задаёт ctx больше доступного → 422 с раскладкой памяти; (в) ctx влезает с выгрузкой → предупреждение и явное «запрошено/применено».

### Настоящая причина путаницы

Одни и те же параметры правятся в **трёх местах** с разным смыслом:

1. «Настройки → Профили» — профиль модели (приоритет 1, источник истины);
2. GGUF-страница, секция профилей (`gguf.profiles_section_*`) — второй вход в то же;
3. GGUF-страница, параметры загрузки — это **дефолты бэкенда** (`defaultCtxSize`), слабее профиля.

Отсюда: «непонятно, где применится», «перетёрло дефолтом для gemma4» (профиль
`contextLength: 8192` + `defaultProfile` против дефолта `65536`), «перезагрузить —
чьей модели?», «вкладка Модели грузит не по тем параметрам» (шлёт UI-состояние
`state.loadOptions`, а не профиль). Имена полей тоже разные: профиль —
`contextLength`/`numGpuLayers`/`kvCacheType`, конфиг — `defaultCtxSize`/….

### Скорректированный порядок работ

1. **Проверка памяти на записи/применении профиля** (единственная реально
   отсутствующая серверная часть). Точка: обработчик `PUT /api/v1/cppworker/model-profiles/{name}`
   и `POST …/{name}/apply` в балансере. Вердикт брать тем же расчётом, что и
   загрузка: либо запросом к cppworker `GET /api/models/effective?model=…&ctx=…&kvCacheType=…`
   (новый эндпоинт R116, отдаёт `memory.stage`/`feasible`/`memory_breakdown`),
   либо существующим preflight-расчётом балансера. Не влезает → отказ 4xx с
   раскладкой; влезает с выгрузкой → предупреждение в ответе и в UI.
2. **Убрать дубли в UI.** Профили — только в «Настройках»; на GGUF-странице
   оставить просмотр «что применится» (из `effective`) + ссылку «править профиль»;
   блок дефолтов переименовать в «Дефолты для моделей без профиля» и отделить.
3. **Вкладка «Модели»** отправляет профиль модели, UI-состояние — только черновик формы.
4. **Применение профиля** — кнопка с именем модели и целевым контекстом, отчёт
   «запрошено → применено» (включая видимое автоуменьшение ctx из `calculateLazyLoadOpts`).

**Форма проверки:** после `validateModelProfile` вызвать у бэкенда
`GET <cppworker>/api/models/effective?model=<name>&ctx=<incoming.ContextLength>&kvCacheType=<incoming.KVCacheType>`
и по ответу:

* `memory.feasible == false` → 4xx, профиль НЕ сохранять, в ответ положить
  `memory_breakdown` и `suggestion` (это ровно та же раскладка, что уходит при
  отказе загрузки, — второй формулы нет);
* `memory.degraded == true` → сохранить, но вернуть `warning` с пояснением
  («часть слоёв на CPU, будет медленнее») и показывать его в UI;
* иначе — как сейчас.

## 10. Что осознанно НЕ делаем



* не вводим второй расчёт памяти (только memfit);
* не «чиним» расхождение подстановкой значений в UI — расхождение устраняется тем, что источник истины один (профиль), а не тем, что UI показывает другое число;
* не убираем автоуменьшение ctx — оно полезно, но обязано быть видимым и объяснённым.
