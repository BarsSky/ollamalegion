# Порядок выбора бэкенда: что заложено и как реализовать `leastconn` (R493)

**Дата:** 2026-11-17. **Связанные документы:** `docs/architecture/debts.ru.md` 12n,
`docs/architecture/balancing-guide.md` §2.1, `docs/plans/2026-11-16-product-decisions-r493.md` §1.

---

## 1. Решение владельца (2026-11-17)

Поле `balancing.algorithm` / `LB_ALGORITHM` **удалено полностью** — и из API, и из
UI. Совместимость со старыми конфигами не нужна: стенд один и обновляется целиком.

Почему это правильнее «оставить и предупредить»: поле обещало переключатель,
которого нет (выбор один — `unified-multistage`), а WebUI предлагал пять
вариантов, из которых три сервер отвергал с 400, а два принимаемых нельзя было
выбрать. Прозрачность (warn + `effectiveAlgorithm`), сделанная в R493 до этого,
объясняла отсутствие эффекта, но не убирала ложный выбор из интерфейса.

Дополнительно решено **заложить реализацию рекомендованного варианта** — `leastconn`
— так, чтобы включение было осознанным шагом, а не переписыванием селектора.

## 2. Что уже реализовано (и проверено)

### 2.1 Шов порядка выбора

`internal/balancer/selection_order_r493.go`:

- `LB_SELECTION_ORDER` — режим порядка:
  - `unified` (по умолчанию) — порядок задаёт fit по VRAM (прежнее поведение);
  - `leastconn` — среди **уже допущенных** кандидатов первым идёт узел с меньшим
    числом активных запросов; при равенстве сохраняется порядок fit по VRAM;
  - неизвестное значение → `unified` + **одно** предупреждение в лог (не молча).
- `orderCandidatesForSelectionR493(candidates, model)` — единственная точка, где
  применяется порядок. Вызывается из `pickLoadableFreeBackendR493`
  (`internal/balancer/availability_first_r493.go`), то есть **после** фильтров
  (тип, здоровье, выключенность R250, донор R304, каталог модели) и **до**
  проверок слота/image-gate.
- Функция может только **переставить** элементы: длина и состав не меняются —
  это проверяется тестом `TestR493_SelectionOrderKeepsCandidates`.

### 2.2 Что этим НЕ меняется (важно)

Порядок — не правило допуска. Все инварианты остаются в силе и проверяются
своими тестами:

| Инвариант | Где |
|---|---|
| Отказ по окну только если промпт не влезает (R447) | `window_serve_as_is_r447.go` |
| Холодный кандидат: «неизвестно» ≠ «нет» (R480) | `cold_candidate_ttl_r480.go` |
| Выключенный оператором узел не выбирается (R250) | `backend_disable_r250.go` |
| Донор раскладки не держит своих копий (R304) | `cannotHostModelR304` |
| Сессионная привязка и кэш префилла (R83/R459) | `session_*`, `selectBackend` |

### 2.3 Тесты и что ими закрыто

`internal/balancer/selection_order_r493_test.go`:

- дефолт (`unified`) не меняет порядок;
- `leastconn` ставит менее занятый первым (3/0/7 → `b,a,c`);
- при равной занятости сохраняется исходный порядок;
- состав и количество кандидатов не меняются, пустой/одиночный вход безопасен;
- неизвестное значение флага → `unified` + одно предупреждение;
- таблица значений (`""`, `unified`, `UNIFIED`, `leastconn`, `roundrobin`).

Мутация: инверсия компаратора в `leastconn` роняет тест порядка.

## 3. Что осталось (полноценный режим)

Сейчас `leastconn` влияет на путь «выбор свободного узла под загрузку модели»
(`pickLoadableFreeBackendR493`). Полноценный режим — это единый порядок для ВСЕХ
точек выбора. Ниже перечень и требования к каждой.

### 3.1 Точки выбора (аудит)

| Точка | Файл:функция | Что делает сейчас |
|---|---|---|
| P1 (загруженные) | `backend_selector.go:236-277` `selectBackend` | перебор группы со скорингом `calculateScore`, порог нагрузки `loadThresholdR479` |
| Реплики | `selectBackend` (репликатор) | выбирает сам, раньше общего пути |
| Sharded-мастер | `shardedMasterForRequestR92` | возвращает мастера группы, общий путь не участвует |
| P3/P4 (свободные/fallback) | `availability_first_r493.go` `pickLoadableFreeBackendR493` | **уже проходит через шов** |
| Resource-scoring | `backend_selector.go:1044` `selectByResources` | свой порядок со скорингом |
| Least-loaded с моделью | `backend_selector.go:643` `findLeastLoadedBackendWithModel` | свой порядок по `loadRatio` |
| Модель-копия под загрузку | `model_catalog.go:639` | свой порядок |

### 3.2 Что изменится при полноценной реализации

1. Ввести `orderCandidatesForSelectionR493` во все точки из §3.1 (кроме
   реплик/мастера — они выбирают не по общему пулу).
2. Для `leastconn` определить метрику: `state.ActiveReqs` (сейчас) или
   `ActiveReqs / EffectiveMaxConcurrentRequests()` (нормированная занятость).
   Второе честнее для разнородных узлов — решить на замерах.
3. Сохранить существующие пороги/гейты: порядок не отменяет `loadThresholdR479`
   и проверку слота.
4. Тесты-инварианты (обязательны, иначе вернёмся к «двум мозгам»):
   - `leastconn` не выбирает узел без свободного слота;
   - `leastconn` не выбирает выключенный/донор/чужой тип;
   - `leastconn` не отменяет отказ по окну (R447);
   - сессионная привязка сохраняется (R83);
   - при равной занятости результат детерминирован (id как последний тай-брейк).
5. Наблюдаемость: по одной Info-строке на смену порядка (как сейчас
   `selection order: leastconn`), плюс поле `selectionOrder` в `/api/v1/cluster/config`
   и в `diag/summary`.
6. Доки: `balancing-guide.md` §2 (описать режимы), `env-vars` (значения и дефолт).

### 3.3 Чего делать НЕ надо

- **Не возвращать поле в конфиг/API.** Порядок — это свойство процесса, а не
  профиль модели; возврат поля снова создаст «настройку без эффекта», если
  селектор один.
- **Не реализовывать `roundrobin` и `weighted`.** Замеров, где они лучше текущего
  выбора, нет; текущий учитывает окно и занятость, а «равномерный» round-robin
  на разнородных узлах даст очередь на слабом.
- **Не дублировать фильтры** внутри порядка: порядок применяется к уже
  допущенным кандидатам.

## 4. Как проверить, что `leastconn` не сломал стенд

1. `LB_SELECTION_ORDER=unified` (дефолт) — поведение и распределение не меняются;
   это же подтверждает весь существующий набор тестов селектора.
2. `LB_SELECTION_ORDER=leastconn` — на двух-трёх узлах с разной занятостью
   ожидаем: новые запросы идут на менее занятый узел; в логе
   `selection order: leastconn`.
3. Инвариант «не добавились узлы»: в логе порядок содержит те же id, что и
   кандидаты до шва (см. `TestR493_SelectionOrderKeepsCandidates`).
4. Откат — одна переменная окружения; перезапуск не обязателен (читается на
   каждом вызове).

## 5. Итог

- Поле-«пустышка» удалено из API, env, WebUI, экспорта/импорта и диагностики.
- Шов и рекомендованный порядок (`leastconn`) реализованы, выключены по
  умолчанию, покрыты тестами и мутацией.
- Полноценный режим (все точки выбора, нормированная занятость) — задача
  следующего шага; критерии приёмки перечислены в §3.2.
