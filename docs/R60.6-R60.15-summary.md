## R60.7 — SSE `/api/v1/events` no longer drops at 60s

**Bug**: API server (port 18081) had `WriteTimeout: 60s`. Go's `http.Server.WriteTimeout` is the ABSOLUTE deadline for the response lifetime, NOT reset on each Write. So SSE streams died at exactly 60s (5 pings × 10s + headers ≈ 60s).

**Fix** (`internal/api/handlers_events.go`, `handlers_cppworker_apply_async.go`, `gguf_backend_proxy.go`):
```go
rc := http.NewResponseController(w)
if err := rc.SetWriteDeadline(time.Time{}); err != nil { /* log */ }
// ... rest of handler writes to w ...
```
Call BEFORE first write. `time.Time{}` = no deadline = stream lives until client disconnect.

**Live E2E**: 14 pings in 150s (was: drop at 60s). Also removed `Connection: keep-alive` header (HTTP/2 forbids it per RFC 7540 §8.1.2.2).

## R60.6 — Load timeout + double-load fix

**Bug 1 — Reload killed at 90s**: `nctx_reload_handlers.go:226` hardcoded `http.Client{Timeout: 90 * time.Second}`. cppworker received `?waitTimeoutSec=300` but http.Client aborted at 90s with "Client.Timeout exceeded while awaiting headers".

**Fix A**: `http.Client.Timeout = cfg.effectiveTimeout() + 30s` (default 300s, max 600s).

**Bug 2 — Retry-After hardcoded 30s**: `effectiveAsyncRetryAfter` clamped to max 30s. For 5GB+131072 n_ctx on 8GB VRAM, reload takes 60-180s, client retry at 30s triggered cascading reloads.

**Fix B**: `nctx_reload.go:159` — raised max clamp to 120s. New field `PreflightAsyncRetryAfterMaxSec` (env override `LB_NCTX_RELOAD_PREFLIGHT_ASYNC_RETRY_AFTER_MAX_SEC`).

**Fix C**: New `EstimatedRetryAfter` field in `PreflightResult`. `EstimateReloadTimeMs(modelSize, nCtx)` heuristic mirrors cppworker's formula. cppworker's `estimatedLoadTimeMs` from 202 body preferred; heuristic fallback.

**Bug 3 — Double-load cascade**: `preflight_nctx.go:578` async goroutine didn't register in `reloadDedupRegistry`. Each retry triggered new reload.

**Fix D**: Use `c.reloadDedup.StartReloadIfNotPending(backendID, modelName, targetNCtx, func)` instead of `c.DoReload` directly. Subsequent prefights see `IsReloadPending=true` and return 503 with same Retry-After.

**Also**: smart-skip guard in OLD `preflightNCtxReloadIfNeeded` (line 416+) checks `IsReloadPending` at top to prevent streaming path from bypassing dedup.

**Live E2E**: `Retry-After: 42` (from estimate, was 30), `model_size: 2497281120`, dedup marker on 2nd request.

## R60.10 — Upstream 4xx passthrough + OpenAI/Ollama error format

**Bug**: Balancer ALWAYS wrapped upstream errors in 502 + Ollama-format body, even for `/v1/*` endpoints. OpenAI clients retry on 502 but not on 404 → infinite retry loops. Also lost useful error info.

**Fix** (`internal/balancer/llamacpp_translate_req.go` + `llamacpp_transport{,_nonstream}.go`):
- `isOpenAIPath(path)` helper — true for `/v1/*`.
- **4xx (incl. 408/429 transient)**: pass through upstream body AS-IS, preserve status code. Set `X-Upstream-Request-Id` for tracing.
- **5xx**: wrap in 502. Format based on `originalPath`:
  - `/v1/*` → OpenAI: `{"error":{"message":...,"type":"upstream_error","code":N}}`
  - `/api/*` → Ollama: `{"model":"","done":true,"done_reason":"error","error":"...","message":{}}`
- Also fixed duplicate `X-Request-Id` (R60.15) in 200 OK path.

**Live E2E**: `GET /v1/models/nonexistent` → 404 + cppworker body (was 502 + Ollama wrapper).

## R60.12 — AutoTune `cpu_only` Warnw log

**Bug**: When client's `n_ctx` exceeds VRAM (even with partial offload), cppworker's adaptive strategy picks `stage="cpu_only"` → KV-cache in system RAM → 60-180s load. INFO-level log was easy to miss in log flood.

**Fix** (`cmd/cppworker/adaptive_loader.go:84`):
- Upgraded Info to **Warnw** when `stage == "cpu_only"`.
- Includes model, target_n_ctx, gpu_layers, kv_cache_type.
- Recommendation in log: "for 8GB VRAM, use n_ctx <= 65536 with kvCacheType=q4_0".
- Plus documentation: `docs/R60.12-cpu-only-strategy.md` (limit table per model size for 8GB VRAM).

## R60.13 — `cpu_only` n_ctx safety clamp (default 65536)

**Bug**: `SelectStrategy`'s cpu_only branch computed `maxNCtx` from `safeVRAM + safeRAM`. On 8GB VRAM + 16GB RAM, `maxNCtx = 200K+`. Model would load with the user's requested n_ctx (e.g. 131072), KV-cache (48GB) goes to RAM, load takes 5+ min.

**Fix** (`cmd/cppworker/adaptive_loader.go:656`):
```go
cpuOnlyMaxNCtx := int64(65536)
if envMax := os.Getenv("CPPWORKER_CPU_ONLY_MAX_NCTX"); envMax != "" {
    if v, _ := strconv.ParseInt(envMax, 10, 64); err == nil {
        cpuOnlyMaxNCtx = v
    }
}
if cpuOnlyMaxNCtx > 0 && int64(finalNCtx) > cpuOnlyMaxNCtx {
    logger.Warnw("SelectStrategy: cpu_only n_ctx clamped (R60.13)", ...)
    finalNCtx = int(cpuOnlyMaxNCtx)
}
```

Operator override via `CPPWORKER_CPU_ONLY_MAX_NCTX` env var. `0` disables clamp (legacy behavior, use with caution).

**5 unit tests**: Default, EnvOverride, Disabled, NonMoE_NotAffected, EnvInvalid.

**Note**: This is a SAFETY NET. For typical 5GB Qwen3-4B on 8GB VRAM, `SelectStrategy` correctly picks `partial_offload` (not cpu_only), so the clamp doesn't trigger. Fix only matters for extreme cases (30GB+ models on small VRAM).

## R60.15 — Audit fixes (BUGS found in fresh audit)

This round was triggered by a fresh audit that revealed several issues:

### Fix A: X-Request-Id duplicate header
- **Bug**: Balancer's `ServeHTTP` (line 524) sets `X-Request-Id`; then `copyResponse` did `w.Header().Add(key, value)` for upstream's `X-Request-Id` → TWO `X-Request-Id` headers in response.
- **Fix**: `copyResponse` (and other copy sites) rename upstream `X-Request-Id` to `X-Upstream-Request-Id`. Result: clean 1 X-Request-Id + 1 X-Upstream-Request-Id pair.
- Files: `internal/balancer/proxy_helpers.go`, `proxy_request.go` (2 places), `virtual_router.go`.
- 3 unit tests pass.

### Fix B: UTF-8 BOM in JSON body — ⚠️ ROLLED BACK
- **Bug**: cppworker's `json.NewDecoder` doesn't strip UTF-8 BOM (EF BB BF). Some Windows tools (PowerShell `Out-File` default) add BOM → 400 "invalid character ï looking for beginning of value".
- **Attempted fix** (`cmd/cppworker/json_bom_strip_r60_15.go` + `json_decode_helper_r60_15.go`):
  - `decodeBOMReader(io.Reader) io.Reader` — strips BOM if present.
  - `decodeJSONRequest(r, &v)` helper — wraps `json.NewDecoder(decodeBOMReader(r.Body)).Decode(v)`.
  - Applied to 7 handlers: `model`, `generate`, `embeddings`, `hf`, `config`, `reset_reload`, `adaptive_loader`.
- 7 unit tests pass in isolation.
- **ROLLED BACK 2026-09-08**: Wrapping `r.Body` with `decodeBOMReader` caused `/api/show` to hang in production. Suspected cause: `decodeBOMReader` returned a `*bufio.Reader` whose underlying reader holds the request body, and the subsequent `r.Body.Close()` / connection-reuse path under concurrent bridge calls deadlocked. Helper files removed via `git clean -f`. Bug remains unfixed.

### Fix C: `/v1/models/{id}` for disk-known models — ⚠️ ROLLED BACK
- **Bug**: R60.8's `handleV1ModelByID` only checked `backend.GetModel(name)` (loaded models). For models on disk but not loaded → 404. OpenWebUI shows a 404 toast in the model picker for these.
- **Attempted fix**: 3-path lookup: (1) `GetModel` for loaded, (2) `mm.GetModelMeta` for disk-known (with .gguf fallback), (3) 404.
- **ROLLED BACK 2026-09-08**: `mm.GetModelMeta()` triggered `ReadGGUFHeader()` (synchronous file I/O) on the request goroutine, which blocked under concurrent bridge usage. Tests for unit (no concurrency) pass, but the hot path is unsafe.
- **Re-attempt plan**: do the disk-known lookup off the request goroutine (background goroutine + cache, or in a `sync.Map` populated at startup). Bug remains unfixed; tracked as a separate ticket.

### Fix D: `config.bundled.json` drift
- **Bug**: `Balancing.NCtxtReload` missing R60.6 fields.
- **Fix**: Added `preflight_async_retry_after_sec` (5s) and `preflight_async_retry_after_max_sec` (120s) with `_note_r60_6` explanation.
