# Семейства моделей (R268)

Как балансер и cppworker узнают «что за модель» и почему это больше не размазано
по коду.

## Зачем это появилось

Поддержка семейств раньше жила условиями в разных файлах: `isGemmaModel`,
`defaultAntipromptsForModel` (switch с четырьмя ветками), пять списков триггеров
текстового tool-call в детекторе, отдельные списки служебных меток в фильтре,
свои проверки версий в n_ctx-коде. Обновление одного семейства требовало помнить
про все эти места; забытая точка возвращала живой дефект:

* «ответ приходит вперемешку с метками `<|tool|>`» (метки шаблона в видимом
  тексте, R266);
* вызов инструмента уезжает клиенту текстом вместо `message.tool_calls`;
* неверные стоп-строки обрывают ответ посередине фразы (R248 про `<|im_end|>`).

Теперь знание о семействе — **данные**, а не ветки: пакет
`internal/modelfamily`.

## Модель данных

```go
type Family interface {
    ID() string                                  // "qwen", "gemma", ...
    Priority() int                               // порядок применения (больше = раньше)
    Match(modelName string, meta Meta) bool      // относится ли модель к семейству
    Versions() VersionRange                      // какие версии поддержаны для конвертации
    CapabilitiesFor(major int) Capabilities      // стоп-строки, метки, диалект вызова
    DetectVersion(modelName string) (int, string)
    Notes() string
}
```

`Capabilities` — то, что нужно тракту: `NativeTools`, `ReasoningChannel`,
`ToolCallTextForm`, `StopStrings`, `ServiceMarkers`.

Порядок применения детерминирован (`priority` по убыванию, затем `id`), а не
зависит от порядка `init()`: итерация по map в Go случайна, и «какое семейство
выиграло» не должно меняться от запуска к запуску. `generic` (приоритет 0)
всегда последний.

## Как добавить новое семейство

Один новый файл — больше править нечего:

1. `internal/modelfamily/family_<id>.go`:

```go
func init() { Register(myFamily{myBase}) }

type myFamily struct{ base }

func (f myFamily) Match(modelName string, _ Meta) bool {
    return strings.Contains(strings.ToLower(modelName), "myfamily")
}

func (f myFamily) CapabilitiesFor(major int) Capabilities {
    return Capabilities{
        ToolCallTextForm: "hermes",             // диалект вызова
        StopStrings:      []string{"<end_of_turn>"},
        ServiceMarkers:   []string{"<|my_marker|>"},
        ReasoningChannel: true,
    }
}

var myBase = base{
    id:       "myfamily",
    priority: 70,
    versions: VersionRange{MinMajor: 1, MaxMajor: 2},
    tokens:   []string{"myfamily"},
    notes:    "чем это семейство отличается",
}
```

2. Тесты: строка в таблице `family_test.go` (распознавание + версия +
capabilities). Тест-сторож `TestFamiliesHaveIdentity` сразу ловит забытую
`base` (пустой id).
3. Строка в этом документе (раздел «Что знаем о семействах»).

Никаких `switch` в тракте добавлять не нужно: детектор, фильтр и cppworker
спрашивают реестр.

## Политика версий: отказ вместо порчи

`VersionRange` описывает, какие версии мы умеем конвертировать в Ollama API.
Версия **выше** известной линейки даёт `UnsupportedVersion` — то есть честный
отказ, потому что диалект мог измениться, а «молча испорченный ответ» хуже
понятной ошибки.

Правила, которые нельзя ослаблять:

* **Неизвестное семейство — не ошибка.** `generic` совпадает со всем, поэтому
  модель, которую мы не знаем, обслуживается как раньше. Запрещено «ужесточать»
  реестр так, чтобы незнакомые имена отвергались (это ломало бы исправную
  работу); сторож — `TestUnknownFamilyNeverRefused`.
* **Не выдумывать версию.** Размер модели — не версия: `qwen-7b` это 7 млрд
  параметров, а `mistral-nemo-12b` — 12 млрд. Для семейств без известной линейки
  версия не определяется вовсе (`VersionRange{}`), иначе получался бы ложный
  отказ на исправной модели.
* **Поддержанная версия не меняет поведение.** Стоп-строки и списки меток
  перенесены дословно; это закреплено характеризационными тестами
  (`TestStopStringsPreservePreviousBehaviour`).

## Что знаем о семействах

| Семейство | Диалект вызова | Стоп-строки | Версии |
|---|---|---|---|
| `qwen` (2.x/3.x, 3.8) | `[TOOL_CALLS]`, канал `<|tool|>` | `<\|im_start\|>system`, `<\|im_start\|>user` | ≤ 3 |
| `gemma` | `[tool_code]`, JSON в `<start_of_turn>model` | версия ≥ 4: только `<start_of_turn>*`; иначе `<end_of_turn>` + `<start_of_turn>*` | ≤ 4 |
| `llama3` | `<\|python_tag\|>` | общий набор | ≤ 3 |
| `hermes` | `<tool_call>{…}</tool_call>` | общий набор | не ограничено |
| `mistral` | `[TOOL_CALLS][…]` | общий набор | не ограничено |
| `deepseek` | общий JSON-детектор | общий набор | не ограничено |
| `generic` | — | общий набор | не ограничено |

Почему `<|im_end|>`/`<|end|>` нет в стоп-строках qwen, а `<end_of_turn>` —
только у gemma-2: обе правки сделаны по живым дефектам (R248 и Round 32 #27) —
модель цитирует эти маркеры в тексте, а проверка суффиксная, и генерация
обрывалась посреди ответа. Комментарии об этом живут в файлах семейств, то есть
рядом с данными, которые они объясняют.

## Отказ в конвертации и порт

Балансер конвертирует ответ llama.cpp в Ollama API только на части путей. На
`/v1/*` и на нативном Ollama-пути ответ идёт клиенту **как есть**, поэтому отказ
там запрещён (иначе запретили бы исправную работу).

Когда конвертация нужна, а версия не поддержана, клиент получает терминальный
чанк с объяснением, а в лог пишется одна строка (`model family not supported for
Ollama conversion`, поля: модель, семейство, версия, поддержанный диапазон, порт).
Текст отказа:

> модель "…" (семейство qwen, версия 4) не поддерживается для конвертации в
> Ollama API — поддержаны версии <= 3. Используйте порт 18079: там
> OpenAI-совместимый эндпоинт без конвертации, ответ отдаётся как есть

Порты поставки:

| Порт | Что отдаёт | Конвертация |
|---|---|---|
| `LoadBalancer.Port` (по умолчанию 18080) | прокси: Ollama API и `/v1/*` | да, для `/api/*` |
| `LoadBalancer.OpenAIPort` (по умолчанию 18079) | OpenAI-совместимый passthrough | нет — ответ как есть |
| `LoadBalancer.APIPort` (по умолчанию 18081) | API управления/WebUI | не применимо |

Практический смысл: если модель/версия не конвертируется в Ollama-формат —
переключите провайдера в клиенте на OpenAI-совместимый эндпоинт порта 18079 и
работайте без конвертации.

## Что осталось за рамками R268

* `qwen_tool_markers_r266.go` держит собственный «нейтральный» список меток —
  он шире семейного и применяется ко всем моделям на `/api/chat`; сведение его с
  реестром изменило бы видимый текст, поэтому вынесено в отдельный пункт.
* Детектор текстовых вызовов по-прежнему пробует форматы цепочкой; семейство
  даёт ему подсказку (`ToolCallTextForm`), но порядок разбора не менялся, чтобы
  не сдвинуть распознавание у уже поддержанных моделей.
* Шаблон чата (chat-template) и stop-токены на стороне cppworker для конкретных
  сборок — отдельная тема: R268 отвечает за то, *что мы знаем о семействе*, а не
  за то, как llama.cpp применяет шаблон.
