# v0.7.239 — R480: стадия очереди в логе, вычищен мёртвый код

**Дата:** 2026-11-09 · **Тип:** исходники + образ балансера
**Образы:** balancer `r261109-2315` (коммит — в `deployments/release-manifest.json`);
cppworker и webui не менялись (`gpu-261109-1754`, `r261109-1747`).

---

## 1. Зачем

Прошлый этап (R479) добавил стадии `preflight`, `client_write` и `stage_final`,
но у единой очереди стадии не было. Из-за этого в `request trace` строка

```
path=/api/chat status=503 stage=select_backend
```

означала три разных ситуации: «бэкенд не выбран», «стоим в очереди за слотом»
и «запрос ушёл воркеру и там умер». По логу нельзя было понять, какой компонент
дал сбой — ровно та претензия, из-за которой R477 вообще появился.

## 2. Что изменено

| Место | Было | Стало |
|---|---|---|
| единая очередь (`waitForInferenceBackend`) | стадии нет | `stage=admission` на время ожидания |
| generic-путь `/api/chat` (`proxyRequest`) | стадии нет | `stage=upstream` перед `client.Do` |
| поток (`handleStreamingResponse`) | стадии нет | `stage=stream` с начала чтения |
| запись клиенту (ошибка `w.Write`) | стадия не менялась | `stage=client_write` |
| мёртвый код | `bindSession`, `acquireSlotWithRetry`, `executeWithFallback`, `extractModel`, дубль `/health` | удалён (`slot_handler.go` целиком, тесты вместе с ним) |
| `SetQueueManagerProxy` | no-op | оставлен осознанно — тест-шов у ~200 сценариев |

Так выглядит трассировка после правки (пример из теста):

```
stage=select_backend -> stage=admission -> stage=upstream -> stage=stream -> stage_final=done
```

Если ход умер, в `stage` остаётся последняя стадия, которую он успел пройти,
а `stage_final` — не `done`. Для 5xx и обрывов причина пишется в кольцо
`recent_failures` (R477).
