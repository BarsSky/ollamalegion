# Агентский цикл: почему симптомы повторяются на другом стенде (план диагностики)

**Статус:** план, правок в поведение нет. **Дата:** 2026-11-07.
**Контекст:** на стенде с A10 (модель qwen3.8-27B, контекст 131k, запас VRAM есть)
повторяются симптомы стенда с 9B: инструменты не применяются (файлы не
редактируются), ход уходит в перезагрузку модели, Cline снова сообщает о потере
текста. Ниже — гипотезы с механизмом, признаком подтверждения и тем, какой
артефакт нужен. Ни одна из гипотез не должна закрываться «моделью»: сначала
исключаем транспорт, окно и промпт.

---

## 1. Честная оценка метода (почему «под модель»)

Что фактически сделано на 9B-стенде:

- R474 — детектор «аргументы вызова выданы текстом» по ФОРМЕ текста (код + хвост
  JSON + ключ `path`). От модели не зависит, но и причину не убирает: он подменяет
  код пояснением.
- R475 — история вызовов отдаётся в форме шаблона. Зависимость от модели не по
  имени, а по признакам текста шаблона (`<function=` + `<parameter=`). Это шире
  «одной модели», но всё же семейный эвристический признак: шаблон 27B может
  оказаться другим, и тогда R475 молча не включится.

Чего НЕТ и что является настоящим корнем:

1. **Сквозной трассировки запроса.** Нет `X-Request-ID`: по логам балансера и
   воркера нельзя доказать, что строка «в очереди» и строка «reload» относятся к
   одному ходу.
2. **Доступа к логам бэкендов.** Пользователь не может выгрузить логи стенда
   (это отдельный запрос, см. §4), поэтому каждый разбор — это переписка, а не
   артефакт.
3. **Проверки «что реально ушло клиенту».** Есть только счётчики сводки воркера;
   нет побайтового доказательства (хеш/длина каждого чанка на двух концах).

Пока этих трёх вещей нет, любая правка проверяется на одном ходе и одной модели —
именно это и произошло.

## 2. Чем стенды объективно различаются (и какой симптом это объясняет)

| Различие | Как влияет | Симптом |
|---|---|---|
| Образы/коммиты (балансер, воркер) | R474/R475 могут быть не выкачены на A10 | «те же симптомы» — правок просто нет в образе |
| Шаблон чата модели | R475 включается только при `<function=`+`<parameter=`; у другого шаблона история остаётся дампом `[[…]]` | вызовы текстом, «text part … not found» |
| Окно на клиента × слоты | `perClientToTotal = Pad(окно)×slots`; 131072×2 = 262144 при потолке 131072 | 413/503 и рост окна на каждом ходу |
| Реальная помещаемость 131k | KV 27B на 24 ГБ может не поместиться: загрузка падает → повтор | «перезагружает» на инструментах |
| `parallel` (слоты) | меняет и окно, и очередь: все слоты заняты → очередь | «в очереди при свободной памяти» |
| Список инструментов и режим Cline | Plan/Act, 6 vs 25 инструментов; вызов необъявленного отбрасывается (R428/R468) | «файл не отредактирован» без ошибки модели |
| Настройка окна в Cline | клиент сжимает контекст по своему числу (32.7k в живом случае) | «text part … not found» после сжатия |
| Размер промпта хода | правки файлов по 10–60 КБ в истории раздувают промпт | рост окна/перезагрузка после первого редактирования |

## 3. Гипотезы (что проверяем и чем)

### H0. На A10 не тот образ
**Механизм:** симптомы совпадают с 9B ДО R474/R475.
**Подтверждение:** `GET :18092/api/info` на каждом воркере A10 → `build_commit` <
`30b9e0cb`; `GET :18080/api/version` на балансере.
**Нужно:** вывод двух запросов.

### H1. Шаблон 27B другой → R475 не включился
**Механизм:** `FunctionTagCalls=false` → история снова `[[…]]` → модель повторяет
дамп → Cline не может привязать часть текста.
**Подтверждение:** `prompt-last.txt` воркера (в истории должны быть `<tool_call>`,
а не `[[{`), плюс сам шаблон из GGUF (скрипт в §5.3).
**Отличие от 9B-стенда:** там шаблон `qwen35` с `<function=` — R475 включился.

### H2. Окно: 131072 на клиента × слоты
**Механизм:** при `parallel≥2` суммарное окно = 262144 > потолок `min(GGUF,
contextLengthMax, LB_NCTX_RELOAD_MAX_N_CTX)` → отказ по физике либо попытка роста.
**Подтверждение:** в логе балансера строки `R466`/`R472`/`R473` с числами
(per-client, total, ceiling, slots) и `why_queued`; в воркере — `context_size`,
`parallel`.
**Нужно:** `parallel`, `LB_NCTX_RELOAD_MAX_N_CTX`, `contextLength`/`contextLengthMax`
профиля модели, одна строка лога «окно».

### H3. 131072 не помещается физически на A10
**Механизм:** загрузка 131072 падает (OOM/таймаут) → воркер повторяет → каждый ход
начинается с перезагрузки; инструмент не успевает примениться.
**Подтверждение:** в логе воркера `async reload`/load fail, `vramFreeMB` до/после,
`/api/ps` (`context_size`), `/api/info` (`loadedModels` скачет).
**Нужно:** лог загрузки модели на A10 (один фрагмент) + `vramTotalMB`.

### H4. Рост окна на каждом ходе
**Механизм:** R301/R385 (рост на стриме/агенте) срабатывает, потому что загруженное
окно меньше запрошенного; стрим нельзя перезагрузить → 503 «started reloading» →
Cline повторяет → снова рост.
**Подтверждение:** повторяющиеся в логе строки роста с одинаковыми числами и `202
accepted`; в сводке воркера — `n_predict`, `budget_exhausted`, `elapsed_ms`.
**Нужно:** 10–20 строк лога балансера вокруг одного хода.

### H5. «Потеря текста» — три разных причины
**H5a наша заметка R474:** если модель выдала аргументы текстом, клиент видит
«Модель вывела вызов инструмента ТЕКСТОМ вместо вызова … файл не создан».
**H5b сжатие контекста Cline:** после `Context compacted` клиент может не найти
часть предыдущего сообщения (это его внутренняя привязка частей).
**H5c наша отдача:** hold/strip на стриме (R430/R471) мог съесть хвост.
**Подтверждение:** сводка воркера (`streamed_content_bytes`, `emitted_len`,
`final_content_len`, `dumped_args_instead_of_call`) против текста в Cline;
побайтово — только с трассировкой чанков (см. §4, `CPPWORKER_STREAM_TRACE`).

### H6. Вызов отброшен как необъявленный
**Механизм:** R428/R468: вызов распознан, но инструмента нет в объявленном наборе
(Plan mode, иной toolset) → клиент получает пояснение, файла нет.
**Подтверждение:** `reason=call_undeclared`, `dropped_tool_names={…}` в логе воркера
и `unparsed-tool-calls.jsonl`.

### H7. Слабость модели в tool-use — только после H0–H6
**Правило:** к этой гипотезе переходим, когда транспорт, окно, промпт и набор
инструментов исключены и подтверждены артефактами. Иначе это то самое «валим на
модель».

## 4. Что нужно сделать для диагностики (предлагаемая правка, ещё не внесена)

### 4.1. Сквозной идентификатор запроса
Балансер генерирует `X-Request-ID` (если клиент не прислал), пишет его в каждую
строку лога хода и передаёт воркеру; воркер пишет его в сводку и в лог.
Без этого нельзя связать «в очереди», «reload» и «сводка хода».

### 4.2. Кольцевой буфер логов и выгрузка из WebUI
- Балансер: `LB_DIAG_RING=5000` (строк в памяти, 0 = выключено), endpoint
  `GET /api/v1/diag/bundle?since=30m` → zip.
- Воркер: `CPPWORKER_DIAG_RING=5000`, endpoint
  `GET /api/v1/cppworker/debug/bundle?lines=2000` (уже есть `last-prompt`,
  `last-stream`, `unparsed` — они войдут в архив).
- Содержимое архива: логи балансера (ring), по каждому бэкенду — ring + `last-prompt`
  + `last-stream` + хвост `unparsed-tool-calls.jsonl`; версии (`/api/version`,
  `/api/info`), действующая конфигурация окна (`parallel`, `context_size`,
  `LB_NCTX_RELOAD_MAX_N_CTX`), секреты вырезаются.
- WebUI: кнопка «Скачать диагностику» → этот endpoint. Без SSH и без docker на стенде.

### 4.3. Флаги ведения логов (все выключены по умолчанию, кроме id)

| Флаг | Смысл | Значения |
|---|---|---|
| `LB_REQUEST_ID` | генерировать `X-Request-ID` и писать его в лог | `1` (по умолчанию) / `0` |
| `LB_REQUEST_TRACE` | решение по ходу: окно, выбор бэкенда, очередь, reload | `off` / `summary` / `full` |
| `LB_DIAG_RING` | строк лога в памяти для выгрузки | `0` … `50000` |
| `CPPWORKER_LOG_LEVEL` | уровень логов воркера | `info` / `debug` |
| `CPPWORKER_STREAM_TRACE` | хеш и длина каждого чанка (доказательство «всё ли отдано») | `0` / `1` |
| `CPPWORKER_DIAG_RING` | строк лога воркера в памяти | `0` … `50000` |
| `CPPWORKER_DIAG_KEEP_FILES` | сколько файлов `last-prompt`/`last-stream`/RAW хранить | `1` … `50` |
| `CPPWORKER_DEBUG_PROMPT_FILE` / `..._REQUEST_FILE` / `..._TOOL_ARGS` | уже есть: пишут промпт/запрос/аргументы | пути / `1` |

## 5. Чек-лист на A10 (что прислать, чтобы разбор был по фактам)

1. `curl /api/version` на балансере и `curl /api/info` на КАЖДОМ воркере
   (`build_commit`, `llama_build`, `cuda_arch_ok`, `vramTotalMB`).
2. `.env` стенда, только эти ключи: `LB_NCTX_RELOAD_MAX_N_CTX`,
   `LB_NCTX_GROW_FOR_STREAM`, `LB_NCTX_GROW_FOR_AGENTS`, `LB_PREFLIGHT_EXACT_TOKENS`,
   `LB_AUTOLOAD*`, `CPPWORKER_MAX_N_PREDICT`, `CPPWORKER_TOOLS_THINKING`,
   `CUDA_ARCH`, `parallel` (или `/api/v1/cppworker/config/runtime`).
3. Профиль модели: `contextLength`, `contextLengthMax` для qwen3.8-27B.
4. **Один неудачный ход, целиком:** строки лога балансера (окно + выбор бэкенда +
   очередь + reload) и строки лога воркера (загрузка + сводка `/api/chat`).
   Лучше архивом из §4.2, как только он появится.
5. `prompt-last.txt` и `request-last.json` с воркера (`/app/diag/`) — там видно
   форму истории и `num_ctx` из запроса Cline.
6. Настройки Cline: Model Context Window, режим (Plan/Act), какая задача
   (модель фиксируется на задачу), и текст, который Cline показал как «потеря».

Команда для шаблона (без загрузки модели, только чтение GGUF):

```bash
docker exec <worker> sh -c "head -c 40000000 '/app/models/<model>.gguf' > /tmp/h.gguf"
docker cp <worker>:/tmp/h.gguf ./h.gguf
python gguf_template.py h.gguf > chat_template.jinja   # скрипт: docs/architecture/tools/
```

## 6. Долг: «свободный бэкенд, а запрос в очереди» (OpenAI-поверхность)

Симптом: новый клиент через OpenAI API попадает в очередь, хотя рядом есть
свободный бэкенд, который мог бы поднять модель.

Вероятные механизмы (проверяются по логам, не по догадке):

- **Q1.** Выбор бэкенда предпочитает бэкенд с загруженной моделью, даже если все
  его слоты заняты; холодный свободный бэкенд в выбор не попадает → очередь.
- **Q2.** Автозагрузка (`ensureModelLoaded*`) выполняется ДО постановки в очередь и
  проигрывает по таймауту, после чего запрос попадает в очередь, хотя загрузка на
  свободном бэкенде могла бы стартовать параллельно.
- **Q3.** Для OpenAI-поверхности автозагрузка отключена/не вызывается, в отличие от
  нативной. Проверяется по наличию строк `ensureModelLoaded` в логе для того же
  `X-Request-ID`.

Что нужно для разбора: строка `admission: request queued` с полями `why_queued`,
`rejected_backends` (R460) именно для OpenAI-запроса и список бэкендов в этот
момент (загруженная модель, занятые слоты).

## 7. Порядок работ (предложение)

1. **Инструментарий** (§4): `X-Request-ID` + ring + bundle + флаги. Без него
   следующий разбор снова будет перепиской.
2. **A10 по чек-листу** (§5): H0–H4 закрываются артефактами, а не объяснениями.
3. **Долг очереди** (§6) — после того как есть `X-Request-ID`, иначе не доказать.
4. Только потом — правки в окне/промпте по подтверждённой причине, с проверкой на
   обеих стендах (9B и 27B) одним и тем же сценарием.
