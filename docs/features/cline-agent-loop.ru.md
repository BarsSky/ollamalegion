## 1. Трассировка одного хода

```powershell
# 1. Один раз достаём НАСТОЯЩИЙ запрос Cline из его лога (имена и схемы
#    инструментов задают и промпт, и разбор ответа — «похожий» payload бесполезен).
node scripts/extract-cline-request.js "List the files in the current working directory."

# 2. Один ход с полной трассировкой: сырые чанки + разбор.
node scripts/trace-cline-turn.js --url http://127.0.0.1:18080/api/chat `
     --payload debug/cline-real-request.json
```

Что печатает трассировщик:

| Поле | Смысл |
|---|---|
| `1-й content` | время до первой дельты content; `НЕТ` = сервер не стримил текст (клиент ждал молча) |
| `content` / `thinking` | сколько символов ушло в каждое поле |
| `tool_calls` | имена и **форма** аргументов (`object` — исполнимый вызов, `array`/`string` — нет) |
| `done` | `done_reason`; `done:true` при нулевом выводе = клиент покажет «COMPLETE», ничего не дождавшись |
| `УТЕЧКИ` | разметка вызова / маркеры размышлений / служебные токены **в content** |

Сырые чанки сохраняются в `debug/trace-turn-<ts>.ndjson` — это и есть «явное
отслеживание ответа»: видно байт-в-байт, что получил клиент.

Код возврата `1` означает, что ход некорректен (утечка, аргументы не объект,
нет ни content, ни вызова).

## 2. Проверка агентского цикла

Один ход не показывает главного: продолжается ли работа ПОСЛЕ вызова
инструмента. Harness играет роль Cline: получает `tool_calls`, отдаёт результат
инструмента и повторяет ход; на каждой итерации проверяется протокол.

```powershell
node scripts/cline-agent-loop.js --url http://127.0.0.1:18080/api/chat `
     --payload debug/cline-real-request.json --iterations 4
```

**Скрипт НЕ исполняет команды, выбранные моделью** — результат инструмента
детерминированная заглушка. Проверяется только протокол:

* `arguments` вызова — JSON-объект, согласованный со схемой инструмента из
  запроса (объявленные параметры, обязательные параметры, типы);
* в `content` нет разметки вызова, маркеров размышлений и служебных токенов;
* `done_reason` = `tool_calls` при вызове и `stop`/пусто при финальном ответе;
* цикл продолжается после результата инструмента, а не обрывается на 1-2 ходах.

Поведение «запрос пришёл, пока модель грузится» проверяется отдельно —
одновременными запросами:

```powershell
node scripts/parallel-turn-probe.js --url http://127.0.0.1:18080/api/chat `
     --payload debug/cline-real-request.json --count 3
```

До R113 второй и третий запросы получали `done:true` за 0.15 с (клиенту нечего
показывать); после — ждут готовности и отвечают так же, как первый.

Живой прогон ДО R113 (запрос настоящего Cline, gemma-4-E4B, 25 инструментов):

```
--- итерация 1 --- tool_calls 1 | done_reason=tool_calls
  вызов: run_commands args=["dir"]                     ← arguments МАССИВ
--- итерация 2 --- content 2456 | tool_calls 1
  вызов: run_commands args=["dir"]
  УТЕЧКА: сырой JSON вызова в content: "tion":{"name":"run_"
--- итерация 3 --- tool_calls 0 | done_reason=stop     ← цикл кончился ничем
```

## 3. Контракты

### 3.1 Аргументы вызова — ВСЕГДА JSON-объект по схеме запроса

`message.tool_calls[].function.arguments` обязан быть JSON-объектом, ключи
которого объявлены в `tools[].function.parameters` запроса.

Модель этого не гарантирует. Живые формы, которые приходили на стенд:

| Что вернула модель | Что уезжало клиенту | Следствие |
|---|---|---|
| `run_commands` + `["ls -A"]` | `arguments: ["ls -A"]` | клиент не может выполнить вызов |
| `list_files` + `"c:\\Ollama\\ollamalegion"` | `arguments: "c:\\…"` | то же |
| `run_commands{[…]}` (нативный тег gemma) | `arguments: […]` | то же |

**Правило приведения** (R113, `cmd/cppworker/tool_args_schema_r113.go`) —
детерминированное и по схеме ИЗ ЗАПРОСА, без имён моделей:

| Значение | Куда попадает |
|---|---|
| объект | остаётся как есть (обёртка `{"args":{…}}`/`{"kwargs":{…}}` разворачивается, если ключ не объявлен) |
| массив | первый объявленный параметр-массив (`required` в приоритете): `run_commands.commands`, `read_files.files`, `search_codebase.queries` |
| скаляр | единственный параметр, иначе первый `required`-строковый, иначе первый — в порядке объявления в схеме (`editor` → `path`) |
| строка с JSON внутри | разворачивается и обрабатывается заново |
| инструмент не объявлен, значение не объект | вызов **отбрасывается** (угадывать имя параметра нельзя) |

Порядок параметров берётся из схемы клиента (декодер, не map) — поэтому выбор
для одиночного значения воспроизводим от запуска к запуску.

### 3.2 Разметка вызова не попадает в content

Если модель выдала разметку вызова (`<|tool_call>…<tool_call|>`, `<tool_call>…`,
`{"tool_call":…}`, `[TOOL_CALLS]`, markdown-фенс с JSON), а разобрать её не
удалось, клиенту **нельзя** отдавать её как текст: агентский клиент считает такое
сообщение финальным ответом и помечает задачу выполненной. Поведение R113:

1. повтор генерации (до `maxEmptyOutputRetries`), пока клиенту не отправлено ни
   байта — сэмплирование стохастично, повтор обычно даёт корректный вызов;
2. если разметка осталась — error-чанк с `done_reason: "error"` (клиент видит
   проблему, а не «готово»);
3. в «сыром» текстовом ответе разметка вырезается (`stripToolCallMarkup`).

Отдельный случай — **эхо вызова из истории**. Клиент присылает второй ход, где
вызов ассистента записан JSON-объектом; мост кладёт его в промпт текстом, и
модель его повторяет в ответе:

```
… I will execute it again.
[[{"id":"call_1","type":"function","function":{"name":"run_commands",
   "arguments":{"commands":["dir"]}}}]]
```

Такой JSON распознаётся как **вызов** (`recoverToolCallsFromText`): клиент
получает `tool_calls` и продолжает работу, а не «инструмент в теле ответа» с
обрывом цикла после первой итерации. Если распознать не удалось — JSON всё равно
вырезается из видимого текста.

Дельты удерживаются не только когда ответ НАЧИНАЕТСЯ с JSON/разметки, но и когда
JSON-форма вызова появляется ВНУТРИ прозы (`toolsStreamJSONCallPos`).

### 3.3 Запрос к загружаемой модели ЖДЁТ готовности

`/api/chat` (и остальные клиентские пути) не отвечает ошибкой, пока модель
грузится или перезагружается (n_ctx другого клиента, auto-tune, параллельный
запрос). Поведение: ожидание готовности (`cppbackend.WaitForModelReady`),
предел — `CPPWORKER_LOAD_WAIT_SEC` (по умолчанию 900 с) или дедлайн/отмена
клиента.

Почему это важно: раньше «модель загружена» означало «есть запись в `b.models`»,
а запись появляется ДО окончания загрузки. Генерация падала с
`model X is not loaded (state: loading)`, стриминговый путь превращал это в
`done:true, done_reason:"error"` — и клиент показывал завершённый ход, не получив
ни одного токена (жалоба «COMPLETE прилетает до того, как вообще происходит
потоковое общение генерации ответа»). Если готовности не дождались, клиент
получает 503 + `Retry-After` (повторить), а не «готово».

### 3.4 Результат инструмента доходит до модели

Сообщение `{"role":"tool","tool_name":"…","content":"…"}` (и OpenAI-форма с
`name`/`tool_call_id`) попадает в промпт как `tool_call_result(<имя>): …`, поэтому
следующий ход видит результат. Поле `tool_name` принимается наравне с `name`
(иначе второй ход цикла падал с 400 и цикл обрывался после первого вызова).

## 4. Что смотреть на сервере

Один запрос = одна строка в логе cppworker:

```
/api/chat stream response summary  model=… streamed_content_bytes=… 
final_content_len=… thinking_len=… tool_calls=1 tool_names=run_commands 
tool_arg_shapes=object done_reason=tool_calls raw_len=… elapsed_ms=…
```

`tool_arg_shapes=object` — клиент сможет выполнить вызов; `array`/`string` —
дефект приведения. `streamed_content_bytes=0` при длинной генерации означает, что
сервер держал вывод до конца (клиент не видел стрима).

## 5. Стриминговый контракт для Cline (R231, 2026-10-24)

Cline читает OpenAI SSE и склеивает `delta.content`; всё, что приходит не тем
каналом или не в том месте, ломает сессию (агент «завершает» ход или рвёт поток).
После R231 контракт зафиксирован и проверяется автоматически.

**Инварианты ответа:**

1. `reasoning_content` и `content` не смешиваются. В стриме размышления уходят
   ТОЛЬКО в `reasoning_content`; `content` — только видимый ответ. Незакрытый
   блок размышлений не копируется в `content` (это был дубль), а даёт честный
   `finish_reason=length`.
2. В видимом `content` нет служебных маркеров: `</think>`, `<think>`,
   `<|channel>thought`, `<channel|>`, `<end_of_turn>`, `<|im_end|>` и подобных.
   Чистится и в воркере (парсер + дельты), и на границе балансера (SSE-фильтр) —
   даже если воркер старый.
3. `[DONE]` приходит **ровно один раз** и **последним** событием; после него нет
   ни одного data-события. `finish_reason` — до `[DONE]`.
4. Ошибки приходят ошибками: `finish_reason:"error"` + `error`, а не пустой 200.

**Проверка (живая, стенд):**

```bash
node scripts/verify-stream-r231.js
# PASS: 1. HTTP 200; 1а нет маркеров; 1б нет дубля; 1в один [DONE];
#       1г [DONE] последний; 1д после [DONE] пусто; 1е пустой content -> length
```

**Контракт клиентов (OpenAI + Ollama, включая tools):**

```bash
node scripts/clients/contract-suite.js
```

Блок 6 в нём — именно этот сценарий (стрим без инструментов): маркеры, дубль,
`[DONE]` один и последний. В воротах он запускается как
`scripts/ci.ps1 -Live -Clients`.

**Если регрессия вернулась:** смотрите в логе воркера
`writeOpenAIChatStream: блок размышлений не закрыт` (причина `length`) и
`translateSSEChatToOllama: stripped reasoning markers` / `stripped service tokens`
(что почистил балансер).
