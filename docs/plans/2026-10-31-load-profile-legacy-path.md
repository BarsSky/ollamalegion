# R364. Профиль модели на legacy-пути загрузки (`POST /api/models/load`)

Дата: 2026-10-31. Стенд: один мастер-бэкенд `cppworker-gpu` (RTX 3070, 8 ГБ),
образ `cppworker:gpu-4ec5e4d0` на момент обнаружения.

## 1. Что случилось

После пересборки контейнеров (диск Docker был очищен, образы собраны заново)
модель `gemma-4-E4B-it-Q4_K_M` поднялась, отвечала — но в **10 раз медленнее
обычного**: 2.9 tok/s против 25.9 tok/s на том же стенде с тем же профилем.

Замер (116 токенов, `num_predict=120`, промпт про тесты в разработке):

| прогон | tokensPerSec | состояние |
| --- | --- | --- |
| «медленный» инстанс | **2.92** | 20/43 слоёв на GPU (остальное в RAM/CPU) |
| после `unload` + повторной загрузки | **25.89** | 42/43 слоёв на GPU |

Первый вывод («тихий откат на CPU не виден») оказался **неверным**: воркер
честно писал `partial GPU offload: model does not fit VRAM`
(`applied_gpu_layers=15/20, n_layers=42`), а `/api/models` отдавал
`gpu_layers_actual` и `offload_degraded=true` — R248 свою работу делает.
Причина деградации была другая.

## 2. Причина: загрузка шла мимо профиля модели

Фактические параметры «медленного» инстанса против профиля оператора:

| параметр | факт в API | профиль модели |
| --- | --- | --- |
| `context_size` | 65536 | 32768 |
| `kv_cache_type` | q8_0 | q4_0 |
| `reasoning_enabled` | false | true |

KV-кэш в q8_0 почти вдвое больше, чем в q4_0, при вдвое большем окне — в
результате VRAM перестало хватать на все слои, memfit оставил часть весов в
RAM, и скорость упала.

Кто именно подставил эти значения: **legacy-обработчик**
`handleLoadModel` (`POST /api/models/load`). Профиль модели применяли
`handleLoadWithParams` (R26), `handleReloadModel` и ленивая загрузка
(`applySyncedProfileToLazyLoadOpts`, R83/v52) — а legacy-путь не применял
никогда.

Отдельная деталь, из-за которой это прожило: **комментарий в `lazyload.go`
утверждал, что `handleLoadModel` профиль применяет**. Проверка исходника
показала, что в теле обработчика нет ни `profileSyncer`, ни
`applyProfileToLoadRequest`. Комментарий описывал намерение, а не код.

Воспроизведение (после `PUT` профиля с `contextLength=32768`,
`kvCacheType=q4_0`, `enableReasoning=true` и успешного `apply`):

```
POST http://127.0.0.1:18092/api/models/load {"name":"gemma-4-E4B-it-Q4_K_M"}
→ GET /api/models: context_size=65536, kv_cache_type=q8_0, reasoning_enabled=false
→ bridge: "loading model: ... (ctx=65536, batch=512, threads=6, gpu_layers=42)"
```

## 3. Почему нельзя было просто вызвать `applyProfileToLoadRequest`

Этот помощник заполняет только ПУСТЫЕ поля (0 / ""). К моменту его вызова
обработчик уже подставил конфиг/env-дефолты (`CPPWORKER_CTX_SIZE` и т.п.), и
для профиля «пусто» неотличимо от «оператор задал в конфиге». Профиль молча
проигрывал бы дефолту — та же ошибка, только слоем ниже.

## 4. Что сделано

Приоритет выражен явно и в одном месте (`cmd/cppworker/load_profile_seed_r364.go`):

```
явное поле запроса  >  профиль модели  >  конфиг/env воркера
```

Это контракт балансера (`internal/balancer/model_management.go`,
`applyProfileLoadParams`: «явные поля запроса > профиль > дефолт cppworker») и
R83/v62: профиль модели применяется ВСЕГДА, а `ignoreDefaults` гасит только
применение дефолтного профиля. Раньше результат загрузки зависел от того, кто
её попросил: балансер или оператор напрямую.

Детали:

- `readProfileForLoadR364` — профиль ищется у ВЛАДЕЛЬЦА ФАЙЛА (R154), чтобы
  загрузка под алиасом не поднимала модель на чужом профиле;
- `resolveLoadParamsR364` — чистая функция разрешения (ctx, batch, gpuLayers,
  flashAttn, kvCacheType, parallel), её же проверяют тесты;
- профиль `disabled` → 403, как и на остальных путях;
- `enableReasoning`: запрос → профиль → глобальный конфиг (раньше профиль
  терялся: «включить размышления» в WebUI не действовало на прямой вызов);
- неподдержанный `kvCacheType` не подменяется значением профиля: грузим на
  дефолте llama.cpp и предупреждаем — иначе API соврал бы о параметрах.

Ограничения, оставленные сознательно:

- `useMmap` / `numa` из профиля на этом пути по-прежнему не применяются —
  туда их не передаёт и `applyProfileToLoadRequest`; менять это отдельным
  решением, а не «заодно».

## 5. Найденный смежный дефект (R366, НЕ исправлен)

Мост трактует поле так: `-1 = auto, 0 = disabled, 1 = enabled`
(`c/bridge/bridge.go:176`). Общий помощник `applyProfileToLoadRequest`
(пути `load-with-params`, `reload`, ленивая загрузка) конвертирует
`flashAttn=false → -1` (auto) вместо `0` (disabled), а из-за «заполняю только
пустое» при дефолте контейнера `-1` профильное «выключить» не применяется
вовсе.

В R364 сделан **правильный** маппинг (`false → 0`, указатель, чтобы отличать
«не задано» от «выключено»), но общий помощник не тронут: его контракт не
умеет выражать «явно выключено», и правильная правка требует той же
явной-флаговой механики на трёх путях. Записано как R366.

## 6. Тесты

- `load_profile_priority_r364_test.go` — приоритет трёх слоёв, `parallel<=0` =
  наследовать, `flashAttn=false → 0`, неподдержанный KV, отсутствие syncer-а;
- `load_profile_steward_r364_test.go` — стюард: **новый** путь загрузки не
  сможет молча обойти профиль (тот же класс защиты, что R304 для донора), и
  `handleLoadModel` обязан собирать параметры через общий резолвер.

## 7. Живая проверка (образ `cppworker:gpu-c71d379e`)

Проверено на стенде после пересборки контейнера:

```
POST /api/models/load {"name":"gemma-4-E4B-it-Q4_K_M"}     (без параметров)
→ лог: handleLoadModel: applied model profile (R364)
       profile_key=gemma-4-E4B-it-Q4_K_M, ctxSize=32768, gpuLayers=-1
       handleLoadModel: reasoning from model profile (R364), enableReasoning=true
→ bridge: loading model (ctx=32768, batch=512, gpu_layers=42)
→ load_tensors: offloaded 42/43 layers to GPU
→ /api/models: context_size=32768, context_per_seq=16384, kv_cache_type=q4_0,
               reasoning_enabled=true, gpu_layers_actual=42/42,
               offload_degraded=false
→ 93 токена: 24.73 tok/s (до правки на том же профиле: 2.92 tok/s)
```

Обратная сторона приоритета — явный запрос по-прежнему главнее профиля:

```
POST /api/models/load {"name":"…","contextSize":16384,"kvCacheType":"f16"}
→ /api/models: context_size=16384, per_seq=8192, kv_cache_type=f16,
               reasoning_enabled=true   ← reasoning взялся из профиля, его в
                                          запросе не было — так и задумано
```

## 8. Что осталось / известные ограничения

- `CPPWORKER_N_PARALLEL` и профильный `parallel`: приоритет определён, но
  живого замера «профиль parallel=1 против env=2» в этом раунде не делалось.
- `useMmap` / `numa` из профиля на legacy-пути не применяются (см. §4);
  на остальных путях их применяет балансер через тело запроса.
- R365 (см. `2026-10-31-load-claim-sync-timeout.md`) — найден при этой же
  живой проверке, исправлен отдельным коммитом.
- Донор (RPC-узел) к этому дефекту отношения не имеет; двухузловая проверка
  остаётся в силе из `2026-10-31-two-node-donor-check.md`.
