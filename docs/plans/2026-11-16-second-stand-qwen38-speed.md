# Второй стенд: почему 27B «думает по 5 минут» и как это ускорить

**Дата:** 2026-11-16 · **Основание:** диагностический архив
`ollamalegion-diag-0422583644ea-20261116-145334.zip` (кольцевой лог балансера
11:59–14:53Z, 94 сводки стрима двух воркеров, `summary.json`, профили моделей) ·
**Стенд:** 2×A10 24 GB (`cppworker-gpu` / `A10-126`) + 2×8 GB (`ASTRA-I9` /
`WIN-I9`, простаивают) + 3 image-бэкенда

Вопрос оператора: как настроить `Qwen3.8-27B`, чтобы быстрее работал на сети
второго стенда и меньше уходил в размышления.

Короткий ответ: **сеть здесь не при чём.** Узкое место — (1) повторный префилл
всего промпта на каждом ходе (35–45 % времени уходит не туда) и (2) размышления,
которые на одном ходе съели весь остаток окна и не оставили места ответу. Ниже —
числа и что крутить.

---

## 1. Что измерено (не оценка)

Из 94 сводок `/api/chat stream response summary` (два узла, 11:59–14:53Z):

| Метрика | Значение |
|---|---|
| Запросов | 94 |
| Медиана времени запроса | **213 с**, p90 **524 с**, максимум **930 с** |
| Медиана сгенерированных токенов | **260**, p90 4139, максимум 9470 |
| Первый ВИДИМЫЙ контент | медиана **205 с** (при медиане запроса 213 с) |
| Контент появился в последние 15 с запроса | **82 из 94 (87 %)** |
| `done_reason=tool_calls` | 93 из 94 (это агентский цикл Cline, не чат) |
| `budget_exhausted=true`, `done_reason=length`, ответа нет | **1** (13:07, см. §1.2) |
| Размышления придержаны (`hold_kept_reasoning=true`) | 36 из 94 (38 %) |
| Суммарно | **115 680 токенов за 24 731 с (6.9 ч GPU) → 4.68 ток/с вместе с префиллом** |

Скорости, вытащенные из тех же сводок:

- **Декод 23–33 ток/с** (запросы, где контент шёл с самого начала: 174 токена за
  7.6 с, 234 за 9.9 с, 451 за 19.9 с, 551 за 20.4 с, 410 за 12.5 с).
- **Префилл 375–450 ток/с**: запрос 14:51 — промпт **89 794 токена**
  (`last-prompt.json`), префилл ≈240 с; запрос 13:07 — 2169 токенов декода при
  23–33 ток/с это 65–95 с из 496 с, остальное префилл.

### 1.1 Откуда 213 с на ход

При медиане 260 сгенерированных токенов декод — это **~10 с**. Остальные
**~200 с — префилл**. И он повторяется **на каждом ходе**: в мосте нет
переиспользования KV-кэша (`n_past` есть только внутри одного запроса, в
`vision_mtmd.cpp`/`bridge.c`; `llama_state_seq_*`, `cache_prompt`, `n_past_reused`
в `c/bridge` отсутствуют). То есть каждый ход агента заново прогоняет 80–90 тыс.
токенов промпта, хотя предыдущие 99 % этого промпта уже считались ход назад.

### 1.2 «Ушёл в размышления и не вернулся» — есть живой случай

Запрос 13:07:24 на `cppworker-gpu-bundled-agent`:

```
budget_tokens=2169 budget_exhausted=true done_reason=length
generated_tokens=2169 elapsed_ms=495814 emitted_len=0 final_content_len=0
raw_len=7255 streamed_content_bytes=7255 thinking_len=0 tool_calls=0
hold_kept_reasoning=true
```

Расшифровка: в окне оставалось **2169 токенов запаса** (промпт к тому моменту
дорос почти до загруженного окна), модель потратила их **все** на размышления,
`done_reason=length`, клиенту не ушло ничего. 8 минут 16 секунд — впустую.
Это не гипотеза: так выглядит жалоба «уходит в размышления по проекту».

### 1.3 Контекст агента уже упирается в окно

- Загружено: `cppworker-gpu` — **180 224** токена `context_per_seq`, 65/65 слоёв
  на CUDA0, VRAM 19.1/22.5 GB, GPU 90 %, **87 °C**;
  `A10-126` — **188 416** токенов, но **4 слоя на CPU** (62/66 на GPU), VRAM
  20.5/22.5 GB.
- Профиль `Qwen3.8-27B-UD-Q4_K_M`: `contextPerSeq 131072`,
  `contextLengthMax 131072`, KV **q4_0**, `parallel 1`, `batchSize 512`,
  `enableReasoning true`, `primary true`.
- В 14:47 запрос потребовал **184 100** токенов при загруженных 180 224 →
  `preflight triggered async n_ctx reload` → **503 клиенту** и перезагрузка
  модели (минуты), после которой KV всё равно пустой (см. §1.1).

Вывод: агентский контекст (Cline) дорос до потолка окна. Дальше расти некуда:
KV q4_0 на 262 144 токена это ~9.7 GB, а веса 15.3 GiB — вместе 25 GB в 22.5 GB
VRAM не влезает.

### 1.4 Что НЕ является узким местом

- **Сеть.** Промпт ~100 КБ на ход — это ничто против 200 с префилла; оба A10 в
  LAN, потери на передаче промпта неизмеримо малы. Шардинг через RPC (свободные
  8 GB узлы) ускорит только за счёт выноса тех 4 слоёв с CPU на `A10-126`, то
  есть единицы процентов — и добавит сетевую задержку в каждый токен.
- **Очередь.** `queuedRequests=0`, `activeRequests=2`; у каждого узла свой слот,
  сессии привязаны (`LB_SESSION_STICKINESS=true`). Для одного агента очереди нет.
- **Картинки.** `image.requests.total=0` — конкуренции за VRAM сейчас нет.

## 2. Что крутить — по убыванию эффекта

### 2.1 Переиспользование префилла (код; самый большой выигрыш)

Сейчас: ~200 с префилла на ход. С кэшем префикса: пересчитываются только новые
токены хода (ответ инструмента + новый вопрос, обычно 2–10 тыс.) → **5–25 с**.
Ожидаемый ход: **213 с → 30–40 с** (в 5–7 раз), суммарные 6.9 ч GPU → ~1 ч.

Это не настройка, а доработка моста: держать `llama_context` живым на сессию,
искать самый длинный общий префикс с прошлым промптом и продолжать с
`n_past = len(prefix)` (`llama_kv_cache_seq_rm` + `llama_decode` только хвоста).
Требует аккуратности: инвалидация при смене окна/модели, лимит памяти под
несколько сессий. Формально — отдельный план; в долгах значится как
«префикс-кэш» (см. §4).

### 2.2 Выключить/ограничить размышления (настройка; минуты)

Сейчас профиль `Qwen3.8-27B-UD-Q4_K_M` имеет `enableReasoning: true`, и
`buildChatPrompt` идёт «нативным» путём `enable_thinking=true` — шаблон
открывает `<think>`, модель думает. Плюс клиент (Cline) сам вписывает в системный
промпт «Reasoning effort is set to **xhigh**…» (это его настройка, не наша).

Что сделать:

1. **Профиль:** `enableReasoning: false` для обеих записей
   (`Qwen3.8-27B-UD-Q4_K_M` и `Qwen3.8-27B`) — тогда в шаблон уходит
   `enable_thinking=false` и блок размышлений не открывается.
   `PUT /api/v1/cppworker/model-profiles/Qwen3.8-27B-UD-Q4_K_M` с полем
   `"enableReasoning": false`, затем `POST .../apply` (перезагрузка узлов).
2. **Клиент:** в Cline поставить Reasoning Effort = minimal/none (он вписывает
   свою инструкцию в промпт — сервер её не убирает; правильнее не просить).
3. **Проверить на живом:** запрос должен отдавать `tool_calls` без
   `hold_kept_reasoning`; в сводке `thinking_len≈0`.

Эффект по числам: из 94 запросов 36 придерживали размышления; в дорогих случаях
это 1000–4000 токенов, что при 25 ток/с = **40–160 с на ход**. И исчезает класс
«съел весь остаток окна и вернул пустоту» (§1.2).

**Внимание:** `CPPWORKER_REASONING_BUDGET` / `reasoningBudget` (в конфиге и API
есть, подписан как «max tokens for thinking») **ни на что не влияет** — в
промпт-пути его никто не читает (проверено: все обращения к `ReasoningBudget`
только в конфиге, API и копировании настроек кластера). Это долг 12o, не
рабочая ручка.

### 2.3 Держать контекст агента ниже окна (клиент; убирает 503 и голодный бюджет)

- В Cline выставить **Model Context Window меньше серверного** (например 96k при
  загруженных 180k). Тогда Cline сам компактит историю, и всегда остаётся
  запас 8–16k токенов на ответ — сейчас в худшем случае оставалось 2169 (§1.2),
  а один раз не хватило даже окна (184 100 против 180 224 → 503, §1.3).
- Альтернатива на сервере: `LB_AGENT_WINDOW_BUDGET=client` заставит расти окно
  под `max_tokens` клиента, но это путь к перезагрузкам каждые несколько ходов
  (R451 уже описал эту обратную связь) и к тому же VRAM не хватит. Не
  рекомендую; правильнее ограничить контекст в клиенте.

### 2.4 Префилл: батч и раскладка (настройка; 10–20 %)

- `batchSize: 512` → **1024** в профиле. Префилл — это 200 из 213 с хода, и
  больший батч обычно ускоряет его на 10–20 % (**−20…−40 с на ход**). Проверить
  VRAM: на `A10-126` свободно всего 2.0 GB, там 1024 может вытеснить слои на CPU —
  тогда сначала освободить окно (§2.5).
- `flashAttn: true` уже стоит, KV `q4_0` уже стоит — это правильно.
- `A10-126` держит 4 слоя на CPU из-за окна 188 416. Вернуть все слои в VRAM
  можно, снизив `contextLengthMax`/`contextPerSeq` (например до 163 840) —
  декод ускорится сильнее, чем что-либо ещё на этом узле (сейчас каждый токен
  платит за 4 слоя в RAM).

### 2.5 Мелочи, которые сбивают диагностику

- `llama_build_mismatch: true` в `/api/info` — env-переменная
  `CPPWORKER_LLAMA_BUILD` в образе осталась `0eadefebd`, а бинарь собран на
  `b1b770d90`. На работу не влияет, но при разборе путает; обновить env в compose.
- 276 WARN «backend VRAM usage above threshold» за 2 ч 54 мин кольцевого
  буфера — ожидаемо при `vram_percent 83–89 %`, порог 85 %. Не ошибка, но шум:
  на живом стенде это треть всех строк лога.

## 3. Итоговая рекомендация (что менять в каком порядке)

1. **Сейчас (настройки, минуты):**
   - профиль 27B: `enableReasoning: false`;
   - Cline: Reasoning Effort = minimal, Model Context Window = 96k;
   - профиль 27B: `batchSize: 1024` (после того как `A10-126` перестанет
     оффлоадить слои);
   - обе записи профиля привести к одному виду (сейчас `Qwen3.8-27B` и
     `Qwen3.8-27B-UD-Q4_K_M` отличаются `contextLength` 32768/131072).
2. **Дальше (код, дни):** префикс-кэш в мосте — единственное, что сокращает ход
   с 3.5 минут до ~30 с. Всё остальное — проценты.
3. **Не делать:** шардинг через 8 GB узлы ради скорости (сеть добавит задержку в
   каждый токен), рост окна выше 180k (VRAM не хватит), `LB_AGENT_WINDOW_BUDGET=client`
   (перезагрузки).

## 4. Что проверить после изменений (чтобы не «на глаз»)

```bash
# профиль применился
curl -s -H 'X-API-Token: <token>' :18081/api/v1/cppworker/model-profiles/Qwen3.8-27B-UD-Q4_K_M | jq '.profile.enableReasoning, .profile.batchSize'
# сводка следующего хода: не должно быть thinking и held
# (в архиве воркера) grep 'stream response summary' | tail -1
#   ожидаем: thinking_len≈0, hold_kept_reasoning=false, elapsed_ms падает на 30–60 %
# первый байт и время хода
grep 'request trace' balancer-logs.txt | grep '/api/chat' | tail -5
```

Ожидаемые числа после шагов 2.2–2.4 (без префикс-кэша): медиана хода **213 → 140–170 с**
(минус размышления и минус часть префилла). С префикс-кэшем — **30–40 с**.
