## Дубли env-обработки в cppworker

### Проблема: `CPPWORKER_RAM_FALLBACK_*` обрабатывается 3 раза

**Путь 1** — `cmd/cppworker/main.go:175-201` (при старте, с приоритетом flag > env):
```go
if !isFlagSet("ram-fallback-n-ctx") {
    if envVal := os.Getenv("CPPWORKER_RAM_FALLBACK_N_CTX"); envVal != "" {
        *ramFallbackNCtx = parseBoolEnv(envVal)
    }
}
```

**Путь 2** — `cmd/cppworker/handlers_config.go:640-652` (при `/config/reload`):
```go
// RAM fallback flags ?? ??????????? ? cppbackend.Config, ?? ??? reload
// ?? .env ?? ???????????? ??, ????? runtime-?????? ?????????????? env.
if envVal := os.Getenv("CPPWORKER_RAM_FALLBACK_N_CTX"); envVal != "" {
    *ramFallbackNCtx = parseBoolEnv(envVal)
}
```

**Путь 3** — `cmd/cppworker/handlers.go:305-316` (тоже при reload):
```go
if envVal := os.Getenv("CPPWORKER_RAM_FALLBACK_N_CTX"); envVal != "" {
    *ramFallbackNCtx = parseBoolEnv(envVal)
}
```

**Поведение**:
- При старте: `--ram-fallback-n-ctx=false` (CLI flag) + `CPPWORKER_RAM_FALLBACK_N_CTX=true` (env)
  → flag wins, runtime = false. Корректно, логируется.
- При `POST /api/v1/cppworker/config/reload`: env wins (no flag check), runtime = true. **Silent change**, без лога.

**Тестовое воспроизведение**:
```bash
# Start with flag false
./cppworker --ram-fallback-n-ctx=false &
# Env says true
export CPPWORKER_RAM_FALLBACK_N_CTX=true
# Trigger reload
curl -X POST -H "X-API-Token: $TOKEN" http://localhost:18092/api/v1/cppworker/config/reload
# Now runtime config is true, NOT false as flag said. No log.
```

## Архитектурный вопрос: имеет ли смысл total `streamTimeout`?

**Короткий ответ: НЕТ, для LLM streaming — не имеет.**

### Почему total stream timeout — неправильный механизм

1. **Непредсказуемая длина ответа**: LLM может сгенерировать 10 токенов или 10 000.
   В одном use case (короткий ответ на "сколько будет 2+2") хватит 5 секунд.
   В другом (объяснить кодовую базу, написать эссе) — может быть 5 минут.
2. **Conversation history растёт**: на 2-м вопросе сессии prompt в 5-10 раз длиннее,
   generation занимает больше времени даже для ответа того же размера.
3. **"Thinking" модели** (Qwen3-thinking, DeepSeek-R1) имеют variable thinking phase —
   от 5 секунд до 5+ минут ДО первого видимого токена.
4. **Per-model profiling не помогает**: `ModelLatencyTracker.GetOrComputeTimeout`
   использует `4096 / avgTokensPerSec` — это эвристика для "typical" ответа, но
   не работает для OpenWebUI multi-turn ("Дай развёрнутый ответ" = 4000+ токенов
   с reasoning).
5. **Hangs не проявляются как total time**: если cppworker повис, он перестаёт
   отправлять chunks. Это idle timeout, не total time. Если cppworker шлёт chunks
   (даже медленно), юзер хочет получить ответ.

### Правильный дизайн

Вместо total stream timeout использовать:

| Mechanism | Что ловит | Default | Per-model override |
|-----------|-----------|---------|-------------------|
| `firstByteTimeout` (N сек до первого chunk) | Зависание при prompt prefill (CPU/partial offload) | 900s (15 min) | `llamaCppModelProfiles[].firstByteTimeoutSec` |
| `streamingIdleTimeout` (N сек между chunks) | Зависание в inference, segfault recovery, network stuck | 600s (10 min) | `llamaCppModelProfiles[].streamingIdleTimeoutSec` |
| `n_predict` в запросе | Жёсткий лимит на generation length | 4096 (config) | per-request или per-model profile |

Total stream timeout оставить **только как safety net против зависшего процесса,
который по какой-то причине шлёт мусорные chunks бесконечно**. И ставить его
**намного больше** idle timeout (например, 2x или 3x от idle). Никогда не как
"лимит на длину ответа".

### Конкретный recommendation для ollamalegion

**Удалить** `LB_LLAMACPP_STREAM_TIMEOUT_SEC` env override (R60.17 уже выключил,
но код остался). Заменить на:

1. **`LB_STREAMING_IDLE_TIMEOUT_SEC`** (env, реализовать) — для быстрого
   override idle timeout без правки config.json
2. **Удалить** phantom `LB_STREAMING_IDLE_TIMEOUT_SEC` references из
   `streaming.go:322/325` (если env не реализован — убрать обещание из ошибки)
3. **Реализовать** `StreamingMaxDuration` (или удалить) — это обещание
   конфига, которое не выполняется
4. **Исправить** duplicate env handling в cppworker (3 раза для одной переменной)

## Memory save

Cross-project lesson (сохранить в agent memory):
- **Жёсткий total stream timeout — неправильный механизм для LLM**.
  Используйте idle timeout (no chunks for N sec) и first-byte timeout.
- **Per-model profile vs env override**: env wins над config (по дизайну fail-fast),
  но env wins даже над per-model profile — это OK для break-glass, но НЕ для
  production defaults. Default лучше держать в config.json / per-model profile.
- **Duplicate env processing** — типичный trap: одна переменная обрабатывается
  в startup path и в reload path с разной логикой → silent state divergence.
  Решение: единый `apply*FromEnv()` helper, вызываемый из обоих мест.
- **Phantom env vars / dead config fields** — задокументированы, но не реализованы.
  Всегда `grep` на `os.Getenv` перед тем, как обещать env var в error message.
