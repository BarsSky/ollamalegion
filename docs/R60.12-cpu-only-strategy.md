# R60.12 — AutoTune `cpu_only` strategy: why reload is slow on small VRAM

> **Date:** 2026-09-07
> **Status:** Documented + warn-log added
> **Scope:** Reference for operators

## Problem

When the requested `n_ctx` for a model exceeds available VRAM (even with
full partial offload, `gpu_layers=-2`), cppworker's adaptive strategy
selects `stage="cpu_only"`. This means:

- All model weights stay in RAM (madvise/dontneed, but still in memory)
- The KV-cache is allocated in **system RAM**, not VRAM
- No GPU is used for inference (or only minimal use)

For large models (5GB+) with very high `n_ctx` (131072+), this makes
reload very slow:
- Read 5GB GGUF from disk
- Allocate 131072 × 36_layers × 4096_hidden × 2_KV × 2_bytes ≈ **48 GB** of system RAM
- Touch every page to populate CPU caches

**Typical wall-clock on RTX 3070 8GB (Linux, NVMe SSD, DDR4):**
| Model size | n_ctx  | Stage     | Reload time |
|------------|--------|-----------|-------------|
| 5GB (Qwen3-4B) | 32768  | exact_fit | 5-15s       |
| 5GB (Qwen3-4B) | 65536  | partial_offload | 15-30s |
| 5GB (Qwen3-4B) | 131072 | **cpu_only** | **60-180s** |
| 5GB (Qwen3-4B) | 262144 | **cpu_only** | **300-600s** |

## Symptoms

1. **Long Retry-After** — clients see 503 with `Retry-After: 90-120s`
2. **No GPU activity** during reload — `nvidia-smi` shows 0% util
3. **RAM consumption spikes** — `free -h` shows dramatic increase
4. **EventBus events** show `EventAutoTuneReloadTriggered` with `reason`
   like `n_ctx 131072 → 69893 (over-allocation fix)` or `cpu_only: kvType=f16, n_ctx=131072/131072, max_viable=202375`

## R60.12 mitigations

1. **Warning log added** (R60.12, 2026-09-07):
   ```
   queryAdaptiveStrategy: CPU-only strategy selected (R60.12)
     model=qwen3-4b
     target_n_ctx=131072
     gpu_layers=0
     kv_cache_type=f16
     warning="reload will be slow (60-180s) due to RAM fallback"
     recommendation="for 8GB VRAM, use n_ctx <= 65536 with kvCacheType=q4_0"
   ```
   Operators see this in `docker logs ol-bundled-balancer` immediately.

2. **Operator guidance** (recommended limits for 8GB VRAM):

   | Model size  | Max recommended n_ctx | kv_cache_type |
   |-------------|----------------------|---------------|
   | < 1.5GB     | 131072               | q4_0 (auto)   |
   | 1.5-3GB     | 65536                | q4_0 (auto)   |
   | 3-7GB       | 32768                | q4_0 (auto)   |
   | 7-15GB      | 16384                | q4_0 (auto)   |
   | > 15GB      | NOT RECOMMENDED on 8GB | (use 24GB+ GPU) |

3. **Workaround for OpenWebUI** (avoid user-requested 131072):
   - WebUI GGUF detail page: set explicit `n_ctx` in profile
   - Profile config (`/api/v1/cppworker/model-profiles/{name}`):
     `contextLength: 32768` (or `auto` for balancer to pick)

## Out of scope (separate tickets)

- **Capping client-requested n_ctx**: not done in R60.12 (would require
  clamping in DecidePreflight, breaking OpenWebUI UX)
- **Pre-loading smaller model before unload**: not implemented
- **Reducing kv_cache_type automatically**: cppworker's adaptive strategy
  already tries q8_0 / q4_0 but for very large n_ctx+small VRAM, even q4_0
  doesn't fit. No fix on balancer side.
