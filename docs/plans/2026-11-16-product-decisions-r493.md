# Продуктовые решения: что нужно выбрать, а не «доделать»

**Дата:** 2026-11-16 · **Статус:** меморандум (решение за оператором) · Основание:
долги 12n/16/17/18 в `docs/architecture/debts.ru.md` и живые числа второго стенда
(`docs/plans/2026-11-16-second-stand-qwen38-speed.md`)

Четыре пункта реестра — не дефекты, а развилки: каждый вариант рабочий, но
меняет контракт или ресурсы. Ниже варианты, цена и что произойдёт с уже
работающим стендом. **Ничего не выбрано специально** — это решает оператор.

---

## 1. Долг 12n: `algorithm` — переключать выбор или убрать поле

Сейчас: значения `roundrobin`/`leastconn`/`resource-aware`/`model-affinity`
проходят whitelist, сохраняются, отдаются API рядом с
`effectiveAlgorithm: "unified-multistage"`, и предупреждают в лог при старте,
смене и импорте (R493). Поведение выбора от них не зависит.

| Вариант | Что делать | Цена | Риск |
|---|---|---|---|
| **A. Оставить как есть** (прозрачно) | ничего | 0 | операторы продолжают спрашивать «почему не работает»; но лог и API отвечают за нас |
| **B. Убрать поле** | выкинуть `algorithm` из whitelist, из `GET/PUT cluster/config`, из импорта/экспорта; на `PUT` с полем — 400 с объяснением | средняя: правки в `internal/api` + тесты + доки + миграция существующих `.env`/конфигов на стендах (значение просто перестанет приниматься) | сломает конфиги, где поле сейчас есть (второй стенд: `LB_ALGORITHM=resource-aware`) |
| **C. Реализовать алгоритмы** | `leastconn` (по активным запросам), `roundrobin` (детерминированный счётчик), `resource-aware` = текущий; выбор — ветка в `selectBackend` | большая: новый код выбора + тесты на каждый + сохранение всех R447/R480/R493-правил (окно, сессия, холодный старт) | самый опасный: правила окна/сессии наработаны живыми дефектами; дублирование логики в трёх алгоритмах вернёт расхождения |

**Рекомендация:** A сейчас, B — при следующей чистке конфигов (после того как
стенды перестанут полагаться на поле). C — только если появится реальная
потребность: текущий выбор уже учитывает нагрузку и окно, «leastconn» даст
единицы процентов.

## 2. Долг 16: семантика окна по протоколам (per-seq как в Ollama против total)

Сейчас: `contextLength` — суммарное окно, `contextPerSeq` — на слот; llama.cpp
делит окно между `parallel`. Ollama-клиенты исторически читают `num_ctx` как
**окно на запрос** (per-seq), OpenAI-клиенты вообще не знают про окно.

Живой факт (второй стенд): профиль `contextPerSeq 131072`, `parallel 1`, но
загружено `180224`/`188416`; запрос с `184100` токенами получил 503 + reload.
Клиент (Cline) считает, что у него окно = объявленное в настройках (96k–128k),
и это расходится с тем, что реально загружено.

| Вариант | Что делать | Цена | Риск |
|---|---|---|---|
| **A. Документировать** (сейчас) | таблица величин в `docs/architecture/context-numbers.ru.md`, `effectiveContextLength` в профиле | 0 | клиент продолжает гадать; но есть поле, по которому он может жить |
| **B. Единая семантика per-seq** | `/api/ps`, `/api/show`, `/v1/models` и `X-Model-Context-Length` отдают **окно на слот**; суммарное — отдельным полем | средняя: правки в 4–5 ответах + golden-тесты клиентов | сломает клиентов, которые читают «total» как окно запроса (сейчас таких большинство) |
| **C. Явные два поля** | везде отдавать `context_total` и `context_per_seq` (имена по поверхности), старое поле оставить как алиас на total | средняя | API раздувается, но миграция безболезненная |

**Рекомендация:** C. Это единственный вариант, который не выбирает за клиента:
оба числа есть, старые поля не ломаются, новые клиенты читают однозначное.

## 3. Долг 17: авто-снижение `parallel` под запрос одного клиента

Сейчас: `parallel` фиксирован профилем (на втором стенде 1). Соблазн: если в
полёте один запрос — отдать ему всё окно (`n_ctx_seq = n_ctx`), при нескольких —
поделить. Цена: смена `parallel` на живой модели = перезагрузка (десятки секунд
на 27B), то есть выигрыш окна оплачивается простоем.

**Рекомендация:** не делать автоматику. Правильное решение уже есть — профиль
`parallel=1` + `contextPerSeq` (второй стенд так и настроен). Авто-снижение
даст выигрыш только при редких одиночных запросах и будет стоить reload'ов.

## 4. Долг 18: автоподбор `n_predict` по свободной VRAM

Сейчас: бюджет вывода считается от клиентского `max_tokens` и свободного окна
(R463), VRAM напрямую не учитывается. Живой случай: при почти полном окне бюджет
был 2169 токенов, модель потратила их на размышления → пустой ответ (R493
исправил: теперь срабатывает повтор без thinking, а если нет — приходит
пояснение).

**Рекомендация:** не делать. `n_predict` — про длину ответа, а не про VRAM;
привязка к свободной VRAM сделает поведение непредсказуемым (тот же запрос
днём и ночью даст разные ответы по длине). Достаточно того, что бюджет честно
упирается в окно (R463) и объясняется клиенту.

---

## Что нужно от оператора

1. **12n:** A / B / C (рекомендация — A).
2. **16:** A / B / C (рекомендация — C).
3. **17 и 18:** подтвердить «не делать» (иначе — приоритет и требования).

После ответа: 12n закрывается как решение (или открывается работа по C),
16 превращается в задачу на ответы API (C: два поля + алиас), 17/18 — закрываются
как «сознательно нет» с записью причины.
