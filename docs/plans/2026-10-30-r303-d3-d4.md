## 2. Разбор причин

### 2.1 D3, первая половина: заявка на загрузку без владельца

`internal/cppbackend/backend.go` держит per-model «заявку на загрузку»:

```go
loading map[string]chan struct{}   // ключ — имя модели
```

* `TryLockLoad` / `TryLockReload` кладут канал в мапу, `UnlockLoad` — закрывает и
  удаляет.
* Пока канал в мапе: `IsLoading(name) == true` → `handleUnloadModel` отвечает
  **409 «model is currently loading»** (`handlers_model.go`), а второй load уходит
  в `respondWhileAnotherLoadInProgress`.
* **Ключевой дефект №1:** в sync-ветке (`?wait=true`) вызывался
  `backend.WaitForLoad(name)` — ожидание канала **без таймаута** (`backend.go:2778`).
  Заявка, которую не снял её владелец (фоновая горутина умерла / C-мост завис на
  узле раскладки), держала запрос вечно. Клиент получал тишину, а строки в логе
  не было, потому что `loggingMiddleware` пишет строку только ПОСЛЕ выхода из
  обработчика (`cmd/cppworker/utils.go:145`).
* **Ключевой дефект №2:** у заявки не было ни времени, ни владельца. Отличить
  «реально грузится» от «заявка осталась от мёртвой горутины» было нечем — поэтому
  единственным лечением был рестарт процесса.

Тот же бесконечный `WaitForLoad` был ещё в пяти местах:
`handlers_model.go` (reload), `handlers_model_async.go`, `lazyload.go` (×2),
`inference.go`.

### 2.2 D3, вторая половина: in-flight без возраста

`internal/cppbackend/inflight.go` считал только число активных запросов на
модель. `in_flight_requests {"gemma": 3}` не отличим от нормальной длинной
генерации: ни возраста, ни того, чей это запрос. В отчёте записи висели от
18:46 до 18:58.

Освобождение счётчика гарантировано (`defer Dec` на всех пяти `Inc`-точках),
поэтому «не снятый» in-flight означает одно из двух:

1. обработчик **не вернулся** (C-вызов `llama_decode` на зависшем RPC-узле — это
   не отменяется из Go);
2. вернулся, но `Dec` был на другом имени модели (алиас/каноническое имя).

R303 не «обнуляет» счётчики (слепой сброс разрешил бы выгрузку под живой
генерацией — это use-after-free в C-мосте, ровно то, ради чего guard и вводился).
Вместо этого состояние стало **наблюдаемым** (`in_flight_age_sec`,
`in_flight_oldest_sec`, `active_query_age_sec` в `/api/models`), а все места, где
in-flight мешал управлению моделью, получили предел ожидания и типизированный
отказ.

ВАЖНО для оператора: три записи в `/api/infer/active`, которые «никто не снял» —
это, скорее всего, не мусор в мониторе, а ЖИВЫЕ горутины, застрявшие в C-вызове
(`llama_decode` на зависшем RPC-узле) либо в ожидании записи в мёртвый сокет.
R303 делает их возраст видимым, но не удаляет: удаление записи скрыло бы
зависший C-вызов и разрешило бы выгрузку модели под ним. Возраст + `/api/info` +
`POST /api/models/unload?force=true` (отмена генераций через `CancelByModel`) —
вот честный путь, а не подчистка счётчика.

### 2.3 D4: решение принималось по устаревшему кэшу, и отказ врал числами

Цепочка, восстановленная по коду:

1. `proxy.go:1288` → `selectBackendPreferWindow` → `selectModelCopyForWindow`
   (`model_copy_window_r118.go`). Кандидаты берутся **только из кэша метрик**
   (`collectModelCopyCandidates` требует `backendHasModel`, т.е. запись в
   `metricsMgr.llamaMetrics`).
2. Кэш опрашивает узлы раз в ~30 c (`rpcDeviceTTL = 30 s`). Модель, загруженную
   на доноре 30 секунд назад, балансер ещё не видит → копий НЕТ → выбор падает на
   **пустой** узел (`selectBackend`).
3. `preflightNCtxReload` (`nctx_reload_handlers.go`) на пустом узле:
   `resolveLoadedWindowNCtx` честно возвращает `loadedWindowAbsent` (= «модели
   здесь нет»), `loaded_n_ctx=0` → секция «loaded < requested» планирует
   **загрузку с нуля** и ждёт `LB_NCTX_PREFLIGHT_WAIT_SEC` (по умолчанию 240 c).
4. Загрузка на мастере не начинается (R119: «модели нет — перезагрузкой её не
   создать»), в логах тишина.
5. По истечении ожидания клиент получает
   `503 … being reloaded to n_ctx=32768 (loaded=0)` — текст, который в этом
   состоянии **неверен**: перезагрузки нет, а «loaded=0» относится к пустому узлу,
   тогда как модель жива на доноре.

То есть D4 — это не «медленная перезагрузка», а **неверный выбор узла на
основании отстающего кэша** плюс **отказ, который не называет состояние**.

## 3. Что изменено

### 3.1 `internal/cppbackend/load_claims_r303.go` (новый файл)

Заявка на загрузку получает метаданные (`startedAt`, `requester`) и публичный
снимок:

```go
type LoadClaimR303 struct {
    Model, Requester string
    AgeSec           float64
    LoadingInstance  bool   // есть инстанс модели в StateLoading (живая загрузка)
    ModelLoaded      bool
}
```

Новые методы:

| метод | назначение |
|---|---|
| `LoadClaimR303(name)` | снимок заявки (возраст, владелец, живой ли инстанс) |
| `LoadClaimsR303()` | все заявки, детерминированный порядок |
| `TryLockLoadR303(name, requester)` / `TryLockReloadR303(...)` | взятие заявки с указанием владельца |
| `WaitForLoadTimeoutR303(name, d)` | ограниченное ожидание: `(loaded, timedOut)` |
| `ReclaimStaleLoadClaimR303(name, minAge)` | снятие МЁРТВОЙ заявки |

Правило снятия — только по положительному признаку смерти: заявка старше
`minAge` **и** в реестре нет инстанса модели в состоянии `StateLoading`. Заявка с
живым инстансом не снимается никогда: вторая `LoadModelWithOpts` на тот же файл —
двойная VRAM и `SIGABRT` в C-мосте.

### 3.2 `cmd/cppworker/load_progress_r303.go` (новый файл)

* `CPPWORKER_LOAD_WAIT_MAX_SEC` (default **90**, `0` = без предела — прежнее
  поведение) — предел ожидания чужой загрузки в sync-путях.
* `CPPWORKER_LOAD_STALE_SEC` (default **300**, `0` = снимать сразу — стенд) —
  возраст, после которого заявка без живого инстанса считается мёртвой.
* `writeLoadInProgressR303(w, name, waited)` — типизированный отказ вместо тишины:

```json
{"status":"load_in_progress" | "load_stuck",
 "error":"…","model":"…","loading":true,
 "waitedMs":…, "loadWaitLimitSec":…, "retryAfterMs":3000,
 "claimAgeSec":…, "claimRequester":"reload",
 "loadingInstance":false, "stale":true, "staleAfterSec":300,
 "hint":"…"}
```

`status=load_stuck` — это ровно то состояние, в котором раньше требовался
перезапуск контейнера: заявка висит дольше `CPPWORKER_LOAD_STALE_SEC` и живого
инстанса нет. Ручка `Retry-After` выставляется всегда.

### 3.3 Точки, где убрано бесконечное ожидание

| файл | что было | что стало |
|---|---|---|
| `handlers_model_async.go` (`respondWhileAnotherLoadInProgress`, sync) | `backend.WaitForLoad` | `waitLoadBoundedR303` + `writeLoadInProgressR303` |
| `handlers_model.go` (reload, «другая горутина уже грузит») | `backend.WaitForLoad` | то же |
| `lazyload.go` (загрузка по требованию) | `backend.WaitForLoad` | `WaitForLoadTimeoutR303(..., loadWaitMaxR303())` |
| `lazyload.go` (auto-load при старте) | `backend.WaitForLoad` | ограниченное ожидание + отдельный лог «still loading after limit» |
| `inference.go` (RAM-fallback) | `backend.WaitForLoad` | ограниченное ожидание |
| `handlers_model.go` load / load-with-params / lazyload / inference | `TryLockLoad` | `reclaimStaleClaimR303` + `TryLockLoadR303` (снимает мёртвую заявку ДО того, как упереться в неё) |

Страж от возврата регрессии: `cmd/cppworker/wait_guard_r303_test.go` —
`TestR303_NoUnboundedWaitForLoad` сканирует не-тестовые `.go` в `cmd/cppworker` и
падает, если встретит `WaitForLoad(` вместо `WaitForLoadTimeoutR303(`.

### 3.4 `handleUnloadModel` — 409 больше не «вечный»

* Мёртвая заявка снимается до проверки (`reclaimStaleClaimR303(name, "unload")`),
  и unload продолжается обычным путём.
* В 409 добавлены `claimAgeSec`, `claimRequester`, `loadingInstance`,
  `staleAfterSec` — видно, ЧТО и СКОЛЬКО держит модель.
* Если `force=true` не помог за 15 c (C-мост не отпустил), вместо прежнего
  «молча идём дальше и отдаём 404/200» теперь `writeLoadInProgressR303` с
  возрастом заявки: `status=load_stuck` + инструкция.

### 3.5 Наблюдаемость

* `internal/cppbackend/inflight.go`: `AgesR303()`, `OldestAgeR303()`; возраст
  ставится на переходе 0→1 и снимается на последнем `Dec`/`Reset`.
* `GET /api/info`: `load_claims[]` (`model`, `age_sec`, `requester`,
  `loading_instance`, `model_loaded`), `in_flight_age_sec`,
  `in_flight_oldest_model`/`in_flight_oldest_sec`, `load_wait_limit_sec`,
  `load_stale_after_sec`.
* `GET /api/models` (per-model): `active_query_age_sec`, `load_claim_age_sec`,
  `load_claim_requester`, `load_claim_stale`.

### 3.6 D4: живой опрос вместо устаревшего кэша — `internal/balancer/live_copy_probe_r303.go` (новый)

Правило: **прежде чем «грузить/растить окно ЗДЕСЬ», спросить живой кластер, где
модель уже загружена.**

* `findLiveLoadedCopyR303(model, needPerSeq, exclude)` — опрашивает здоровые
  llama.cpp-узлы (не R92-воркеры, не disabled, не исключённые), берёт
  `resolveLoadedWindowNCtx(..., allowRefresh=true)` (это существующий R118-механизм,
  третий не писался) и `loadedPerSeqNCtx` — окно **на слот**. Предпочитает копию,
  покрывающую запрос; иначе — с самым большим окном (растить там дешевле, чем
  грузить с нуля); при равенстве — по ID.
* Кэш результата 3 c (`liveCopyProbeTTLR303`) — иначе каждый клиентский запрос
  бил бы по всем узлам; общий предел опроса 4 c.
* `modelNotLoadedHereButAliveElsewhereR303(backendID, model, need)` — для
  preflight: срабатывает **только** на `loadedWindowAbsent` (опрос прошёл и модели
  нет). `loadedWindowUnknown` (опрос не прошёл) сюда не попадает, иначе один
  недоступный узел блокировал бы нормальную загрузку.

Точки применения:

1. `model_copy_window_r118.go` → `selectBackendPreferWindow` (Ollama-поверхность):
   копий в кэше нет → живой опрос → узел с загруженной моделью.
2. `model_copy_window_r118.go` → `selectLlamaCppBackendForModelWithNCtx`
   (OpenAI-поверхность): то же.
3. `nctx_reload_handlers.go` → `preflightNCtxReload`: если модель на этом узле
   отсутствует (`loadedWindowAbsent`), а на другом жива — **загрузка с нуля не
   планируется**, клиент получает немедленный ответ с именем узла и его окном:

   ```
   model "gemma-…" is not loaded on backend cppworker-gpu-bundled-agent,
   but it is already loaded on backend cppworker-cyborg-bundled-agent
   (n_ctx=32768 per slot); no new load was started on cppworker-gpu-bundled-agent
   — retry and the request will be routed to cppworker-cyborg-bundled-agent
   ```

4. Текст финального 503 перестал врать. Было всегда `(loaded=%d)`, стало по
   состоянию:

   * `(loaded=N per slot)` — окно действительно известно;
   * `(not loaded on this backend — a load was requested)`;
   * `(loaded state unknown — probe failed)`.

5. `internal/balancer/proxy.go` — **переезд залипшей сессии**. Сессия, привязанная
   к узлу, где модели уже нет, раньше не могла уехать: `selectBackendPreferWindow`
   вызывается только когда `targetBackend == ""`, а залипшая сессия приходит с
   готовым `targetBackend` из `sessionMgr`. Теперь перед слотом стоит проверка
   `modelAbsentOnBackendR303` (только положительное доказательство: живой опрос
   узла прошёл и модели там нет) → `findLiveLoadedCopyR303` → `targetBackend`
   переезжает, и привязка сессии перевешивается на новый узел (иначе следующий
   запрос вернулся бы на пустой узел — пинг-понг 503). «Состояние неизвестно»
   (узел не отвечает) переезд НЕ вызывает.

Флаг оператора **`LB_LIVE_COPY_PROBE`** (default `1`, горячий): зарегистрирован в
`internal/settings/builtin_r278.go`, проброшен в `deployments/docker-compose.stack.yml`,
описан в `deployments/.env.example`, `docs/api/env-vars.md`, `docs/api/env-vars.ru.md`.
`0` возвращает прежнее поведение без рестарта.

## 5. Чего НЕ проверено живьём (без этого R303 не «PASS»)

Честно, чтобы не выдать частичный успех за закрытие:

1. **D3 на настоящем зависшем C-мосту не воспроизводился.** Юнит-тесты
   воспроизводят состояние «заявка без живого инстанса» (это и есть условие
   зависания), но сам факт, что llama.cpp на мёртвом RPC-узле зависает в
   `LoadModelWithOpts`/`llama_decode`, здесь не проверялся. R303 гарантирует:
   клиент получает типизированный ответ за `CPPWORKER_LOAD_WAIT_MAX_SEC`, узел
   выходит из состояния «409 навсегда» без рестарта, состояние видно в `/api/info`.
   Если C-вызов действительно не возвращается, освобождается только заявка, но не
   память llama.cpp — для этого остаётся `POST /api/models/unload?force=true`
   (`AbortLoad`) и рестарт.
2. **D4 требует двух живых узлов.** Тест использует два настоящих
   `httptest`-cppworker'а с пустым кэшем метрик — это точная модель дефекта, но не
   стенд с донором по Tailscale. Проверка на стенде:
   * донор держит модель, мастер пуст;
   * клиент с окном, которое на мастере потребовало бы загрузки с нуля;
   * ожидаем в логе балансера `R303: найден узел с уже загруженной моделью`
     и отсутствие `POST /api/models/load` на мастере; латентности в минутах быть
     не должно.
3. **`loaded=0` в отказе** проверено кодом и юнит-тестами сообщения не покрыто
   (сложный fixture preflight'а) — проверять на стенде по тексту ответа.

Рекомендуемые значения для агентских клиентов (Cline/DSH): оставить
`CPPWORKER_LOAD_WAIT_MAX_SEC=90` (клиент получает ответ, а не тишину) и
`LB_NCTX_PREFLIGHT_WAIT_SEC=30` — если по какой-то причине перезагрузка ВСЁ ЖЕ
планируется, клиент узнаёт об этом через 30 c, а не через 4 минуты.
