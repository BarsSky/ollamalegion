# План: модуль ре-экспорта моделей (GGUF / diffusion bundles)

Статус: **Фазы 0–1 реализованы и проверены живьём; Фаза 2 частично (light-образ, UI-блок по `capabilities`); Фаза 3 (torch/full) не начата.** Отложенное ранее решение разблокировано вердиктом инспекции: в файле `Inkling-2-Mini` тензоры контроллеров **есть** → путь `normalize` работает (22 мин 57 с, +1 408 байт шапки, загрузчик принял все 744 тензора).

## 0. Почему отложено и что разблокирует старт

Модуль нужен как фича независимо от исхода, но **объём первой фазы зависит от одного факта** — есть ли в проблемном файле тензоры loop-контроллеров. Инспекция (отдельная задача) отвечает на три вопроса:

1. присутствуют ли `blk.{core_start..core_end-1}.loop_{attn,k,v,mlp}_{down,gain,forget}` и `loop_res_query` / `loop_kv_res_query`;
2. записаны ли ключи `inkling2.loop.core_start/end`, `loop.gate_rank`, `num_loops` и развёрнуты ли массивы `head_count` / `head_count_kv` / `sliding_window_pattern` по визитам (48);
3. совпадает ли `block_count` (48 визитов) с числом физических блоков (24) так, как ожидает b12642.

Развилка:

| Вердикт инспекции | Что делаем | Объём |
|---|---|---|
| Ключей/длин массивов не хватает, тензоры контроллеров **есть** | `normalize` (Фаза 1) закрывает кейс; полный сервис остаётся как фича, но не срочно | малый: скрипт патча + валидация |
| Тензоров контроллеров **нет** | `normalize` не поможет, нужен `convert` из HF-чекпоинта → без модуля не обойтись | Фазы 0–3 |
| Ключи на месте, а загрузчик всё равно падает по другой причине | фиксируем причину, план пересматривается по факту (`print_info` + код загрузчика) | уточнение спеки |

Пока вердикта нет — **ничего из этого не начинаем**, чтобы не строить сервис под сценарий, который может не понадобиться.

## 0.1 Риски, которые план принимает осознанно

**Риск 1. `normalize` может оказаться бесполезным для конкретного файла** (нет контроллеров) — тогда единственный путь `convert`, а он требует исходного чекпоинта и места. Митигация: `inspect` обязан выдавать этот вердикт до запуска тяжёлых операций; UI показывает «нужен ре-экспорт из HF-чекпоинта», а не общую ошибку.

**Риск 2. torch в образе — 5–8 ГБ.** Если конвертация части архитектур без него невозможна, образ становится тяжёлым и его нельзя ставить по умолчанию. Митигация: профиль `reexport` (не входит в `full`), при подтверждённой необходимости — два образа (`-lite` без torch для `inspect/normalize`, `-full` с torch для `convert`); выбор фиксируется по замеру, а не заранее.

**Риск 3. Диск: «вход + выход + запас».** 15 ГБ модель при `convert` требует до ~35–40 ГБ свободных. Митигация: предварительная проверка с числами (`insufficient_space`: сколько нужно/сколько есть), автоочистка неудачных артефактов, лимит `max_input_gb`.

**Риск 4. Долгие задачи и отмена.** Минуты/десятки минут, риск «висящих» задач. Митигация: таймаут, отмена по контексту, TTL для `running` после рестарта сервиса, прогресс по стадиям в UI.

**Риск 5. Расхождение версий конвертера и рантайма.** Файл, собранный новее, чем воркер, снова окажется несовместим. Митигация: `capabilities` публикует оба коммита (`llama_cpp.commit` рантайма и конвертера), `inspect` сравнивает и предупреждает.

**Риск 6. Кэш каталога на воркере.** После успешной задачи файл может не появиться в `/api/models`. Митигация: обязательный `scan` + подтверждение через `GET /api/models`; иначе задача считается не завершённой, даже если файл создан.

**Риск 7. Безопасность путей и токенов.** Сервис работает с файловой системой и моделями. Митигация: разрешённые корни (`${MODELS_DIR}` rw, `${REEXPORT_INPUT_DIR}` ro), отказ на симлинки вне корней, обязательный токен, публикация только через балансер.

**Риск 8. Модуль «есть, но бесполезен»** (профиль поднят, а конвертер не поддерживает нужную архитектуру). Митигация: `capabilities` — единственный источник правды для UI; вкладка с пустым списком форматов не показывается.

**Риск 9. Регресс для тех, кто модуль не включает.** Митигация: отдельный профиль, дефолтные `.env` не меняются, `compose config` проверяется в CI в двух вариантах (с профилем и без), `check-image-tags.ps1` знает новый образ только при его наличии.

## 1. Зачем

Покрытие моделей ограничено форматом, который понимает текущая сборка движка. Живые примеры:

- `Inkling-2-Mini-UD-Q4_K_M.gguf` — loop-развёрнутая схема: 24 физических блока при `block_count=48` и ключе `num_loops`; b12642 читает такую схему только для arch `inkling2_loop`, поэтому файл отвергается (`model_schema_unsupported`, R704).
- image-модели, скачанные как «сырой» набор файлов: роли (diffusion/vae/clip/t5/llm) определяются по содержимому, но набор может требовать ре-экспорта в ожидаемую раскладку (R696).
- Часть репозиториев существует только в формате HF-чекпоинта (safetensors) и требует конвертации в GGUF.

Идея: пользователь выкачивает нужные файлы (например через HF-вкладку WebUI), указывает их модулю, модуль приводит их к формату, который движок точно загрузит, и переводит модель в обычный каталог моделей.

## 2. Не-цели

- Не заменяем `llama.cpp`-конвертер своей реализацией: используем `c/llama.cpp/conversion/` + `gguf-py` из зафиксированного пина (b12642 и далее).
- Не делаем конвертацию «на лету» в воркере: долгие операции не должны жить в горячем пути инференса.
- Не обещаем поддержку всех архитектур: список поддерживаемого определяется версией конвертера и явно публикуется.

## 3. Решение: отдельный сервис, а не встраивание в бэкенды

Причины:

1. **Вес зависимостей.** Конвертер — Python + `numpy` (+ `torch` для части архитектур), `gguf-py`; это сотни мегабайт и минуты/десятки минут на задачу. Встраивание в `cppworker` раздувает базовый образ и риск регрессий инференса.
2. **Изоляция отказов.** Падение конвертера не должно трогать воркер, обслуживающий запросы.
3. **Опциональность.** Профиль `reexport` в compose: есть профиль — есть функциональность; нет профиля — остальной стек работает ровно как раньше (тот же принцип, что у RPC-раскладки).
4. **Квотирование.** Отдельный сервис проще ограничить по CPU/RAM/диску и параллелизму (1 задача).

Сервис — Go-хост (HTTP API, задачи, прогресс) + встроенный Python-вызов конвертера. Образ собирается один и содержит конвертер из пина `c/llama.cpp`.

## 4. Компоненты

### 4.1 Сервис `services/gguf-reexport/`

- `main.go` — HTTP-сервер, graceful shutdown, health, версия из OCI-меток.
- `jobs.go` — очередь (параллелизм 1 по умолчанию, настраивается), таймауты, отмена (контекст), перезапуск «зависших» задач по TTL.
- `store.go` — персист задач: каталог `${REEXPORT_STATE_DIR}/jobs/<id>.json` + `<id>.log`; без БД, чтобы переживать рестарт.
- `runner.go` — запуск конвертера (`python -m conversion ...` или `python convert_hf_to_gguf.py ...`), разбор вывода в прогресс, изоляция рабочего каталога.
- `validate.go` — пост-проверка результата: заголовок GGUF (`arch`, `block_count`, `num_loops`, `key_length`, число тензоров), сверка с ожиданиями, отказ при несоответствии.
- `guard.go` — проверки путей (только внутри `${MODELS_DIR}` и `${REEXPORT_INPUT_DIR}`), лимиты размера/времени/диска, запрет симлинков извне.

### 4.2 Конвертер (внутри образа)

- Источник: `c/llama.cpp/conversion/` и `gguf-py` из зафиксированного пина; версия конвертера публикуется в `capabilities`.
- Поддерживаемые сценарии:
  - **HF → GGUF** (cppworker): одиночный чекпоинт и MoE/loop-архитектуры;
  - **нормализация существующего GGUF** (метаданные/схема): loop-ключи (`num_loops`, `loop.core_start/end`, `loop.gate_rank`), развёрнутые по визитам массивы, `attention.key_length(_swa)`; перепаковка тензоров не требуется;
  - **набор файлов → bundle** (imageworker): раскладка по ролям (diffusion/vae/clip_l/clip_g/t5xxl/llm/clip_vision), запись `profile.json` и `sd-server.config.json` (R696-правила).
- Режимы: `inspect` (только чтение заголовка и вердикт), `normalize` (метаданные), `convert` (полный ре-экспорт из чекпоинта).

### 4.3 Интеграция с бэкендами

- cppworker: после успешной задачи — `POST /api/models/scan` (существующий механизм), затем `GET /api/models` для подтверждения, что модель видна.
- imageworker: пересканирование моделей image (его собственный эндпоинт), затем проверка `compat`-вердикта (R696).
- Балансер: получить уведомление о появлении модели (событие) — не обязательно в первой версии, достаточно ручного обновления панели.

### 4.4 WebUI

- Вкладка **«Ре-экспорт»** на странице моделей, видна **только** если `GET /api/reexport/capabilities` доступен (проверка через балансер-прокси или прямой вызов — см. п.7).
- Содержимое: список поддерживаемых архитектур/форматов + версия конвертера; форма создания задачи (выбор каталога/файлов из уже скачанного, целевой режим `inspect|normalize|convert`, опции); список задач с прогрессом/временем/ошибкой; кнопки «Отменить», «Пересканировать модели».
- При отсутствии модуля вкладки нет вообще (никаких прочерков и «недоступно»).

## 5. API-контракт (v1)

```
GET  /api/reexport/capabilities
     -> {version, llama_cpp: {commit, date}, converter_version, modes: [inspect|normalize|convert],
         formats: [{backend: cppworker|imageworker, from: [...], to: [...]}],
         limits: {max_input_gb, max_job_minutes, parallelism}}

POST /api/reexport/jobs
     body: {backend: "cppworker"|"imageworker", mode: "inspect"|"normalize"|"convert",
            source: {dir?: "…", files?: ["…"]}, target: {dir: "…", name?: "…"},
            options: {arch_hint?: "inkling2_loop", num_loops?: 3, core_start?: 6, core_end?: 18,
                      outtype?: "q4_k_m"|"f16"|"copy", roles?: {...}}}
     -> 202 {id, status: "queued", created_at}

GET  /api/reexport/jobs/{id}
     -> {id, status: queued|running|succeeded|failed|canceled,
         progress: {stage: "reading"|"writing"|"validating", percent},
         started_at, finished_at, duration_ms,
         result?: {path, size_bytes, arch, block_count, physical_blocks, num_loops},
         error?: {code, message, hint}, log_url}

GET  /api/reexport/jobs/{id}/log (text/plain, tail)
DELETE /api/reexport/jobs/{id}   -> отмена (если running) или удаление записи
GET  /api/reexport/health        -> {ok, version}
```

Коды ошибок: `source_not_found`, `path_not_allowed`, `unsupported_arch`, `converter_error`, `validation_failed`, `insufficient_space`, `timeout`, `canceled`.

## 6. Конфигурация / compose

Новый профиль `reexport` (по умолчанию выключен):

```yaml
  gguf-reexport:
    image: ${IMAGE_REGISTRY:-}ollama-legion/gguf-reexport:${GGUF_REEXPORT_TAG:-dev}
    profiles: ["reexport"]
    environment:
      - REEXPORT_STATE_DIR=/app/state
      - REEXPORT_INPUT_DIR=/app/downloads      # откуда брать скачанные файлы
      - REEXPORT_MAX_INPUT_GB=${REEXPORT_MAX_INPUT_GB:-60}
      - REEXPORT_MAX_JOB_MINUTES=${REEXPORT_MAX_JOB_MINUTES:-180}
      - LB_API_TOKEN=${CPPWORKER_API_TOKEN}     # для scan/verify на бэкендах
    volumes:
      - ${MODELS_DIR:-../models}:/app/models:rw
      - ${DOWNLOADS_DIR:-../downloads}:/app/downloads:ro
      - reexport_state:/app/state
    healthcheck: curl -fsS http://localhost:8080/api/reexport/health
```

Переменные в `.env.example`: `GGUF_REEXPORT_TAG`, `DOWNLOADS_DIR`, `REEXPORT_MAX_INPUT_GB`, `REEXPORT_MAX_JOB_MINUTES`, `REEXPORT_PORT_HOST`.
Версии: OCI-метки (`org.opencontainers.image.revision`, `...created`, плюс `ru.ollamalegion.llama.commit` конвертера), запись в `release-manifest.json`, поддержка в `scripts/release-all.ps1 -Services` и проверка в `scripts/check-image-tags.ps1`.

## 7. Обнаружение модуля в WebUI

Вариант предпочтительный: **прокси через балансер** — `GET /api/v1/reexport/capabilities` → 200, если сервис настроен (`REEXPORT_URL` в env балансера), 404 если нет. Тогда:
- нет CORS-проблем и лишних портов, наружу торчит только балансер;
- WebUI включает вкладку по факту 200 (тот же паттерн, что у других optional-модулей).
Fallback: прямой вызов по `${REEXPORT_PORT_HOST}` с CORS — только если прокси окажется неудобен.

## 8. Валидация результата (обязательно)

После каждой задачи:
1. Прочитать заголовок результата: `general.architecture`, `block_count`, физические блоки (число `blk.N.*`), `num_loops`/`loop.*`, `attention.key_length(_swa)`.
2. Для `normalize`: сверить, что ключи добавлены, длины массивов = числу визитов, тензоры не тронуты (хэш набора тензоров до/после).
3. Для `convert`: проверить, что «физические блоки + loop-ключи» согласованы; иначе `validation_failed` с объяснением.
4. **Пробная загрузка** (опционально, настраиваемо): `POST /api/models/load` на воркере, дождаться `loaded` или `failed` с причиной; результат сохраняется в записи задачи. Это то, что отличает «файл пересобран» от «файл работает».

## 9. Безопасность и лимиты

- Разрешённые корни: только `${MODELS_DIR}` (rw) и `${REEXPORT_INPUT_DIR}` (ro); `filepath.Clean` + отказ на симлинки, выходящие за корни.
- Токен: сервис не публикуется наружу без токена; при прокси через балансер — обычная авторизация балансера, плюс внутренний токен.
- Квоты: `max_input_gb`, `max_job_minutes`, свободное место (отказ `insufficient_space` заранее, с требуемым объёмом в сообщении — оценка «вход + выход + 1 ГБ»).
- Параллелизм 1 (настраивается); задача не стартует, если уже есть running.
- Никаких сетевых загрузок: модуль работает **только** с уже скачанными файлами (скачивание — существующая HF-вкладка). Это упрощает безопасность и делает поведение предсказуемым.

## 10. Наблюдаемость

- Лог задачи в `${REEXPORT_STATE_DIR}/jobs/<id>.log`, доступен по `/log` (tail N строк).
- Счётчики: `jobs_total{status}`, `job_duration_seconds`, `bytes_written_total`, `validation_failures_total`.
- В WebUI: прогресс по стадиям (`reading → writing → validating → loading`), явная причина отказа и подсказка (например «нужен ре-экспорт из HF-чекпоинта, у файла нет тензоров контроллеров»).

## 11. План реализации по фазам

**Фаза 0 — каркас (уже начат исполнителем):** каталог сервиса, HTTP API-скелет, health, версия, профиль `reexport` в compose, `.env.example`, прогон `compose config` с профилем и без, регистрация в релизном скрипте.
Критерий: `docker compose --profile full config -q` валиден; без профиля стек не меняется; сервис отвечает `health`.

**Фаза 1 — `inspect` + `normalize` для GGUF:** чтение заголовка (Go, без Python), вердикт «поддерживается / что не так»; нормализация метаданных (loop-ключи, длины массивов) с сохранением тензоров и проверкой хэшей; `validate` + опциональная пробная загрузка.
Критерий: `Inkling-2-Mini` (если в файле есть loop-контроллеры) проходит `normalize`, грузится, `print_info` показывает 48 визитов при 24 физических; при отсутствии тензоров — честный отказ с кодом `unsupported_arch` и подсказкой.

**Фаза 2 — WebUI:** вкладка по факту `capabilities`, форма задачи (только `inspect|normalize`), список задач, прогресс, отмена, «Пересканировать модели»; i18n ru/en; поведение при отсутствии модуля — вкладки нет.
Критерий: e2e-сценарий в браузере (create → progress → success/failed → rescan), скриншоты, тесты на «нет модуля → нет вкладки».

**Фаза 3 — `convert` (HF → GGUF) для cppworker:** вызов конвертера из пина, `outtype` (copy/f16/q4_k_m), изоляция рабочего каталога, валидация + пробная загрузка; поддержка loop-архитектур через обновлённый `conversion/inkling2.py`.
Критерий: конвертация реального чекпоинта (не только «сухого»), файл грузится; время и размер зафиксированы в отчёте.

**Фаза 4 — imageworker:** режим «набор файлов → bundle»: определение ролей по заголовкам (R696), запись `profile.json`/`sd-server.config.json`, валидация `compat`, пересканирование image-моделей.
Критерий: набор, скачанный через HF, становится загружаемым; вердикт `ready` в UI.

**Фаза 5 — эксплуатация:** метрики, ограничение по диску, автоочистка неудачных артефактов, документация `docs/operations/gguf-reexport.ru.md`, запись в CHANGELOG, включение профиля в release-скрипт и `check-image-tags`.

## 12. Тестирование

- Unit: разбор заголовков (в т.ч. массивы по визитам), `normalize` (ключи/длины/хэши), guard путей, коды ошибок, machine-readable прогресс.
- Integration: мини-GGUF (синтетический) для `normalize`; реальный `Inkling-2-Mini` — «есть контроллеры / нет контроллеров».
- E2E: compose-профиль + WebUI (CDP), задача create → progress → success, rescan, отсутствие вкладки без модуля.
- Регресс: без профиля `reexport` — ни одна существующая проверка не меняется (в т.ч. `check-image-tags`, `run-webui-tests`).

## 13. Риски и открытые вопросы

1. **Тензоры контроллеров.** Если в файле нет `blk.N.loop_*`/`loop_res_query`, `normalize` не поможет — нужен полный ре-экспорт из исходного чекпоинта. План учитывает это как отдельный вердикт `inspect`.
2. **torch в образе.** Если конвертация части архитектур без torch невозможна — образ станет большим (≈5–8 ГБ). Решение: один образ с torch, профиль `reexport` (не по умолчанию). Альтернатива — два образа (`-lite` без torch, `-full`), решается по факту замера.
3. **Место на диске.** Ре-экспорт требует «вход + выход + запас»; оценка в `insufficient_space` должна быть заранее.
4. **Долгие задачи.** 15+ ГБ файлы: нужен таймаут и отмена, плюс предупреждение в UI «может занять N минут».
5. **Согласованность скана.** Воркер может держать кэш каталога; после задачи обязателен `scan` и проверка `GET /api/models`.
6. **Версия конвертера vs версия рантайма.** Файл, сделанный новее рантайма, снова окажется несовместим — `capabilities` должен публиковать оба коммита, а `inspect` — сравнивать.
