## Пункт 1 закрыт: вместимость = фактические слоты (проверено живьём)

**Диагноз был не в очереди, а в источнике вместимости.** Очередь на стенде
работает; завышалась вместимость.

| Проверка | До (R116-profile1) | После (r117-cap1) |
|---|---|---|
| Модель не загружена (`count=0`) | `maxConcurrentRequests=2`, источника не видно | `=1`, `source=model_slots_unknown`, `runtimeModelSlots=0` |
| `parallel=2` загружена | 2 | `=2`, `source=model_slots` |
| `parallel=1` загружена | 1 | `=1`, `source=model_slots` |
| `unload` без запросов в полёте | оставались слоты прошлой модели (2 при `count=0`) | сброс 2→0 в логе (`«слотов у загруженной модели нет — вместимость сброшена»`), `=1`, `model_slots_unknown` |
| `wait_max_sec` (`/api/v1/queue/stats`) | 300 | 900 (= `LB_AUTO_LOAD_WAIT_SEC`) |
| `go test ./cmd/cppworker/` | пачкал отслеживаемый `config/cppworker-defaults.json` | дерево чистое |

Сценарий «два запроса с одной машины» (модель загружена `max_slots=1`,
`num_predict=120`): оба запроса с разными `X-Session-Id` — первый получил слот
сразу (200, `durationMs=250136`), второй **встал в очередь** (`waiting=1`,
`waiting_detail.session = sess-B::Qwen3.8-27B-UD-Q4_K_M::gen`, `position=1`) и
получил слот через 256 с (`unified queue: слот получен после ожидания`). 503 на
300-й секунде (как было до бюджета) не случилось.

Тесты: `pkg/types`, `internal/api` (54 с), `internal/balancer` (104 с, зависания
в этот прогон не было), `cmd/cppworker` — зелёные (`-tags llama_stub`).

## Открытые пункты (координаты уточнены живыми прогонами)

### 1a. Сессии и видимость очереди (остаток пункта 1 входящей передачи)

Что уже есть: `/api/v1/queue/stats` → `admission.waiting_detail[]` = `{session,
backend, waited_ms}` (R91), UI рисует строку с индексом, ключом сессии и временем
(`webui/js/modules/renderers.js`, `queueView` + `queueAdmissionRows`, ~1940–2118).

Чего нет и что нужно решить (это НЕ механическая правка):

* **Ключ сессии живёт в двух местах.** Для Ollama-пути очередь получает ключ из
  `(*Proxy).getSessionIDWithModel` (`internal/balancer/client.go:299`) →
  `proxy.go:1154` (`sessionKey = sessionID`) → `waitForInferenceBackend` →
  `aq.enqueue`. `RequestSessionKey` (`autoload_wait.go:520`) — только fallback,
  когда `sessionID` пуст. Живые наблюдения одного и того же места:
  * с заголовком `X-Session-Id: sess-B` → `sess-B::Qwen3.8-27B-UD-Q4_K_M::gen`
    (клиентский идентификатор, очередь различает запросы);
  * без заголовков (голый curl) → `fp:d1c51dcaef1cbdbe::curl/8.21.0::<модель>::gen`
    — отпечаток IP+User-Agent; у двух запросов одной машины он ОДИНАКОВЫЙ, то
    есть «балансер не различает сессии».
* **Идея из входящей передачи «сессию из `X-Request-Id`» требует осторожности.**
  Тот же ключ — ключ липкости (`sessionMgr.Set/Get`): если добавить per-request
  `X-Request-Id` в синтетический fallback `getSessionIDWithModel`, клиент с
  пофреймовым `X-Request-Id` потеряет привязку к бэкенду. В ветке `X-Client-ID`
  этот id уже добавляется (`::req:`), то есть для Cline поведение уже такое.
* **Минимальный полезный шаг** (то, что просит передача): пометить синтетический
  ключ явно. Ключи `fp:` и `tkn:` порождаются в `client.go` (там же, где
  классифицируются), `usr:`/`cid:`/`sid:`/`chat:`/`req:` — клиентские. Отсюда:
  `session_known` в `waiting_detail`, `unidentified_waiting` в статистике и
  подпись «клиент не различает сессии (IP+User-Agent)» в UI вместо пустой строки.
  Позицию в UI уже можно брать из `position` (его считает `aq.position`), но в
  `waiting_detail` это поле сейчас не отдаётся — добавить.
* Проверять так: загрузить модель `parallel=1`, послать два запроса БЕЗ заголовков
  (получится `fp:`-ключ) и убедиться, что статистика/UI честно говорят «сессии не
  различаются»; затем с `X-Session-Id` — что ключ клиентский.

### 1b. НАЙДЕНО ЖИВЬЁМ: холостой reload n_ctx посреди обслуживания (~10 мин)

Пока ждал в очереди, второй запрос после выдачи слота получил не обслуживание, а
перезагрузку модели:

```
preflightNCtxReload: num_ctx decision ... chosen_source: "profile" (32768)
preflightNCtxReload: detected n_ctx mismatch, scheduling async reload
  loaded_n_ctx: 0, requested_n_ctx: 32768          ← вот это и есть дефект
preflightNCtxReload(async): starting reload ... target_n_ctx: 32768
llamacpp_transport_nonstream.go:101: «модель готова после ожидания reload — запрос
  продолжается», waited_sec: 900
```

`loaded_n_ctx` прочитан как **0** у ЗАГРУЖЕННОЙ модели (за минуту до этого тот же
preflight видел `loaded_n_ctx: 8192` и писал «reload не нужен»). Итог: запрос,
который должен был занять ~4 мин, занял ~20 (256 с в очереди + ~617 с на
бессмысленную перезагрузку + генерация). Правки R117 эту ветку не трогают
(`NCtxBackendState` / `loaded_n_ctx` не менялись), но проверить стоит: похоже на
известную «stale cache»-переходность (ср. `stale_cache_live_refresh_r83_test.go`).

## Грабли окружения (добавлено к входящей передаче)

* **PowerShell + `Start-Process`**: элементы `-ArgumentList` с пробелом НЕ
  квотируются — заголовок `'X-Session-Id: sess-A'` доезжает как `-H X-Session-Id:`
  и лишний URL. Проверено дважды: без кавычек очередь показала `fp:`-отпечаток,
  с вложенными кавычками (`'-H','"X-Session-Id: sess-A"'`) — клиентский ключ.
  Вывод: проверять, что сервер реально видит заголовок, а не только что запрос прошёл.
* `Start-ThreadJob` в этом окружении НЕТ; `Start-Job` рискован (именованные
  каналы). Два параллельных клиента надёжнее всего двумя `Start-Process curl.exe`
  с `-o`/`-D`/`-w` в отдельные файлы.
* `Invoke-WebRequest` для API балансера всегда с `-UseBasicParsing` (иначе 401
  превращается в «HTTP 0» и попытку интерактивного ввода) — из входящей передачи.
* Ждать тик поллера вместимости — 30 с; после `unload`/`load` не проверять
  мгновенно (в этот прогон сброс слотов был виден на 30–50-й секунде).
* `unload` модели с активным запросом отклоняется
  (`model is busy with active inference requests`), нужен `&force=true`.
* Клиентский `--max-time` надо ставить с запасом: у меня `curl --max-time 1200`
  оборвал как раз тот запрос, который ждал 900 с разрешённого ожидания загрузки,
  и результат остался не снятым (сам запрос балансер довёл: «модель готова после
  ожидания reload — запрос продолжается»).
* `debug/*` в дерево не писать: полезные payload'ы держать в `$env:TEMP` и
  копировать в контейнер через `docker cp` (иначе мусор уезжает в коммиты, ср.
  входящую передачу про `debug/*.ndjson`).
