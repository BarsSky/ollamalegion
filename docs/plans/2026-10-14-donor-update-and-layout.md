### 2a. ДОНОР ОБНОВЛЁН — и это НЕ ПОМОГЛО (гипотеза плана опровергнута)

Что было на доноре (живая инвентаризация по SSH, ключ `id_ed25519_donor`):

| Контейнер | Образ | Роль |
|---|---|---|
| `ol-rpc-server` (50052) | `cppworker:gpu-**rpc86-r115b**` | RPC-узел раскладки — **старый** |
| `cppworker-node2` (18092/18034) | `cppworker:gpu-**rpc86-r115d**` | инференс-бэкенд донора (тоже старее мастера `r116c`) |

При этом в env RPC-узла стояло `CPPWORKER_LLAMA_BUILD=1d2869c6e` — **тот же, что у
мастера**, хотя бинарник был из `r115b`. Отсюда ложное «версии совпадают»: гейт
читает env образа, а не бинарник. Прав `docs/plans/2026-10-13-rpc-full-mode.md`:
проверять надо запуском.

Сделано: образ мастера `ollama-legion/cppworker:gpu-rpc86-r116c` (сборка
`CUDA_ARCH=86;120`, `CUDA_VERSION=12.8.0`, tar 2.34 ГБ) передан на донор
(`scp` → `docker load`), `docker-compose.rpc-node.yml` скопирован в
`C:\ollama\ollamalegion\deployments`, старый узел удалён и поднят новый:

```
docker rm -f ol-rpc-server
cd /d C:\ollama\ollamalegion\deployments && set CPPWORKER_GPU_TAG=rpc86-r116c&& set RPC_PORT=50052&& docker compose -f docker-compose.rpc-node.yml up -d
→ CONTAINER ID 402a9aadbb0c  IMAGE ollama-legion/cppworker:gpu-rpc86-r116c  Up 0.0.0.0:50052->50052/tcp  ol-rpc-server
```

**Повторная проба — падение ТО ЖЕ САМОЕ:**

```
[bridge] RPC: узел 192.0.2.10:50052 подключён, его устройств: 1
[bridge] RPC: устройств в раскладке 2 (локальные + удалённые)
SIGABRT: abort
ggml-rpc.cpp:345: Remote RPC server crashed or returned malformed response
{"caller":"cppbackend/backend.go:908","msg":"загрузка отменена: узел раскладки недоступен","servers":"192.0.2.10:50052"}
{"caller":"cppworker/handlers_model_async.go:317","msg":"runAsyncLoad: background load failed"}
```

При этом **узел здоров**: `docker inspect ol-rpc-server` →
`RestartCount=0`, `OOMKilled=false`, `ExitCode=0`, в его логе только
`Accepted client connection` / `Client connection closed` (без ошибок). То есть
узел принимает соединение и молча закрывает его, а клиент мастера считает ответ
неразборчивым. `RestartCount` мастера в этой попытке НЕ вырос (был 3 после первой):
R115-обвязка поймала отказ и отменила загрузку с ошибкой вместо падения процесса.

**Вывод:** «поставить на обе машины один образ» — необходимое, но НЕ достаточное
условие. Причина отказа лежит либо в транспорте до узла (LAN + Docker Desktop),
либо в узле/его CUDA-ядрах, и её надо искать отдельно:
* запустить `rpc-server` на доноре с `-v` и посмотреть, что он делает между
  `Accepted` и `closed`;
* проверить, какие ядра реально в бинарнике (`grep` по `sm_86`/`sm_120` врёт —
  в передаче R115 записано «проверять запуском»); образ мастера построен с
  `CUDA_ARCH=86;120`, но метка образа по-прежнему гласит «CUDA sm_86»;
* проверить сеть: MTU/фрагментация, правила фаервола на 50052, отсутствие
  прокси между машинами;
* контрольный опыт: тот же образ на узле **локально** (сайдкар) работает —
  значит дело не в образе, а в паре «мастер ↔ удалённый узел».

Ещё наблюдение: во время обеих попыток донор (ноутбук) **уходил в сон/пропадал
целиком** на несколько минут, после чего возвращался сам. Для проб раскладки это
надо исключить (питание/сон/сеть), иначе результат неотличим от падения узла.

## 4. РАСКЛАДКА С ДОНОРОМ РАБОТАЕТ — при `gpuLayers=10`

После обновления узла проба с донором **прошла**: модель `gemma-4-E4B-it-Q4_K_M`
загружена с раскладкой мастер + донор (запрос: `contextSize=4096, gpuLayers=10,
kvCacheType=q4_0`), `state=loaded` за ~120 с, падений нет, `RestartCount` не рос.

```
[bridge] RPC: узел 192.0.2.10:50052 подключён, его устройств: 1
[bridge] RPC: устройств в раскладке 2 (локальные + удалённые)
[bridge] multi-GPU tensor_split: applied 2 proportions [0.54, 0.46], split_mode=1
llama_prepare_model_devices: using device CUDA0 (NVIDIA GeForce RTX 3070) - 7097 MiB free
llama_prepare_model_devices: using device RPC1 (192.0.2.10:50052) - 7033 MiB free
load_tensors:   CPU_Mapped model buffer size =  3556.96 MiB
load_tensors:        CUDA0 model buffer size =   297.02 MiB
load_tensors: RPC0[192.0.2.10:50052] model buffer size =   511.33 MiB
[bridge] model loaded successfully: gemma-4-E4B-it-Q4_K_M.gguf (effective n_ctx=4096, n_batch=512)
```

**Распределение слоёв:** `CUDA0 = 6`, `RPC1 = 4` (слои 39–42 — на доноре),
`CPU = 33` (из 42). Память донора реально занята узлом: во время загрузки
`/api/gpu` донора показывал `used=7127 MB, free=996 MB` из 8123 MB, после
выгрузки вернулось `used=1090 / free=7033` — то есть удалённый буфер жил на
карте донора, а не только «числился».

**Скорость (через балансер, :18080):** 27 токенов за 28.3 с → **0.96 ток/с**,
ответ корректный («1, 2, 3, 4, …»). Это ожидаемо мало: 33 слоя из 42 считает CPU.

### 4a. Граница: `gpuLayers=-1` (все слои на GPU) — падает

Тот же узел, тот же образ, но все слои на GPU → прежний отказ:

```
ggml-rpc.cpp:345: Remote RPC server crashed or returned malformed response
SIGABRT: abort  →  «загрузка отменена: узел раскладки недоступен»
```

При этом узел здоров (`RestartCount=0`, `OOMKilled=false`, в логе только
`Accepted client connection` / `closed`). Вывод: транспорт и версии **исправны**
(иное доказывает успешная проба §4) — ломается путь «вся модель на двух GPU»:
планировщик просит у узла буфер, который тот не может выдать, и отказ узла
приходит так, что клиент считает ответ неразборчивым. Это отдельный дефект
(нужна внятная обработка отказа выделения на удалённом устройстве вместо
`RPC_STATUS_ASSERT`), и он не связан с обновлением донора.

### 4b. Почему вторая генерация «висит»

Вторая попытка генерации через балансер не ответила за 600 с. Это тот самый
дефект пустого кэша n_ctx: модель загружена напрямую (через API cppworker), а
балансер своего `loaded_n_ctx` не знает → `preflightNCtxReload` считает, что
«не совпало», и запускает ПОЛНУЮ перезагрузку (профильный ctx=32768). Отсюда же
много-минутные ожидания в прошлых прогонах. Лечение описано в передаче R118
(трактовать `loaded_n_ctx == 0` как «неизвестно»).

### 4c. Подтверждения по версиям и ядрам (чтобы не гадать)

* образ мастера и узла — **один и тот же** (`sha256:fdff663eb015…`), и хеш
  `/app/rpc-server` совпадает: `4243134b5e3a56650370f1dcc86f03f210a6afc34d241c8d927a5601c081f251`;
* гипотеза «в образе нет ядер под sm_120» **опровергнута запуском**: пробный
  контейнер из `gpu-rpc86-r116c` на доноре загрузил gemma-4 на его карте —
  `model loaded successfully`, `CUDA0 KV buffer size = 42.75 MiB`,
  `CUDA0 compute buffer size = 543.00 MiB`;
* у `rpc-server` **нет** флага подробности: `-v` → `unknown argument`; есть только
  `-h/-t/-d/-H/-p/-c`, поэтому его лог ничего не говорит об операциях;
* мелочь на будущее: `PUT /api/v1/cppworker/config/update {"rpcEnabled":…,
  "rpcServers":…}` применяется, но хендлер пишет
  `unknown field: rpcEnabled / rpcServers` — поля не внесены в `knownKeys`.

## 5. R118: пометки раскладки в WebUI и замер канала (сделано)

Запрос: «не хватает пометок в webui, что осуществлена раскладка на донора и по
какой модели и по каким слоям, а также замер пропускной способности канала».

**Замер канала (живой, `measure-network.ps1`; iperf3 на стенде падает — Cygwin):**

```
RESULT dir=download bytes=524288000 seconds=4.499 MBps=111.1 Mbps=889   (клиент на мастере)
RESULT dir=upload   bytes=524288000 seconds=4.499 MBps=111.1 Mbps=889
донор: dir=send 111.8 МБ/с = 895 Мбит/с, dir=recv 110.9 МБ/с = 887 Мбит/с
```

Замер положен в `.env` (`LB_RPC_LINK_MBPS=889`, `LB_RPC_LINK_MEASURED_AT=2026-10-14`,
`LB_RPC_LINK_SOURCE=scripts/measure-network.ps1`) и прокинут через
`docker-compose.stack.yml`; балансер отдаёт его как `rpcLink` в записи бэкенда.

**Пометки в WebUI** (вкладка GGUF Models, строка загруженной модели). Живой текст,
снятый на стенде (модель gemma-4, раскладка на донора):

```
раскладка = донор 192.0.2.10:50052 · CUDA0 33–39 (7) · RPC0 40–42 (3) → 192.0.2.10:50052 · CPU (33)
канал     = 889 Мбит/с (111.1 МБ/с)
```

Лог llama.cpp того же прогона: `CUDA0=7 RPC=3 CPU=33` — совпало.

**Важная деталь реализации.** В этом развёртывании WebUI ходит за runtime-
параметрами **напрямую на воркер через прокси балансера**
(`/api/v1/gguf/backends/<id>/proxy/...`), а не в агрегатор балансера, поэтому:
* состояние раскладки (`rpc_enabled`, `rpc_servers_active`, `vram_*`) WebUI берёт из
  `/api/models` воркера тем же прокси;
* слои по устройствам считает сам (зеркало правила балансера,
  `deriveLayerPlanJS`), из `n_layers`/`gpu_layers`/`tensor_split`;
* замер канала приходит из записи бэкенда (`rpcLink`).

**Найденный по ходу дефект:** агрегатор балансера декодировал `tensor_split` в
`map[string]interface{}`, а воркер отдаёт массив — ответ не декодировался целиком,
и runtime-строка пропадала ровно при загруженной с раскладкой модели. Исправлено,
регрессия закрыта тестом.

**Что честно про «какие слои»:** API не отдаёт точный список слоёв — его печатает
llama.cpp в лог воркера. В UI показывается расчёт (помечен `estimated` + подсказка),
сверенный с логом на трёх живых прогонах (23/19/1; 6/4/33; 7/3/33). Чтобы отдавать
точный список, нужна правка cppworker (перехват лога загрузки) — это отдельная
задача с пересборкой GPU-образа.

## Место под модель
| Носитель | Свободно | Комментарий |
|---|---|---|
| `D:` (модели мастера) | **111.4 ГБ** | занято ~19.3 ГБ (27B 15.33 + gemma 3.93) |
| Донор `C:` (`fsutil`, живой замер) | **207.7 ГБ** | диска `D:` на доноре нет |

ВНИМАНИЕ к методике: балансер показывает по донору `diskFree=943285 МБ` (921 ГБ),
а живой `fsutil volume diskfree C:` — **207.7 ГБ**. Метрика агента отражает диск
Docker-VM (контейнерное окружение), а не том Windows, поэтому для планирования
загрузок её использовать нельзя — мерить на хосте. Для моделей это критично.

По странице модели (внешние данные, HuggingFace:
`vcruz305/Qwen3.8-Flash-Next-GGUF`): весь репозиторий **538 ГБ**, каталог
`Q4_K_M` — **86.2 ГБ** (7 частей), отдельный блок `PLE-BF16`
(shared BF16 `per_layer_token_embd`) — **~95 ГиБ**.

* `Q4_K_M` на `D:` **влезает** (86.2 из 111.4 ГБ, останется ~25 ГБ);
* `Q4_K_M` **+** `PLE-BF16` на `D:` **не влезает** (86 + 95 > 111) — тогда часть
  держать на доноре или освобождать диск;
* на доноре (207.7 ГБ) `Q4_K_M` тоже влезает, но с учётом уже занятого — проверить
  перед копированием (там же лежат образы Docker, ~40 ГБ).

Важная оговорка по раскладке: суммарная VRAM двух карт — 8 ГБ + 8 ГБ (с
headroom ~14 ГБ). Модель на 86 ГБ в неё не укладывается: это будет
преимущественно CPU/RAM-исполнение (мастер 25 ГБ RAM, донор 7.8 ГБ), то есть
проба на таком классе модели проверяет **масштабируемость раскладки**, а не
скорость.

## Что нужно, чтобы закончить

1. Включить/разбудить донор, убедиться, что снова открыты `22`, `50052`, `18092`.
2. Доставить на донор образ мастера и поднять узел тем же коммитом:

```powershell
# на мастере
docker save ollama-legion/cppworker:gpu-rpc86-r116c -o C:\Ollama\cppworker-rpc86-r116c.tar   # ~6.5 ГБ
# скопировать на CYBORG (scp/шара) и там:
#   docker load -i cppworker-rpc86-r116c.tar
# в каталоге развёртывания донора (node2.env + docker-compose.rpc-node.yml, см. docs/architecture/rpc-coordinator.ru.md:356):
#   $env:CPPWORKER_GPU_TAG='rpc86-r116c'; docker compose -f docker-compose.rpc-node.yml up -d
```

3. После подъёма узла — повторить пробу: `rpcServers=["192.0.2.10:50052"]`,
   загрузить gemma-4 (и затем 27B), зафиксировать «устройств в раскладке 2»,
   распределение слоёв по `CUDA0`/`RPC0`, `restarts=0` и TTFT/tok-s.

Доступ к донору с мастера: SSH-порт открыт, но мои ключи
(`id_ed25519`, `id_ed25519_main`, `id_ed25519_donor`) отклонены —
`Permission denied (publickey,password,keyboard-interactive)`. Нужен рабочий
ключ/пароль (в `docs/plans/2026-10-07-model-distribution-multi-gpu-next-session.md:210`
упоминается вход по SSH именем Microsoft-аккаунта `<owner-email>`).
