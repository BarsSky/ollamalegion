# Демо-режим WebUI (R232, 2026-10-24)

Демо-режим — это витрина панели без реального стенда: WebUI показывает
синтетический, но правдоподобный сценарий работы кластера и **не обращается к
балансеру**. Нужен для показа/обучения: любой гость открывает страницу и видит,
как подключаются клиенты, как балансер распределяет запросы, как растёт и
рассасывается очередь, как назначается донор по RPC и как работает AutoTune.

## Включение (только через env)

В `deployments/.env`:

```dotenv
WEBUI_DEMO_MODE=1
```

и пересоздать webui:

```bash
docker compose -f deployments/docker-compose.stack.yml up -d --force-recreate webui
```

**Нужен образ webui из R232+**: переменную читает `docker/webui/entrypoint.sh`,
поэтому старый образ (`webui:r229m-*` и раньше) её проигнорирует. Собрать и
подставить:

```bash
pwsh -File scripts/build-containers.ps1 -WebUI -Tag r232-demo
# deployments/.env: WEBUI_TAG=r232-demo
```

Других способов нет: **в интерфейсе переключателя нет**. Это режим развёртывания
(витрина/обучение), а не пользовательская настройка. Выключение — `WEBUI_DEMO_MODE=0`
(или удалить строку) и снова пересоздать контейнер. Значение по умолчанию — `0`.

Проверка, что режим поднялся:

```bash
curl -s http://<webui>/js/modules/config.js | grep DEMO_MODE
# DEMO_MODE: true,
```

или в логе контейнера: `DEMO_MODE=true (WEBUI_DEMO_MODE=1)`.

## Что видит гость

- Вход **не запрашивается**: демо подставляет гостевую сессию `viewer`
  (только чтение). Админские действия скрыты штатной ролевой логикой.
- Сверху — баннер **«ДЕМО-РЕЖИМ»**: данные синтетические, время ускорено.
- Внизу справа — панель **«Демо-сценарий»**: текущая фаза, счётчики (клиенты,
  очередь, слои на GPU, слои на доноре, tok/s, состояние AutoTune) и лента
  событий.
- Данные приходят на все страницы, которые читают `/api/`: обзор (бэкенды,
  очередь, сессии), монитор (топология, очередь, раскладка), AutoTune-бейджи и
  история. Все `/api/`-запросы перехватываются в браузере; реальный балансер не
  опрашивается, мутации отвечают `403 read-only`.
- Вместе с `fetch` подменяются `WebSocket` и `EventSource` (SSE
  `/api/v1/events`): живые обновления и колокольчик уведомлений работают, но
  соединений с сервером нет.
- Служебные страницы (`health.html`, `rpc-status.html`, `tp-pipeline.html`,
  `virtual-models.html`) в сценарий не входят — ссылки на них в демо скрыты,
  чтобы гость не попадал на страницы без синтетических данных.

## Сценарий (цикл 150 с)

| Время | Фаза | Что происходит |
|---|---|---|
| 0–8 с | Загрузка модели | мастер грузит `Qwen3.8-27B-UD-Q4_K_M` (15.3 GB), ctx 16384, KV q8_0 |
| 8–14 с | Клиенты | подключаются Cline, Open WebUI, curl; все ходят на один адрес балансера |
| 14–45 с | Очередь | один слот: запросы встают в очередь, балансер ведёт позиции и время ожидания |
| 45–80 с | Донор (RPC) | в раскладку входит донор: 22 слоя уходят на RPC0, CPU-слоёв 46 → 18, очередь рассасывается |
| 80–96 с | AutoTune | анализ: KV q4_0 → f16 (бюджет 8.0 GB), reload модели, проверка применённой конфигурации |
| 96–128 с | Стабильная работа | AutoTune: optimal, очередь пуста, клиенты работают |
| 128–150 с | Завершение цикла | часть клиентов отключается; сценарий повторяется |

Числа согласованы с живым замером R231 на qwen3.8 27B Q4 (мастер 8 ГБ + донор
8 ГБ): 20/66 слоёв на GPU до донора, 48/66 после (26 CUDA0 + 22 RPC0), 0.71 →
2.08 tok/s. Время в демо ускорено, иначе один ответ шёл бы ~2 минуты.

## Ограничения (честно)

- Это **имитация**: к реальному кластеру запросов нет, поэтому демо не заменяет
  проверку стенда (для неё — `scripts/ci.ps1 -Live -Clients`).
- Демо read-only: кнопки изменений либо скрыты ролью viewer, либо получат
  `403 read-only`.
- Неизвестные `/api/`-ручки отвечают пустым `{demo:true}`: страницы, которых нет
  в сценарии (например, сложные формы настроек), могут выглядеть пустыми — это
  ожидаемо.
- Значения в сценарии фиксированы (детерминированы), а не случайны: так демо
  воспроизводимо для скриншотов и проверок.

## Проверка режима

```bash
# unit: логика сценария и API-роутер (21 проверка)
node webui/js/modules/demo-mode.test.js

# unit: проводка (HTML и порядок скриптов, entrypoint, compose, документация) — 8 проверок
node webui/js/modules/demo-mode-wiring-r232.test.js

# живая проверка: временный контейнер с WEBUI_DEMO_MODE=1 + Playwright (стенд не трогается)
pwsh -File scripts/verify-demo-r232.ps1

# только Playwright-сценарий против уже поднятого демо-webui
WEBUI=http://127.0.0.1:18084 node scripts/webui-e2e/check-demo-mode-r232.js
```

Playwright-проверка по умолчанию запускает канал `msedge` (как и остальные проверки
`scripts/webui-e2e`); переопределяется переменной `PW_CHANNEL`, при недоступности канала
берётся встроенный chromium.

Живая проверка подтверждает главное свойство режима: на `index.html` и `monitor.html`
**ни один** запрос к `/api/` не уходит на сервер (включая `ws`/SSE), поэтому демо можно
включать даже на боевом стенде — гость не увидит и не нагрузит реальный кластер.
