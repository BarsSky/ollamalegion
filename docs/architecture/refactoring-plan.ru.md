# Рефакторинг: два мозга, четыре окна, четыре очереди (план)

**Дата:** 2026-11-09. **Статус:** план, код не менялся.
**Повод:** живые жалобы после серии правок R459–R476 — «перестал работать
OpenWebUI», «потеряно распределение нагрузки», «потеряна работа с разными типами
моделей». Аудит кода (четыре независимых прохода: стриминг, распределение, типы
бэкендов, архитектура) показал: это не «сломалось одно место», а **несколько
параллельных реализаций одного пути**, которые расходятся в поведении.

## 2. Почему это не «переписать всё»

Формулы окна уже сведены в одну точку и покрыты тестами; парсеры tool-call'ов —
это РАЗНЫЕ форматы моделей, а не дублирование; `pkg/types`, `internal/settings`,
`pkg/logger`, i18n — стабильны. Проблема в **маршрутизации и дублировании пути
запроса**, а не в математике.

## 3. Этапы (каждый — отдельный коммит с флагом и откатом)

Сначала тесты-предохранители (их сейчас нет; **T1 и T5 сделаны 2026-11-11**,
см. ниже и `debts.ru.md` п.11-star):

- **T1 матрица маршрутов** — для (поверхность 18080/18079, путь из
  `/api/chat`, `/ollama/api/chat`, `/v1/chat/completions`, тело
  `stream:true|false|отсутствует`, `tools:да|нет`) утверждать, какие стадии
  вызвались и что формат ответа одинаков при отсутствии `stream`.
- **T2 golden-байты** NDJSON/SSE для шести комбинаций + «ровно один терминатор».
- **T3 окно**: таблица (needed, loaded, requested, активные стримы, reload) →
  вердикт, одинаковый на всех путях.
- **T4 очередь**: одинаковые `X-Queue-*` и `/queue` на обоих путях.
- **T5 стюард**: у каждой стадии R477 есть prod-вызов; `w.(http.Flusher)` только
  в `safe_stream_writer.go`.

- **T1 — матрица маршрутов** (`internal/balancer/route_matrix_t1_test.go`):
  - решение о пути НЕ зависит от тела (`stream:true|false|нет`, `tools`): 4 пути ×
    3 состава кластера × 4 тела;

  - тип, который видит диспетчер, задаёт ПОВЕРХНОСТЬ (R112): `/api/*` → "",

- **T3 — таблица окна** (`internal/balancer/window_table_t3_test.go`): состояния

  совпадать. Пороги расходятся только по правилу R480 (активная сессия включает

### Этап 3 сделан (R493-12n, 2026-11-13): что именно и чего в нём нет

Сделано (`internal/balancer/window_decision_r493.go`,
`window_decision_paths_r493.go`):

- `decideWindowR493` — чистая функция: на входе числа и факты, на выходе вид
  вердикта (`noop` / `serve` / `defer` / `grow` / `refuse`) с целью, сроком
  повтора и причиной. Внутри — R288, R447, R466, R385 и правило «окно никогда не
  опускается» (R493-12h). Кластер, метрики и HTTP ей не нужны.
- Вердикт стал ОДНИМ по виду на всех путях: отличие пути — это ВХОД
  (`GrowBlockedBy`: выключатель роста, роль донора), а не второй набор правил.
  «Кто нажимает кнопку перезагрузки» осталось за путём: не-стриминговый запрос
  отдаёт reload preflight-движку (он умеет выбрать свободный узел вместо
  перезагрузки), стриминговый перезагружает сам и отвечает 503+Retry-After.
- Все входные точки зовут её: guard до admission-очереди (`growthVerdictR301`),
  вход транспортного preflight (`growthDeferR299`), план роста R385
  (`streamGrowthPlanR385` — при едином решении цель приходит из вердикта, второй
  расчёт не запускается).
- Флаг `LB_WINDOW_UNIFIED` (горячая настройка, группа `nctx`): `0` —
  историческое поведение (по умолчанию), `1` — единое решение, `2` — «тень»:
  единое считается и расхождения с историческим пишутся WARN-строкой
  `R493-12n shadow divergence`, поведение остаётся историческим.
- T3 на всех путях: `window_decision_t3_r493_test.go` — таблица «вход →
  вердикт», паритет входов (разница только `GrowBlockedBy`), паритет вида на
  трёх путях, откат при `0` (вердикт равен историческому), «тень» при `2`.
  Мутации (снять R288 / R447 / R466 / способность пути / выравнивание цели /
  запрет «не-стриминговый путь предписывает 503») роняют тесты — проверено.

Чего в этапе НЕТ (это следующие этапы, а не «сделано»): общий `Admitter` (4),
общий `runInference` (5), общий стрим-пайплайн (6). Preflight-движок по-прежнему
сам считает конкретное окно загрузки (`DecidePreflight` → `reloadTargetForState`):
единое решение называет ВИД вердикта и цель для роста на стриме, а планирование
загрузки на узле осталось за движком. Это осознанная граница этапа: она позволяет
включить единое решение, не переписывая планировщик загрузки.

## 4. Проверка на двух стендах (один чек-лист на этап)

- **9B / частичный оффлоад:** длинный prefill (>60 c) + heartbeat; запрос без
  поля `stream`; tool-call на три хода; отмена в очереди; ответ дольше 120 c.
- **A10 / 27B:** две копии модели (выбор копии под окно, R118.5; переезд R459);
  reload под окно (R385); отказ по памяти с числами; четыре параллельных клиента.
- Артефакты на этап: `request trace` по `request_id` на трёх поверхностях,
  `recent_failures`, `X-Queue-*`/`X-Backend-ID`, байтовый diff ответа
  старый/новый.

## 5. Чего пока нет в коде

- ни одной метрики с меткой стадии (только лог-строки);
- теста, фиксирующего, какой внутренний путь обслуживает `/api/chat` против
  `/v1/chat/completions` (поэтому расхождение и живёт);
- общего интерфейса очереди/селектора/транспорта;
- лимита тела на generic-пути.
