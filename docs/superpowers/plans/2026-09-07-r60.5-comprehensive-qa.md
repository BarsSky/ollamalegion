## 1. User-reported failures (must be diagnosed in R60.5)

1. **«Параметры загрузки бэкенда» infinite loading** — webui `loadAndRenderBackendOptions()` shows "Loading…" forever on Settings tab. Endpoint `/api/v1/gguf/backends/{id}/proxy/api/v1/cppworker/config` returns 200 from curl, but webui doesn't render the form. **Not browser cache** (user confirmed reloaded).
2. **«Модели на диске» empty when no model loaded** — when `data.llamaCpp.loadedModels = []`, webui GGUF tab shows no info about files in `/app/models/`. Should fall back to `/api/models/files` (R60.3 endpoint).
3. **OpenWebUI: load timeout + double-load** — client (OpenWebUI) gets "load timeout" response when first request triggers model load. Then balancer restarts the model even though it's now loaded. Two problems:
   - Load timeout too short for slow hardware
   - Subsequent request should hit the (now loaded) model without triggering a fresh load
4. **SSE `/api/v1/events` keeps dropping** — `ERR_INCOMPLETE_CHUNKED_ENCODING` every ~5 min. R60.2 fix (`proxy_send_timeout 86400s`) didn't help. Bug is in balancer's SSE handler, not nginx.
5. **No Ollama API compliance test** — previous "smoke tests" only check 1-2 endpoints (chat, embeddings). No full Ollama API surface coverage. No OpenAI API compliance either.
6. **No generative dialogue test** — previous tests only check 1 chat call. No multi-turn context, no streaming, no "are the responses actually coherent" check.

## 7. Phase E — Diagnose + fix webui bugs

### E.1 — Bug: «Параметры загрузки бэкенда» infinite loading

**Diagnostic steps:**

1. Open browser DevTools → Network tab
2. Navigate to Settings tab
3. Look for XHR to `/api/v1/gguf/backends/{id}/proxy/api/v1/cppworker/config`
4. Check: status code, response body, time elapsed
5. If 200 + valid body: JS bug (renderBackendOptionsForm fails silently)
6. If pending forever: nginx/balancer bug

**Likely root cause** (from prior analysis): webui `loadAndRenderBackendOptions` does `await GgufApi.requestViaBackend(...)` then sets `container.innerHTML = formHtml`. If `data.config` is not a plain object (e.g. has cyclic refs, function values, etc.), or if `renderBackendOptionsForm` throws inside, the catch block replaces spinner with error. But if exception is swallowed by promise chain, spinner stays.

**Fix candidate:** Add explicit error handling in webui, fall back to "manual config" form if backend doesn't expose `/config` endpoint.

### E.2 — Bug: «Модели на диске» empty when no model loaded

**Diagnostic steps:**

1. Unload any model (POST `/api/models/unload` with name)
2. Navigate to Models tab
3. Look for XHR to `/api/models/files` (should hit balancer→cppworker)
4. Check: status code, response body

**Likely root cause** (from R60.4): webui's `gguf-renderer-detail-render.js:223` reads `state.localModels` which is now set to `data.llamaCpp.loadedModels` (R60.4 fix). When no model is loaded, `data.llamaCpp.loadedModels = []` → `state.localModels = []` → empty card. Webui never falls back to `/api/models/files` (disk enumeration).

**Fix candidate:** In webui, when `state.localModels.length === 0`, also fetch `/api/models/files` and render disk models as a separate section.

## 8. Phase F — Diagnose + fix balancer bugs

### F.1 — Bug: SSE `/api/v1/events` keeps dropping

**Diagnostic steps:**

1. Check balancer logs for `websocket read error: i/o timeout` (every ~5 min)
2. Check whether balancer sends periodic ping frames in SSE
3. Check whether Go's `http.Flusher` is properly used

**Likely root cause:** Balancer's SSE handler doesn't send periodic `: ping\n\n` comments. After ~5 min of idle, nginx or browser drops the connection. R60.2 fix on nginx side didn't help because the issue is on balancer side.

**Fix candidate:** Add periodic ping every 30s in balancer's SSE handler. Use `time.NewTicker` + select in the handler goroutine.

### F.2 — Bug: Load timeout too short + double-load

**Diagnostic steps:**

1. Look at balancer config: `LB_NCTX_PREFLIGHT_*` env vars
2. Find current default timeouts
3. Check whether loaded state persists across requests (no double-load)

**Likely root cause:** Default timeouts (e.g. 30s) too short for large models on slow hardware. When load takes 90s, first request gets 503, model continues loading, second request sees "loading" state and... doesn't check if model is now loaded?

**Fix candidate:** 
1. Make timeouts auto-detect from hardware (CPU/GPU info from agent)
2. Add `lastKnownState` check: if model was loading and now state=loaded, use it instead of triggering new load
