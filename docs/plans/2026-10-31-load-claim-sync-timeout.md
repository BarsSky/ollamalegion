# R365. Sync-загрузка (`wait=true`) больше не теряет заявку на загрузку

Дата: 2026-10-31. Стенд тот же, что в R364 (`cppworker-gpu`, RTX 3070),
образ `cppworker:gpu-c71d379e`.

## 1. Что случилось

Дефект найден при живой проверке R364. Последовательность (логи воркера,
время по эпохе внутри контейнера):

```
1793482629  POST /api/models/load?wait=true  → 202 (таймаут 61 с; дефолт 60 с)
1793482636  "model loaded" (ctx=16384)                     ← загрузка завершилась
1793482648  POST /api/models/load          → "model is already being loaded by
                                             another request; waiting (wait=true)",
                                             wait_limit_sec=90
1793482738  → 200 «load finished while we waited» за 90001 мс,
              модель осталась с ПАРАМЕТРАМИ ПРЕДЫДУЩЕЙ загрузки (ctx=16384)
```

То есть через **12 секунд после того, как модель уже загрузилась**, заявка на
загрузку всё ещё была занята, и следующая загрузка (с профилем: ctx 32768,
KV q4_0) прождала предел ожидания и вернула 200, **не перезагрузив модель**.

## 2. Причина

Заявка (`TryLockLoadR303` → `b.loading[name]`) снимается ровно одним
`UnlockLoad`. В `handleLoadModel` снятие стояло в ветке успеха `select`:

```go
select {
case loadErr := <-loadDone:
    backend.UnlockLoad(modelName)   // ← выполняется только при успехе
    ...
case <-timeout.C:
    // заявку не снимает НИКТО
}
```

Таймаут — не редкий случай: `parseLoadWaitParams` по умолчанию даёт 60 секунд,
а холодная загрузка `gemma-4-E4B-it-Q4_K_M` занимает 60–100 секунд. Значит
**большинство** синхронных загрузок шли по ветке таймаута и оставляли заявку
висеть до тех пор, пока её не сочтут устаревшей (`CPPWORKER_LOAD_STALE_SEC`).

Это уже было исправлено в `handleLoadWithParams` (Round 52: `defer UnlockLoad`
внутри горутины загрузки), но legacy-путь `/api/models/load` остался с прежним
поведением — тот же класс «две реализации одного правила», что и в R364.

## 3. Что сделано

`handleLoadModel`: заявка теперь снимается `defer backend.UnlockLoad(name)`
**внутри** горутины загрузки, а ветка успеха `UnlockLoad` не зовёт (двойного
снятия нет; оно идемпотентно, но правило должно быть одно).

Плюс стюард-тест `load_claim_steward_r365_test.go`:

- для каждого обработчика с sync-веткой (`handleLoadModel`,
  `handleLoadWithParams`) требует `defer ...UnlockLoad(...)` внутри горутины
  загрузки;
- запрещает `UnlockLoad` в ветке `select`;
- негативная проверка выполнена: при удалении строки `defer` тест падает с
  сообщением про R365 (проверено в этом же раунде, строка возвращена).

## 4. Что этот дефект объяснял у оператора

Любая «перезагрузка с другими параметрами» после синхронной загрузки,
упёршейся в таймаут, могла вернуть 200 и оставить модель со старыми
параметрами. Снаружи это выглядит как «нажал загрузить — ничего не изменилось,
но ошибки нет».

## 5. Не исправлено сознательно

Ветка «жду чужую загрузку» (`respondWhileAnotherLoadInProgress`) по-прежнему
возвращает текущий инстанс и не перезагружает модель, даже если у ожидающего
запроса другие параметры. Это отдельное решение (нужно решать, чей запрос
главнее — ожидавшего или загрузившего); после R365 оно перестало быть
массовым, потому что заявки больше не виснут. Записано как известное
ограничение, а не как «готово».
