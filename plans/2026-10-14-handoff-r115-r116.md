## Что проверено живьём (можно не перепроверять)

1. **Раскладка работает на одном образе**: `state=loaded`, `RPC0[...] KV 18 MiB + RS 18.7 MiB + compute 505 MiB`, `restarts=0`; три устройства дали `устройств в раскладке 3`.
2. **Причина прежних падений**: `ggml-rpc.cpp:823` — это `get_device_memory()`, то есть наш фоновый опрос узла во время загрузки; правило «не дозваниваться во время работы» (`layoutBusy` + `rpcSnapshot`) это закрыло, плюс защита от самоблокировки (`TryLock`/`TryRLock`).
3. **Выключение раскладки флагом**: `PUT {"rpcEnabled":false}` → `applied:["rpcEnabled","rpcServers(cleared)"]`, отчёт: `rpc=False nodes=0 remote=0 layout_free=7075 local=7075`.
4. **Настройка доходит до живого конфига**: смена списка узлов через API сразу видна в `/api/models` (до фикса — нет).
5. **Приоритет параметров**: `GET /api/models/effective?model=…` → `request > profile > default`, с источником каждого. Живьём: 27B `kv=q8_0 source=profile`, gemma-4 `kv=q4_0 source=profile`, модель без профиля → `source=default` = `q8_0`.
6. **Проверка памяти при записи профиля**: `PUT /api/v1/cppworker/model-profiles/Qwen3.8-27B-UD-Q4_K_M {"contextLength":262144,"kvCacheType":"f16"}` → **422** `profile_does_not_fit_memory` с `memory_breakdown` (`cpu_kv_mb: 10334`, `max_ram_n_ctx: 240152`, `feasible_max_context: 240152`); выполнимая конфигурация (gemma `131072/f16`) → 200.
7. **Гейт версии узла**: неизвестная версия → предупреждение, узел остаётся (`устройств в раскладке 2`); несовпадающий коммит → исключение.
8. **WebUI «модели исчезают»** — правка из трёх частей, тесты `gguf-disk-inventory-r93`, `gguf-refresh-resilience`, `gguf-unload-state`, `gguf-state-scope`, `gguf-host-ram` зелёные.

## Как обращаться к API стенда (выяснено живыми пробами)

* управляющий API балансера — порт **18081**, заголовок **`X-API-Token`**, токен = **`LB_API_TOKEN`** из окружения контейнера балансера (НЕ `CPPWORKER_API_TOKEN`);
* Ollama-поверхность — **18080**, OpenAI — **18079**;
* cppworker напрямую — 18092; профили: `/api/v1/cppworker/model-profiles[/{name}]`, применение: `…/{name}/apply`;
* в PowerShell использовать `-UseBasicParsing` (иначе 401 превращается в «HTTP 0» и попытку интерактивного ввода).

## Что осталось (по приоритету)

### 1. Вместимость балансера = реальные слоты (ваш сценарий «два запроса с одной машины»)

Подтверждено живьём: балансер сообщает бэкенду `maxConcurrentRequests=2` (heartbeat каждые 5 с), при этом у загруженной модели `max_slots=1`. Очередь включена (переменных `LB_ADMISSION_*` нет → лимит ожидания 300 с по умолчанию), но второй запрос **не встаёт в очередь**, потому что вместимость завышена; сериализует его сам llama.cpp, и в WebUI нет ни очереди, ни отдельной сессии.

Правка: вместимость брать из `max_slots` (до загрузки — 1, а не 2); сессию — из `X-Request-Id`/`X-Session-Id`, иначе явно показывать «клиент не различает сессии»; в UI вывести позицию очереди и ключ сессии. Механизм уже есть: `admission_queue.go` (`X-Queue-Position`, `X-Queue-Wait-Ms`), `RequestSessionKey(r, body)`.

### 2. Прогон Cline в двух режимах (незавершённая диагностика «преждевременный конец»)

Требует загруженной модели. Схема: тот же запрос с `tools` (например `run_commands` с `commands: string[]`) в двух состояниях `LB_AUTO_CONTINUE_ON_TRUNCATION` (0 и 1), в каждом снимать четыре поля: upstream `finish_reason` → клиентский `done_reason`, наличие `tool_calls`, длину `content`, факт авто-продолжения. Плюс контроль доезда параметров по сводке cppworker (`tool_calls`, `done_reason`).

Известное по коду: параметры **доезжают** (`tools` переносятся в `llamacpp_translate_req.go:110-126`; `num_ctx` читает 3-уровневый резолвер — тест `TestResolveNumCtx_R69_RecordsClientRequest`). Подозреваемое место — обработка обрезки/`finish_reason` и отсутствие правила «не продолжать, если в ответе есть вызов инструмента».

## Грабли окружения (чтобы не терять час заново)

* сборка `cppworker-gpu` — ~1,5 ч, кэш CUDA-слоёв **вытесняется** между сборками; лог сборки писать в отдельный файл (`debug/build-<tag>.log`), потому что пайп молчит и проценты видны только в логе;
* `docker compose ... build <service>`: сервис балансера называется **`loadbalancer`**, не `balancer`;
* дефолтное зеркало `dockerhub.timeweb.cloud` практически останавливает сборку CUDA 12.8 — `CUDA_BASE=mirror.gcr.io/nvidia/cuda` в `.env`;
* проверка архитектуры — **запуском**, не `grep`: в собранном бинарнике `grep sm_86` даёт 0, while модель считает на CUDA0;
* `debug/*.ndjson`, `debug/node2.env` попали в коммит `4c3952e` — если не нужны в истории, вынести отдельным коммитом.
