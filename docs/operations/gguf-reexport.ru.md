# Ре-экспорт GGUF: отдельный опциональный модуль (R709)

**Состав:** `services/gguf-reexport/` (Go-хост) + `py/reexport_job.py` (python-драйвер),
образ `ollama-legion/gguf-reexport`, профиль compose `reexport`. **Статус:** путь
метаданных/переупаковки проверен на живом 16.6 ГиБ файле (§7); полный ре-экспорт из
HF-чекпойнта — отдельный таргет образа (§6, §8).

## 1. Задача
Пользователь выкачивает нужные файлы (например из HF через WebUI) и указывает их →
система приводит их к формату, который понимает бэкенд. Случай, ради которого модуль
написан: `Inkling-2-Mini-UD-Q4_K_M.gguf` объявляет `general.architecture=inkling2` и
`block_count=48`, а физических блоков в тензорах 24 — это loop-экспорт. Загрузчик
llama.cpp знает loop-схему как ОТДЕЛЬНУЮ архитектуру `inkling2_loop` (физические слои,
`loop.start/end/count/gate_rank`, контроллеры `blk.N.loop_*_ctrl_*` и
`blk.N.loop_msg_query`). Файл не грузится не «потому что битый», а потому что упакован
по другой схеме — ровно это ре-экспорт и снимает.

## 2. Почему отдельный сервис, а не ручка в cppworker/imageworker
- **Зависимости.** Полный путь — `convert_hf_to_gguf.py`, импортирующий torch в первой строке, плюс numpy/transformers/sentencepiece: +2.5 ГБ в образ, который и так линкует llama.cpp.
- **Объём работы.** 16.6 ГиБ файл = 16.6 ГиБ чтения + 16.6 ГиБ записи на единственном диске моделей (§7); рядом с инференсом это промах кэша страниц и пик места.
- **Слот инференса.** Воркер однослотовый: долгая задача заняла бы его и выглядела бы для балансера как «воркер завис».
- **Обновления.** Версия конвертера привязана к сабмодулю llama.cpp, а не к коду воркера: менять конвертер не значит пересобирать llama.cpp.
- **Профиль отказа.** «Модуля нет» — штатное состояние стенда; ручка в воркере дала бы API, отвечающий по-разному в зависимости от сборки образа.
Скриптом «руками» не решается: нужны статус, прогресс, отмена, история и однозначный
ответ WebUI «модуль есть / нет». Go держит состояние и HTTP, python делает работу;
отсюда два таргета образа (§6) — лёгкий без torch и полный с ним.

## 3. Контракт API
```
GET    /health                      → 200 {"status":"ok"} (HEALTHCHECK)
GET    /api/version                 → запечённая идентичность образа (R486)
GET    /api/reexport/capabilities   → что умеет ПРЯМО СЕЙЧАС
GET    /api/reexport/models         → GGUF тома моделей + вердикт схемы
POST   /api/reexport/jobs           → {model_dir, target, options} → 202 задача
GET    /api/reexport/jobs           → список задач (свежие первыми)
GET    /api/reexport/jobs/{id}      → статус/прогресс/ошибка/хвост лога
DELETE /api/reexport/jobs/{id}      → отмена: процесс убит, недописанный файл удалён
```
`capabilities` — источник истины для WebUI: версия конвертера (`converter.revision` из
образа), `python`, `torch_state`, `architectures`, `targets` с `available`/`reason`,
`limits`. Возможность объявляется ПРОБОЙ (`python3 py/reexport_job.py --info`), а не
константой: кнопка «полный ре-экспорт» не может быть доступна там, где нет torch.
Ошибки — `{"error":{"code","message","detail"}}` с осмысленным статусом: 404 (модель/
задача), 409 («результат уже есть»), 422 (цель недоступна, путь вне корней), 507 (мало
места), 429 (очередь). Коды задач: `unknown_target`, `target_unavailable`,
`model_not_found`, `out_of_models_dir`, `out_path_denied`, `dst_exists`,
`insufficient_space`, `model_not_patchable`, `converter_failed`, `canceled`, `interrupted`.
**Задачи хранятся файлами** в томе `reexport_jobs` (`/app/jobs/<id>.json`, атомарная
запись tmp+rename): БД нет — задач десятки, состояние переживает пересоздание
контейнера, человек читает его `cat`. Задача, бывшая `running`, после рестарта
становится `interrupted` с объяснением (делать вид, что она продолжается, нельзя), а
частичный файл виден в ошибке. Параллелизм жёстко 1: диск один, вторая задача не
ускоряется, зато делит кэш и удваивает пик места; остальные стоят `queued` — видно.

## 4. Как WebUI узнаёт о наличии модуля
WebUI не читает ни профиль compose, ни флаг в `.env`. Страница моделей всегда создаёт
пустой `#ggufReexportHost`, а `js/modules/gguf-reexport.js` делает
`GET /api/reexport/capabilities` через nginx панели (same-origin, без CORS и второго
порта). Ответ 200 → блок рисуется; 424/502/таймаут → хост пуст, **вкладки нет вообще**.
Флаг в `.env` был бы вторым источником правды и врал бы в обе стороны: профиль включили
без флага — блока нет; сервис выключили с флагом — мёртвая вкладка.
nginx: `location /api/reexport/`, upstream — **переменная**
(`set $reexport_upstream "${REEXPORT_HOST}:${REEXPORT_PORT}"`). Статический
`proxy_pass http://gguf-reexport:18095` разрешается на старте nginx и без контейнера
модуля роняет ВСЮ панель («host not found in upstream») — этот класс ловили в R229.
Дефолты задаёт `docker/webui/entrypoint.sh`; связка «шаблон ↔ sed-подстановки»
закреплена тестом `webui/tests/reexport-nginx-proxy-r709.test.js`.

## 5. Связь с воркерами, профиль, версии
Ре-экспорт кладёт НОВЫЙ файл в том моделей (`${MODELS_DIR}`, тот же, что у cppworker и
imageworker, RW). Воркер держит инвентарь каталога с TTL, поэтому после успешной задачи
WebUI показывает кнопку «Пересканировать модели» → существующий механизм страницы GGUF
(`GgufModule.rescanAllBackendModels` → `POST /api/models/refresh` на воркере, R93) плюс
сброс кэша фактов сервиса (`?refresh=1`). Своего запроса модуль не изобретает: правило
пересканирования должно быть одно; балансер о модуле не знает и не меняется.
Compose: `gguf-reexport` с `profiles: ["reexport"]`, том `${MODELS_DIR}:/app/models:rw`,
том `reexport_jobs`, healthcheck своим бинарём, порт только на `127.0.0.1` (диагностика;
WebUI ходит через nginx). Запуск: `--profile reexport` или `--profile full
--profile reexport`; без профиля контейнер/порт/образ не создаются — как у `rpc-node`.
Переменные (`.env.example`): `GGUF_REEXPORT_TAG`, `GGUF_REEXPORT_BUILD_TARGET` (light|
full), `GGUF_REEXPORT_WITH_TORCH`, `GGUF_REEXPORT_PORT_HOST`, `GGUF_REEXPORT_OUT_DIR`,
`GGUF_REEXPORT_SCAN_DEPTH`, `GGUF_REEXPORT_LOG_LEVEL`.
Версии: `scripts/release-all.ps1` знает компонент `gguf-reexport` (`-Services
gguf-reexport`), собирает его с теми же `-ldflags`/OCI-метками, что остальные
(+`LLAMA_BUILD`/`LLAMA_BUILD_DATE`, их теперь считает `scripts/build-identity.ps1`), и
пополняет `release-manifest.json`. Компонент помечен `Optional`: в выпуск по умолчанию
не входит; строку тега в локальном `.env` при первом выпуске модуля скрипт дописывает
сам (`.env.example` — контракт, `.env` — локальная копия, которая может отставать).
`scripts/check-image-tags.ps1` видит новый образ: для опционального профиля отсутствие
переменной в локальном `.env` — предупреждение, но в `.env.example` она обязана быть.

## 6. Два таргета образа (и почему torch всё-таки нужен)
- **light** (по умолчанию): python3 + стандартная библиотека +
  `scripts/gguf_loop_meta_patch.py` (один источник правды — его же запускают руками).
  Умеет `inkling2_loop`: переупаковка метаданных и раскладка уже лежащих в файле матриц
  запросов. torch не нужен: веса не пересчитываются, байты данных копируются как есть.
- **full** (`--target full --build-arg WITH_TORCH=1`): `convert_hf_to_gguf.py` +
  `conversion/` + `gguf-py/` из сабмодуля и зависимости из `c/llama.cpp/requirements/`,
  включая torch (CPU-колесо). Умеет полный ре-экспорт из HF-чекпойнта.
Без torch на полном пути не обойтись: `convert_hf_to_gguf.py` импортирует его
безусловно, а per-arch логика живёт в `conversion/*.py` и расходится с загрузчиком при
каждом обновлении llama.cpp. Свой «лёгкий» конвертер весов — вторая реализация, которая
через неделю не совпадёт с апстримом.

## 7. Живой прогон (2026-11-23, CPU, без GPU)
`Inkling-2-Mini-UD-Q4_K_M.gguf`: 16 610 543 328 Б (15.47 ГиБ), 58 KV, 734 тензора,
данные с байта 11 978 464. Том моделей смонтирован только на чтение, результат писался
на второй диск (`REEXPORT_OUT_DIR`); оба — bind-mount Windows/Docker Desktop.

| Проверка | Результат |

## 8. Что осталось
1. **Состояние `loaded` на CPU не доснято.** Барьер схемы снят (все 744 тензора созданы,
   буферы выделены, §7). Дальше чтение 16.6 ГиБ через bind-mount Windows идёт ~30 МиБ/с:
   первый прогон оборвал сторож `load_stall` (300 с), второй (`CPPWORKER_LOAD_STALL_SEC=1800`)
   за 11 минут дошёл до `done_getting_tensors` и стоял в чтении весов (48 с CPU за 10.7 мин
   — ждёт ввод-вывод). Финал проверять на модели в локальном linux-томе.
2. **Образ с torch (`full`) не собран и не проверен живьём**: +2.5 ГБ загрузки и
   отсутствие HF-чекпойнта Inkling-2 на стенде. Цель `hf_to_gguf` объявлена в
   `capabilities` с `available=false` и причиной — кнопка не врёт.
3. **Место и каталог результата.** Свободное место проверяет python перед записью
   (`insufficient_space`), отдельной проверки в Go нет; `REEXPORT_OUT_DIR` глобальный, а
   задача может задать `out_path` только внутри разрешённых корней. Прогресс — только по
   копированию; внутри `convert_hf_to_gguf.py` событий нет. Отмена не докачивает: процесс
   убивается, недописанный результат удаляется.
