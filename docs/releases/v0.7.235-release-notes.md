# v0.7.235 — R448…R473: the context window stopped being a guess

**Date:** 2026-11-07 · **Type:** sources + stand images
**Images:** balancer `r261106-2329` (`f306aa48`), cppworker `gpu-r261106-2122`
(`5a97880d`), webui `r261106-1716`. Manifest: `deployments/release-manifest.json`.

---

## 1. In short

This release removes one class of defects from the agent loop: **context-window
decisions were made from our own guess**. The prompt estimate (a character-count
heuristic) overshot by 1.8–5x, and that produced 413 refusals, cancelled window
growth, misleading client messages, and model reloads to a window larger than needed.

Now the estimate is replaced by **the model's own tokenizer**, a physical-ceiling
refusal exists only for a window the client asked for explicitly, and window growth
is no longer blocked by a profile load hint.

| Was | Live fact | Fixed by |
|---|---|---|
| 413 "needs 151743 tokens" while the client showed 63.6k used | our estimate, not the client's request | **R466**: 413 only for an explicitly requested window; a derived window is capped and loaded |
| a live session moved to a copy with a smaller window (65536 → 32768) and broke | rebalancing looked at load only | **R459**: no move unless the target covers the window (and never onto a cold copy) |
| "a free backend, yet the request queued" with no explanation | one line `admission: request queued` | **R460**: a per-backend reason in the log and in the 503 body |
| "the model produced reasoning only, raise max_tokens" at a 131072 window | the notice always claimed the budget was exhausted | **R461**: "exhausted (X of Y)" vs "not exhausted, the model stopped on its own" |
| `num_predict` is in env but not in the WebUI | the fields never reached the UI | **R463–R465**: budget in the API and a chip in the WebUI |
| client got 503 "needs 39542" while its own counter said 20.7k | 39542 = our estimate 36601 + budget | **R473**: exact tokenizer count (`POST /api/tokenize`), 36601 → 10036 |
| window growth refused by a "32768 ceiling" while the operator cap was 65536 | `WindowFeasibility` treated the profile's load hint as the ceiling | **R472**: ceiling = min(GGUF, `contextLengthMax`, `LB_NCTX_RELOAD_MAX_N_CTX`); refusal reason is WARN |
| Cline showed reasoning and answer merged in one field | the client folds `message.thinking` into the answer text | **R470/R471**: reasoning is not forced on clients that did not ask for `think`; the stream start no longer leaks into `content` |
| "call not executed: unrecognised format" for a valid call | the call was parsed but the tool was not declared (Plan mode) | **R468**: the notice names the real cause and the declared tool set |

## 2. How it was verified (live numbers)

- **R466**: log line `R466 derived window capped to the ceiling` → `async reload succeeded
  new_n_ctx=65536` in 48 s; a repeat request makes no growth decision.
- **R472**: `503 "started reloading … retry in 60"` → model loaded with
  `context_size=40704` in 40 s → retry **200**, full answer (250 KB NDJSON).
- **R473**: same request — `estimated_tokens: 36601` → `exact_tokens: 10036`, no reload;
  one tokenizer HTTP call per unique text (cache + single-flight).
- **R468**: `reason=call_undeclared, dropped_tool_names={write_file}` and a notice naming
  the declared tools instead of "unrecognised format".
- **R461**: both branches live — "budget exhausted (32 of 32)" and "not exhausted
  (21 of 2048), the model stopped on its own".
- **R470/R471**: `thinking_chunks=0` without `think`; 90 chunks with `think:true`.

## 3. New surface

- `POST /api/tokenize` (cppworker, R467): exact token count with `source=tokenizer|estimate`.
- `GET /api/v1/cppworker/config[/runtime]`: output budget policy (`outputBudget`) and
  `default_num_predict` per model.
- WebUI "Loaded": `num_predict` chip; headers `X-Model-Max-Context` (serving ceiling) and
  `X-Model-Gguf-Max-Context` (raw GGUF).
- Switches: `CPPWORKER_TOOLS_THINKING` (`auto|on|off`), `LB_PREFLIGHT_EXACT_TOKENS`
  (default **on**), `CPPWORKER_MAX_N_PREDICT` (16384).

## 4. Upgrading a stand

```bash
cd deployments
# .env: BALANCER_TAG=r261106-2329, CPPWORKER_GPU_TAG=gpu-r261106-2122, WEBUI_TAG=r261106-1716
docker compose -f docker-compose.stack.yml up -d --no-deps loadbalancer cppworker-gpu webui
curl -s http://127.0.0.1:18080/api/version   # build_commit=f306aa48
```

After the upgrade: `GET /api/v1/cppworker/config` → `outputBudget.ceiling=16384`; the first
large request logs `prompt tokens: exact tokenizer count`.

## 5. Open (decisions, not code)

1. **Per-protocol window semantics** — currently a single "per client" semantic; proposal:
   keep it and add a steward that forbids conversions bypassing `perClientToTotal`.
2. **Automatic `parallel` reduction** — deliberately not implemented (the feedback loop
   already caused unload+load churn, R416/R444).
3. `TestReload_DegradedHeaderOnCPUOnly` flake — not reproducible (three `-race` runs green).
4. **llama.cpp is pinned at b10731** (2026-09-01); b11844 (2026-10-23, 1113 commits) is
   available locally. Benefit/risk analysis: `docs/architecture/llama-cpp-pin.ru.md`.
