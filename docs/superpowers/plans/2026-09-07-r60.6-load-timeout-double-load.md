## 2. Root causes (in priority order)

### RC1. `http.Client.Timeout: 90s` is hardcoded — kills the reload at 90s even though cppworker is told `?waitTimeoutSec=300`

**File:** `internal/balancer/nctx_reload_handlers.go:226`

```go
return &DefaultNCtxReloadHTTPClient{
    HTTPClient: &http.Client{Timeout: 90 * time.Second},  // ← BUG
    APIToken:   token,
    HeaderName: headerName,
}
```

The 90s Client.Timeout is shorter than `cfg.effectiveTimeout()` (default 300s,
max 600s). When cppworker is loading 5GB model with 131072 n_ctx, it takes
60-180s. The http.Client cancels the request at 90s with
"Client.Timeout exceeded while awaiting headers", and `DoReload` returns error.
The `?waitTimeoutSec=300` query param is meaningless because the http.Client
aborts first.

**Fix:** derive http.Client.Timeout from `cfg.effectiveTimeout()` (with a small
buffer: `cfg.effectiveTimeout() + 30s`, max 600s).

### RC2. `effectiveAsyncRetryAfter` clamped to max 30s — too short for big models

**File:** `internal/balancer/nctx_reload.go:159-171`

```go
func (c NCtxReloadConfig) effectiveAsyncRetryAfter() int {
    r := c.PreflightAsyncRetryAfterSec
    if r <= 0 { r = 5 }
    if r < 2 { r = 2 }
    if r > 30 { r = 30 }  // ← BUG
    return r
}
```

cppworker reports `estimatedLoadTimeMs` (60-180s for 5GB model + large n_ctx).
The balancer hardcodes 30s max. Client (OpenWebUI/Cline) retries at 30s, but
reload isn't done. Triggers another reload cycle.

**Fix:** raise the clamp from 30s to 120s (covers most realistic loads), and
add a new field `PreflightAsyncRetryAfterMaxSec` for operator override (default
120s). When `estimatedLoadTimeMs` is available from cppworker's 202 response,
use `max(effectiveAsyncRetryAfter, ceil(estimatedLoadTimeMs / 1000))`.

### RC3. `preflight_helper.go:117-136` does not read `estimatedLoadTimeMs` from cppworker's 202 response

**File:** `internal/balancer/preflight_helper.go:127-135`

cppworker's `/api/models/reload?wait=true&waitTimeoutSec=300` returns 200 with
body that includes `model.estimatedLoadTimeMs` (from
`cmd/cppworker/handlers_model.go:357`). The balancer's `DoReload` ignores this
field and just uses `cfg.effectiveAsyncRetryAfter()` for the client response.

**Fix:** when `DoReload` returns 200, parse the body to extract
`estimatedLoadTimeMs` and surface it through the result so preflight_helper can
return it as `Retry-After` (in seconds, rounded up, with min 5s / max 120s
clamp). When the value is unavailable, fall back to `effectiveAsyncRetryAfter`.

### RC4. Async reload goroutine does NOT register in `reloadDedupRegistry` → double-trigger

**File:** `internal/balancer/preflight_nctx.go:578-599`

```go
go func() {
    defer func() { recover() ... }()
    reloadCtx, cancel := context.WithTimeout(...)
    defer cancel()
    if err := c.DoReload(...); err != nil {
        logger.Errorw(...)
        return
    }
    c.SetLastKnownNCtx(backendID, decision.TargetNCtx)
    ...
}()
```

`c.DoReload` is wrapped by `state.inflight` in `nctx_reload.go:712-736`, so the
in-process dedup is at the coordinator level (in-flight reload tracked in
`backendReloadState.inflight`). BUT the new code path in
`preflight_nctx.go:RunPreflight` does NOT use the `reloadDedupRegistry`
mechanism (`StartReloadIfNotPending` / `IsReloadPending` / `WaitReloadDone`).

When client retries 30s later, `IsReloadPending(backendID, modelName)` returns
false because:
- the `reloadDedupRegistry` was never populated for the async reload
- only `state.inflight` (different mechanism) is used, and after `DoReload`
  returns (even on error) `state.inflight` is cleared
- so the second preflight sees loaded=32768 (LastKnownNCtx not updated on
  failure) and triggers ANOTHER reload

**Fix:** in `RunPreflight` async path, register the reload in
`reloadDedupRegistry` via `c.reloadDedup.StartReloadIfNotPending(backendID,
modelName, targetNCtx, func() { ... do reload ... })` instead of calling
`c.DoReload` directly. This makes the dedup registry the single source of
truth. Also, when preflight is about to trigger async reload, check
`IsReloadPending(backendID, modelName)` first; if true, just return 503 with
remaining wait time (from `WaitReloadDone` with a short timeout) instead of
triggering a new reload.

### RC5. `c.SetLastKnownNCtx` is not called on reload failure

**File:** `internal/balancer/preflight_nctx.go:587-591`

```go
if err := c.DoReload(reloadCtx, backendID, backendAddr, modelName, plan, loader); err != nil {
    logger.Get().Errorw("preflight: async reload failed", ...)
    return  // ← LastKnownNCtx not updated, so next request also triggers
}
c.SetLastKnownNCtx(backendID, decision.TargetNCtx)
```

On reload failure, `LastKnownNCtx` stays at the OLD value (32768). The next
preflight sees loaded=32768 < target=131072 and triggers reload again. This
amplifies RC4.

**Fix:** on reload failure, set `LastKnownNCtx` to a special "in-progress"
sentinel or use the reloadDedupRegistry's pending entry to short-circuit future
prefights. Concretely: when `IsReloadPending(backendID, modelName)` is true,
the preflight helper should return 503 WITHOUT triggering a new reload (just
say "reload in progress" with the time remaining).

### RC6. `preflightNCtxReloadIfNeeded` (OLD path) does not use the dedup registry

**File:** `internal/balancer/nctx_reload_handlers.go:589`

```go
go p.executeAsyncReload(backendID, modelName, requestedNCtx, backendState.Backend)
```

The OLD preflight path bypasses the coordinator entirely. If a request comes
through `llamacpp_transport.go:64` (streaming) or
`llamacpp_transport_nonstream.go:65` (non-streaming), the new dedup logic in
the coordinator is NOT engaged.

**Fix:** refactor the OLD path to also go through the coordinator's
`RunPreflight` so the dedup is applied uniformly. If the refactor is too risky
for R60.6, at minimum add `IsReloadPending` check before spawning
`executeAsyncReload`.

### Phase A — Fix http.Client timeout (RC1)

**File:** `internal/balancer/nctx_reload_handlers.go:208-230`

```go
func (p *Proxy) newNCtxReloadHTTPClient() NCtxReloadHTTPClient {
    token := ""
    headerName := "X-API-Token"
    if p.config != nil { ... }
    if envToken := os.Getenv("LB_API_TOKEN"); envToken != "" {
        token = envToken
    }
    // R60.6 fix: derive http.Client.Timeout from nctxReload config instead of
    // hardcoded 90s. cppworker /api/models/reload?wait=true&waitTimeoutSec=300
    // needs up to 300s+ for large models (5GB+ with 131072 n_ctx). Old
```

```go
// Mirrors cppworker cmd/cppworker/handlers_model_async.go:estimateLoadTimeMs
func estimateReloadTimeMs(modelSizeBytes, targetNCtx int64) int64 {
    const baseSpeed = 100 * 1024 * 1024  // 100 MB/s fallback
    const baseMinMs = 1000
    const overheadMs = 2000
    const ctxInitMsPer4K = 500
    baseMs := modelSizeBytes * 1000 / baseSpeed
    if baseMs < baseMinMs { baseMs = baseMinMs }
    ctxMs := ((targetNCtx + 4095) / 4096) * ctxInitMsPer4K
    return baseMs + ctxMs + overheadMs
}
```

```go
retryAfter := coord.Config().effectiveAsyncRetryAfter()
if estimatedMs > 0 {

    if estimatedSec > retryAfter { retryAfter = estimatedSec }

        retryAfter = coord.Config().PreflightAsyncRetryAfterMaxSec

}
```

## 7. Risks & open questions

### 7.1. Will the dedup registry break the sync reload path?

Currently `RunPreflight` has both sync (line 621) and async (line 555) paths.
The async path needs dedup. The sync path is single-flight by design (it
blocks until reload completes). The sync path uses `state.inflight` in
`DoReload` for its own single-flight, which is fine. R60.6 will add dedup
only in the async path.

### 7.2. What if the model size is unknown?

`getModelSizeBytes` may return 0 if the metrics poller hasn't picked up the
model yet. In that case, fall back to `cfg.effectiveAsyncRetryAfter()` (the
config default). This is the same behavior as before for cold-start cases.

### 7.3. The async reload goroutine PANIC after recover()

Log shows: `preflight: PANIC in async reload goroutine — RECOVERED, panic:
runtime error: invalid memory address or nil pointer dereference`. The
recover() DOES catch the panic (that's why the "RECOVERED" message is
logged). But this is unusual: a panic after `return` should not happen.

Hypothesis: the `defer cancel()` runs BEFORE the `defer recover()`, and
`cancel()` itself panics (e.g., on a nil context). Or the panic is from a
goroutine launched by `DoReload` (e.g., a callback) and propagates here.

This is NOT a R60.6 blocker (the recover works), but should be investigated
in R60.7+.

### 7.4. The OLD `preflightNCtxReloadIfNeeded` path

Used by `llamacpp_transport.go:64` (streaming) and
`llamacpp_transport_nonstream.go:65`. If a request hits this path AFTER the
new path's dedup is set, the OLD path will still trigger another reload.

For R60.6, add an `IsReloadPending` check at the top of
`preflightNCtxReloadIfNeeded` (cheap guard) and refactor the rest of
`preflightNCtxReloadIfNeeded` to delegate to the coordinator's `RunPreflight`
in a follow-up patch. This way the old path becomes a thin wrapper around
the new path.

   - Third request after reload completes → 200 OK.
   - Fourth request → 200 OK (no reload).
5. **Log inspection:** exactly ONE `triggering ASYNC reload` per preflight
   cycle, not multiple.
6. **Clean-slate rebuild not required** (balancer-only changes).
7. **Memory entry:** document the dedup-in-async pattern as cross-project lesson.

## 10. Memory plan

Append to agent memory after commit:
```
### R60.6 async reload dedup pattern (verified 2026-09-07, ollamalegion)

**Bug pattern**: when async preflight reload is triggered, the in-flight
reload MUST be registered in the dedup registry BEFORE the goroutine
starts. Otherwise subsequent prefights don't see the pending reload and
trigger cascading reloads.

**Symptom**: 503 with Retry-After=30s, client retries at 30s, model still
loading, balancer triggers another reload. Cppworker TryLockLoad prevents
the second reload from actually starting but logs "reload in progress"
500-errors that confuse the user. After 90s the FIRST reload times out at
http.Client.Timeout level, then a THIRD reload is triggered, etc.

**Two-part fix**:
1. http.Client.Timeout in reload client must match cfg.effectiveTimeout()
   (default 300s, max 600s). Hardcoded 90s kills the request before cppworker
   can finish loading.
2. Async reload goroutine must call reloadDedup.StartReloadIfNotPending()
   which registers the entry. Subsequent preflight calls check
   IsReloadPending() and return 503 with the same Retry-After (no new reload).

**Reusable pattern (cross-project, HIGH value)**: any async-job launcher
should expose a "is this job already running?" query to its callers, AND
register the job in that query BEFORE spawning the goroutine. Otherwise
callers can't dedup and will trigger parallel duplicate jobs.
```
