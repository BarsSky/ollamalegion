# R368. `/api/generate` изредка отдаёт `***` и останавливается

Дата: 2026-10-31. Стенд: `cppworker:gpu-0e72f0b3` (после R364/R365), модель
`gemma-4-E4B-it-Q4_K_M`, ctx 32768 / KV q4_0 / reasoning on / 42 слоя на GPU.

**Статус: диагностировано, НЕ исправлено.** Ниже — замеры, причина и почему
правка не сделана «заодно» в этом раунде.

## 1. Симптом

Один из ответов через клиентский порт выглядел так:

```
POST http://127.0.0.1:18080/api/generate
{"model":"gemma-4-E4B-it-Q4_K_M",
 "prompt":"Write a short paragraph about why tests matter in software engineering.",
 "stream":false,"options":{"num_predict":120}}

→ {"response":"***","done":true,"tokens":3,"durationMs":146,
   "prompt_eval_count":13,"tokensPerSec":20.45}
```

То есть модель сгенерировала три токена `***` и завершилась по EOS за 146 мс —
это не деградация скорости и не обрыв транспорта, а именно такой ответ.

## 2. Замеры (одинаковый промпт и `num_predict=120`)

| путь | коротких ответов |
| --- | --- |
| прямой воркер `:18092/api/generate` | 1 из 12 |
| через балансер `:18080/api/generate` (→ `/v1/completions`) | 3 из 12 |
| прямой воркер `:18092/api/chat` (применяется чат-шаблон) | **0 из 8** |
| `/v1/completions` с явным `temperature: 0.8` | 0 из 8 |
| `/api/generate` с явным `temperature: 1.0` | 1 из 8 |

## 3. Причина (насколько установлено)

`/api/generate` у нас — «сырой» single prompt, **чат-шаблон модели не
применяется** (это осознанное решение, см. комментарий в
`cmd/cppworker/handlers_generate.go:101-118`: нативный путь через
`common_chat_templates_apply` требует structured messages, а `/api/generate` их
не имеет; вместо шаблона подмешивается текстовая инструкция для reasoning).
`/api/chat` шаблон применяет — и там деградации нет ни разу из восьми.

Настоящий Ollama для `/api/generate` **применяет** шаблон модели, если клиент не
передал `raw:true`. Значит расхождение с Ollama есть: клиент, который ожидает
ollama-поведение на `/api/generate`, у нас получает «продолжение с чистого
листа», и instruction-модель иногда завершает его вырожденным `***`.

Температура влияет на частоту (при 0.8 — 0 из 8, при 1.0 — 1 из 8), но не
является причиной: дефолт воркера и так 0.7.

## 4. Почему не исправлено в этом раунде

Правка «применять шаблон в `/api/generate`, если не `raw:true`» меняет промпт
для **всех** вызовов `/api/generate`, а не только для этого случая:

- меняется `prompt_eval_count` и подсчёт контекста (клиенты, которые сами
  считают окно, это заметят);
- ломается сценарий «сырое продолжение» (клиенты, которые сознательно
  используют `/api/generate` как completion без шаблона);
- существующие тесты воркера (`handlers_generate*`, `build_generation_params*`)
  завязаны на текущее поведение и должны быть переписаны осознанно, а не
  подогнаны;
- нужен честный замер на всех поддерживаемых моделях стенда (gemma, Qwen,
  DeepSeek, Phi), а не на одной.

Это отдельная работа с приёмкой, а не «попутная правка» в конце длинного
раунда.

## 5. Что предлагается делать (порядок)

1. В `/api/generate` при `raw:false` (то есть по умолчанию, как в Ollama)
   применять чат-шаблон модели к одиночному user-сообщению (номинально
   `messages=[{role:user, content:prompt}]` + system), сохраняя текущие
   текстовые инъекции reasoning/инструментов только там, где шаблона нет.
2. Флаг `raw:true` оставить как escape hatch — он уже принимается и уже
   используется для отключения инъекций.
3. Замерить: `prompt_eval_count`, длину ответа и частоту `***` до/после на
   4 моделях × 12 прогонов; приёмочный критерий — «0 коротких ответов на
   шаблонных промптах и сохранённый `raw`-режим».
4. Пока не сделано — в инструкции оператора отметить, что `/api/generate`
   у нас completion-семантика, а не ollama-семантика.

## 6. Что НЕ является причиной (проверено)

- Не балансер: прямой воркер ведёт себя так же (1/12).
- Не R364/R365: провал воспроизводится и до правок, и после; загрузка идёт с
  профилем (ctx 32768, 42 слоя на GPU, offload_degraded=false).
- Не скорость: 20–29 tok/s, `***` приходит за 146 мс (штатная генерация).
- Не память: `offload_degraded=false`, VRAM 5.2/8 ГБ.
