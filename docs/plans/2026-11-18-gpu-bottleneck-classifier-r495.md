## 0. Что сделать (одним абзацем)

Балансер сегодня судит о занятости GPU по `utilization.gpu` (SM busy) и из-за этого
считает **memory-bound** карту — то есть карту, которая уже уперлась в пропускную
способность памяти на декоде, — **свободной** и посылает на неё ещё запросов. Нужно:
(1) довезти до балансера сигнал занятости памяти и причину троттлинга (NVML/`nvidia-smi`),
(2) считать по уже измеряемым окнам префилла/декода раздельные tok/s,
(3) ввести классификатор `bottleneck` (memory / compute / power / stall / idle / unknown),
(4) использовать его в двух точках — `score` и подсказки автотюна — **в режиме shadow
по умолчанию**, чтобы включение было осознанным шагом, а не переписыванием селектора.

### Определение готовности (DoD)

- `GPUMetrics` несёт `MemBusyPercent`, `ThrottleReasons`, `PState`, `PCIELink*`;
  заполняется **обоими** путями (NVML на Linux и `nvidia-smi` на Windows), старые
  агенты без полей дают 0 = «неизвестно» и **ничего не ломают**.
- Классификатор выдаёт `bottleneck` на бэкенд; ≥ 6 тестов + 3 мутации красный→зелёный.
- `LB_GPU_BOTTLENECK=shadow` (дефолт после S2): диагноз виден в `/api/metrics` и в
  cluster state, но решения НЕ меняет. `=on` — влияет на `score`. `=off` — прежнее поведение.
- В отчёте — **измеренные** числа до/после на стенде (не оценки): prefill tok/s,
  decode tok/s, p50/p95 времени до первого токена, распределение запросов.

## 1. Проблема: это дефект наблюдаемости, а не «пожелание фичи»

### 1.1 Memory-bound карта выглядит свободной

`internal/balancer/scoring.go:23-38` (`computeBaseScoreAndPenalty`):

```go
gpuFree := 100 - m.GPU.UsagePercent          // ← SM busy, не занятость памяти
baseScore = gpuFree*0.30 + vramFree*0.20 + cpuFree*0.15
```

`UsagePercent` заполняется только из `util.Gpu` (`internal/agent/nvml_unix.go:226-232`).

Физика: на декоде каждый токен требует прочитать **все веса модели + KV-cache**.
Предел скорости упирается в полосу памяти, а занятость SM при этом падает до 40–70 %
(тензорные ядра ждут данные). Итог на живом стенде: карта уже насыщена, а `gpuFree`
показывает 30–60 %, `score` высокий → балансер шлёт ещё запросов → растёт очередь
и время до первого токена у всех, хотя пропускная способность не выросла ни на токен.

Это ровно тот класс дефекта, который проект уже ловил в других местах (R493:
«числа только измеренные», `stats_windows_r493.go:4-32`): наблюдаемая величина
подменяла измеряемую.

### 1.2 Сигнал уже приходит из NVML — и выбрасывается

`GetUtilizationRates()` возвращает **две** величины: `Gpu` и `Memory`. В коде берётся
только первая (`nvml_unix.go:229`), вторая не читается нигде:

```
grep -rn "util.Memory" internal/ → пусто
```

То есть на Linux исправление «увидеть занятость памяти» — это одна строка, но она
не сделана, и до балансера сигнал не доходит.

### 1.3 В типах нет полей, чтобы довезти сигнал

`pkg/types/metrics.go:118-149` (`GPUMetrics`): `UsagePercent`, `MemoryTotal/Used/Free`,
`Temperature`, `PowerUsage/Limit`, `GPUClock`, `MemClock`, `UUIDs`.
Нет ни занятости памяти, ни причины троттлинга (`sw_power_cap` / `hw_slowdown` /
`hw_thermal`), ни состояния PCIe. Следствие: даже когда карта «уперлась», **объяснить
почему** нечем — ни в логе, ни в панели, ни в отчёте оператору.

### 1.4 Раздельные prefill/decode уже измеряются — но не используются в решениях

`internal/balancer/stats_windows_r493.go:23-32` фиксирует правило отрезков:

```
UpstreamSent → FirstDelta : prompt_eval_duration (префилл)
FirstDelta   → End        : eval_duration       (генерация, включая размышления)
```

`Durations()` (`:111`) даёт `Load / PromptEval / Eval / Total` с инвариантом суммы,
а `prompt_eval_count`/`eval_count` приходят в том же usage-чанке
(`llamacpp_translate_resp.go:813-816`). Значит **prefill tok/s и decode tok/s на
пару (бэкенд, модель) вычислимы из того, что балансер уже имеет** — не хватает
только накопления и классификации по ним. Этот источник на порядок точнее
10-секундного сэмпла NVML (`internal/agent/collector.go:305`: `minCollectInterval = 10s`).

### 1.5 Тюнер весов слеп к причине деградации

`internal/balancer/weight_tuner.go:161-243` (`tune`) правит веса по `successRate` и
`avgLatencyMs`. При memory-bound деградация выглядит как «латентность выросла» — и
тюнер усиливает `QueueDepth`/`ErrorRate`, хотя причина не в очереди и не в ошибках,
а в полосе памяти. Различить «перегрузка» и «уперлась» ему нечем.

### 1.6 Оператор не видит диагноз нигде

`internal/balancer/metrics.go:68-166` (`GetMetrics`), cluster state и WebUI не содержат
ни занятости памяти, ни вердикта. В `/api/metrics` и мониторе видно «GPU 55 %», и это
читается как «есть запас» — что неверно.

## 3. Какие данные добавить

### 3.1 Обязательный минимум (без внешних зависимостей)

| Поле `GPUMetrics` | Linux (NVML) | Windows (`nvidia-smi`) | Зачем |
|---|---|---|---|
| `MemBusyPercent float64` | `util.Memory` из `GetUtilizationRates()` | `utilization.memory` | занятость интерфейса памяти — первый признак memory-bound |
| `ThrottleReasons uint64` (+`[]string` для панели) | `GetCurrentClocksThrottleReasons()` (константы биндинга: `SwPowerCap`, `HwSlowdown`, `HwThermalSlowdown`, `HwPowerBrakeSlowdown` — **сверить имена в go-nvml**) | `clocks_throttle_reasons.active` | «почему медленно»: питание / температура / браке |
| `PState int` | `GetPerformanceState()` | `pstate` | P0/P2 — карта реально считает; P8 — простаивает |
| `PCIELinkGen int`, `PCIELinkWidth int` | `GetCurrPcieLinkGeneration()` / `GetCurrPcieLinkWidth()` | `pcie.link.gen.current`, `pcie.link.width.current` | узкое место раскладки: слой через сеть идёт по PCIe |
| `PowerUsage`/`PowerLimit` | **уже есть** | **уже есть** | отношение `power/limit` — признак power-bound |
| `MemClock` | **уже есть** | **уже есть** | срезанная частота памяти = memory-троттлинг |

Требования к парсингу:

- новые колонки **только в конец** запроса `nvidia-smi` и парситься с индекса 11+;
  в `gpu_common.go:45-47` прямо записано, почему середину двигать нельзя
  (переиндексация всех полей ломает NVML-путь и тесты);
- отсутствующая колонка (`N/A`, `[Not Supported]`) → поле остаётся 0 = «неизвестно»,
  предупреждение в лог **один раз за карту**, а не на каждый сбор;
- старый агент без новых полей и старый балансер с новыми: JSON-совместимость
  (`omitempty`), 0 трактуется как «неизвестно» и **не блокирует** решения.

### 3.2 Второй источник: раздельные скорости (уже измеряются)

По каждому завершённому запросу сохранять в разрезе `(backendID, model)`:

```
decodeTps  = eval_count        / (Eval        / 1e9)
prefillTps = prompt_eval_count / (PromptEval  / 1e9)
```

и держать экспоненциальное среднее (EMA) + счётчик наблюдений. Нули и «меньше 0»
из окна не попадают в статистику (в `stats_windows_r493` такие случаи уже отделены:
`WorkerLoad` вычитается, отрицательные обнуляются) — иначе средняя скорость будет
занижена загрузкой модели, а не декодом.

### 3.3 DCGM — НЕ в этой задаче

`DCGM_FI_PROF_DRAM_ACTIVE` — единственная метрика, которая даёт «долю пиковой ПСП»
напрямую, в отличие от `utilization.memory` (доля **времени** занятости интерфейса).
Но она тянет за собой обязательную внешнюю зависимость (dcgm-exporter / DCGM API)
и MIG-особенности. В этой задаче — только зафиксировать в §11 как путь развития,
если `utilization.memory` на A10 окажется непригодной.

## 4. Классификатор `bottleneck`

### 4.1 Правила (стартовые пороги; калибруются на стенде, §11)

| Условие | Вердикт | Смысл |
|---|---|---|
| есть активные запросы, `MemBusy ≥ 85 %`, `SM ≤ 70 %`, `power/limit < 0.9` | `memory` | декод уперся в полосу памяти |
| `SM ≥ 90 %`, `power/limit ≥ 0.95`, throttle содержит `sw_power_cap`/`hw_slowdown` | `power` | префилл уперся в TDP |
| `SM ≥ 90 %`, `MemBusy 40–80 %`, `power/limit < 0.9` | `compute` | уперся в тензорные ядра |
| `SM ≤ 40 %`, `MemBusy ≤ 40 %`, запросы активны > N секунд, `Eval` растёт | `stall` | ждёт сеть/PCIe/RPC/CPU — карта не «свободна», она простаивает в ожидании |
| `SM ≤ 5 %`, нет активных запросов | `idle` | действительно свободна |
| метрик нет / `MemBusy == 0` и `UsagePercent == 0` / старый агент | `unknown` | **прежнее поведение**, ничего не блокируем |

Обязательные свойства:

1. **Гистерезис.** Вердикт меняется не мгновенно, а после подтверждения K подряд
   сборов (K = 2–3) или по EMA — иначе на границе порога классификатор будет
   дёргаться и вместе с ним «дёргаться» будут score и подсказки.
2. **`unknown` — не «плохо».** Отсутствие данных не должно ни повышать, ни понижать
   score (иначе старая сборка агента начнёт получать штраф).
3. **Несколько карт.** Классифицировать карту из `EffectiveGPUIndex()`; если индекс
   неизвестен — агрегировать `max` по картам хоста и пометить вердикт как
   `aggregated: true` (в панели это должно быть видно, а не выглядеть как факт по карте).
4. **Где живёт.** Сырьё собирает **агент**, вердикт считает **балансер** (у него
   окна запросов и модель). Один классификатор, не два.

### 4.2 Флаг

```
LB_GPU_BOTTLENECK=off|shadow|on     # off — прежнее поведение; shadow — считать и публиковать,
                                    # но решения не менять (дефолт после S2); on — влиять на score
```

Неизвестное значение → `shadow` + **одно** предупреждение в лог (как в
`selection_order_r493.go`, не молча).

## 5. Как это влияет на решения

### 5.1 `score` (`scoring.go:23-38`)

Вместо `gpuFree = 100 - UsagePercent` ввести `loadPressure`:

- `memory` → `loadPressure = max(SM, MemBusy)`. Насыщенная по памяти карта перестаёт
  выглядеть свободной — это и есть исправляемый дефект §1.1.
- `stall` → штраф (аналог `requestPenalty`): простаивающая карта с живыми запросами
  **не** хороший кандидат, она их только задержит.
- `compute`/`power` → `loadPressure = SM` (как сейчас), ничего не меняем.
- `unknown`/`idle` → прежняя формула.

Формулу и веса `baseScore` не переписывать целиком: правка минимальная и
проверяемая, иначе получим «два мозга» вместо одной формулы.

### 5.2 Вместимость — НЕ трогать

`EffectiveMaxConcurrentRequests` и `EffectiveMaxConcurrentRequests`-эхо из R71/R83 не
должны зависеть от классификатора. При `memory` вердикте меняется только **выбор**
и **подсказка** оператору; вместимость остаётся там, где ей владеют (слоты модели,
runtime-лимит, `LB_CAPACITY_FROM_MODEL_SLOTS`). Иначе одна и та же карта получит
два источника вместимости — это уже было дефектом R71.

### 5.3 Подсказки автотюну (advisory, без автоприменения)

- `power` → подсказка «уменьшить `n_ubatch`/`n_batch`»: рост батча упирается в TDP,
  частота сбрасывается, время до первого токена растёт.
- `memory` → подсказка «поднять `parallel`/слоты»: при декоде веса читаются один раз
  на N токенов, батчинг почти линейно поднимает агрегатный tok/s на одной карте —
  это **главный рычаг** на memory-bound, и он противоположен интуиции «разгрузить».
- Подсказка публикуется как advisory в cluster state и `/api/metrics`, автоприменение —
  отдельной задачей после замеров (прецедент: R83-fix «совет оператору, ничего не меняем сами»).

**S1. Метрики без решений.**

**S3. Влияние на `score`** под `=on`: `loadPressure` для `memory`, штраф для `stall`.

**S4. Подсказки автотюну + панель + доки** (`balancing-guide.ru.md` §2,
`feature-switches.ru.md`, CHANGELOG с измеренными числами).

## 8. Тесты и мутации (минимум)

1. `MemBusy` заполняется на NVML-пути и на `nvidia-smi`-пути; `N/A` → 0 без паники.
2. Старый формат вывода `nvidia-smi` (11 колонок) парсится как раньше — регрессия §1.3.
3. `mergeGPUMetrics`: локальные значения перекрывают снимок движка по новым полям,
   а при отсутствии локальных — значения движка сохраняются.
4. Классификатор: `memory`, `power`, `compute`, `stall`, `idle`, `unknown` (6 кейсов);
   `MemBusy == 0` (старый агент) → `unknown`, **score не меняется**.
5. Гистерезис: одиночный выброс не меняет вердикт, серия из K — меняет.
6. Несколько карт: известный `EffectiveGPUIndex` → вердикт по одной карте;
   неизвестный → `aggregated: true`.
7. Score при `LB_GPU_BOTTLENECK=off` совпадает с прежним (эталонное значение).
8. Статистика tok/s: `WorkerLoad` вычитается, отрицательные окна не портят EMA.

Мутации (обязаны краснить): `max(SM, MemBusy)` → `SM`; порог `memory` 0.85 → 0.5;
`unknown` → штраф; гистерезис K → 1.

## 10. Чего делать НЕ надо

- **Не строить решения на `utilization.gpu` там, где речь о памяти.** И наоборот:
  `utilization.memory` не заменяет `utilization.gpu` для префилла.
- **Не вводить DCGM/dcgm-exporter обязательной зависимостью** (§3.3) — только как
  исследовательский путь в §11.
- **Не менять `EffectiveMaxConcurrentRequests`** из классификатора (§5.2).
- **Не агрегировать метрики по всем картам хоста молча** — либо карта из
  `EffectiveGPUIndex()`, либо явный признак `aggregated`.
- **Не включать `on` по умолчанию** и не смешивать S1–S3 в одном коммите.
- **Не выдумывать числа в отчёте.** Нет замера — писать «не измерено» (культура R493:
  `stats_windows_r493.go`, живой дефект §1.1).

## 11. Открытые вопросы (решаются замерами, не рассуждением)

1. **`utilization.memory` на A10.** В контейнере/на датацентровых картах поле может
   отдаваться как `N/A` или постоянный 0 (зависит от драйвера и прав). Проверить на
   обоих стендах первым делом: если 0 — вердикт `memory` строить по паре
   (`power/limit`, `clocks_throttle_reasons`, падение `decode tok/s` относительно
   пикового) и/или переходить к DCGM (§3.3).
2. **Пороги.** 85/70/95 — стартовые. Настроить по живым числам: снять зависимость
   `decode tok/s` от `MemBusy` на 3–4 моделях разного размера.
3. **Калибровка потолка полосы.** Проверить формулу на живой карте:

   ```
   потолок decode (tok/s) ≈ BW_эффективная / размер_весов
   A10:  600 ГБ/с, Q4_K_M 7B ≈ 4.1 ГБ  → ~146 tok/s теоретически, 60–80 % достижимо
   RTX 4000: 416 ГБ/с                                    → пропорционально ниже
   ```

   Если измеренный decode даёт 60–80 % от потолка — вердикт `memory` верен, и
   «разгружать» карту бессмысленно; если 20–30 % — узкое место не память, и надо
   смотреть `stall` (слои на CPU, RPC-узлы, разбиение `device_layers`).
4. **MIG.** Если на A10 включён MIG, метрики per-instance; проверить, что
   классификатор не смешивает инстансы (иначе — только `aggregated` + предупреждение).
5. **`stall` vs «просто медленный префилл».** Отличить ожидание сети от долгого
   префилла по `PromptEval`/`Eval` и `requests_processing`; критерий зафиксировать
   числами, иначе порог будет подгонкой.
