## 1. Bug analysis (live reproduction 2026-09-07)

**Reproduction command:**
```powershell
curl.exe -N -i -s --max-time 240 `
  "http://localhost:18083/api/v1/events?token=changeme-bundled-with-agent-token"
```

**Observed result (direct to API server 18081, bypassing nginx):**
- HTTP 200, headers correct (text/event-stream, chunked, no-cache)
- 5 `: ping\n\n` heartbeats (one every ~10s)
- Connection severed at ~50-60 seconds
- No data after that; no error message; client curl just exits

Same result through nginx (port 18083) → confirms nginx is NOT the cause.

**Log evidence** (`ol-bundled-balancer`):
- No `events`/`heartbeat`/`SSE`/`client disconnected` log entries
- Connection drops silently on the server side, no graceful close

## 2. Root cause

**File:** `cmd/balancer/main.go:361`

```go
apiHTTPServer := &http.Server{
    Addr:         fmt.Sprintf("%s:%d", conf.LoadBalancer.Host, conf.LoadBalancer.APIPort),
    Handler:      apiServer,
    ConnContext:  enableTCPKeepAlive,
    ReadTimeout:  30 * time.Second,
    WriteTimeout: 60 * time.Second,  // ← BUG
    IdleTimeout:  120 * time.Second,
}
```

**Mechanism:** Go's `http.Server.WriteTimeout` is implemented as
`SetWriteDeadline(time.Now().Add(WriteTimeout))` called ONCE per response
(at end of readRequest). **It is the absolute deadline for the entire
response lifetime**, NOT reset on each Write. From Cloudflare's "complete
guide to Go net/http timeouts":

> Deadlines are not timeouts. Once set they stay in force forever (or until
> the next call to SetDeadline), no matter if and how the connection is used
> in the meantime.

> WriteTimeout normally covers the time from the end of the request header
> read to the end of the response write (a.k.a. the lifetime of the
> ServeHTTP).

The 10s `: ping` heartbeats do NOT reset the deadline. After exactly 60s
from request start, the connection is killed mid-stream.

**5 pings × 10s + initial headers = 50-60s** — matches reproduction exactly.

**Secondary issue (HTTP/2 compat):** `Connection: keep-alive` header is set
in `handleEvents` (line 90). HTTP/2 forbids this header. Not the cause of
drops but a future-proofing concern.

**Tertiary issue:** The webui `notifications.js` has
`this.eventSource.onerror` that calls `eventSource.close()` and reconnects.
This is correct EventSource behavior, but means the user-visible symptom
is "bell icon flicker every 1 minute" (or "every 5 minutes" if they have
other browser caching that masks the reconnect).

## 3. Fix

**Primary fix:** in `handleEvents` (and any other SSE handler in
`internal/api/`), call `http.NewResponseController(w).SetWriteDeadline(time.Time{})`
BEFORE any write. This removes the per-response deadline so the stream can
live forever (limited only by client disconnect / TCP keepalive).

**Required Go version:** 1.20+. Project is on 1.25.4.

**Secondary fix:** remove `Connection: keep-alive` header (HTTP/2 doesn't
allow it, and Go's chunked encoding already implies keep-alive for HTTP/1.1).

**Heartbeat:** keep at 10s (well under any reasonable client proxy timeout).
The previous comment in `handlers_events.go:25` says "30 сек" but the actual
constant is 10s. Update comment for accuracy.

"""Test SSE /api/v1/events survives for >2 minutes (was: 60s)."""
import time, threading, requests

URL = "http://localhost:18083/api/v1/events?token=changeme-bundled-with-agent-token"
DURATION_SEC = 150  # 2.5 min — well past old 60s WriteTimeout

def main():
    events = []
    pings = []
    sse = requests.get(URL, stream=True, timeout=10)
    assert sse.status_code == 200
    assert "text/event-stream" in sse.headers["content-type"]

    start = time.time()
    for line in sse.iter_lines():
        if time.time() - start > DURATION_SEC:
            break
        if line:
            line_str = line.decode("utf-8")
            if line_str.startswith(": ping"):
                pings.append(time.time() - start)
            elif line_str.startswith("data:"):
                events.append(line_str)

    # Assertions:
    # 1. At least 5 pings received (heartbeat every ~10s over 150s)
    assert len(pings) >= 5, f"Only {len(pings)} pings, expected >= 5 over {DURATION_SEC}s"
    # 2. Pings are roughly evenly spaced (10s ± 2s)
    for i in range(1, len(pings)):
        delta = pings[i] - pings[i-1]
        assert 7 <= delta <= 13, f"Ping gap {delta}s outside [7,13]s window"
    # 3. No connection drop before DURATION_SEC
    print(f"OK: {len(pings)} pings over {pings[-1]:.1f}s, no drops")

if __name__ == "__main__":
    main()
```

## 6. Risks & open questions

### 6.1. Will removing WriteTimeout break other endpoints?

No — we ONLY remove it for `/api/v1/events` (via `SetWriteDeadline(time.Time{})`
in handleEvents). All other endpoints keep the 60s WriteTimeout. The
`/api/v1/cppworker/*` endpoints and health checks are short and don't need
write deadline bypass.

### 6.2. Is 150s test runtime acceptable?

For CI, maybe not. Options:
- `testing.Short()` skip pattern (long tests only on demand)
- Configurable duration via env var (default 150s for production, 30s for CI)
- Don't add to `run_all_tests.py` master runner; add as standalone

For R60.7, I'll add a `if SKIP_SSE_LONG: skip` check in test and
`run_all_tests.py` to allow skipping in CI.

### 6.3. What about WebSocket endpoints?

WebSocket endpoints (`/ws/metrics`, `/ws/logs`) use `conn.SetWriteDeadline()`
explicitly per write (handlers_core.go:117,175,195,214). They don't have
this bug. The R60.2 fix `proxy_send_timeout 86400s` on nginx is for
WebSocket specifically, not SSE. They share `WriteTimeout=60s` on the
server but the per-write SetWriteDeadline overrides it.

### 6.4. The webui notifications.js

It already handles onerror + auto-reconnect. The "every 5 min" user
observation may have been imprecise (actual drop is at 60s but the
webui's reconnect-and-event-loss may mask the rate). After R60.7, no
drops at all.

### Go http.Server WriteTimeout per-response (verified 2026-09-07, ollamalegion)

**Symptom**: SSE /api/v1/events connection drops after exactly 60s. Heartbeat
pings (every 10s) don't help. 5 pings received, then EOF.

**Root cause**: `http.Server.WriteTimeout` is implemented as
`SetWriteDeadline(time.Now() + WriteTimeout)` called ONCE per response
(at end of readRequest). It is the ABSOLUTE deadline for the response
lifetime, NOT reset on each Write. Per Cloudflare: "Deadlines are not
timeouts. Once set they stay in force forever (or until the next call to
SetDeadline)."

**Fix** (Go 1.20+): in the SSE handler, call
`http.NewResponseController(w).SetWriteDeadline(time.Time{})` BEFORE any
write. This removes the per-response deadline so the stream lives until
client disconnects / TCP keepalive fires.

**Also**: don't set `Connection: keep-alive` header in SSE handlers
(HTTP/2 forbids it; Go's chunked encoding implies keep-alive for HTTP/1.1).

**Reusable pattern (cross-project, HIGH value)**: any long-lived HTTP
response (SSE, WebSocket-via-HTTP, long polling, server-streaming gRPC)
must call `http.NewResponseController(w).SetWriteDeadline(time.Time{})`
at the top of the handler, otherwise the server-level `WriteTimeout` will
kill the connection at the absolute deadline. WebSocket handlers using
gorilla/websocket avoid this by calling `conn.SetWriteDeadline` per write,
but plain `http.ResponseWriter` doesn't expose the underlying `net.Conn`
for that.

**Diagnostic** (quick check): if a streaming endpoint drops at exactly
`WriteTimeout` seconds, it's this bug. If it drops at random intervals
(minutes), check for proxy timeouts, TCP keepalive, or upstream timeouts.
```
