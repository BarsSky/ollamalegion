# Выравнивание окон копий одной модели (R494)

Документ закрывает вопрос оператора по архиву стенда A10 ×2 (2026-11-12):
«в мониторе уже выскакивает уведомление с предложением перераспределения по
моделям и сейчас оно не корректно… в такой же механизм можно реализовать
уведомление с возможностью подтвердить увеличение окна ну или прописать в
настройках балансера и вывести в управление через webui для балансера».

## 1. Что было в архиве

| узел | модель | окно копии | сессий | активных |
|---|---|---|---|---|
| `cppworker-gpu-bundled-agent` (мастер) | Qwen3.8-27B-UD-Q4_K_M | 198656 | 1 | 1 |
| `A10-126` | Qwen3.8-27B-UD-Q4_K_M | 131072 | 0 | 0 |
| `WIN-I9`, `ASTRA-I9` | — | — | 0 | 0 |

Один и тот же файл модели, два разных окна. Следствия из логов балансера:

```
session re-stick: привязанная копия не покрывает окно клиента
R459: кандидат на ребалансировку отклонён  (окно 131072 < 198656)
no available backends with exclusions
```

То есть вторая копия существовала, была свободна — и бесполезна для живой
сессии, потому что её окно меньше. Со стороны это выглядит как «балансер не
использует второй узел».

## 2. Правило оператора (дословно)

> «если копия не занята сессией то принимать решение по выравниванию если же
> занята а есть бэкенд с нужным окном то ставить в очередь к нему на обработку»

Из него — две разные вещи, и они реализованы в разных местах:

1. **Занятая копия** → заявка ждёт слот ЭТОЙ копии или встаёт в очередь к
   другой копии с нужным окном. Это гейт R459 для очереди
   (`internal/balancer/unified_queue_r459_gate_r480.go`) плюс разделение
   «предпочтение» / «источник окна» в `availability_first_r493.go`.
2. **Свободная копия** → можно принимать решение по выравниванию: поднять её
   окно до окна самой широкой копии. Это R494.

Занятую копию выравнивать НЕЛЬЗЯ: перезагрузка 27B — это выгрузка модели,
то есть обрыв чужой генерации. Правило R287 («отложить, а не ломать») остаётся
в силе.

## 3. Что сделано

### 3.1 Решение считает балансер, а не браузер

`internal/balancer/window_align_r494.go`:

* `windowAlignDecideR494(model, copies, cap)` — чистое решение по таблице копий:
  * считается только по копиям с ИЗВЕСТНЫМ окном (`Window > 0`): «неизвестно» —
    не «узкая», иначе предложение врёт;
  * цель — окно самой широкой копии, но не выше потолка оператора;
  * в `alignable` попадают только СВОБОДНЫЕ узкие копии (0 сессий, 0 активных);
  * занятые узкие копии уходят в `busy` (видно, почему их нет в предложении);
  * если свободных узких копий нет — предложения нет вовсе (а не «предложим и
    оборвём»).
* `Proxy.WindowAlignSuggestionsR494(model)` — снимок метрик + сессии из
  `sessionMgr` + активные запросы из состояния бэкендов. Никаких перезагрузок
  и долгих блокировок: метод читают HTTP-ручка и тесты.

Почему не в JS: в браузере нет ни сессий с активными запросами, ни потолка
`LB_WINDOW_ALIGN_MAX_N_CTX`. Вторая арифметика рядом с R459 разошлась бы с ней
на первом изменении правил.

### 3.2 Настройка в реестре (видна в WebUI → «Настройки»)

`LB_WINDOW_ALIGN_MAX_N_CTX` — тип `int`, группа `nctx`, hot-reload,
дефолт `262144`.

* Дефолт именно 262144, а не 131072: при меньшем дефолте живой случай из архива
  (198656 против 131072) не давал бы предложения вовсе — цель обрезалась бы до
  уже существующего узкого окна.
* `0` — предложения выключены совсем.
* Это НАСТРОЙКА, а не действие: балансер по ней только считает потолок. Сама
  перезагрузка остаётся за оператором.

### 3.3 Ручка чтения

```
GET /api/v1/window/align[?model=<имя>]
→ { suggestions: [ { model, cap, targetWindow,
                     copies: [ { backendId, window, sessions, active, free } ],
                     alignableBackends: [...], busyBackends: [...] } ],
    count, cap, setting: "LB_WINDOW_ALIGN_MAX_N_CTX" }
```

Только чтение. Подтверждение идёт существующей ручкой
`POST /api/v1/cluster/models/{name}/reload` с
`{"operation":"reload","backendId":"<узел>","contextSize":<targetWindow>}` —
второй дороги загрузки моделей со своим набором проверок состояния узла (R263)
не заводим.

### 3.4 Монитор: баннер с подтверждением

* `webui/js/monitor/api.js` — `GET /api/v1/window/align` в общий опрос; старая
  сборка отвечает 404 — блока просто нет, ложного баннера не появляется.
* `webui/js/monitor/state.js::windowAlignAlerts` — правило показа (чистая
  функция, покрыта тестом): баннер строится только при непустом
  `alignableBackends`, в тексте — текущее окно и цель.
* `webui/js/monitor/ui-renderer.js` — кнопка «Выровнять» рядом с текстом
  (индекс действия, а не строка из данных: никакой склейки HTML из имён).
* `webui/js/monitor/init.js::alignWindowAction` — `confirm()` с числами и
  POST перезагрузки; ответ показывается баннером (успех / отложено / ошибка).

Автоматической перезагрузки нет намеренно: 27B грузится минутами, и «само
поднялось» оператор увидел бы как зависший стенд.

## 4. Почему это не ломает остальное

* Порядок выбора бэкенда, гейт R459 и очередь не тронуты: R494 только ЧИТАЕТ
  состояние и отдаёт предложение.
* Копия, на которой есть сессия или активный запрос, в `alignable` не попадает
  — значит, кнопка не может предложить оборвать чужую работу.
* Настройка по умолчанию включена «мягко» (потолок 262144), но действие всё
  равно требует подтверждения; `0` полностью отключает предложения.
* Старый балансер без `/api/v1/window/align` — монитор просто не рисует блок
  (404 перехвачен).

## 5. Проверки

Go (`go test -tags llama_stub ./internal/balancer`):
`internal/balancer/window_align_r494_test.go` — 12 тестов: свободная узкая
копия предлагается; занятая — нет; `busy` рядом с `alignable`; потолок
ограничивает цель; потолок ниже копий отключает предложение; `0` отключает;
равные окна и одна копия — предложения нет; неизвестное окно не считается
узким; интеграция по реальным сессиям и активным запросам; сессия на узкой
копии снимает предложение; фильтр по модели.

JS (`npm run test:webui`): `webui/js/monitor/window-align-r494.test.js` —
6 проверок правила показа (числа в тексте, занятая копия, пусто/`null`, цель 0,
`more`, две модели).

## 6. Чего НЕ проверено

* Реальной перезагрузки 27B на стенде с новым окном в этом раунде не делали:
  проверена логика решения, ручка и рендер, а не «поднялось ли окно за N минут
  на конкретной A10». Проверять на стенде следует так:
  `GET /api/v1/window/align` → кнопка «Выровнять» → в логах
  `cluster model operation requested` с `context_size=198656`, затем
  `GET /api/v1/window/align` пустой.
* Влияние более широкого окна на свободную VRAM узла не оценивается
  предварительно: решение принимает cppworker при загрузке (R248/R83). Если
  VRAM не хватит, перезагрузка откажется — и это будет видно в баннере как
  ошибка, а не как «выровнялось».
