## R309: панель показывает и меняет горячие настройки реестра

**Живой пробел.** Балансер с R278 держит реестр «горячих» настроек (17 штук —
применяются без рестарта), и `GET /api/v1/settings` отдаёт готовый ответ «что
действует и откуда взято». Поиск `api/v1/settings` по `webui/**` давал **ноль
совпадений**: в панели были только старые поля `config.json` (требуют
перезапуска), а значения из env выглядели как «ни на что не влияет». Это ровно
жалоба оператора «всё, что задаётся в env, должно быть изменяемо из WebUI».

**Что сделано.** Секция «Горячие настройки (применяются без рестарта)» на странице
настроек: группировка по `group`, в строке — имя, описание с сервера, ДЕЙСТВУЮЩЕЕ
значение, бейдж источника (`по умолчанию` / `из env` / `задано в панели`), поле
ввода, «Применить» и «Сбросить» (активна только для override). Всё состояние
реестра живёт в одном модуле `webui/js/modules/settings-registry.js`; страница
отдаёт только контейнер, поэтому «правка в одном месте не лечит» здесь больше не
воспроизводится.

## R310: восстановление русских комментариев из истории git

**Живой факт.** В 10 Go-файлах русские комментарии превратились в `????`: массовый
коммит 2026-07-03 записал файлы через кодировку без кириллицы, каждый не-ASCII
символ стал одним `?`. Код не пострадал (там ASCII), потерялся только текст
комментариев — включая объяснения живых дефектов, из-за которых этот код и
переписывался.

**Метод (и почему не «в лоб»).** Исходный текст лежит в истории: у 8 из 10 файлов
есть блобы с кириллицей (2026-06-16…2026-07-03). Ключ строки строится
СИММЕТРИЧНО: в текущей строке участки `?` свёрнуты в ранги, в исторической — все
не-ASCII символы заменены на `?` (порча была 1:1 по символам). Матчинг идёт по
ВСЕМ историческим блобам файла, а не по одному коммиту: порча внесена раньше, чем
казалось (в `e196fd4f^` уже 447 `????` в `handlers_chat.go`). Отступ берётся из
текущей строки, окончания строк сохраняются.

**Результат: 539 строк восстановлено, 141 осталась** (см. отдельный список

## R311: версия сборки едет в heartbeat (запись самовосстанавливается)

**Живой факт, найденный при проверке R305.** Агент регистрируется ОДИН раз при
своём старте, а балансер перезапускается независимо и восстанавливает запись из
`state.json`. В результате после рестарта балансера у главного узла снова стояло
`buildInfo="0eadefebd"` без даты и `relation=unknown` — правка R305 выглядела как
«не применилась», хотя образ и env уже несли дату. Восстанавливалось только
перезапуском ВОРКЕРА.

**Что сделано.** Агент кладёт `buildInfo` в каждый heartbeat; оба обработчика
heartbeat (per-backend и legacy) обновляют запись, если значение пришло и
отличается. Пустое значение не затирает известное — старый агент поля не шлёт
вовсе. Тот же приём, что R121 для заявки о вместимости: регистрация — разовое
событие, heartbeat — единственный регулярный канал с узла.

**Проверка живьём** (образы `balancer:25cb3153`, `cppworker:gpu-25cb3153`):

| шаг | результат |
| --- | --- |
| до подмены | `buildInfo="0eadefebd 2026-09-01"`, `relation=behind` |
| `PUT /api/v1/backends/<id>` с `buildInfo="0eadefebd"` (имитация стейт-файла после рестарта) | запись стала «старой» |
| через один heartbeat (~40 c) | снова `"0eadefebd 2026-09-01"`, `relation=behind` — **PASS** |

Офлайн-донор так и остаётся со старым значением — у него нет heartbeat, и это
честно: «нет связи» не выдаётся за «версия совпадает».

Тесты: `TestR311_HeartbeatUpdatesBuildInfo`,
`TestR311_EmptyHeartbeatBuildInfoKeepsKnown`.

### R316: отказ про окно больше не означает «модели нет»

**Что нашли.** Проверка ветки 413 вскрыла живую аварию: отказ воркера «requested
n_ctx=262144 exceeds the physically feasible maximum 131072 … (обучающий контекст
**модели**)» записывался в реестр «модели нет», после чего **каждый** следующий
запрос к живой загруженной модели получал терминальный 404 `model_not_found` /
`decision: model_missing` до конца TTL записи.

**Причина.** `isModelMissingResponse` искал в теле подстроку `"модели"` (и
`"available_models"`) — это совпадает с любым русским текстом, где упомянута
модель, включая отказ про окно. Маркер обязан быть про «файла нет», а не про «в
тексте есть слово про модель».

**Что сделано.** Первым делом отсекаем отказ про окно тем же предикатом, каким
пользуется остальной код (`isNCtxInfeasibleResponse`), и оставляем только точные
маркеры (`model_file_not_found`, `model_not_found`, `model not found`,
`not found in`, `not found:`, `no such file`, «не найдена/не найден»). Тесты: отказ
про окно не признаётся «модели нет» ни при одном статусе; настоящие 404 (три
формулировки воркера + русская) по-прежнему распознаются.

**Проверка живьём** (потолок оператора намеренно поднят выше GGUF-максимума):

| шаг | до R316 | после R316 |
| --- | --- | --- |
| запрос окна сверх GGUF | **404** `model_not_found` / `model_missing` | **503** `context_growth_pending`, `target n_ctx=131072` (физический предел, а не 262144), `hint` |
| следующий обычный запрос к той же модели | **404** до конца TTL | **200 за 1 c** — реестр не отравлен |

Env возвращён на `LB_NCTX_RELOAD_MAX_N_CTX=32768`, стенд перепроверен (чат 200,
модель `loaded ctx=32768`).

**Арифметика цели окна — проверена, это НЕ дефект (закрыто).** Разобрал по коду и
по логу: `262144` — это `requested_total_n_ctx` = окно клиента на слот (131072) ×
число слотов (2), то есть СУММАРНОЕ окно, а `gguf_max_context` — тоже суммарный
потолок модели. Отказ арифметически верен, и все числа уже есть в ответе
(`requested_n_ctx`, `requested_total_n_ctx`, `slots`, `max_per_client_n_ctx`,
`backend_ceiling_n_ctx`) и в тексте
`window_too_big_error` («Запрошенное окно %d токенов на клиента не поместится: %s.
При %d параллельных слотах суммарное окно %d делится между клиентами…»). Ложным
было только ОБОЗНАЧЕНИЕ отказа (404 `model_missing` вместо 413) — это и починил
R316.

Единственная оставшаяся мелочь (не признак дефекта, риск правки выше пользы):
асинхронный путь перезагрузки отправляет воркеру уже посчитанное суммарное окно и
узнаёт «не влезает» от воркера, а не отсекает сам по физическому потолку. Эффект —
один лишний отказ воркера без выгрузки модели; клиенту всё равно приходит отказ от
балансера.

## R318: мёртвый тумблер «Prediction filtering» стал настоящим

**Что нашли (этап 5).** В панели настроек есть тумблер «Prediction filtering».
Сервер принимал поле `predictionFiltering` структурой `PUT /api/v1/cluster/config`
и **нигде его не читал**: ответ «saved», `GET` всегда отдавал константу `true`,
фильтр продолжал работать. Оператор менял тумблер и не видел эффекта — ровно та
жалоба, ради которой затевался аудит настроек.

**Почему это не косметика.** Фильтр не сортирует, а **исключает**: узел, которому
прогноз даёт меньше 5 минут до критического ресурса
(`Prediction.SecondsToCritical < 300`), выпадает из кандидатов целиком — в четырёх
местах (`candidate.go`, `backend_selector.go` ×3). При шумном прогнозе живой узел
оказывается вне выбора, и клиент получает «нет доступных бэкендов» на здоровом
стенде. Тумблер, который это действительно выключает, — способ проверить и
обойти, не читая код.

**Что сделано.**

| слой | изменение |
| --- | --- |
| реестр настроек | `LB_PREDICTION_FILTER` (bool, дефолт 1 — поведение по умолчанию не меняется), проброшен в compose и `.env.example` (стюард R274) |
| балансер | одна точка правды `predictedCriticalR318` вместо четырёх размазанных условий — иначе «выключить целиком» было невозможно |
| API | `GET` отдаёт ДЕЙСТВУЮЩЕЕ значение (`balancer.PredictionFilterEnabled`), `PUT` пишет override в реестр; второй копии состояния нет |
| валидация | реестром (0/1); ошибка возвращается как 400 |

**Проверка живьём** (балансер `007d0b30`):

| шаг | результат |
| --- | --- |
| `GET /api/v1/cluster/config` | `predictionFiltering: true` |
| `PUT {"predictionFiltering":false}` | `200`, `updatedFields` содержит поле |
| `GET` после записи | `predictionFiltering: false` |
| `GET /api/v1/settings` | `effective=0 source=override default=1` |
| `POST /api/v1/settings/reset` | `effective=1 source=default`, `GET` снова `true` |
| обычный чат | `200` — фильтр в дефолтном состоянии ничего не сломал |

**По второй находке этапа 5 (секция `agent`):** проверил по `webui` — панель эту
секцию больше не отправляет, а сервер её игнорирует **намеренно** (R65d: тайминги
задаются в окружении agent-контейнера). То есть это не мёртвый контрол, а
задокументированное решение — полей в интерфейсе нет.
## R319: «чем ограничено окно» — причина, которую некому было показать

**Что нашли (этап 6 аудита мёртвых контролов).** Скрипт «объявленное-но-не-использованное
поле» по `internal/api` дал 9 попаданий; все оказались полями ОТВЕТА (DTO) или
намеренно принимаемой совместимостью — мёртвых контролов там нет. Зато рядом
обнаружилось другое: `GET /api/v1/cppworker/model-profiles` с R267 отдаёт per-model

## R320: «завершение посреди рассуждений» — done_reason на tools-пути

**ЖИВАЯ ЖАЛОБА (Cline через балансер, Ollama API).** Потоковый ответ обрывается
прямо внутри рассуждений модели, всё, что модель собиралась сказать, теряется; а
на следующий запрос «продолжи» клиент показывает рассуждение как готовый ответ.

**ЧТО ПОКАЗАЛ РАЗБОР.**

1. Воспроизведено: при исчерпании бюджета внутри размышлений воркер отдаёт
   `done:true`, `message.content:""` и размышления в `thinking`. Клиент
   видит ЗАКОНЧЕННЫЙ ход без ответа.
2. Воспроизведено: `/api/chat` без tools в этом случае честно ставит
   `done_reason:"length"` (R231), и там же с R314 есть пояснение вместо пустого
   content — но только на НЕпотоковом пути.
3. Найдено в коде: tools-путь (`writeChatStreamResponseWithTools` — им ходит
   Cline, он всегда прикладывает `tools[]`) прошивал `done_reason` ЖЁСТКО в
   `"stop"` в трёх местах. По контракту Ollama `stop` = «модель закончила»;
   для усечения по бюджету существует `length`. То есть обрезанный по бюджету
   ход уезжал клиенту как полноценно завершённый — клиент закрывал ход, остаток
   терялся, а следующий запрос начинал НОВЫЙ ход (отсюда «рассуждение как ответ»).
4. Дополнительно: на tools-пути размышления удерживаются и уходят одним финальным
   чанком, поэтому до конца стрима клиент не видит вообще ничего, а пустой
   `content` в финале читается как «модель ответила пустотой».

**ЧТО СДЕЛАНО (воркер).**

| место | изменение |
| --- | --- |
| `toolsStopReasonR320` | одна формула причины на tools-путь: `tool_calls` при вызове, `length` если вывод кончился ВНУТРИ незакрытого блока размышлений (маркер в выводе ИЛИ канал, открытый шаблоном в промпте), иначе `stop` |
| три места с прошитым `"stop"` | заменены на вызов этой формулы |
| финальный чанк tools-пути | пустой видимый ответ при непустых размышлениях получает то же пояснение, что R314 на не-потоковом пути (одна функция, один текст) |
| потоковый не-tools путь | то же пояснение в done-чанк, когда content-дельт не было (балансер его не срежет: `stripNativeDoneContent` чистит done только при уже отданных дельтах) |

**Тесты.** `cmd/cppworker/tools_done_reason_r320_test.go`: таблица причин
(tool_calls / stop / length по обоим признакам незакрытого reasoning / пустой
вывод), разбор «незакрытый reasoning», пояснение вместо пустоты и AST-стюард,
запрещающий вернуть прошитый `done_reason="stop"` внутрь
`writeChatStreamResponseWithTools`.
## R321: контрактное завершение стрима — слой совместимости в балансере

**Зачем ещё один слой, если воркер уже исправлен (R320).** Воркер — отдельный
образ. На стенде может стоять образ СТАРШЕ правки, и тогда все клиенты снова
видят `done:true` + `done_reason:"stop"` + пустой `content` после
размышлений. Правило клиентского контракта не должно зависеть от того, какой
билд воркера сейчас в кластере.

**Что делает балансер** (`native_done_hygiene_r321.go`) — только при
наблюдаемом нарушении контракта:

| условие | действие |
| --- | --- |
| `done:true` + `done_reason:"stop"` + пустой `content`/`response` | `done_reason` → `length` (контракт Ollama: остановка по бюджету) |
| в этом стриме уже уехали размышления (`message.thinking`/`reasoning`) | в `content` кладётся пояснение с числом символов размышлений (клиент до этого не видел ничего) |
| непустой ответ, `length`/`tool_calls`/`error`/`cancelled`, стрим без размышлений, не-done кадры, не-JSON | не трогаем (идемпотентно: исправленный воркер ничего не требует) |

**Тесты.** `internal/balancer/native_done_hygiene_r321_test.go`: главный случай,
идемпотентность на исправленном воркере, непустой ответ, стрим без размышлений,
`/api/generate` (поле `response`), сохранение `tool_calls`/`error`/`cancelled`,
не-done и битые строки.
