# R299 (2026-10-29): три живых дефекта прогона `793db393`

Основание: живой прогон на `793db393` (R298). Оператор назвал три дефекта; ниже —
что именно изменено, чем это доказано СЕЙЧАС и что нужно увидеть на стенде, чтобы
считать пункт закрытым. Ни один пункт не объявлен исправленным «по коду».

## 1. Guard «окно мало» срабатывал ПОСЛЕ admission: 503 за 88.2 с

**Живой факт.** Запрос с `num_ctx` больше загруженного окна при чужом стриме
висел 88.2 с и получал 503 телом старого формата
`{"error":"…","decision":"async_reload","retry_after_seconds":30}`, а в тексте
стояло `active streams=0`.

**Причина — две, и обе про порядок.**

- Проверка R288 стояла в роутере ПОСЛЕ `runInferencePreflight`, а тот ходит в
  сеть (`RunPreflight`) и способен потратить всё это время, пытаясь вырастить
  окно, которое вырасти не может, пока идёт стрим (guard R271 всё равно отложит
  перезагрузку). Решение было известно ДО первого сетевого вызова.
- Отказ формировался двумя самописными телами в транспорте, а не общим
  писателем R291. Отсюда `decision:"async_reload"` в snake_case, которого нет
  больше ни у одного отказа балансера.

**Что сделано.**

- `internal/balancer/growth_guard_r299.go` — `growthDeferR299`: одно правило на
  оба входа в preflight (роутер и транспорт). Отказ только при ДВУХ условиях:
  окно мало (`needed > loaded`, числа по контракту
  `needed = max(оценка промпта + бюджет, явно запрошенное окно)`) И росту
  что-то мешает (стримы на бэкенде/модели или идущая перезагрузка). Если не
  мешает — preflight обязан попробовать вырасти, как раньше.
- `preflight_helper.go` — проверка стоит перед `RunPreflight`.
- `nctx_reload_handlers.go` — та же проверка на транспортном входе
  (`preflightNCtxReloadIfNeeded`), потому что это ВТОРОЙ вход в preflight; если
  бы правило жило только в роутере, транспортный путь остался бы прежним (в этой
  серии так уже случалось).
- `writePreflightDeferredR299` заменил оба самописных тела: теперь один формат
  (`status:deferred`, `deferredReason:context_growth_pending`) и числа
  `requiredTokens` / `loadedWindowTokens` / `activeStreams` / `reloadPending`.
  Заголовок `X-NCtx-Reload-Decision` оставлен для совместимости.
- `growthBlockersR288` — `activeStreams` берётся как максимум из учёта по
  бэкенду и по модели, а `reloadPending` идёт отдельным полем. Ноль стримов при
  `reloadPending:true` — честная картина, а не «никто не мешает»: запрос, ждущий
  в preflight, стримом ещё не учтён (`beginClientStreamR271` — после admission).

**Тесты.** `TestR299_GrowthDeferVerdict` (4 подслучая: не мешает / стрим /
перезагрузка / окно покрывает запрос), `TestR299_PreflightGuardAnswersBeforeWorkerCall`
— поведенческий: фейковый воркер считает запросы, их ДОЛЖНО БЫТЬ НОЛЬ, ответ
за < 3 с, 503 с числами и `activeStreams=1`, `TestR299_PreflightGuardKeepsNormalPath`
— обычный путь не перекрыт, `TestR299_TransportDefersUseUnifiedBody` — стюард:
самописное тело не вернётся в транспорт (комментарии не считаются).

## 2. «Модель ещё загружается» отдавалось как ошибка 500

**Живой факт.** На 148 с клиент получал HTTP 500 с текстом «модель ещё
загружается» — то есть собственный текст балансера противоречил коду ответа.
5xx для клиента значит «сломалось, повтори»; оператор жал «загрузить» повторно
поверх живой загрузки.

**Причина.** Последняя попытка цикла загрузки (`executeLlamaCppLoad`) возвращала
`ModelOpResult{Success:false, Error:"cppworker still loading model …"}`, хотя
формат «ещё грузится» (R262, `StillLoading` → 202 Accepted) уже существовал.

**Что сделано.** `model_load_wait_r262.go` — `stillLoadingAfterLoadRetriesR299`:
тот же результат R262 (202, `stillLoading:true`, `pollAfterSec`, текст «это не
ошибка»), а не 500. Настоящие ошибки (`cppworker error (HTTP 5xx)`, «модель не
появилась») по-прежнему ошибки.

**Тест.** `TestR299_StillLoadingAfterRetriesIs202`: `Error` пуст,
`StillLoading=true`, `PollAfterSec>0`, текст есть; маппинг в 202 закреплён
отдельно (`internal/api/model_op_status_r185_test.go`).

## 3. Спам одинаковыми предупреждениями

**Живой факт.** `EnsureRPCLayout: не удалось применить раскладку` — каждые 20 с
(тик гарда); `no available backends with exclusions` — 299 строк за один прогон.

**Причина.** Оба сообщения писались на каждой попытке: тик гарда и retry-цикл
запроса. Полезные сообщения в таком количестве делают лог нечитаемым.

**Что сделано.** `internal/balancer/log_rate_r299.go` — ограничитель частоты по
ключу: первое сообщение проходит ВСЕГДА, подавленные считаются и показываются в
следующем (`suppressed_since_last`), успешное применение раскладки снимает
отметку (`reset`), чтобы повторный сбой был виден сразу. Окна: 5 мин для
раскладки (тик 20 с), 1 мин для селектора.

**Тест.** `TestR299_LogRateLimiter`: 299 подавленных считаются, ключи не глушат
друг друга, после окна сообщение проходит с числом подавленных, `reset`
возвращает немедленный показ.

## Что проверено и что ещё нужно

Зелёное локально: `go build -tags llama_stub ./...`, `go vet` (balancer, api),
`go test -tags llama_stub ./internal/balancer ./internal/api ./pkg/types
./internal/settings` — все пакеты ok.

На стенде (после выката) смотреть именно это:

1. Запрос с `num_ctx` больше окна при живом стриме: ответ 503 БЫСТРО (не 88 с),
   тело `deferredReason:"context_growth_pending"`, `requiredTokens` больше
   `loadedWindowTokens`, `activeStreams` — живое число, `reloadPending` отдельным
   полем. Строки `decision:"async_reload"` в теле быть не должно.
2. Загрузка модели, которая ещё идёт дольше 30 с: HTTP 202 с `stillLoading:true`
   и `pollAfterSec`, а не 500.
3. Лог: одна строка `apply failed` на эпизод недоступного донора (не каждые
   20 с), одна строка `no available backends` на модель в минуту.
