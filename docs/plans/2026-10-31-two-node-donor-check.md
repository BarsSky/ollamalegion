# Два узла: донор стал доступен — что проверено и что нашлось

Дата: 2026-10-31. Стенд: этот Windows-хост (`ol-stack-*`, balancer `r346` = f0440d4d,
cppworker `gpu-584ba305`) + донор на соседней машине. Донор
`cppworker-cyborg-bundled-agent` до этого был недоступен, поэтому пункты плана,
завязанные на второй узел, стояли в «не проверено» (см.
`2026-10-30-r304-donor-only-memory.md`, раздел «Проверка живьём», и
`2026-10-30-r303-d3-d4.md`).

## 1. Причина недоступности — СТАРЫЙ АДРЕС (D1), а не выключенный узел

Факты (проверено `Test-NetConnection` с хоста и `curl`/`wget` из ОБОИХ контейнеров):

| адрес | :18034 (agent) | :18092 (cppworker) | :11434 (ollama) | :50052 (rpc-server) |
| --- | --- | --- | --- | --- |
| `192.168.13.34` (был в конфиге балансера) | ✗ | ✗ | ✗ | ✗ |
| `100.64.0.7` (реальный) | ✓ | ✓ | ✗ | ✓ |

То есть узел жил всё это время: агент слал heartbeat (поэтому `hasAgent:true` и
свежий `lastAgentContact`), но балансер звал его по мёртвому адресу — отсюда
`status: ollama_unavailable` и «донор недоступен» в отчётах. Классический случай
«heartbeat есть, инференса нет»: направление «узел → балансер» работало,
«балансер → узел» — нет.

Исправлено на стенде (обратимо, одна строка конфига):

```
PUT /api/v1/backends/cppworker-cyborg-bundled-agent {"host":"100.64.0.7"}
→ host=100.64.0.7, status: ollama_unavailable → healthy, /api/v1/health: 3/3
```

Причина, почему адрес не исправляется сам: у записи донора **нет метки
`auto-registered`** (`labels: [linux, amd64, gpu]`), а `refreshRegisteredBackend`
(handlers_backends.go:1109) обновляет `host` только для повторной саморегистрации
авто-бэкенда (`isSameBackendRegistration` / `isReRegistrationOfAutoBackend`).
Без метки запись считается операторской, и её адрес меняет только оператор. Это не
баг кода, но объясняет, почему «узел переехал» не лечится перезапуском.

Версия llama.cpp у обоих узлов одна (`buildInfo=0eadefebd`), поэтому проверка
совместимости сторон RPC проходит. Донорский `rpc-server` уже был поднят
(`enabled:true, running:true, listening:true, addr:0.0.0.0:50052`, аптайм 57 448 с).

## 2. Раскладка на два узла применилась

`PUT /api/v1/backends/<donor>/role {"role":"donor"}`:

```json
{"applied":["cppworker-gpu-bundled-agent"],"donors":["100.64.0.7:50052"],
 "role":"donor","rpcNode":{"reachable":true,"listening":true,"addr":"100.64.0.7:50052"}}
```

Мастер (`/api/models` на :18092) подтвердил: `rpc_enabled:true`,
`rpc_servers_active:["100.64.0.7:50052"]`.

Загрузка gemma-4-E4B-it-Q4_K_M с раскладкой (58.7 с) дала реальный сплит —
`device_layers_exact`: `CPU 0-0`, `CUDA0 1-23`, `RPC0 24-42`; все 42 слоя на GPU
(23 локально + 19 на доноре), 0 на CPU (кроме выходного слоя, как всегда), ctx 32768.

## 3. Пропускная способность: два узла ХУЖЕ одного (замер)

Промпт и параметры одинаковые (`num_predict: 64`, `temperature: 0`), замер по
`tokensPerSec` воркера + сквозное время запроса:

| конфигурация | «по горячему» | второй запрос подряд | сквозное время |
| --- | --- | --- | --- |
| один узел, 42/42 слоёв на CUDA0 | 2.7 с, **27.6 tok/s** | 3.2 tok/s | 2.7 с |
| два узла, 23 CUDA0 + 19 RPC0 | — | **3.9 tok/s** (через балансер 3.2-4.0) | **~100 с** |

Внутри этих чисел смешаны два эффекта, и их важно разделить:

1. **RPC через сеть дорогой по задержке**: 19 слоёв из 42 считаются на удалённой
   машине, каждый токен идёт через сеть → 3.9 tok/s против 27.6 tok/s на одном
   узле. Для этой модели и этой карты раскладка на два узла **не даёт ускорения**:
   она даёт только «влезает больше», но не «быстрее». Ожидаемый вывод для парка из
   слабых карт: раскладка — способ ПОДНЯТЬ модель, которая не влезает в одну карту,
   а не способ ускорить ту, которая влезает.
2. **Выгрузка модели после каждого ответа** (см. пункт 4): сквозное время 100 с
   почти целиком — повторная загрузка (58.7 с), а не генерация.

## 4. Найденный живой дефект (R347): keep_alive терялся, модель выгружалась после КАЖДОГО ответа

Логи воркера (сопоставлены по времени с запросами балансера):

```
handlers_generate.go:441  generate returned empty output (R334 ...)
handlers_generate.go:299  model unload requested via keep_alive=0   ← клиент НЕ просил
backend.go:2458           model unloaded
utils.go:167              POST /api/generate 200 (934 ms)  remote 172.18.0.2 (балансер)
```

Причина: `runGenerateCore(w, r, req generateRequest)` принимает запрос **по
значению** и нормализует свою копию (`normalizeGenerateRequest(&req)`); обработчик
же регистрировал `defer applyKeepAlive(modelName, req._keepAliveDuration)` со своим
`req`, где поле оставалось нулевым. А ноль для `applyKeepAlive` — это «клиент
попросил выгрузить». То есть модель выгружало незаполненное служебное поле, а не
клиент; `keep_alive:"30m"` игнорировался.

Замер цены (тот же стенд): «по горячему» 2.7 с / 27.6 tok/s, следующий запрос
78-80 с / 3.2 tok/s из-за загрузки 58.7 с; в RPC-раскладке ~100 с на запрос.

Исправлено: `cmd/cppworker/handlers_generate.go` — `keepAliveOfRequest(req)`
считается в обоих обработчиках (`/api/generate`, `/api/ollama/generate`) сразу
после декодирования тела, до `runGenerateCore`; семантика та же (`""`/`-1` — дефолт
30 минут, `0` — единственный случай выгрузки). Тесты:
`cmd/cppworker/keepalive_after_answer_r347_test.go` (семантика + сторож по AST на
порядок «посчитать до runGenerateCore»). Коммит `61dcd693`, образ
`cppworker:gpu-61dcd693` развёрнут.

**Проверка после развёртывания (тот же стенд, RPC-раскладка 23/19):**

| прогон | tokens | tok/s воркера | сквозное время |
| --- | --- | --- | --- |
| запрос 1 | 63 | 3.32 | 19.0 с |
| запрос 2 (сразу после) | 65 | 3.34 | 19.5 с |

До правки второй запрос занимал 78-100 с (перезагрузка 58.7 с), после — те же ~19 с,
и модель остаётся загруженной (`models=1`). То есть 19 с здесь — это честная
стоимость генерации через RPC, а не перезагрузка.

## 5. Найдено попутно (не исправлено, зафиксировано)

1. **Бюджет раскладки считает только ЛОКАЛЬНУЮ VRAM.** При активной RPC-раскладке
   мастер отдаёт `vram_layout_total_mb=8191, vram_layout_free_mb=7067` (только своя
   карта), а балансер — `vramRemoteFreeMb:0, vramRemoteNodes:0, vramRemoteSource:"none"`
   при `rpcEnabled:true` и живом доноре с 7033 МБ свободной VRAM. Раскладка при этом
   работает (слои реально уехали на RPC0), но memfit/предпросмотр «сколько влезет»
   удалённую память не учитывает — то есть панель не отвечает на вопрос «влезет ли
   модель в два узла». Это следующий кандидат в план (R348), с проверкой на
   `vram_remote_*` в `/api/models` и в отчёте размещения.
2. **Дублирующаяся строка при загрузке.** В `/api/v1/cluster` во время загрузки одна
   и та же модель присутствовала и в `loadingModels` (`state=loading`,
   `contextLength=0`), и в `loadedModels` (`state=loading`, `gpuLayers=42`). В UI это
   два бейджа «загружается» на одну модель.
3. **`/api/models` перечисляет только ЗАГРУЖЕННЫЕ модели** (`backend.ListModels()`),
   а не инвентарь диска: `count:0` при лежащих в `/app/models` GGUF — штатное
   состояние, не дефект сканирования. Инвентарь — `/api/models/files` +
   `POST /api/models/refresh` (которым и наполнил: `added:[Qwen3.8-27B, gemma-4-E4B]`).

## Не проверено

- Повторный прогон R304-строк J/K/L на доноре: на нём образ без R304. Нужен
  пересбор/обновление образа на донорской машине.
- Стабильность RPC через `100.64.0.7` под нагрузкой (один запрос за раз, без
  параллельных стримов и без длинных генераций >64 токенов).
- Влияние Tailscale-адреса на латентность RPC: не отделял «сеть» от «RPC-протокола».

## 7. Найдено при втором проходе: раскладка нестабильна, а вклад узлов не виден

После того как раскладка применилась, повторная загрузка сообщила в лог:

```
backend.go:1545  раскладка НЕ применилась: узлы переданы, а RPC-устройств в загрузке нет
                 servers=["100.64.0.7:50052"]
```

и модель поднялась ЛОКАЛЬНО (42/42 на CUDA0) при `rpc_enabled:true`. То есть «два
узла» живут в двух состояниях: сплит 23/19 (первая загрузка) и «узлы есть,
RPC-устройств нет» (следующие). Причина пока не установлена — в план отдельным
пунктом (R349).

Что измерено точно:

1. **`vram_remote_*` в справочном пути всегда 0.** Снимок узлов живёт
   `rpcDeviceTTL` = 30 с, после чего `LayoutBreakdownCached` обнуляет вклад узлов —
   это осознанное решение R132 (протухшее нельзя выдавать за текущую ёмкость,
   закреплено тестом `TestR132_StaleSnapshotIsNotPresentedAsCurrent`). Но тогда
   «узлов в раскладке нет» и «7 ГБ донора, измеренные 10 минут назад» неотличимы,
   и вопрос «влезет ли модель в две карты» остаётся без ответа. **Закрыто в R348**
   (см. §8).
2. **`GET /api/models` в логе воркера не виден на уровне Info** — и это НЕ отсутствие
   логирования: middleware общий, просто путь входит в `pollingPaths`
   (`cmd/cppworker/utils.go:137`), поэтому пишется в Debug («Suppress frequent poll
   requests to Debug level»). Первая редакция этого отчёта утверждала «не логируется
   как HTTP-запрос» — неверно; проверил по коду после того, как логи Info показали
   только `/api/models/files`. Практический вывод тот же: при разборе нагрузки на
   воркер нужно поднимать уровень логов, иначе опрос не виден.
3. **На rpc-server донора идут периодические TCP-подключения** (пары
   «Accepted client connection / Client connection closed», каденция нерегулярная —
   от секунды до десятков секунд; во время загрузки — чаще). Источник в этой сессии
   НЕ атрибутирован: кандидаты — проверка живости узла перед генерацией
   (`checkRPCNodesForInference`), watchdog (15 с), проверка узла при применении
   роли (`rpcNodeCheck`) и `rpc-peers`. Утверждать «это /api/models» оснований нет:
   интервал поллера — 30 с, а не 2 с.
## 8. R348: последний замер VRAM узлов — отдельно от текущей ёмкости

Реализовано (коммит `361cd855`). Идея: не менять контракт R132, а добавить
ОТДЕЛЬНУЮ историю, которая не участвует ни в одном решении о загрузке.

| слой | что добавлено |
| --- | --- |
| `internal/cppbackend/rpc_mode_r115.go` | `LayoutBreakdown.RemoteLastKnown{Free,Total,Nodes,Age}`; ёмкость (`RemoteFree/Nodes/RemoteSource`) не тронута |
| `internal/cppbackend/memfit_adapter.go` | `lastKnownRemoteVRAM()` — берёт снимок текущей раскладки, а если в нём нет удалённых устройств (типичный результат busy-пути) — последний УСПЕШНЫЙ замер для ТОГО ЖЕ списка узлов (R174). Ничего не опрашивает: справочный путь не имеет права дозваниваться (R131/R132) |
| `cmd/cppworker/handlers_model.go` | `/api/models`: `vram_remote_last_known_{free,total}_mb`, `vram_remote_last_known_nodes`, `vram_remote_last_known_age_sec` |
| `pkg/types`, поллер балансера | те же четыре поля в `LlamaCppMetrics` (класс дефектов R45/F-15: snake_case на проводе) |
| WebUI | строка «Свободно VRAM (RPC-узлы, последний замер)» с обязательным возрастом («назад 12 мин»); не показывается, если есть текущий замер, если `rpcEnabled=false`, и если история нулевая |

Критерий приёмки, который это закрывает: «оператор видит, сколько памяти было у
донора и когда это измерено, вместо нуля». На стенде после развёртывания ожидаем
`vramRemoteLastKnownFreeMb≈7019`, `vramRemoteLastKnownNodes=1`,
`vramRemoteLastKnownAgeSec` = возраст последнего замера, при `vramRemoteFreeMb=0`
(контракт R132 цел).

Что этим НЕ закрыто и остаётся в плане:

- **R349:** почему повторная загрузка с раскладкой иногда идёт «узлы переданы, а
  RPC-устройств в загрузке нет» (сплит 23/19 воспроизводится не каждый раз).
- **R349-б:** атрибутировать и ограничить периодические TCP-подключения к
  `rpc-server` донора; попутно — залогировать `GET /api/models` на воркере.
- Обновление узла: снимок обновляется только путём загрузки/раскладки. Кнопки
  «обновить замер» нет; если оператор хочет свежие данные без загрузки модели,
  сейчас это возможно только через применение роли/раскладки.
## 9. Что дали R350 и R351 (и чем это подтвердилось живьём)

Пока проверялся R348, выяснилось, что «нестабильность раскладки» из §7 — не гонка
протокола, а два независимых дефекта вокруг СТАРОГО адреса донора.

### R351: адрес, порты и имя бэкенда не переживали рестарт

`PUT /api/v1/backends/{id}` обновлял запись в памяти и через 5 с autosave попадал в
`state.json`, но `LoadState` переносил поля **по списку** (status, runtime-лимиты,
nodeAddr, disabled), а `host`/портов/имени в этом списке не было. `config.json` в
bundled-развёртывании read-only и содержит прежний адрес, поэтому после
пересоздания контейнера балансер поднимал `192.168.13.34`: health давал провал,
раскладка уходила в пустоту («узлы раскладки недоступны 192.168.13.34:50052»),
загрузка молча шла локально. Правка адреса жила до первого рестарта.

Исправлено (`c1ad20b9`): `LoadState` переносит `name`, `host`, `ollamaPort`,
`cppWorkerPort`, `agentPort`, `imagePort`; пустые/нулевые значения в `state.json`
не затирают конфиг (тот же принцип, что у `NodeAddr` в R-MultiHost).

Живая проверка: `host` исправлен на `100.64.0.7` → `state.json` обновился →
`--force-recreate` балансера → `GET /api/v1/backends` показывает `host=100.64.0.7`,
`status=healthy`, `role=donor`. До правки после рестарта был `192.168.13.34` и
`ollama_unavailable`.

### R350: мёртвый «сообщённый» адрес узла побеждал живой host

Сам воркер донора продолжал сообщать `rpc_server.addr=192.168.13.34:50052` (внешний
адрес задан `CPPWORKER_RPC_EXTERNAL_ADDR` и не обновлялся). По R171 отчёт воркера
главнее догадки балансера, поэтому даже с исправленным host мастер получал мёртвый
адрес, guard писал «раскладка работает не в полном составе», и модель грузилась
локально (42/42 на CUDA0) при `rpc_enabled=true`.

Исправлено (`6ab9aa56`): `rpcNodeAddrResolved()` — сообщённый адрес по-прежнему
приоритетен, но проверяется пробой; если он мёртв, а `host:port` записи бэкенда
отвечает, берётся `host:port` **с предупреждением в лог**. Одно правило используют и
guard, и `layoutDonorServers` (список для мастера не может разойтись с тем, что
проверяет балансер).

Живая проверка после развёртывания:

```json
cppworker-gpu-bundled-agent: rpcLayout {"enabled":true,"servers":["100.64.0.7:50052"],"degraded":false}
cppworker-cyborg-bundled-agent: rpcNode {"addr":"100.64.0.7:50052","reachable":true,"running":true,"listening":true}
```

Загрузка с раскладкой воспроизвелась сразу и штатно: `CPU 0-0, CUDA0 1-23, RPC0 24-42`,
ctx 32768 (то есть пункт §7 «сплит 23/19 воспроизводится не каждый раз» закрыт: он не
воспроизводился, пока адрес был мёртв).

### R348 живьём (после загрузки, RPC включён)

```
vram_remote_free_mb=0   vram_remote_nodes=0   vram_remote_source=none        ← R132: текущее только свежее
vram_remote_last_known_free_mb=7019  nodes=1  age=157s                       ← R348: история с возрастом
```

В `/api/v1/cluster` те же числа доходят до панели
(`vramRemoteLastKnownFreeMb=7019`, `vramRemoteLastKnownNodes=1`,
`vramRemoteLastKnownAgeSec=162`), а отданный `webui:361cd855` содержит чтение
`vramRemoteLastKnownFreeMb`, функцию `formatAgeR348` и подпись «последний замер» —
то есть строка «Свободно VRAM (RPC-узлы, последний замер) 6.9 GB / 1 узлов назад
2 мин» действительно отрисуется.

### Стенд после проверки

`balancer:r351`, `cppworker:gpu-361cd855`, `webui:361cd855`; донор `role=donor`,
раскладка `enabled=true` и не деградирована, модели выгружены, `/api/v1/health` 3/3.

### 20.1. Stop на двух узлах с одноимёнными копиями — пройдено, но не с первого раза

Сценарий: клиент запускает стрим через балансер, пока мастер и донор оба
держат модель с одним и тем же именем; затем Stop.

**Случай 1, отмена по имени модели.** Мастер: `cancelled:1`. Донор:
`cancelled:0`, причина `no_active_generation` — у него не было своей
генерации, копия осталась `loaded`. Клиент получил финальный кадр с
`done_reason:"cancelled"`. Правильно: отмена не должна выгружать чужую
копию.

**Случай 2, отмена по `request_id`, выданному клиенту.** Первый прогон —
провал:

```
{"status":"unreachable","results":[{"error":"request_id not found: req8fab2156"}]}
```

Оба стрима дошли до конца, хотя клиент отменил. Причина: балансер
генерирует `request_id` (вид `req<hex>`) и отдаёт его клиенту, но в
апстрим-запрос его не клал — воркер искал отмену по идентификатору,
которого никогда не видел. Исправлено в R376 (d5b4e168):
`stampUpstreamRequestIDR376` ставит клиентский id в каждый исходящий
инференс-запрос (14 точек создания запроса, покрыто AST-стюардом).

Живой повтор после фикса: мастер `cancelled:1, by:"id"`; донор
`request_id not found` — это верный ответ (у донора этой генерации нет);
параллельный 600-токенный стрим на доноре при этом дошёл до
`done_reason:"stop"`, то есть отмена по id не задела чужой запрос.

### 20.2. Смоук `/v1` и эмбеддингов — пройдено

| запрос | результат |

| `POST /v1/chat/completions` (stream) | `Content-Type: text/event-stream`, `Cache-Control: no-cache`, 115 кадров `data:`, в последнем `delta`-кадре есть `finish_reason`, финал — ровно `data: [DONE]` |
| `POST /v1/chat/completions` (non-stream) | `choices[0].message.content='Готов'`, `finish_reason=stop`, `usage.total_tokens=25` |

ставит Go, то есть ровно разрешённый вариант. Первая редакция этого раздела
называла chunked расхождением: ошибка чтения контракта, исправлено.

### 21.3. Столкновение с SIGSEGV в llama.cpp (не наш код) — R382 containment

Сценарий: слот донорского `rpc-server` занят (узел обслуживает одно
соединение за раз; воспроизводится удержанием TCP-соединения к 50052).
Загрузка модели на мастере падает:

```
negotiate_hello: RPC server did not answer the hello handshake
get_dispatcher: RPC node unavailable, skipping: RPC handshake failed for 100.64.0.7:50052
SIGSEGV: segmentation violation
signal arrived during cgo execution
```

Стек (полный, из лога):

```
bridge._Cfunc_bridge_collect_devices
  c/bridge.CollectDevices
  cppbackend.(*Backend).rpcDeviceSnapshot     memfit_adapter.go:432
  cppbackend.memfitBudget → MemfitBudget
  main.checkNCtxBeforeLoad → main.handleLoadModel
```

То есть падает **перечисление устройств перед загрузкой**, а не инференс:
memfit просит свободную память узлов, мост зовёт
`ggml_backend_rpc_add_server`, тот делает hello-handshake, получает отказ —
и падает уже ПОСЛЕ своей строки «RPC node unavailable, skipping». Это код
vendored llama.cpp; из нашего слоя SIGSEGV не перехватить.

Повторные прогоны падали не всегда (гонка в инициализации RPC), но один
прогон из трёх — стабильно. Практическое следствие: «узел принял TCP» ≠
«узел готов к RPC», и старая проверка reachability этого не ловит.

Что сделано:
- **R380**: результат гейта R177 теперь влияет на список серверов — если узел
  не принял команду, адрес в мост не уходит (загрузка локальная, degraded
  честно выставляется). Раньше гейт был декоративным.
- **R381**: ключи раскладки в реестре известных (класс R374), стюард расширен
  на `get*`/`updates[...]`.
- **R382**: предохранитель против цикла падений: маркер ставится перед
  рискованным вызовом моста и снимается после; маркер на месте при старте =
  прошлая попытка не вернулась → RPC-перечисление пропускается 10 минут,
  планировщик считает только локальную карту, в лог уходит действие
  «перезапустить rpc-server узла». Одно падение вместо бесконечного.
