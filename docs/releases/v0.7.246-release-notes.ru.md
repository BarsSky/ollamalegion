# v0.7.246 — R486: идентичность сборки печётся в образ

**Дата:** 2026-11-10 · **Тип:** исходники + все четыре образа
**Образы:** balancer `r261110-1925` и cppworker `gpu-261110-1925` (собраны из
`24b3a151`), webui `r261110-2130` и imageworker `72ec210a` (пересобраны из
`ee901744`; их собственный код между этими коммитами не менялся). Все четыре
образа несут запечённую идентичность — см. §3a.

---

## 1. Зачем

Образы балансера и воркера были собраны и проштампованы ПРЕДЫДУЩИМ коммитом, и
никто этого не заметил:

| Что | Значение |
|---|---|
| HEAD репозитория на момент выпуска | `8b246ffe` |
| `deployments/.env` | `BALANCER_GIT_COMMIT=850923d7`, `CPPWORKER_GIT_COMMIT=361490ec` |
| что сообщал `/api/version` собранного образа | коммит `850923d7` |

Механизм: `scripts/release-all.ps1` не передавал build-аргументы идентичности
вообще, поэтому в Dockerfile срабатывал дефолт `ARG GIT_COMMIT=unknown`, а
`pkg/version` принимал `unknown` как значение. Образ с чужой/пустой печатью
выглядел как штатный.

Ни одна из проверок, которые должны были это поймать, не смотрела на факт
внутри образа:

| Проверка | Что видела | Почему пропустила |
|---|---|---|
| `scripts/check-image-tags.ps1` | только строки `image:` | тег образа не связан со штампом внутри |
| `deployments/release-manifest.json` | `gitCommit` из репозитория | а не из образа |
| `pkg/version` | принимал `unknown` как значение | «unknown» неотличим от факта |

Обнаружено случайно, по `/api/version` после выкатки, уже на стенде.

Корень дефекта в одной фразе: идентичность лежала в `deployments/.env`, то есть
была **намерением оператора**, а не свойством образа, и сверить намерение с
фактом было нечем.

## 2. Что сделано

Правило R486: **идентичность сборки запекается в образ на сборке и не может быть
перекрыта окружением на запуске.**

### 2.1. `pkg/version`: поля и порядок источников

Добавлены поля `Commit`, `CommitFull`, `CommitDate`, `BuildDate`, `Author`,
`Service`, `Version`, `ImageTag`, `LlamaCommit`, `LlamaDate`, `RPCProto`.

Порядок источников (`pkg/version/version.go`):

```
-ldflags -X  >  /app/identity.json  >  env (APP_VERSION/VERSION/GIT_COMMIT/BUILD_DATE)
```

Env оставлен только для локальной разработки (`go run ./cmd/balancer`), когда
образа нет вовсе. В образе env не перекрывает запечённые значения: иначе один и
тот же образ снова мог бы «честно сообщать» чужую версию — ровно так и выглядел
случай `850923d7`.

`unknown` больше не значение: `cleanStampR486` превращает `unknown`/пусто/пробелы
в отсутствие поля. Поле «unknown» хуже отсутствующего, потому что выглядит как
факт.

Где теперь живёт идентичность:

| Слой | Что несёт | Может ли быть перекрыт на запуске |
|---|---|---|
| `-ldflags -X pkg/version.*` | коммит, тег, дата коммита, дата сборки, сервис, версия, llama.cpp, `rpc_proto` | нет |
| `/app/identity.json` в образе | те же значения + автор, читается процессом | нет (менять только пересборкой) |
| OCI-метки образа (`docker image inspect`) | версия, ревизия, дата, исходник, автор, заголовок, `ru.ollamalegion.*` | нет (свойство образа) |
| env `APP_VERSION` / `VERSION` / `GIT_COMMIT` / `BUILD_DATE` | — | да, но только если запечённых значений нет (dev) |

### 2.2. Проверка на старте: `VerifyR486` / `MustVerifyR486`

`pkg/version/identity_r486.go` сверяет бинарник с запечённым `/app/identity.json`:

- файла нет → это локальная сборка (`go run`), не ошибка;
- файл есть, а бинарник собран без `-ldflags` → ошибка («собран без штампа»);
- `commit` бинарника и файла расходятся → ошибка (в образ положили чужой бинарь);
- `service` в файле и у процесса расходятся → ошибка (бинарь воркера в образе
  балансера);
- нет `BuildDate` у бинарника при наличии даты в файле → ошибка.

`MustVerifyR486(service)` вызывается первой строкой `main()` в балансере,
cppworker, агенте и sdworker и на ошибке печатает `FATAL: ...` в stderr и
завершает процесс. Это ровно та проверка, которая поймала бы `850923d7`:
контейнер, который не может доказать свою идентичность, не принимает запросы.

### 2.3. `scripts/build-identity.ps1` — единственный вычислитель

Считает из git и сабмодуля и БРОСАЕТ исключение, если значение вычислить нельзя
(«не угадываю»):

| Значение | Источник |
|---|---|
| короткий/полный SHA | `git rev-parse --short HEAD` / `rev-parse HEAD` |
| дата коммита | `git log -1 --format=%cI` |
| дата сборки | текущее время, RFC3339 UTC |
| автор | `git config user.name` + `user.email` или `BUILD_AUTHOR` |
| коммит llama.cpp + дата | `git -C c/llama.cpp rev-parse --short HEAD`, `log -1 --format=%cs` |
| версия протокола RPC | `c/llama.cpp/ggml/include/ggml-rpc.h`: `RPC_PROTO_MAJOR/MINOR/PATCH` → `6.0.0` |

Функции: `Get-BuildIdentity -Service <s> -Version <v> -ImageTag <t>`,
`Get-BuildArgLinesR486 -Identity $id`. Вызывается из
`scripts/build-containers.ps1` и `scripts/release-all.ps1`.

### 2.4. Dockerfiles: страж до сборки, `identity.json`, OCI-метки

10 файлов: balancer, cppworker (`gpu`, `cpu`, `gpu.86`, `r66`, `stub`), agent,
imageworker, webui, плюс `docker/webui/entrypoint.sh`.

- у всех Go-образов build-аргументы без дефолта `=unknown`;
- перед КАЖДЫМ `go build` — страж: пустое значение или `unknown` даёт
  `FATAL: GIT_COMMIT not supplied (build arg) — identity must be baked, see
  scripts/build-identity.ps1` и сборка падает;
- `/app/identity.json` пишется в КАЖДЫЙ образ, включая nginx-WebUI и
  imageworker, где Go-бинарника нет; WebUI получает побайтно тот же файл ещё и в
  корень статики, поэтому `curl /identity.json` показывает запечённое;
- OCI-метки: `org.opencontainers.image.version/.revision/.created/.source/.authors/.title`,
  `ru.ollamalegion.git.commit`, `ru.ollamalegion.image.tag`, а у cppworker ещё
  `ru.ollamalegion.llama.commit`, `.llama.date`, `.rpc.proto`;
- в cppworker настоящий коммит llama.cpp передаётся в cmake
  (`-DLLAMA_BUILD_COMMIT` / `-DLLAMA_BUILD_NUMBER`): до этого `git init && git
  commit` внутри образа заставлял `build-info.cpp` сообщать синтетический SHA.

### 2.5. WebUI — единственный образ без Go-бинарника

Стража «`-X pkg/version.Commit` не пуст» здесь быть не может, поэтому у него
свой страж — `RELEASE` (compose всегда передаёт `RELEASE=1`): при `RELEASE=1`
сборка требует непустые `GIT_COMMIT`, `GIT_COMMIT_FULL` и `BUILD_DATE`, при
`RELEASE=0` (dev) пропускает. Поэтому dev-сборка остаётся возможной, а релизная
не может запечь `dev`/`unknown`.

### 2.6. `-X ...Author=` убран из `-ldflags` (живое падение)

Строка автора из git содержит пробел (`Имя <mail>`), линкер разбирал её как
отдельный флаг и сборка падала. Автор едет в `/app/identity.json` и в
OCI-метке, а `pkg/version` читает его из файла. Это единственное поле
идентичности, которое сознательно НЕ передаётся через `-ldflags`.

### 2.7. Compose: аргументы из окружения процесса, лишние переменные удалены

`deployments/docker-compose.stack.yml` и три исторических варианта
(`bundled-full`, `cppworker-bundled`, `cppworker-bundled-with-agent`): аргументы
идентичности берутся из ОКРУЖЕНИЯ ПРОЦЕССА (`${GIT_COMMIT:-}` и т.д.), а не из
`.env` — `env_file` на build-аргументы не действует, а `.git` в контекст сборки
не попадает из-за `.dockerignore`, поэтому вычислить коммит внутри `RUN` нельзя.

Удалены из compose-файлов: `BALANCER_GIT_COMMIT`, `BALANCER_BUILD_DATE`,
`CPPWORKER_GIT_COMMIT`, `CPPWORKER_BUILD_DATE`, `WEBUI_GIT_COMMIT`,
`WEBUI_BUILD_DATE`, `AGENT_GIT_COMMIT`, `AGENT_BUILD_DATE`. Они больше ни на что
не влияют; если лежат в локальном `.env` — можно удалить.

`CPPWORKER_LLAMA_BUILD` и `CPPWORKER_LLAMA_BUILD_DATE` больше не приходят в
контейнер с дефолтом `unknown` и стали только переопределением оператора:
пусто = намерение не заявлено. Иначе каждый старт писал бы
`llama_build_mismatch` против запечённого факта.

### 2.8. Балансер видит, из какого РЕЛИЗА собран узел

Регистрация несёт `workerVersion` / `workerCommit` / `workerBuildDate` /
`workerRpcProto`; `GET /api/v1/backends` отдаёт их плюс
`workerReleaseMismatch`. Пустые значения никогда не затирают известные — старые
образы (до R486) остаются пригодными.

### 2.9. Гейт версии узла RPC: сравнение протокола

`internal/cppbackend/rpc_version_gate_r115.go` теперь сравнивает и версию
протокола RPC: причина `rpc_proto_mismatch:<node>!=<master>`. Если хотя бы одна
сторона версию не сообщает, узел всё равно допускается — урок R115: молча не
отнимать ёмкость. `cfg.LlamaBuild` и `buildInfo` регистрации берутся из
запечённого значения; env остаётся запасным путём для образов до R486.

### 2.10. `scripts/check-image-tags.ps1` (его запускает CI)

Падает на: оставшейся удалённой переменной; дефолте `unknown` в build-аргументе;
build-блоке без `GIT_COMMIT_FULL`; Dockerfile без `/app/identity.json`; без
стража `GIT_COMMIT not supplied`; без `-X pkg/version.Commit`.

### 2.11. Диагностика

Оба архива диагностики содержат `identity.json` отдельным файлом: `env.json`
показывает, что ПЕРЕДАЛИ в контейнер, `identity.json` — что ЗАПЕЧЕНО.
`/api/version` воркера теперь отдаёт те же поля сборки, что и балансер; новые
ключи добавлены, ни один не переименован.

Новые ключи `/api/version` (балансер и воркер; прежние `build`, `build_commit`,
`build_date`, `build_version` не менялись):

| Ключ | Смысл |
|---|---|
| `build_commit_full` | полный SHA сборки |
| `build_commit_date` | дата коммита (ISO 8601), не дата сборки |
| `build_author` | кто собрал (`git config` или `BUILD_AUTHOR`) |
| `build_image_tag` | фактический тег собранного образа |
| `build_service` | какому сервису принадлежит бинарник (`balancer`, `cppworker`, …) |
| `llama_commit` | коммит llama.cpp, слинкованного в образ |
| `llama_date` | дата того же коммита |
| `rpc_proto` | версия протокола RPC из `ggml-rpc.h` (`6.0.0`) |

### 2.12. Оператору: «какой образ реально запущен»

Четыре независимых ответа, от самого образа к самому процессу:

```bash
# 1. что запечено в образ (метки) — не требует запуска контейнера
docker image inspect ollama-legion/balancer:r261110-1925 \
  --format '{{json .Config.Labels}}'
#   → org.opencontainers.image.revision / ru.ollamalegion.git.commit / .image.tag

# 2. что запечено в файл идентичности
docker run --rm --entrypoint sh ollama-legion/balancer:r261110-1925 \
  -c 'cat /app/identity.json'
#   → {"service":"balancer","version":...,"commit":"9d42a329",...}

# 3. что говорит сам процесс
curl -s http://127.0.0.1:18080/api/version
#   → build, build_commit, build_commit_full, build_date, build_service, ...

# 4. из какого релиза узлы раскладки
curl -s http://127.0.0.1:18081/api/v1/backends
#   → workerCommit / workerVersion / workerBuildDate / workerRpcProto
#     и workerReleaseMismatch: true, если узел из другого релиза
```

Если контейнер не поднялся и в логе `FATAL: R486: идентичность образа не
совпадает с бинарём (...)` — образ и бинарь внутри него из разных сборок;
пересобрать, а не искать дефект в коде.

## 3a. Дополнение: идентичность у ВСЕХ четырёх образов, флейки, валидатор

Работа, не требующая второго стенда (R486.1/R486.2), доделана в том же выпуске.

**WebUI и imageworker тоже несут идентичность.** Раньше они оставались на образах,
собранных до R486: `/app/identity.json` в них не было, а WebUI-футер брал версию из
env. Пересобраны и выкачены:

| Образ | Тег | commit в образе | Проверено |
|---|---|---|---|
| webui | `r261110-2130` | `ee901744` | `/identity.json` отдаётся nginx-ом и совпадает с `/app/identity.json`; `config.js`: `VERSION=0.7.246`, `GIT_COMMIT=ee901744`, `BUILD_DATE` из файла |
| imageworker | `72ec210a` (пересобран) | `ee901744` | `service=sdworker`, стартовый лог `version=72ec210a (commit ee901744)`, контейнер healthy |

Балансер и воркер пересобраны из `24b3a151` (в балансер вошёл валидатор из R486.2).
Штампы образов разные — это честно: каждый образ собран из своего коммита, и код
webui/sdworker между `ee901744` и `24b3a151` не менялся.

**R486.1 — флейки убраны.** Оба теста падали не по вине кода, и оба дважды портили
зелёный прогон.

| Тест | Что было | Что стало |
|---|---|---|
| `TestCppWorker_LazyLoad_Async_Returns503WithRetryAfter` | `elapsed < 700 ms` при штатном окне `awaitModelMissing` ~500 ms; на загруженном CI под `-race` дал 7.57 s и красный прогон | загрузку завершает сам тест (`gateLoad`), контракт проверяется СОСТОЯНИЕМ: к моменту ответа модель не `loaded`; если код решит ждать загрузку — тест скажет это прямым текстом по таймауту |
| `TestVirtualRouter_HeavyModel_LeastLoaded_RespectsLoad` | корень: провайдер свободных слотов ключевался по `host:port`, а роутер спрашивает по ID бэкенда → ничья → round-robin → «w2 >= w1» держалось на удаче | провайдер принимает оба ключа; контракт проверяется на самом селекторе (10 вызовов `Select` обязаны дать узел с большим числом слотов) + живой запрос; ошибки транспорта проверяются |

**R486.2 — валидатор композиции видит релиз и протокол.** `checkVersions` сравнивал
только коммит llama.cpp, поэтому стенд из разных релизов при совпадающем llama.cpp
считался совместимым. Добавлено: `release_mismatch` (разные релизные коммиты узлов
группы) и `rpc_proto_mismatch` (разные версии протокола RPC) — уровень error;
«узел не сообщил» — hint, а не warning (образы до R486 обязаны работать, а
постоянное предупреждение приучало бы игнорировать список). Пять новых тестов.

**Манифест теперь фиксирует идентичность каждого образа.** Раньше
`deployments/release-manifest.json` знал только тег и `imageId`, поэтому на
вопрос «какой коммит внутри вон того образа» не отвечал — и разница между
балансером (`24b3a151`) и webui/imageworker (`ee901744`) была невидима, хотя она
законна (собраны позже, из другого коммита). Добавлено по каждому образу:
`commit`, `commitFull`, `commitDate`, `buildDate`, `author`; у cppworker ещё
`llamaCommit`, `llamaDate`, `rpcProto`. Значения взяты не «на память», а из
`/app/identity.json` самого образа:

```
docker run --rm --entrypoint sh ollama-legion/cppworker:gpu-261110-1925 -c 'cat /app/identity.json'
```

`scripts/check-image-tags.ps1` (то, что запускает CI) проверяет контракты C1–C4:
per-image `commit` (7–40 hex) у **каждого** образа, `buildDate` и `imageId`,
llama/rpc-поля у cppworker, и что верхнеуровневый `gitCommit` совпадает с
`commit` записи балансера. Негативные ноги проверены: подсаженный манифест без
`commit`/`llamaCommit` даёт `C1`/`C3` и exit 1; подсаженный `gitCommit=deadbeef`
даёт `C4b`; реальный манифест зелёный.
