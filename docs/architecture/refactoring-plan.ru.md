**Дата:** 2026-11-09. **Статус:** план, код не менялся.
**Повод:** живые жалобы после серии правок R459–R476 — «перестал работать
OpenWebUI», «потеряно распределение нагрузки», «потеряна работа с разными типами

## 2. Почему это не «переписать всё»

Формулы окна уже сведены в одну точку и покрыты тестами; парсеры tool-call'ов —
это РАЗНЫЕ форматы моделей, а не дублирование; `pkg/types`, `internal/settings`,
`pkg/logger`, i18n — стабильны. Проблема в **маршрутизации и дублировании пути
запроса**, а не в математике.

### Этап 3 сделан (R493-12n, 2026-11-13): что именно и чего в нём нет

Сделано (`internal/balancer/window_decision_r493.go`,
`window_decision_paths_r493.go`):

- `decideWindowR493` — чистая функция: на входе числа и факты, на выходе вид
  вердикта (`noop` / `serve` / `defer` / `grow` / `refuse`) с целью, сроком
  повтора и причиной. Внутри — R288, R447, R466, R385 и правило «окно никогда не
  опускается» (R493-12h). Кластер, метрики и HTTP ей не нужны.
- Вердикт стал ОДНИМ по виду на всех путях: отличие пути — это ВХОД
  (`GrowBlockedBy`: выключатель роста, роль донора), а не второй набор правил.
  «Кто нажимает кнопку перезагрузки» осталось за путём: не-стриминговый запрос
  отдаёт reload preflight-движку (он умеет выбрать свободный узел вместо
  перезагрузки), стриминговый перезагружает сам и отвечает 503+Retry-After.
- Все входные точки зовут её: guard до admission-очереди (`growthVerdictR301`),
  вход транспортного preflight (`growthDeferR299`), план роста R385
  (`streamGrowthPlanR385` — при едином решении цель приходит из вердикта, второй
  расчёт не запускается).
- Флаг `LB_WINDOW_UNIFIED` (горячая настройка, группа `nctx`): `0` —
  историческое поведение (по умолчанию), `1` — единое решение, `2` — «тень»:
  единое считается и расхождения с историческим пишутся WARN-строкой
  `R493-12n shadow divergence`, поведение остаётся историческим.
- T3 на всех путях: `window_decision_t3_r493_test.go` — таблица «вход →
  вердикт», паритет входов (разница только `GrowBlockedBy`), паритет вида на
  трёх путях, откат при `0` (вердикт равен историческому), «тень» при `2`.
  Мутации (снять R288 / R447 / R466 / способность пути / выравнивание цели /
  запрет «не-стриминговый путь предписывает 503») роняют тесты — проверено.

Чего в этапе НЕТ (это следующие этапы, а не «сделано»): общий `Admitter` (4),
общий `runInference` (5), общий стрим-пайплайн (6). Preflight-движок по-прежнему
сам считает конкретное окно загрузки (`DecidePreflight` → `reloadTargetForState`):
единое решение называет ВИД вердикта и цель для роста на стриме, а планирование
загрузки на узле осталось за движком. Это осознанная граница этапа: она позволяет
включить единое решение, не переписывая планировщик загрузки.

### Этап 4 сделан (R493-12p, 2026-11-13): один вход в очередь

Сделано (`internal/balancer/admission_admitter_r493.go`):

- Интерфейс `Admitter` — единственный вход «дай бэкенд или скажи, почему нет» — и
  ДВЕ реализации, которые уже существовали: `unified-admission` (единая
  admission-очередь, эталон generic-пути: сессии, backpressure, лизинг слота,
  бюджет max(`LB_ADMISSION_WAIT_SEC`, `LB_AUTO_LOAD_WAIT_SEC`)) и `probe-wait`
  (историческая очередь ожидания ПОЯВЛЕНИЯ бэкенда, R403: FIFO по модели, бюджет
  `LB_BACKEND_WAIT_SEC`). Исход ожидания — ОДИН набор полей
  (`BackendID`/`Lease`/`Waited`/`Position`/`Budget`/`Queued`/`Err`), поэтому
  транспорт (503, заголовки, лог) на обоих путях один.
- Путь обработчиков (`waitForLlamaCppBackendR403`) получает механизм из
  `admitterForR493`: при флаге 0 — исторический `probe-wait` (поведение не
  меняется), при 1 — входит в единую очередь (общий бюджет, справедливость по
  сессиям, одна видимость).
- T4 закрыт по телу: ожидающие на пути обработчиков ВИДНЫ в `/api/v1/queue/stats`
  блоком `backend_wait` (`waiting`, `by_model`, `wait_max_sec`, `unified`) —
  раньше они не были видны оператору нигде, кроме лога, и запрос, «висящий»
  120 c в ожидании бэкенда, выглядел как «очередь пуста, ничего не происходит».
- Тесты: `admission_admitter_t4_r493_test.go` — выбор механизма по флагу и по
  наличию probe, контракт обеих реализаций (мгновенный бэкенд, выключенное
  ожидание, отсутствующий probe), видимость в `/queue` (включая `unified=true`
  при флаге 1), различие бюджетов как ЕДИНСТВЕННОЕ различие путей. Мутации
  (проигнорировать флаг; убрать блок из `/queue`; считать выключенное ожидание
  успехом) роняют тесты — проверено.
- Полный `./internal/balancer` зелёный при `LB_UNIFIED_ADMISSION` = 0 и 1.

Чего в этапе НЕТ: режима «тень» (осознанно: ожидание занимает слот и меняет
состояние, «посчитать в тени» его нельзя — проверяется тестами и стендом); путь
обработчиков при флаге 1 входит в единую очередь БЕЗ окна запроса в кандидатах
(выбор копии под окно остаётся downstream: preflight/R459/R385), а бюджеты
путей по-прежнему читаются из разных переменных — их сведение к одной ручке это
отдельное решение оператора, а не код.

  меняет ни одного байта клиенту на всех шести комбинациях T2 (длительности
  нормализуются тем же помощником, что у golden). Мутации (забыть флаш; не
  добавлять перевод строки; не вести счётчик) роняют тесты. Полный
  `./internal/balancer` зелёный при `LB_STREAM_PIPE` = 0 и 1 (173 с каждый).

**Продолжение (2026-11-13, тот же этап): hijack-SSE-цикл на том же стоке.**
У стока появился `WriteFrame` — транспортное обрамление стало его делом: обычный
ResponseWriter пишет как есть, hijack-сток сам обрамляет chunked-фреймом (R32 #16)
и флашит. Шесть мест записи hijack-цикла (heartbeat, кадры, терминатор,
финализация) сведены в два хелпера `writeFrameR493`/`writeKeepaliveR493`; при флаге
0 они вызывают прежние `writeChunkedFrame/String`. Паритет проверен БАЙТ-В-БАЙТ:
`TestR493r_HijackFrameMatchesLegacyChunkWriter` сравнивает фреймы стока с
историческим писателем, `TestR493r_HijackSinkOwnsTransportFraming` — что счётчик
считает полезные байты без обрамления. Мутации (не писать завершающий CRLF; не
вести счётчик) роняют тесты.

**Третий цикл (SSE OpenAI без hijack) уже был «однострочным» — это закреплено
стражем.** Он пишет через `sseDoneTrackerR252` (`tw.Write`), который сам пишет,
считает и флашит; рядом с ним оставались ПЯТЬ повторных
`if canFlush { flusher.Flush() }` — второй набор правил флаша поверх того же
писателя. Они убраны (флаш живёт в трекере), а страж

(`w.Write`/`fmt.Fprintf(w,`/`flusher.Flush()`) в стриминговой части цикла — и то
же для hijack-цикла (только `writeFrameR493`). Первая версия стража ловила
подстроку `w.Write(` внутри `tw.Write(` — то есть саму разрешённую запись;
исправлено регуляркой, и это записано в самом тесте.
