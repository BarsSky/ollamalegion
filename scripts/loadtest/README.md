# Нагрузочный тест балансера

Проверяет балансер **реальными** запросами с нескольких клиентов одновременно:
текстовая генерация и генерация картинок. Появился по запросу «протестировать
балансер с нескольких клиентов на реальные запросы» (2026-10-08); этим прогоном
были найдены дедлок admin-плоскости, падение cppworker по SIGSEGV и пустые
ответы HTTP 200 — см. CHANGELOG 0.7.47.

## Запуск

```bash
# текст: 4 клиента, 45 секунд
node scripts/loadtest/loadtest.mjs --text-clients 4 --duration 45

# картинки: 4 клиента по 3 картинки
node scripts/loadtest/loadtest.mjs --image-clients 4 --image-requests 3

# смешанная нагрузка (текст и картинки на одной GPU)
node scripts/loadtest/loadtest.mjs --text-clients 4 --image-clients 2 --duration 60 \
  --out loadtest-reports/mixed.json
```

Зависимостей нет: нужен только Node 18+ (используется глобальный `fetch`).
Полный список аргументов — `--help` не реализован, смотрите `parseArgs` в начале
файла; основные: `--base` (OpenAI-поверхность балансера, по умолчанию
`http://127.0.0.1:18079`), `--admin` (admin-API, `http://127.0.0.1:18081`),
`--token`, `--model`, `--image-model`, `--max-tokens`, `--timeout-ms`,
`--error-backoff-ms`, `--no-warmup`.

## Что измеряется

| Метрика | Зачем именно так |
|---|---|
| TTFT (время до первого токена) | Клиент судит о работе по первому токену; равенство TTFT и полного времени означает, что ответ пришёл ОДНИМ куском (инкрементального вывода нет) |
| Полное время, p50/p90/p99 | Перцентили, а не среднее: при 8 клиентах разброс больше, чем сам ответ |
| Токены ответа | Пропускная способность инстанса (tok/s) |
| Картинка: байты, ширина×высота, сигнатура PNG | «200 OK» без картинки — не успех; проверяется, что вернулся настоящий PNG нужного размера |
| Раз в секунду: `/api/v1/metrics` + `/api/v1/queue/stats` | Отличает «балансер держит нагрузку» от «клиенты стоят в очереди»; заодно проверяет, что admin-плоскость жива под нагрузкой |

## Важные детали, без которых прогон врёт

- **Разные клиенты = разные сессии.** Каждый клиент шлёт `X-User-Id`/`X-Session-Id`
  (`RequestSessionKey` в `internal/balancer/autoload_wait.go`). Без этого это была
  бы одна сессия в N потоков, и балансер вёл бы себя иначе.
- **Потоковый режим обязателен.** С `stream:true` клиент видит каждый чанк; в
  не-потоковом режиме балансер сам включает внутренний стриминг
  (`LB_OPENAI_AUTO_STREAM=true`), и обрыв апстрима маскируется под успешный ответ
  HTTP 200 с пустым `content` (наблюдалось).
- **Прогрев.** Первый запрос после старта включает загрузку модели (десятки
  секунд) и испортил бы перцентили — харнесс делает отдельный прогревающий
  запрос, который в отчёт не попадает. Отключается `--no-warmup`.
- **Откат при ошибке.** Без него отклоняющий запросы балансер превращает клиента
  в генератор тысяч отказов в секунду: в прогоне 2026-10-08 image-гейт VRAM
  отдавал 503 за ~2 мс, и за минуту набралось 23 396 «запросов». Это не нагрузка,
  это забивание лога.
- **503 через 300 с — это admission-очередь, а не молчание.** Балансер ждёт слот
  до `wait_max_sec=300`, затем честно отдаёт 503
  (`admission: wait timeout, returning 503`). Ставьте `--timeout-ms` больше 300 с,
  иначе увидите «0 байт» вместо этой ошибки.

## Чего харнесс не делает

- Не проверяет качество ответов (только непустоту и валидность PNG).
- Не умеет отменять запросы на середине (проверка `Abort`/`cancel` — отдельная задача).
- Не работает через несколько машин-источников: все клиенты идут с одного хоста.
