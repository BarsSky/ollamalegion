# Окно: один вопрос «надо ли отказывать» для всех путей (R447, вторая половина)

Дата: 2026-11-17. Задача: «каждый путь, который отказывает или перезагружает
модель из-за нехватки окна, должен применять одно правило «нужен ли рост»
(R447), а не `needed > loaded`».

**Итог одной строкой.** Правило отказа вынесено в одну функцию
`windowServeAsIsR447` (`internal/balancer/window_serve_as_is_r447.go`) и
применено в четырёх местах, где до этого решали `needed > loaded` (или
отказывали всем, кому «нужен рост»). Живой 503 (окно 180224, оценка промпта
180200, `needed` 184296, чужой стрим) больше не воспроизводится: запрос
обслуживается загруженным окном. Правило РОСТА (`growthNeedR447`, включая запас
под ответ 256 токенов) не менялось — это отдельный вопрос, и он остался за
прежней функцией.

---

## 1. Живой дефект: что именно было не так

Из архива второго стенда (`2026-11-16T14:53:34Z`, разбор
`docs/architecture/context-numbers.ru.md` §5.5) и постановки задачи:

| величина | значение |
|---|---|
| загруженное окно на слот | **180224** |
| оценка промпта (эвристика `pkg/tokencount`) | **180200** (в §5.5 того же архива — 180004) |
| точный подсчёт токенизатором | **93962** (в §5.5 — 93891): завышение ×1.92 |
| `needed = оценка + бюджет вывода (4096)` | **184296** (в §5.5 — 184100) |
| активные стримы | 1 |
| явно запрошенное клиентом окно | нет (в §5.5 клиент присылал 131072 — меньше загруженного) |
| что получил клиент | 503 «needs 184296 tokens of context, the loaded window is 180224 and cannot grow right now (active streams=1, reload pending=false)» |

Промпт ВЛЕЗАЛ в загруженное окно (запас 24 токена по оценке, 86k по факту).
`needed` не влезал только потому, что в него входит бюджет вывода — верхняя
граница запроса, которую воркер урезает сам. Ровно об этом R447 (2026-11-06), и
ровно это сравнение продолжало жить в четырёх местах, куда R447 не доехал (четвёртое — не-стриминговая ветка вердикта R301, см. §2 и §3.5).

Две записи одного события в коде:

- **отказ** — `growthDeferR299` (текст выше дословно из
  `nctx_reload_handlers.go:923`; это постановка задачи);
- **рост** — `R385: стриминговый запрос требует большего окна … needed_tokens=184100
  … 503» (это запись архива §5.5).

Эта правка закрывает первую. Вторая остаётся осознанно (см. §7): там рост
происходит по `growthNeedR447` п.3 (запас под ответ < 256 токенов), и корень
проблемы — сама оценка, а не правило отказа.

## 3. Принятые правки

### 3.1 Новое правило: `windowServeAsIsR447` (`window_serve_as_is_r447.go`)

Вопрос: «обслужит ли загруженное окно этот запрос КАК ЕСТЬ».

```
loaded <= 0        → true  (окно неизвестно: по догадке не отказываем)
requested > loaded → false (воркер отвергнет чужой num_ctx — живой дефект R301)
estimated > loaded → false (промпт не влезает — воркер ответит кадром ошибки)
иначе              → true  (обслуживаем; бюджет ответа урежет воркер)
```

Почему отдельная функция, а не второй вызов `growthNeedR447`: это ДРУГОЙ вопрос.
`growthNeedR447` отвечает «нужен ли рост» и включает запас 256 токенов под ответ
(R447 п.3, R253) — причина пойти перезагрузить модель, когда это возможно. Отказ
же оправдан только там, где окно не обслуживает запрос вообще. Первые два
пункта у правил общие намеренно (промпт не влезает / клиент попросил больше) —
поэтому «расти» и «отказать» не могут разойтись на них.

### 3.2 `growth_guard_r299.go` — guard preflight-входа

Было: `if needed <= 0 || loaded <= 0 || needed <= loaded { … }` → отказ при
занятости. Стало: два условия разделены — «чисел нет» (`needed <= 0 ||
loaded <= 0`) и «окно обслуживает запрос» (`windowServeAsIsR447`). Комментарий в
коде: живой дефект → правило → следствие, с числами 180224/180200/184296.

### 3.3 `context_growth_r288.go` — blocker перед admission-очередью

То же правило; `needed` остаётся числом для тела отказа (оператор видит «сколько
нужно» рядом с «сколько есть»). `promptNeedsMoreContext` помечена как
историческое правило: продакшн её больше не вызывает, таблица теста R288
оставлена как эталон прежнего порядка проверок.

### 3.4 `window_decision_r493.go` — ветка занятости единого решения

Видов вердикта не добавлял: «окно обслуживает запрос» → `windowNoopR493` с
причиной; отказ (`windowDeferR493`) остаётся для «промпт не влезает / клиент
попросил больше». Это выравнивает единое решение с уже существующим поведением
стриминга (`serveOrDeferR493`) и с исправленным guard'ом.

### 3.5 `growth_stream_guard_r301.go` — не-стриминговая ветка вердикта

Нашлось при сверке ТЕКСТА отказа из задачи с кодом: `growthDeferMessageR301`
(«… cannot grow right now (active streams=%d, reload pending=%t), retry later»)
вызывается на не-стриминговых путях (`proxy.go:1577`,
`nctx_reload_handlers.go:798`), а решение об этом отказе принимала ветка
`if !streaming { if Active>0 || ReloadPending { v.Defer = true } }`. То есть
четвёртое место с той же ошибкой: отказ всем, кому «нужен рост», при чужом
стриме. Теперь и там сначала спрашивается `windowServeAsIsR447`; отказ остаётся,
когда промпт не влезает или клиент попросил окно больше загруженного.

**Паритет путей после правки** (проверен тестом `TestR447_UnifiedDecisionAgreesWithGuard`):
`growthDeferR299` (историческая ветка), `growthDeferR299` (единая ветка) и
`decideWindowR493` на одном входе дают один ответ; вердикт R301 на стриминге и
на не-стриминге — тот же.

## 7. Что осталось (осознанно)

1. **Перезагрузка ради запаса под ответ.** Если росту ничто не мешает, окно всё
   ещё растят, когда после промпта остаётся меньше 256 токенов
   (`growthNeedR447` п.3, R253). Именно так в архиве §5.5 появился
   `R385 … needed_tokens=184100 … 503`: оценка 180004 при окне 180224 дала запас
   220 < 256. Это решение о РОСТЕ, а не об отказе; чтобы убрать и его, нужен
   продукт-ответ «обслуживать укороченным ответом или ждать роста» (для агента
   укороченный ответ может выглядеть как пустой — живой дефект R301).
2. **Сам корень — оценка.** Пока токенизатор не успел (таймаут 1.5 с, R473/R493),
   решение опирается на эвристику, завышающую ×1.92–2.01. Это дефект 12c(4) и
   §7 п.3 `context-numbers.ru.md`; данная правка его не лечит и не маскирует.
3. **`DecidePreflight` (R451) в том же положении по росту:** запрос без явного
   окна с запасом < 256 токенов может уехать в перезагрузку, а при занятости
   guard R271 её отложит — тогда клиент получит 503 «reload pending» уже от
   preflight-движка, а не от guard'а. Guard теперь такой запрос обслуживает, но
   preflight запускается ПОСЛЕ него и решает свой вопрос (расти). Это
   зафиксировано как остаток, а не спрятано.
4. **`nctx_reload_handlers.go:894`** (перезагрузка уже идёт) по-прежнему отвечает
   503 независимо от того, влезает промпт: во время подмены модели обслуживать
   нечем. Отдельного «а если окно успело вырасти» решения нет — это не правило
   окна, а состояние модели.
